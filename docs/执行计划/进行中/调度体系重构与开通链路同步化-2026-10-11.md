# 调度体系重构与开通链路同步化-2026-10-11

## 背景与裁决

2026-10-11 用户连续下达系列裁决，对本轮交付汇总：

1. **定时任务清单重构**：供应商接口/商品同步/上游开通/服务状态 4 个任务移出系统清单；删除两个财务对账任务；优惠券发放改每分钟；系统维护 4 任务合并为 3。
2. **开通链路去队列化（三次演进收敛）**：`开通改为同步，不要队列` → `支付完之后进行开通` → 最终形态为 HTTP 场景 `afterResponse`（支付响应先返回，terminate 阶段立即开通）、控制台场景 `dispatchSync`。
3. **并发阻塞补齐**：优惠券每分钟调度加命令内分布式锁（对齐 queue:drain 命令内锁模式，规避 Windows file cache mutex 降级）。
4. **兜底修复**：开通不走队列后队列 `failed()` 兜底失效，以「超时未履约巡检打标」恢复 requires_refund 兜底语义。

## 决策日志

- 2026-10-11：上游任务"归入插件模块"以模块级归属落地（内置 HostingPanelApi 驱动非物理插件，彻底插件化需单独立项：驱动迁移涉及 provider_key 绑定与插件安装状态，风险另评）。
- 2026-10-11：开通同步化的队列重试/failed 兜底等价物 = 履约锁（`lock:paid-order-fulfillment:{orderId}`）防重 + 网关重发幂等重入 + 超时巡检打标（60 分钟覆盖网关重发窗口）。
- 2026-10-11：打标不受 dry-run 约束的理由：幂等纯标记写入（无资金动作、无上游调用，只标记不退款），重试决策仍交人工。
- 2026-10-11：HTTP 下返佣（队列即时消费）可能先于履约（响应后执行）完成——与改动前双队列并行消费语义一致，返佣 job 自有幂等，接受。

## 风险与观察项

- 支付回调响应时长不再含开通耗时（afterResponse），但开通失败不再有队列级 3 次退避重试——观察 `provision:retry-failed` 告警量与 requires_refund 标记增速。
