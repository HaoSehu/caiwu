# 余额支付渠道展示与 0 元账单余额收口

## 背景

用户在订单记录里看到自己明明用余额付过的订单，「支付渠道」一列显示 `--`。

根因不是前端漏渲染，而是**已知的架构约定与展示判据不一致**：

- `ARCHITECTURE.md` §2 明确「`payments` 是第三方资金流入记录，只记录支付宝等外部渠道真实入账；余额支付、管理员手动开服、免费订单不产生 Payment」；
- `BalanceInvoicePaymentService::payByBalance()` 的类注释同样写着「不产生 Payment 记录」，它只写一条 `finance_ledger_entries`（`event_type=invoice_payment`、`source_type=invoice`、`source_id=账单ID`）的现金扣款流水；
- 但所有「支付渠道」读取点（账单摘要 `resolveInvoicePaymentSummary`、订单列表 `ClientOrderQueryService::paymentChannelLabel`、管理端订单支付链、管理端用户账单列表）都只从 `payments` 派生渠道。

于是余额支付的订单/账单拿不到任何渠道事实，只能落到前端的占位符。

实测（本地 `idc`）：已支付订单 339 个，有 `payments` 记录 253 个、仅有台账证据 52 个、两者皆无 43 个（历史导入数据）。截图里的 4 张 0.01 订单中 3 张 `payments` 为 0。

同时，0 元账单当时的行为是**不可支付**的：`availablePaymentMethods(0)` 返回一个 `key=free` 的占位选项，前端渲染成 disabled 的「零元账单无需操作」，`payByBalance` 又以 `$amount <= 0` 直接抛出「当前账单无需支付」，账单永远停在待支付。

## 范围与验收

- [x] 余额支付的账单在账单摘要、订单列表、订单详情、管理端订单支付链、管理端用户账单列表都能还原出「余额支付」。
- [x] 第三方支付的账单/订单不会被台账回落改写（`gateway_key` 有值时以支付单为准）。
- [x] 待支付账单/订单不给渠道（保持空串由前端兜底占位符），不臆造。
- [x] 余额支付摘要不编造 `id`/`payment_no`：`id=0`、`payment_no=''`，避免用户拿不存在的单号对账。
- [x] 0 元账单只提供「余额支付」一个选项，`free` 占位选项删除。
- [x] 0 元账单可正常下单：账单与订单照常创建，不被价格守卫拦截。
- [x] 0 元账单余额支付不扣款、不校验余额，只推进状态机并补一条 0 元结清证据（金额 0 的 `invoice_payment` 台账）。
- [x] 第三方支付入口对 0 元账单明确拒绝，文案指向余额支付。
- [x] 未配置计费周期仍然拒绝下单（`Product::hasBillingCyclePrice()` 区分「配成 0 元」与「未配置」）。
- [x] 后端 Feature 8 例、控制台 e2e 2 例通过；后端全量 1413 passed / 1 skipped / 0 failed。

## 实施步骤

1. `PaymentChannelLabel` 新增 `channelNameFromLedger()`：认可 `event_type=invoice_payment`、金额 ≤ 0 **且 `operator_type ∈ {member, admin}`** 的台账行，返回「余额支付」。

   —— 只认「减」与「零」：正数行是退款/恢复类更正，不构成「用余额支付」的事实。
   —— 只认有溯源标记的行：`trace_id` 非空，或备注含「支付账单 / 账单余额支付 / 余额结清」。
     `operator_type` 是后加的列，历史行普遍为 `NULL`/`legacy`，但它们的 `trace_id` 与备注仍在；
     用 `operator_type` 做白名单会把 `auto_renew:service:147:…` 这类真实余额扣款一并误杀
     （实库 66 张仅台账证据的账单里，58 张的 `operator_type` 为空却带有效 `trace_id`）。
     真正无溯源的行（`trace_id` 与备注都空）才留空，不臆造。

2. `Invoice` 新增 `ledgerEntries()` 关系（`source_type='invoice'` + `source_id=账单ID`），并在所有账单查询点预载 `event_type/change_amount/operator_type` 等判据所需列，避免逐行回查。

3. 新增 `App\Support\InvoicePaymentSummary::fromBalanceLedger()`，供 `InvoiceService` 与 `UserService` 两处摘要复用同一结构。

4. `InvoiceService::resolveInvoicePaymentSummary()`、`UserService::buildInvoicePaymentSummary()`、`OrderService::buildPaymentSummary()`、`ClientOrderQueryService::paymentChannelLabel()`、`AdminOrderSummaryResource::payments()` 在无支付单时回落台账证据。订单侧渠道以**账单支付单**为准（`invoice_id` 是权威关联），订单侧支付单只作兼容回落。

5. 0 元链路：删除 `availablePaymentMethods()` 的 `free` 分支；`BalanceInvoicePaymentService` 允许 0 元收口并补 0 元结清台账（锁 users 行后取账户，保证 `balance_after` 快照一致）；`quote()` 与 `CheckoutService` 改用 `hasBillingCyclePrice()` 校验周期；`GatewayInvoicePaymentService` 明确拒绝 0 元。

6. **管理端 0 元价格可配置**：`HandlesProductCatalogHelpers::normalizePricing()` 原先丢弃所有 `$value <= 0` 的周期，导致 0 元商品在库里退化成「未配置」，整条 0 元链路不可达。改为保留显式 0、只丢弃负数与非法值；月价为 0 时不做周期推导（免费周期必须显式配置）。上游同步侧 `normalizeImportedAmount()` 保持「0 视为缺价」的语义不变——上游 0 价是数据缺失而非免费。

7. 余额流水列表与汇总排除 0 元结清证据行（`excludeZeroAmountInvoiceEvidence()`）：0 元台账是渠道证据、不是资金流水，否则会渲染成无意义的「扣款 ¥0.00」。

8. 前端：控制台支付页删除 `free` 分支与「零元账单无需操作」按钮，确认弹窗与提示文案区分「0 元不扣款」；Flutter 端同步确认文案。

9. 测试：后端 `BalancePaymentChannelDisplayTest` 7 例（含 0 元商品走 `ProductAdminService::createProduct()` 真实链路、历史导入台账行不被判为余额支付）；控制台 e2e 覆盖余额支付订单渠道与 0 元账单可支付。

## 顺带修复的存量缺陷

`ClientOrderQueryService::paymentRelations()` 的支付单投影缺 `invoice_id`。Eloquent 加载嵌套关系（`invoice.payments`）时必须靠外键把子行归到父行，缺这一列会让**所有**嵌套支付单被静默丢弃——表现为订单侧渠道判定长期失效，只是因为订单侧通常也有 `order_id` 匹配的支付单才没暴露。

## 风险与回滚

- **渠道判据扩大**：台账回落只对 `status ∈ {PAID, REFUNDED}` 的账单生效，且要求存在 `invoice_payment` 流水；待支付账单与零元未结清账单都不会命中。
- **0 元台账行**：金额 0、余额不变、不建批次，只留溯源事实。`LedgerConsistencyCheck` 的两种口径（快照/合计）都以金额为 0 的差分判定，不受影响。
- **回滚方式**：删除 `channelNameFromLedger()` 调用点即回到「只认 payments」的旧口径；0 元支口回滚需同时恢复 `free` 选项与 `payByBalance` 的 `$amount <= 0` 守卫。
