# 财务功能全链路与溯源审查方案（只读）

## 背景

财务是系统最高风险面。2026-08 以来连续暴露并修复了多类财务缺陷：会员折扣续费复利衰减（`services.amount` 被反写为折后价）、财务三页空参 422、阻塞账单积压、无订单账单奖励落库。2026-09-23《后端全面审查方案》D1 财务域产出 P0×1（组合支付预扣余额二次退回）与 P1×约 37，但那次是全后端横切审查，财务专项的三个维度从未系统回答：

1. **链路正确性**：八类资金事件的每条链路是否事务闭环、幂等、金额守恒、状态机完备。
2. **溯源能力**：一笔钱从进入到退出，能否凭单据链、台账、trace_id 与审计日志完整还原。
3. **机制差距**：对照同源商业系统魔方财务 3.5.8（`zjmf-manger-decoded-main/` 全解密版），哪些机制已有等价物、哪些缺失需要评估补齐。

参照库是 WHMCS 风格财务：`accounts` 单表双向流水（`amount_in`/`amount_out` + `refund` 溯源关联 + `trans_id` 防重）+ `credit` 余额变动日志（含 `balance` 快照）+ `pay_log`/`gateway_log`/`notify_log`/`activity_log` 过程留痕，账单级核销靠 `getSurplus`（total − Σamount_in + Σamount_out）。其已知弱点（accounts 行无操作人、依赖 activity_log 文本关联、orderPayHandle 同事务外副作用）也是反面参考。

**目标**：多智能体并行只读审查后端 + 三端前端 + shared 的财务功能，产出可逐条跟踪的分级问题清单、zjmf 机制对照表与缺失功能补齐优先级建议。

**非目标**：

- 不修改任何生产代码、不跑迁移、不动 git。
- 实库核查仅本地 `idc` 库只读抽验；**不含生产实库核查**（生产结论一律标注「待生产验证」）。
- 不做 UI 视觉审查（已有 2026-08-28 三端 UI/UX 审查）。
- 不重复深挖已修复历史缺陷，只做回归确认（复利衰减、422、阻塞账单、组合支付 P0 等）。

**关联**：`docs/参考资料/后端/财务单据生成规则.md`（八类场景契约，审查以它为基准真源）、`docs/设计文档/后端/后端全面审查报告-2026-09-23.md`（财务相关 P0/P1 逐条复验三态化）、`docs/执行计划/已完成/TuraIDC对齐修复方案-2026-10-02.md`（其中财务相关未修复项纳入回归确认）、`docs/执行计划/已完成/财务账务一致性与回归修复-2026-08-04.md`（历史修复基线）。

## 范围与验收

**范围**：

- 后端：`backend/app/Services/Finance/`、`app/Services/Referral/`、`app/Services/User/AccountService.php`、`app/Services/Admin/V2/AdminManualEntryV2Service.php`、`app/Constants/` 财务枚举、`app/Models/` 财务模型、`routes/v2-client.php`/`v2-admin.php` 财务端点、`app/Console/Commands/` 对账命令、`plugins/servers/zjmf_finance/`、`plugins/gateways/`。
- 管理前端：`frontend-admin-v3/src/pages/finance/`、`src/pages/users/detail/`（补录与退款对话框）、`src/api/admin/finance.ts`、`src/api/user.ts`。
- 用户前端：`frontend-user-v4-console/src/pages/client/`（订单/账单/支付/充值/checkout-resume）、`src/domains/finance/`；`frontend-user-v3-www/` 购买报价与跳转控制台链路。
- 共享：`shared/statusConfig.js`、`shared/extraStatusMaps.js`、`shared/user-v3/components/`（StatusTag/DataState）。
- 参照库：`zjmf-manger-decoded-main/`（只读对照，不作实现要求）。

**通用审查清单（每条链路都要过这 7 条）**：

1. 事务边界：写入是否同事务、事务外副作用顺序、失败回滚后状态可恢复。
2. 幂等与并发：唯一键/幂等键/命名锁/事务内状态复查是否层层有效，重复回调、并发支付、重试是否安全。
3. 金额守恒：订单=账单=余额+第三方之和、分位换算、`decimal(12,2)` 两位小数、部分退款累计不超剩余可退。
4. 状态机：Invoice/Payment/Order 状态 0/1/4/5 值域内迁移、非法迁移拦截、取消/退款后的联动。
5. 台账凭证：AccountTransaction 与业务单据一一对应、`balance_after` 连续、currency 固定 CNY。
6. 溯源字段：trace_id、source_type/source_id、origin_type/origin_id、operator_* 是否齐全。
7. 前端触达：该链路在三端有无对应入口、参数构造、状态映射与后端是否一致。

**验收**：

- [ ] 覆盖面：八类资金场景（新购、续费、用户充值、退款、管理员扣费、管理员充值、补录账单、补录订单）逐条过清单；9 条链路（见实施步骤）各有结论。
- [ ] 证据质量：每条发现含 `文件:行号`；实库抽验 SQL 只读且参数绑定，结论可复算。
- [ ] 对照闭环：zjmf 机制对照表每项落到「已有等价物 / 部分等价 / 缺失需评估」三态之一，缺失项给补齐优先级建议。
- [ ] 历史复验闭环：承接的既有结论（组合支付 P0、后端全面审查 P1 财务项、TuraIDC 财务未修复项）逐条落到「仍存在 / 已修复 / 无法判定」。
- [ ] 不新增 docs 失败项：`npm run docs:check` 失败数不高于当前既有断链。
- [ ] 零代码改动：审查结束 `git status` 与基线比对，除新增文档外无差异。

### Wave 1 · 后端资金链路审查（4 个智能体并行）

| 编组 | 链路 | 审查要点 |
| --- | --- | --- |
| G1 支付入账 | **A 在线支付入账** + **B 余额/混合支付** | `PaymentService::handleGatewayNotify` 幂等三层（幂等键/命名锁 `lock:{gateway}:payment:{id}`/事务内复查）；Invoice PAID → `handlePaidInvoice` 编排（开通→返利→优惠券→通知）；已 PAID 再回调转余额入账口径；`payByBalance`/`payByBalanceAndGateway` 失败回补（组合支付预扣余额二次退回 P0 复验）；`completePaymentFromQuery` 补偿与回调的竞态 |
| G2 充值与退款 | **C 充值** + **D 退款** | `completeRechargePayment` 三单齐发（Invoice recharge + AccountTransaction + RechargeRecord）；`cancelExpiredPendingRecharge` 超时取消与迟到回调竞争；原路退款 `refundOrderByGateway` 预扣快照→网关调用→二次事务落 Refund 的中断窗口；回余额 `refundInvoiceToBalance`；`FinanceDocumentService` 红字账单（`origin_invoice_id`）与负充值记录（`origin_recharge_record_id`）冲抵；部分退款累计口径 `remainingRefundableAmount`；返利回收 `reverseRewardForRefundedOrder` |
| G3 补录与调整 | **E 手工补录** + **F 管理员余额调整** | `AdminManualEntryV2Service` 两步/三步入账事务；trade_no 查重 + 空交易号内容指纹命名锁 + 120s 短窗；manual Payment 语义对照《财务单据生成规则》§6.3/6.4（`callback_raw.source=admin_manual_entry`、gateway 权威口径 manual、不动余额）；`adjustBalance` 幂等键 10 分钟占位、deduction 禁建充值记录；权限码 `invoice.manual_entry`/`order.manual_entry` 与默认不下发策略 |
| G4 计价与上游 | **H 计价链路** + **I 上游资金对接** | `CheckoutService`/`ServiceBillingController` 建单金额快照（config/coupon/member_discount）；复利衰减回归点 `Money::catalogAmountOf` 写回（RenewPricingMemberDiscountCompoundingTest 覆盖面）；`InvoiceOrderReconciliationService` 一致校验；优惠券 `syncInvoiceCouponUsage` 回收；`plugins/servers/zjmf_finance/` 的 getBalance/fundInvoice/续费账单恢复与库存双闸门衔接 |

### Wave 2 · 溯源专项 + 本地实库抽验（2 个智能体并行）

1. **S1 代码层溯源**：
   - trace_id 连续性：`app/Models/Concerns/EnsuresTraceId.php` 兜底 `auto:uuid` 的设计意图 vs 实际断点；PaymentService 全链路传递是否覆盖充值/退款/补录路径。
   - `FinanceLedgerEventType` 全量 event_type 对 `source_type/source_id/origin_type/origin_id` 的覆盖；旧值归一化完整性；`BackfillLedgerSourcesCommand` 后存量缺口。
   - operator_* 覆盖：RechargeRecord/Refund/Payment 补录/台账行，对照 zjmf accounts 无操作人的弱点验证当前确实完整。
   - 留档双层：`payment_callbacks`（逐笔原文 + is_verified）与 `gateway_logs`（请求/响应 + trace_id）覆盖所有网关动作；`PayloadLimiter` 审计脱敏与「管理端不脱敏」规则的边界（日志脱敏允许、管理端展示不脱敏）。
   - ActivityLogService 对八类场景关键动作的覆盖（对照 zjmf `active_log_final` type=6 账单类）。
2. **S2 本地 idc 库抽验**（只读 SQL、全参数绑定）：
   - `balance_after` 链式连续性（按 user 分组逐行核对前一行 + change = 当前行）。
   - Σchange_amount = 当前 `user_accounts.cash_balance`（全量 + 近 90 天窗口）。
   - 四条事务路径（回调入账/余额调整/补录/退款冲抵）各抽样：业务单据与台账行数、金额一致。
   - `refunds` 累计 vs 红字账单金额 vs 负充值记录绝对值一致性。
   - 对账命令体检：`AuditLedgerConsistencyCommand`/`ReconcileAccountBalanceCommand`/`CheckAccountProjectionsCommand` 覆盖面与调度注册状态。
