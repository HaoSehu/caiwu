# 数据库写入治理二期（增长收敛与调度恢复）

## 背景

一期（[数据库写入治理与归档可见性-2026-11-01](数据库写入治理与归档可见性-2026-11-01.md)）已落地 P0-1/P0-2/P0-4a/P1-3 四项，提交 7d51fa2e。本轮重新核对实施状态与当前库实况后，发现四个一期未覆盖的新事实，需要二期方案承接：

1. **调度器已停机**：2026-10-31 16:00 起 `schedule_task_runs`/`schedule_ticks`/`activity_logs`(cron)/`schedule_run_logs` 四表零写入，本机无 PHP 进程、无相关计划任务。一期落地代码无法用新数据验证，增长问题的「主要写入方」当前处于停摆状态。
2. **旧副本双写**：`E:/www/新建文件夹/backend` 旧副本仍在写 `schedule_run_logs`（代码注释称 2026-10-10 已停写，实库 10-31 16:00:36 仍有中文 task_name 写入，停机前 ~315KB/天），与本仓库台账逐分钟同构镜像。
3. **探测白名单外仍有高频动作**：`captcha.config`/`captcha.script`/`mail.send_html` 等用户请求驱动动作未纳入 `PROBE_ACTIONS`，30 天合计 ~1134 行/~1.2MB。ipl 表 P0-1 后残余日增量约 204KB/天（用户请求驱动的真实业务量）。
4. **归档排除表积压 7,003 行**：是白名单内积压（4,910 行）的 1.4 倍，一期只做了可见性未处置。

当前库（2026-11-01 13:40 实测）：79 表 358.97 MB。停机前稳态日增量 ≈1.8MB/天，其中：
- `integration_plugin_runtime_logs` ~700KB/天（P0-1 后预计骤降至 ~204KB/天）
- `schedule_task_runs` 315KB/天（1085 行/天，7 天窗口内多个 task_key 冗余度 87.5%~99.8%）
- `activity_logs` cron 镜像 459KB/天（1085 行/天，30 天窗口 cron 模块 12.6MB 占该表 85%+）+ 其他模块 ~60KB/天
- `schedule_run_logs` 315KB/天（旧副本双写，非本仓库写入）

### 目标

- 恢复调度器运行，使一期已落地代码获得真实数据验证窗口。
- 终止旧副本对 `schedule_run_logs` 的双写。
- 调度驱动写入量在 P0-1 基础上再降一档（台账去重 + cron 镜像降频）。
- 归档排除表积压获得处置路径（清理或纳入归档）。

### 非目标

- 不改表结构、不删列、不重建表。
- 不清退正常 90 天窗口内的业务数据。
- 不调整 MySQL 服务端参数、不执行 `OPTIMIZE TABLE`。
- captcha/mail/payment 等用户请求驱动的 ipl 残余增量（~204KB/天）属真实业务量，本轮不治理。

## 实施步骤

1. **2P0-A 调度恢复（前置，人工操作）**：查明 10-31 16:00 调度停机原因（本机应为 `app:serve --with-schedule` 或手工循环，生产为宝塔每分钟 `schedule:run`）；按 [部署与调度指南](../../参考资料/运维/部署与调度指南.md) 重启调度。恢复后先观察 24h 再实施后续条目，隔离「调度恢复本身引入的变量」。
2. **2P0-B 旧副本停写（人工操作）**：停用 `E:/www/新增文件夹/backend` 的调度入口（或整目录下线）；确认其连接的库与生产是否同一实例——若是，双写终止后 `schedule_run_logs` 应零新增。
3. **2P0-C 台账去重（已完成）**：实施形态为「紧凑行」——`ScheduleTaskRunRepository::markSucceeded` 内 `dedupeSummary` 比对缓存指纹（`CacheKey::scheduleTaskRunSummaryFingerprint`，md5 of limitSummary 后 json，TTL 7 天），一致则该行 summary 落 `{"__same_as_previous":true,"__previous_run_id":N}` 紧凑引用；行本身逐次写入（timing/重试语义不动），首行与内容变化行原样落库。未采用「跳过写入」：同槽重复投递已被 markQueued firstOrCreate 幂等拦截，行数真实，冗余在内容重复。

   **审查修正（2026-11-01，专家双视角）**：① 失败重置——`markRetrying`/`markTerminalFailed`/`markDispatchFailed` 更新成功后 `Cache::forget` 指纹键，「失败后首次恢复成功」重新落完整 summary，紧凑引用不再跨过失败行；② 原子性——`dedupeSummary` 改为只读比对，指纹由 `rememberSummaryFingerprint` 在 CAS update === 1 之后写入，CAS 拒绝（并发终态化）时不记忆，避免 `__previous_run_id` 指向从未成功落库的 run；③ 缓存降级——get/put 包 `try/catch`，故障时视为无前驱原样落库（去重是优化不是正确性依赖）。
4. **2P1-A cron 镜像降频（已完成）**：实施形态为「指纹一致跳过镜像行」——`ScheduleRunLogService::record` 成功路径先走 `shouldSkipSuccessMirror`（`CacheKey::cronMirrorSummaryFingerprint`，指纹与落库同口径取 compactCronSummary 后的 md5），与上一条成功镜像完全一致则整行跳过（hook 照跑、返回值照传）；首行/内容变化行/失败行无条件落库。未实施 N 次聚合计数器：那需新增计数存储与展示口径改造（D1 未决），本形态已达成「重复行不再产生」。
   **审查修正（2026-11-01）**：① 失败重置——record 失败路径落失败镜像后 `Cache::forget` 镜像指纹键，失败后首次恢复成功重新落镜像行；② 原子性——`shouldSkipSuccessMirror` 改为只读，指纹由 `rememberMirrorFingerprint` 在 `storeCronActivityLog` 返回 true 后写入（该函数由 void 改 bool：「表未就绪/写库异常」返回 false），行未落则不记忆，消除 TTL 窗口内镜像断档；③ 缓存降级——get/put/forget 均包 `try/catch`，缓存故障时逐行落库（宁多不漏）。

5. **2P1-B captcha 探测白名单扩项（已完成）**：`PluginRuntimeRegistry::PROBE_ACTIONS` 增补 `captcha.config`/`captcha.script`（白名单 4→6 动作）；沿用「成功跳过、失败落库」语义与请求内 memo，无新配置项。行均 8.8KB 的 `captcha.script` success 行是 ipl 残余增量的主要字节来源。
6. **2P2-A 排除表积压处置**：先跑 `db:logs:archive:health --json` 输出最新 `excluded_backlog` 明细供裁决；`invoices`/`invoice_items`/`account_transactions`/`payment_callbacks`/`payments` 属财务数据，是否纳入归档或单独清理需用户决策后执行。

## 风险与回滚

- **2P0-A**：调度恢复后 P0-1/P0-2 效果验证依赖真实数据，若观察窗口内 ipl 增量未降至 ~204KB/天，说明白名单未生效或存在未知写入方，需回查。
- **2P0-B**：旧副本若同时承担其他职能（如旧前端 API），整目录下线可能影响依赖方；建议先只停其调度入口。旧副本连接的库若与生产不同，则双写影响的是另一实例，需重新确认本库 srl 行的真实来源——当前推断依据是中文 task_name 与同构时刻分布，**此点标注待验证**。
- **2P0-C**：台账去重改 `markSucceeded` 调用链，需保证手动重跑/失败重试路径不受指纹缓存误伤；指纹一致只跳过「完全相同的成功」，任何 status 变化仍落库。
- **2P1-A**：cron 镜像降频直接影响管理端「任务日志」页展示密度，需与用户对齐口径后再动手。
- **2P2-A**：财务表清理不可逆，必须走裁决记录，不自动执行。

| 2026-11-01 | 2P1-A 采用「指纹一致跳行」而非「聚合计数」 | 聚合计数需新增计数存储与展示口径改造（D1 未决）；跳行方案已达成「重复行不再产生」，首行/变化行/失败行保留完整时间轴 |
| 2026-11-01 | 2P0-C/2P1-A 指纹走 Cache（redis/file）而非查表 | schedule:run 每分钟新进程，activity_logs 无 task_key 索引查表会全扫 cron 模块；Cache 跨进程共享且 O(1)，TTL 7 天过期仅导致一次原样落库，无正确性影响 |
| 2026-11-01 | 去重指纹在**落库成功之后**写入，而非判定时写入 | 判定时写会导致「指纹已写、行未落」：镜像侧 TTL 7 天内同 summary 全跳过（断档），台账侧 CAS 拒绝后 `__previous_run_id` 悬挂。put 后移一行即消除两个非原子窗口 |
| 2026-11-01 | 失败终态**清除**去重指纹，而非保留 | 保留会让「失败后首次恢复成功」被误判为重复而跳过：镜像层恢复确认不可见、台账层引用跨过失败行，审计无法区分「连续成功」与「失败后恢复」。清除成本一行，换取审计真实性 |
| 2026-11-01 | 指纹读写故障降级为「不去重」而非中断执行 | 去重是优化不是正确性依赖；缓存故障若向上传播，会把业务成功的任务误判为 retrying/failed（AuditM 双重污染）。fail-open=逐行落库，最坏退化为治理前行为 |
| 2026-11-01 | 紧凑引用行**不刷新**指纹链头 | P1-② 把 put 移到 CAS 成功后，若对引用行也执行 remember 会把链头 run_id 刷成引用行 id，连续相同 summary 形成 run3→run2→run1 链式引用，破坏「链深恒 1」。限定「仅完整 summary 行刷新链头」修复，并新增链深锁定回归用例 |
| 2026-11-01 | 紧凑引用呈现层就地翻译（P2-④） | Resource 直接透传会让管理端看裸 `__same_as_previous`/ `__previous_run_id`。AdminScheduleTaskRunResource 新增 translateDeduplicationMarkers：去重行 summary 输出 `{deduplicated,note,ref_run_id}` 语义结构，库内原始 JSON 不动 |
| 2026-11-01 | 指纹比较统一为 `===`（P5） | 镜像侧原用 hash_equals、台账侧用 ===；指纹是公开数据 md5 摘要非秘密，时序侧信道无意义，统一 === 语义更直白 |
