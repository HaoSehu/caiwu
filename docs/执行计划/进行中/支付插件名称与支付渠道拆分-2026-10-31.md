# 支付插件名称与支付渠道拆分

## 背景

支付方式选项此前用一个 `name` 字段同时承载「插件名称」与「支付渠道」：易支付插件在 `plugins/gateways/yi_pay/lib/YiPayClient.php` 里把 `name` 拼成「易支付 - 微信」，宿主 `PaymentGatewayManager::normalizeGatewayOption()` 又把这个拼接串原样下发。后果有三：

1. 用户端直接渲染 `gateway_label`（当时取 `name`），充值页、支付列表、账单详情都出现「易支付 - 支付宝」这类只有内部才关心的插件名；
2. 管理端同样读 `gateway_label`，看不出「插件」与「渠道」是两个维度，订单详情只有一个「支付渠道」格；
3. `payments.option_name` 落库的是拼接串，无法机器区分插件与渠道，日志里也只有网关级标签。

本计划把两个维度拆成独立字段，两端各取所需：插件名只给管理端与日志，渠道名是用户端唯一可读的展示名，落库与日志都不允许再出现拼接串。

## 范围与验收

- [x] 支付方式选项 JSON 拆成 `plugin_name`（插件名称）与 `channel_name`（支付渠道）两个独立字段；`name`/`label` 保留为历史别名，分别恒等于插件名与渠道名，不得再承载拼接串。
- [x] 管理端读两个字段并按两行展示：插件名称一行、支付渠道一行。
- [x] 用户端只读 `channel_name`，任何位置（含支付页面、支付渠道筛选下拉）不得出现插件名。
- [x] 账单、订单、支付单记录支付渠道：新建支付单落 `option_name` 为渠道快照；账单/订单/支付单读取时由 `payment` 派生 `plugin_name`/`channel_name` 两个字段下发。
- [x] 日志完整输出插件名与渠道名，不脱敏、不拼接。
- [x] 只改数据结构与读取/展示，不改支付流程（下单、预创建、回调、入账、退款逻辑均未改）。
- [x] 验证：后端 `composer analyse`、`composer format:check`、`composer audit:plugins` 全绿；用户端 `npm run build`/`lint`/`stylelint` 与 3 个 spec（4 例）e2e 全绿；管理端 `npm run build` 与 3 个 spec（8 例）e2e 全绿。
- [x] 旧库迁入的 `gateway_key` 为空支付单按回调证据还原渠道，展示侧不再整条丢弃；还原不出的不猜，保持「未知方式」。
- [x] 渠道判据双版本（PHP 逐行还原 / SQL 过滤）实测集合全等，见「旧库空 `gateway_key` 的渠道还原」。

## 字段落点

### 选项 JSON（宿主下发）

`PaymentGatewayManager::normalizeGatewayOption()` 与 `defaultGatewayOption()` 统一产出：

| 键 | 语义 | 消费方 |
| --- | --- | --- |
| `plugin_name` | 插件名称，取插件身份（`PluginIdentity::pluginName()`），缺失回落插件自报名称 | 管理端展示、日志 |
| `channel_name` | 支付渠道名，取插件自报渠道，缺失回落 `PaymentGatewayCode::channelLabel()` | 用户端唯一可读 |
| `name` | 历史别名，恒等于 `plugin_name` | 未迁移的旧消费方、历史记录回落 |
| `label` | 历史别名，恒等于 `channel_name` | 同上 |
| `key` / `option_key` / `payment_type` / `plugin_id` / `plugin_key` | 沿用原有语义 | 全链路 |

插件侧同步改造：`plugins/gateways/yi_pay/lib/YiPayClient.php::paymentOptions()` 删除 `'name' => '易支付 - '.label`，改为自报 `channel_name`，插件名由宿主按插件身份补齐。

### 渠道名解析

`PaymentGatewayCode` 新增渠道字典与解析入口：

- `CHANNEL_LABELS`：`alipay => 支付宝`、`wxpay => 微信支付`、`wechat => 微信支付`；
- `channelLabel(string $gateway, string $paymentType = '')`：传 `payment_type` 时先命中渠道字典，否则按网关回落到网关级渠道名（`alipay => 支付宝`、`wechat => 微信支付`、`yipay => 易支付`、`balance => 余额支付` 等）；原 `label()` 未改，`displayLabel()` 因全仓无调用方已删除。

### 支付单落库

`PaymentGatewayOperationService::snapshotColumnsFor()` 的 `option_name` 改为记渠道快照（优先 `channel_name`，其次 `label`，最后 `PaymentGatewayCode::channelLabel()`），不再回落插件名。`payments.plugin_name` 仍由插件身份单独写入，两列不再混用。历史记录里的「易支付 - 微信」不回改，读取时还原。

### 读取派生

新增 `App\Support\PaymentChannelLabel`（集中解析，避免九处私有 match 各写一套）：

- `pluginNameFromPayment()`：取 `payments.plugin_name` 快照；
- `channelNameFromPayment()`：优先取 `option_name` 快照并按 ` - ` 还原历史拼接串，其次按 `payment_type` 精确还原，最后回落网关级渠道名；
- `fromPayment()`：一次给出两维；
- `logContextForGateway()`：日志用两维上下文，无支付单时按网关回填插件身份；
- `fromGateway()`：只有网关标识时的渠道名；
- `resolveGatewayKey()`：先取 `gateway_key`，为空则按回调证据还原（见下节）；
- `hasKnownChannel()`：`resolveGatewayKey() !== ''`，即「这条支付能否说明自己走了什么渠道」；
- `channelScopeSql()` / `manualMethodValues()`：同一判据的 SQL 与取值版本，供列表筛选与可见范围使用。

### 旧库空 `gateway_key` 的渠道还原

旧库 dump 迁入的支付单里有一批 `gateway_key` 为空（本地 `idc` 实测 452 行中 285 行）。这些行不是迁移写丢的：旧库 `payments` 表本来就没有 `payment_type`/`option_key`/`option_name`/`plugin_key`/`plugin_name` 五列，`gateway_key` 在原表也是可空列，dump 侧分布与本地逐行一致。

但改造后的读取链路一律以 `isThirdPartyGateway()`（`gateway_key ∈ [alipay, yipay, wechat, stripe]`）为判据，空网关整条被丢弃：账单详情 `payment_summary` 为 `null`、`payments` 为空、「支付方式」整行被剔除；用户端支付列表分页总数不含该单；管理端订单详情 `payment_chain.payments` 为空。

处理方式是不改数据、只扩判据：

- `PaymentChannelLabel::gatewayFromCallback()` 从 `payments.callback_raw`（合并 `payment_callbacks.payload_json`）按顺序判定：`payment_gateway ∈ manualMethodValues()`（`bank_transfer`/`cash`/`alipay`/`wechat`/`other`）→ `manual`；`source === 'balance'` → `balance`；`source` 含第三方网关名 → 该网关；命中 `ALIPAY_CALLBACK_KEYS`（`notify_id`/`trade_status`/`buyer_logon_id`）→ `alipay`；否则返回空串。
- 证据盘点（本地 `idc` 实际分布）：有渠道 439 行 = `alipay` 373 + `balance` 47 + `manual` 19；未识别 13 行，其 `callback_raw` 只有 `{"days":3,"reason":"pending_recharge_expired","source":"automation"}` 且 `status=4`（已取消）无账单/订单/交易号 —— 无渠道可言，保持未识别，不猜。
- 判据两侧必须一致：`channelScopeSql()` 生成 `gateway_key = ? OR EXISTS (payment_callbacks 证据)`，PHP 侧 `resolveGatewayKey()` 逐行还原，实测全库主键集合完全相等（全部 439/439、`alipay` 373/373、`manual` 19/19、`balance` 47/47、`yipay`/`wechat`/`stripe` 0/0）。
- 还原依赖 `payment_callbacks` 关联，各展示点必须预取 `callbacks:payment_id,callback_type,payload_json`，否则每次取 `callback_raw` 都触发一次 `loadMissing('callbacks')`。已核对 N+1：查询条数与页大小无关（用户端列表 3 条、管理端充值 1 条）。
- 影响面（本地 `idc` 实测）：可见支付单 439 行（原先按第三方网关只可见 167 行）；可展示支付方式的账单 398 个（原先 149 个，库内账单共 3076 个）；可展示支付链的订单 289 个（原先 126 个）。

不采用的两条路及原因：

- **回填 `gateway_key`**：`alipay` 206 行实测不撞 `payments_plugin_trade_unique`，但会改动资金边界审计口径（`InvoiceService`/`InvoiceRefundService` 用 `gatewayKey() !== MANUAL` 算可退金额，把 `manual` 写进 `gateway_key` 会让 19 个账单从可退变不可退），且违背「迁移只读不反写」的既有约束。
- **在展示层加特判**：`thirdPartyPayments()` 有 4 个调用点、SQL 过滤有 12 处，逐点特判必然漂移；改成统一判据后两端自然一致。

## 兼容性影响

- **接口字段只增不改语义**：`plugin_name`/`channel_name` 为新增键；`name`/`label` 保留但语义收窄为插件名/渠道名别名。已全仓 grep 确认用户端无下游依赖旧 `name`（原值是拼接串）。
- **`gateway_label` 口径变更**：由「插件名（拼接串）」变为「渠道名」。管理端已同步改为读 `plugin_name`+`channel_name` 两字段，读 `gateway_label` 的位置（充值列表、账单抽屉）语义仍是渠道名，展示一致。
- **历史数据不需要迁移**：`payments.option_name` 里既有的「易支付 - 微信」在读取时由 `PaymentChannelLabel` 按分隔符还原为渠道名；迁移只新增的既有约束未被突破（新增列本就在 `2026_10_26_100000_add_plugin_snapshot_columns.php` 里）。
- **`gateway_logs` 表未改列**：渠道信息随日志 payload 输出，不新增列。
- **订单与账单表未加列**：支付方式仍以 `payments` 为唯一真源，订单/账单详情在读取时派生，履约结构零改动。
- **插件契约**：`paymentOptions()` 允许插件只报 `channel_name`；宿主负责补齐插件名。第三方插件若仍只报 `name`，`channel_name` 会回落到该值，与旧行为一致。

## 风险与回滚

- **渠道名歧义**：`channelLabel()` 在缺 `payment_type` 时回落网关级名称（易支付 → 「易支付」）。这是插件名与渠道名同值的合法场景（无渠道声明的单渠道插件），不是泄漏；已由插件侧自报 `channel_name` 优先规避。
- **历史拼接串还原依赖分隔符**：`PaymentChannelLabel` 用 `' - '` 切分，遇到不含分隔符的旧值原样返回；若某插件名本身含 `' - '` 会被切错。当前三插件无此情况，后续新插件需遵守「不得拼插件名」的契约（已写入 `normalizeGatewayOption()` 注释）。
- **接口消费方扩散**：`plugin_name`/`channel_name` 已下发到账单、订单、支付三处读取块，若后续新增消费方误读 `name`，仍可能拿到插件名。契约以 `PaymentChannelLabel` 类注释与选项字段注释为准。
- **回滚方式**：改的是读取与展示口径，回滚就是把 `PaymentChannelLabel` 调用点还原为旧的私有 label 方法并删除新增字段；数据层无需回滚（新增列本就存在，历史 `option_name` 未被改写）。
