# 实名通过后用户名落成真实姓名

## 背景

产品规则：用户实名认证通过后，控制台显示的用户名应为真实姓名，优先级「真实姓名 > 自定义」。

现状（改动前）：

- `User::getDisplayNameAttribute()` 在已实名时**无条件**返回 `real_name`，昵称读不回来；
- 控制台登录态归一化（`frontend-user-v4-console/src/store/modules/user.ts`）只读 `nickname`，丢了后端已算好的 `display_name`；控制台首页同样 `nickname` 优先；
- 实名通过的唯一写口 `VerificationService::syncUserStatus()` 只落认证状态，不碰昵称；
- 已实名存量用户的昵称仍是注册时填写的字符串。

## 范围与验收

- [x] 实名通过（`verification_status` 由非 2 跃迁为 2）时，`users.nickname` 写成本次认证的 `real_name`。
- [x] 已是已认证状态时（轮询重复命中同一 certify_id）不再覆盖昵称，用户改回的自定义名称不被冲掉。
- [x] `display_name` 改为「昵称优先、真实姓名兜底」；用户实名后仍可在个人中心改回自定义名称并立即生效。
- [x] 管理端保持实名优先：`AdminUserListItemResource` / `AdminUserDetailResource` 的 `resolveDisplayName()` 自带实名优先分支，不受模型 getter 变更影响。
- [x] 存量数据迁移：已实名且昵称≠真实姓名的用户，昵称回填为真实姓名。
- [x] 控制台顶栏 / 首页账号名统一读 `display_name`；个人资料页显示「已实名认证，用户名默认使用真实姓名」提示，输入框保持可编辑。
- [x] 实名解绑不回滚昵称。
- [x] 后端 Feature 6 例、控制台 e2e 3 例通过。

## 实施步骤

1. `VerificationService::syncUserStatus()` 成功分支追加 `nickname`；`persistVerificationState()` 增加 `nickname` 写口；新增 `resolvedRealNameNickname()`（快照 `real_name` 为空时返回 `null`，不写空值）。
2. `User::getDisplayNameAttribute()` 顺序改为昵称 → 真实姓名（仅已实名）→ 邮箱 → 手机。
3. 迁移 `2026_11_05_000001_backfill_verified_user_nickname_from_real_name.php` 回填存量；`down()` 留空（原昵称无快照，不可逆）。
4. 控制台 `normalizeUserInfo()` / 首页 `displayName` 改为 `display_name` 优先；`useProfile` 增加 `verification_status` 与 `nicknameHint`，资料页用 `t-form-item :help` 展示。
5. 补 `backend/tests/Feature/VerifiedUserNicknameTest.php` 与 `frontend-user-v4-console/e2e/profile-nickname.spec.ts`。

## 风险与回滚

- **迁移不可逆**：迁移会把已实名用户的昵称直接覆盖，原自定义昵称未留快照；如需恢复只能从备份还原。`down()` 刻意留空，避免「回滚后用户名变成注册值」这种与规则相反的结果。
- **覆盖范围**：仅 `verification_status = 2` 或历史双轨 `verification_status = 0 && is_verified = 1`，且 `real_name` 非空、`deleted_at IS NULL` 的行。
- **行为变化**：`User::display_name` 从「实名永远优先」变为「昵称优先」。所有直接读 `display_name` 的场景（工单、账单、通知变量、代登录日志等）在用户改回自定义昵称后会跟随昵称；管理端用户列表/详情不受影响（资源类自己判实名）。
- **回滚方式**：还原 `User::getDisplayNameAttribute()` 与 `VerificationService` 的昵称写入，前端还原 `normalizeUserInfo`；数据侧从备份还原 `users.nickname`。
