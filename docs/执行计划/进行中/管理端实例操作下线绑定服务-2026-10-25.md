# 管理端实例操作下线「绑定服务」

## 背景

管理端用户详情「服务控制台」抽屉的实例操作区曾并列入口：开机、关机、重启、刷新远程、重置密码、上游绑定、调价、改名称、绑定服务。

其中「绑定服务」对应 `PUT /v2/admin/users/{user}/services/{service}/manual-provision`（manual-provision）：按当前上游绑定把失败服务重新提交上游开通，最终落到 `ProvisionService::retryFailedProvision` / `retryFailedProvisionByInvoice`。它与「上游绑定」（`PUT .../meta` 写 `supplier_id` / `upstream_host_id`）职责重叠，同一实例存在两条独立开通路径，且按钮是否可用依赖 `actions.manual_provision` 能力位。

本次按需求删除「绑定服务」入口及其整条链路，只保留「绑定上游服务」能力（即现有「上游绑定」）。界面与代码中不存在其它名字为「调用上游开通」的入口，该说法即指管理端的这条 manual-provision 重试链路。

## 范围与验收

- [x] 实例操作区不再出现「绑定服务」按钮与「将按当前上游绑定重新提交上游开通」弹窗说明；开机/关机/重启、刷新远程、重置密码、上游绑定、调价、改名称保持原状。
- [x] 后端删除路由 `PUT /users/{user}/services/{service}/manual-provision`、`UserServiceController::manualProvision`、`ManualProvisionUserServiceRequest`、`HandlesAdminUserServices::manualProvisionService`、`ServiceTransformService::canManualProvisionService` 与 `actions.manual_provision` 能力位。
- [x] `ProvisionService::retryFailedProvision` / `retryFailedProvisionByInvoice` 保留：孤儿单补偿命令 `RetryFailedProvisionCommand` 与既有测试仍在调用，不属于本次入口范围。
- [x] 自动生成物由脚本重生成（前端 API 目录、后端 API 清单、OpenAPI），`composer api:check` 通过。
- [x] 管理端 e2e `frontend-admin-v3/e2e/user-service-console-actions.spec.ts` 锁定五项入口与「绑定服务」不再出现。

## 实施步骤

1. 只读定位：路由 → 控制器 → 请求类 → 服务层 → 资源能力位 → 前端按钮/弹窗/API 方法，确认无其它调用方。
2. 自后端向前端顺序删除；电源链路（管理端 `power-actions`、客户端 `power-actions`）与 `ProvisionService` 重试方法不动。
3. 重生成自动生成物，全仓 grep 复查 `manual_provision` / `manual-provision` / `manualProvision` 残留。
4. 补管理端 e2e，跑后端三项检查、`api:check`、管理端 build 与 e2e。

## 风险与回滚

- 破坏性变更：`PUT .../manual-provision` 下线后外部调用方会得到 404。仓库内已无其它调用方（全仓 grep 确认），前端三端均无该键消费。
- `actions.manual_provision` 从服务资源输出移除；旧版前端若仍读取该键只会拿到 `undefined`，不会影响其它能力位。
- 无数据迁移、无表结构变更；`services.provision_error` 等字段与 `manual_provisioned_*` 历史字段保留。
- 回滚方式：按 Git 历史恢复被删的路由、控制器动作、请求类与服务方法即可。
