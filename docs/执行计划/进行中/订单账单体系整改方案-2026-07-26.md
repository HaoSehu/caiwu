# 订单账单体系整改方案

- 文档性质：跨产品、财务、交付、平台与安全的实施计划
- 依据：[企业级治理审计报告](./订单账单体系企业级评审报告-2026-07-26.md)
- 当前状态：Phase 0 的 P0-2/P0-3 已实施并完成静态校验；隔离测试库权限阻断了 PHPUnit。未修改生产数据、权限或生产配置。

## 背景

系统已具备 Invoice-first 新购、支付回调校验、幂等锁、履约去重、上游开通尝试等基础能力。整改目标不是推倒重做，而是补齐交易类型分流、统一关联标识、状态历史、无订单账单审计视图、职责分离和可运营对账。

本计划遵循四条边界：

1. 先修复已付未履约风险，再推进治理能力；不以大重构延迟止血。
2. 保留 invoice-only 的合法业务语义；充值、扣款、返利和部分续费不应被机械强制创建 Order。
3. 所有数据库变更仅新增，审计与审批事件必须可追溯、可回滚、不可覆盖历史交易。
4. 金额阈值、审批角色、保留期限和上线窗口须由业务负责人确认；本计划不擅自假定。

## 范围与验收

### 总体验收

- [ ] 主机升降级的真实“创建账单 -> 支付 -> 履约 -> 服务/上游记录”集成用例通过，且重复支付/回调不会重复履约。
- [ ] Invoice、Order、Payment、Service 和上游开通尝试可用同一关联标识或关系图追溯。
- [ ] 所有高风险状态变更均在同一事务写入结构化、仅追加的交易事件。
- [ ] 无 Order 的账单与直接账单动作可在管理端审计视图完整回放。
- [ ] 取消、退款、人工开通等受控动作具备申请、审批、执行、复核与紧急授权闭环。
- [ ] 每日财务-支付-账户-履约对账产生异常队列、责任人和处理时限。
- [ ] 每个阶段都完成受影响的自动化测试、回滚演练和变更记录。

### 非目标

- 不在首期删除 Order 的金额、优惠或快照字段。
- 不在未完成调用方和历史数据影响分析前移除 createFromOrder、payment.order_id 或现有表字段。
- 不直接改写历史账单、订单、支付或开通记录来“补齐”证据。
- 不将通用日志平台替代为仅靠前端展示的时间线。

## Phase 0：P0 止血与影响确认

### 目标

消除 host_upgrade 已支付而未进入预期履约的静态断链，并以证据确认历史影响范围。

### 工作项

| 编号 | 工作项 | 负责 | 交付物 | 验收 |
| --- | --- | --- | --- | --- |
| P0-1 | 由产品和交付负责人决定临时关闭、隐藏或拦截主机升降级购买入口；紧急措施必须有变更单和回滚条件。 | 产品 + 交付 | 风险处置记录 | 新建 host_upgrade 不会进入未验证路径。 |
| P0-2 | 增加从客户创建到支付后的端到端回归用例，覆盖成功、重复回调、无 Order 和上游失败。 | 后端 | 失败复现测试与回归测试 | 修复前能捕获断链，修复后断言上游处理器和记录均被调用。 |
| P0-3 | 选择最小一致的领域修复：在主机升降级账单创建事务中创建并绑定开通 Order，或按明确的 fulfillment kind 将 invoice-only 账单分派到正确处理器。 | 后端 + 交付 | 设计决策记录和实现 | 不混淆流量包与主机升降级；幂等、库存/金额语义和退款链路保持兼容。 |
| P0-4 | 进行只读影响分析，识别已支付 host_upgrade、无开通尝试、无服务状态变化的候选交易。 | 财务 + 交付 | 异常清单与人工核对结论 | 每条候选均有处理责任人和关闭证据。 |
| P0-5 | 对确认受影响的历史交易执行受控人工补偿或复核；每项引用交易、上游和审批证据。 | 财务 + 交付 | 补偿台账 | 不通过批量脚本静默改历史状态。 |

### 本轮实施记录（2026-07-26）

- P0-3 已实施：`ServiceUpgradeService` 在创建 `host_upgrade` Invoice 的同一事务中创建并绑定内部 `Order`，复制财务、配置与 `trace_id` 快照，并在创建操作记录中同时写入账单与订单标识；正常支付转入既有订单履约队列。针对旧的未付或异常缺失 Order 的主机升降级账单，按 `meta.kind=host_upgrade` 原子补齐 Order 后再调度，不把 invoice-only 语义扩展到充值、续费等其他类型。
- P0-2 已实施：新增“创建账单 -> 余额支付 -> 主机升降级订单处理”的回归，覆盖流量包处理器不得被调用、重复履约不重复访问上游，以及无 Order 的恢复投影。
- 失败语义已收紧：主机升降级处理未把 Order 置为 `completed` 时，履约 Job 会保留待处理状态并进入既有重试路径，不再被当作已完成清理。
- 静态验证通过：目标文件 PHP 语法、Pint 格式检查与 PHPStan 定向分析均通过。
- 集成测试受环境阻断：`php artisan test tests/Feature/ServiceUpgradeServiceTest.php` 在初始化阶段因 `idc_test@127.0.0.1` 无权访问 `idc_testing`（MySQL 1044）失败，5 个用例均未进入业务断言；恢复测试库最小权限后必须重跑。

### 回滚原则

先回滚入口开关或新分流，不回滚已成功履约的外部资源。若修复部署后出现重复履约信号，立即停止队列消费者或对应业务开关，依据开通尝试和幂等键人工裁决。

## Phase 1：交易关联与不可变状态事件

### 目标

让交易从创建、支付、履约到服务实例使用统一关联语义，并让每个关键状态变化具有可回放的结构化事件。

### 设计约束

1. 在 HTTP、队列、定时任务和上游调用边界生成或恢复 correlation_id/trace_id；Invoice 创建后必须显式传给关联 Order、Payment、Service、Job 和开通尝试。
2. 交易事件与业务状态更新处于同一数据库事务。事件写入失败时，关键资金或履约状态不能静默成功。
3. 事件仅追加，禁止业务应用更新或删除；修正以新事件表示，不覆盖旧事件。
4. 事件记录关联 ID、from_status、to_status、事件类型、原因、actor、source、审批引用、关联标识、幂等键摘要和受控元数据；不记录密钥、原始敏感凭据或不必要个人信息。
5. 现有 activity_logs 和 operation_logs 继续兼容读取，是否迁移为辅助投影由数据影响分析决定，不直接替代或删除。

### 工作项

| 编号 | 工作项 | 负责 | 交付物 | 验收 |
| --- | --- | --- | --- | --- |
| P1-1 | 编写交易关联与事件 ADR，定义 Invoice-first、invoice-only、Order projection、服务实例和上游尝试之间的关系。 | 架构 + 财务 + 交付 | 已批准 ADR、字段字典 | 所有账单类型均有明确是否需要 Order 的规则。 |
| P1-2 | 新增仅追加的交易事件存储与写入服务，并先覆盖创建、支付成功/失败、取消、退款、履约开始/成功/失败、人工处置。 | 后端 | 新增迁移、模型、服务、测试 | 每个覆盖路径可查询 from/to、actor、source、reason 和关联标识。 |
| P1-3 | 修复新购 shadow Order 的初始 trace 继承，并让履约 Job 显式携带或恢复上下文。 | 后端 | 传播契约与回归测试 | 从 Invoice、Order、Payment、Service、开通尝试均可关联同一次交易。 |
| P1-4 | 为自动开通前提不满足、人工待开通和人工重试建立明确事件与处置状态。 | 交付 + 后端 | 异常事件模型、待办查询 | 能区分“未尝试”“不可自动开通”“上游失败”“已人工关闭”。 |
| P1-5 | 建立交易状态机契约测试，覆盖非法回退、重复事件、乱序回调和补偿。 | 后端 QA | 单元/特征测试 | 不允许用散落的 forceFill 绕过已定义的关键状态转换。 |
| P1-6 | 将新购业务意图的幂等性从短 TTL 缓存提升为可恢复的持久化契约，并定义缓存失效、重复请求和恢复时的行为。 | 后端 + 财务 | 幂等 ADR、约束与测试 | 缓存重启或过期后，相同业务意图不会静默产生额外 Invoice/Order。 |
| P1-7 | 将 PSP 每次通知与 payment_callbacks 当前投影分离；以外部事件标识、接收时间和验签结果保存逐次事件。 | 支付 + 后端 | 回调事件模型与重放测试 | 重复、乱序和失败回调可审计、可安全重放且不覆盖历史证据。 |

### 上线与回滚

事件表和传播字段只新增。第一阶段采用双写和影子校验：先写新事件、与现有日志对比覆盖率，再逐步将审计查询切换到新事件。回滚只关闭新查询或新写入开关，不删除已追加事件。

## Phase 2：审计查询、目录治理与前端证据面

### 目标

让财务、交付和合规人员可从任一交易对象看到同一条证据链，并让产品分类变更可解释。

### 工作项

| 编号 | 工作项 | 负责 | 交付物 | 验收 |
| --- | --- | --- | --- | --- |
| P2-1 | 建立统一审计查询：支持从 Invoice、Order、Payment、Service 或 trace/correlation_id 获取关联实体与事件时间线。 | 后端 + 平台 | 受权限保护的查询 API | 无 Order 的账单、直接取消和退款同样返回完整记录。 |
| P2-2 | 管理端账单与订单详情接入事件时间线、关联关系、关联标识搜索和安全导出。 | 管理端 + 后端 | 审计视图 | 仅展示当前管理员有权查看的数据；导出有权限和下载留痕。 |
| P2-3 | 补齐 shared 中部分退款状态与后端 InvoiceStatus 的共享契约测试。 | 前端 + 后端 | 状态字典与测试 | 三端对状态 6 显示一致且筛选可用。 |
| P2-4 | 建立产品分类字典：business_product_type、catalog_type、order_type、invoice_type、fulfillment_kind 的名称、责任人和关系。 | 产品 + 架构 | 类型字典 | “项目类型”不再作为含糊字段出现在接口或报表。 |
| P2-5 | 为商品种类变更新增版本、有效期、变更原因、审批/影响分析和替代分类策略。 | 产品 + 后端 | 目录治理流程 | 历史订单和账单始终可按当时快照解释，当前目录变更可回放。 |
| P2-6 | 消除类型漂移：裁决 downgrade 和 legacy normal 的支持策略，并在后端、前端、结构文档和测试中统一。 | 架构 + 后端 + 前端 | 契约变更记录 | 所有类型均可在代码、结构说明和 UI 中找到同一语义。 |
| P2-7 | 制定每种账单类型的财务凭证与退款契约，明确 new、renew、upgrade、recharge、refund 等是否产生 Payment、Refund、红字 Invoice、RechargeRecord 与 Order。 | 财务 + 支付 + 后端 | 凭证/退款矩阵与回归测试 | 升级收款、invoice-only 原路退款、部分退款和余额退款均有可执行且可对账的链路。 |

### 上线与回滚

新审计视图先与现有详情页并行，不移除旧日志标签。目录版本先增量采集，确认导入与权限影响后再将变更流程设为强制。

## Phase 3：审批、职责分离与持续对账

### 目标

将“谁能做”升级为“谁申请、谁审批、谁执行、谁复核”，并将资金与履约异常转化为可运营的队列。

### 工作项

| 编号 | 工作项 | 负责 | 交付物 | 验收 |
| --- | --- | --- | --- | --- |
| P3-1 | 由财务、交付和安全共同批准审批策略：适用动作、金额/风险规则、审批人来源、超时、拒绝、紧急授权和复核。 | 财务 + 安全 + 交付 | 审批政策与 ADR | 无代码硬编码未经批准的阈值或角色。 |
| P3-2 | 实现申请、审批、执行、撤回、过期和复核事件；业务执行必须引用批准记录。 | 后端 | 审批域与测试 | 同一人不可在需分离情形下申请并批准；重复执行幂等。 |
| P3-3 | 将权限拆分为至少账单取消、退款申请、退款审批、退款执行、人工开通、服务高危操作、审计导出和紧急授权。 | 安全 + 后端 + 管理端 | 权限矩阵、迁移和回归测试 | 默认角色最小授权；旧权限迁移有审批和回滚。 |
| P3-4 | 建立每日对账：除 Invoice、Payment、AccountTransaction、Refund、PaymentCallback、Service 和开通尝试外，接入 PSP payout/settlement 数据形成订单-PSP-结算三方差异规则。 | 财务 + 平台 + 交付 | 对账任务、异常队列、仪表盘 | 每条异常有分类、负责人、时限、处理事件和关闭证据；账户余额对账不再被误当作 PSP 清算对账。 |
| P3-5 | 建立运行指标与告警：已付未履约、无关联标识、无开通尝试、审批超时、对账差异和异常积压。 | 平台 + 交付 + 财务 | SLI/SLO 与告警规则 | 有演练记录，告警不会泄露交易敏感数据。 |

### 上线与回滚

审批先以影子模式输出“本应审批”的报告，再对低风险动作灰度强制。紧急授权应在上线前完成演练。权限收缩采用角色快照、分批验证和可撤销配置，避免一次性锁死正常运营。

## Phase 4：数据模型收敛（条件阶段）

只有在 Phase 0 至 Phase 3 的查询、对账和回归全部稳定后，才评估模型瘦身：

1. 对 createFromOrder、Order 金额/优惠快照、Payment.order_id 和 invoice_items 的全部读取方做影响清单。
2. 确认哪一份数据是财务凭证、哪一份是履约投影、哪一份是展示缓存。
3. 先停止新写入，再进行长周期双读/对账，最后才考虑新增替代字段或弃用旧字段。
4. 任何历史迁移都应可 dry-run、可抽样校验、可回滚；不得用删除历史行的方式“清理冗余”。

这不是当前实施承诺，避免以领域纯洁性破坏已上线交易链路。

## 质量门禁与测试矩阵

| 场景 | 最低验证 |
| --- | --- |
| 新购 | 幂等键重复、缓存过期/重启、并发下单、余额/第三方支付、无效签名、重复/乱序回调、取消补偿、一次履约。 |
| 续费 | invoice-only、自动续费、重复回调、上游账单恢复、人工待办。 |
| 流量包与主机升降级 | 正确按 fulfillment_kind 分流、成功/失败/重试、无 Order 防御、重复支付。 |
| 退款与取消 | 申请审批执行分离、真实原路/余额退款、invoice-only 原路退款、部分退款、拒绝、过期、PSP 成功但本地失败与重复执行。 |
| 追溯 | 任一实体反查全链路；异步 Job 和上游尝试保留同一关联标识。 |
| 权限 | 客户归属、管理员最小权限、无权访问、紧急授权到期与审计导出。 |
| 对账 | 正常一致、缺回调、金额差异、已付未履约、上游失败和异常关闭。 |

每次代码变更至少运行受影响后端测试；涉及管理端或 shared 状态字典时运行对应构建与类型检查。数据迁移、支付网关或队列配置变更还必须在隔离环境演练，不能以本地静态审阅代替。

## 风险与回滚

| 风险 | 控制策略 | 回滚触发 |
| --- | --- | --- |
| 修复分流导致重复上游开通 | 交易/上游幂等键、唯一任务、开通尝试核对、灰度开关。 | 发现重复资源或同一关联标识多次外部创建。 |
| 强制审计写入影响主流程 | 与交易同库同事务、压测、监控写入失败率和延迟。 | 审计写入异常导致非预期交易失败率。 |
| 审批拦截正常运营 | 影子模式、分级灰度、紧急授权和超时策略。 | 高优先级业务被错误拦截且无可用处置路径。 |
| 权限收缩误伤岗位 | 角色快照、最小灰度、场景回归和紧急恢复。 | 正常值班无法执行已批准动作。 |
| 历史数据处理破坏证据 | 只增量、dry-run、抽样对账、保留原始记录。 | 对账差异或证据链无法重建。 |
