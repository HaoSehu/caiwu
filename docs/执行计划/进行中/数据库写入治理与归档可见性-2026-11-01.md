# 数据库写入治理与归档可见性整改

## 背景

2026-10-31 的只读排查确认：库内 79 张表中，四张日志表贡献了约 92.4% 的日增量；剔除四张日志表后全库增量约 0.20 MB/天，与「4 到 5 天涨 1MB」的观察吻合。排查同时发现四处可收敛的浪费：插件探测动作成功也全量落库、调度运行台账 `summary` 无上限且高度重复、归档健康检查看不到被排除表的超期积压、管理端日志保留期默认值与后端不一致。

本计划承接该排查结论，只处理已确认的问题对象，不扩大范围。

### 目标

- 插件运行日志的探测噪声降到可接受量级，且不牺牲失败诊断。
- 调度运行台账单行 `summary` 有硬上限，不再随业务结果无限膨胀。
- 归档健康检查能暴露「被排除归档表」的超期积压，不再自证 healthy。
- 管理端展示的日志保留期默认值与后端配置同源同值。

### 非目标

- 不改表结构、不新增删除列、不重建表。
- 不改「日志不做脱敏」的既有裁决。
- 不删除 `schedule_run_logs` 表与存量数据（仍有只读消费链路）。
- 不调整 MySQL 服务端参数，不执行 `OPTIMIZE TABLE`。
- 不清退三张超期表的存量数据（待决策）。

## 范围与验收

| 条目 | 验收项 | 验证方式 |
| --- | --- | --- |
| P0-1 插件探测日志 | `server.resolve_capability`/`server.supplier_form_schema` 成功行/日为 0；失败行不减少；`integration_plugin_runtime_logs` 的 success 增量 ≤ 250 KB/天 | 单测断言 + 只读 SQL 统计按 action 的行数与字节 |
| P0-2 台账 summary 上限 | 落库 `summary` 编码后严格 ≤ 4096 B；普通结果原样保留 | `ScheduleTaskRunSummaryLimitTest` 两条用例 |
| P0-4a 归档可见性 | 被排除表存在超期积压时健康状态不得为 `healthy`，并输出各表超期行数 | `db:logs:archive:health` 实跑文本与 JSON |
| P1-3 保留期默认值 | 管理端「保留策略」默认值与 `config/log_archive.php` 一致（90/180） | 设置页 e2e |

## 实施步骤

1. P0-1：把两个探测动作纳入 `PluginRuntimeRegistry::PROBE_ACTIONS`，沿用「成功跳过运行日志、失败照常落库」的既有语义；探测结果继续走请求内 memo 短路。
2. P0-2：`ScheduleTaskRunRepository` 在写台账前复用 `PayloadLimiter`，并按落库编码长度再做一次收缩，保证 `json` 列存储后不超过 4096 B。
3. P0-4a：`db:logs:archive:health` 增加被排除表积压统计，写进 `excluded_backlog`，并在存在超期时把健康度降级。
4. P1-3：管理端「日志保留天数」默认值改为与后端一致的 90。

## 风险与回滚

- P0-1 把动作加入探测白名单后，这两类调用在成功时不再有运行日志行；若排查需要，可临时从白名单移除，行为立即回到全量落库。
- P0-2 只对超过 4096 B 的结果做降级，正常结果字节不变；回滚即去掉限量调用。
- P0-4a 只新增输出字段并调整健康度判定，不改变退出码语义以外的行为；下游若依赖固定字段集合需同步。
- P1-3 只改前端默认值，不写库；已保存的设置值优先于默认值。

## 决策日志

| 日期 | 决策 | 原因 |
| --- | --- | --- |
| 2026-11-01 | P0-1 采用「白名单扩项」而非新增采样率配置 | 复用既有「成功不落库、失败必落库」语义，改动面最小且不引入新配置项 |
| 2026-11-01 | P0-2 在 `PayloadLimiter` 之外再收缩一次 `__preview` | `PayloadLimiter::limit` 的总量阈值是原文判定阈值，超限后返回的摘要结构会额外承载三个下划线键，实测落库 4236 B，需按编码后长度收紧 |
| 2026-11-01 | P0-4a 只统计与降级，不自动清理被排除表 | 被排除表含财务与自动化幂等数据，删除语义需单独裁决 |
| 2026-11-01 | P0-3 与 P0-4b 不纳入本轮 | 前者影响管理端日志展示口径，后者涉及财务相关表的历史数据，均需用户决策 |
