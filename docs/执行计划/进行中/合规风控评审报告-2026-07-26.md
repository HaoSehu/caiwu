# 订单账单体系合规与职责分离专项工作底稿

- 文档性质：专项审计工作底稿，不构成法律意见
- 评审范围：账单取消、退款、人工开通、服务退款、操作记录与管理端权限
- 主报告：[订单、账单与产品类型企业级治理审计报告](./订单账单体系企业级评审报告-2026-07-26.md)

## 审计口径

本底稿只回答“静态代码能否证明控制存在”。它不判断任何人员是否违规，也不以未观察到的功能推断生产环境没有补偿性控制。生产审批制度、跳板机、工单、日志保留、组织角色和监管适用性均需由业务与合规负责人另行确认。

## 已验证的治理缺口

| 编号 | 观察事实 | 治理风险 | 结论边界 |
| --- | --- | --- | --- |
| SOD-01 | invoice.manage 直接执行账单取消与退款；被审阅的路径未见该动作的申请/审批状态机。 | 发起人与执行人不可由代码证明分离。 | 提现审批路由另有实现，本结论不外推到提现。 |
| SOD-02 | user.manage 同时覆盖人工开通、服务退款、删除、开关机和密码重置。 | 单一权限的授权面过宽，难以按职责最小化授权。 | 不代表当前角色一定被过度授予；需实库核对角色成员。 |
| SOD-03 | order.manage 出现在常量和权限目录中，但本轮检索未找到由其独立保护的管理端订单写路由。 | 权限命名、权限模型和实际能力可能漂移。 | 可能是预留权限；需由产品和权限负责人裁决。 |
| AUD-01 | 通用操作日志不是强制状态事件账本；双写 activity_logs 失败不会中断主流程。 | 审计证据的完整性需依赖多处调用方。 | 不能据此断言日志已缺失，只能说明不具备统一强制保证。 |
| AUD-02 | 账单详情对无订单账单返回空日志，且对有关联订单的账单主要按订单 subject 查询。 | 财务凭证与实际操作记录不能稳定从一个入口完整回放。 | 全局日志页或数据库中可能仍有记录。 |

## 企业控制目标

### 职责分离

敏感操作至少应拆分为四类能力，且默认不由同一普通角色同时拥有：

| 能力 | 责任角色 | 不应拥有的默认能力 |
| --- | --- | --- |
| 申请 | 财务运营或交付运营 | 自行审批和自行执行高金额/高风险事项。 |
| 审批 | 财务负责人、交付负责人或合规指定角色 | 修改原始业务数据和绕过风控。 |
| 执行 | 受控系统任务或受限执行角色 | 修改审批结论。 |
| 复核/对账 | 独立财务或内控角色 | 发起同一笔申请。 |

紧急处置可以使用 break-glass 角色，但必须要求风险理由、有限时授权、二次确认、自动通知和事后独立复核；它不能成为常规退款或人工开通的旁路。

### 最小审计记录

每次影响金额、服务状态或上游资源的变更至少要以同一事务写入仅追加的业务事件。最低字段包括：

- 事件编号、发生时间、实体类型和实体 ID；
- Invoice、Order、Payment、Service 的关联 ID；
- 变更前后状态、事件类型、原因和来源；
- 操作者类型/ID/名称快照，申请与审批引用；
- trace_id 或 correlation_id、幂等键摘要、请求来源；
- 上游 provider、外部事务号或开通尝试引用；
- 脱敏后的必要上下文与证据保留策略。

金额阈值、审批级数、保留年限、日志不可修改的数据库权限和地域合规要求必须由财务、法务与安全负责人配置和确认，不在本底稿中虚构数值。

### 风险控制与复核

1. 取消、退款、人工开通和目录大范围变更应先进入请求，再由规则决定是否需要审批。
2. 规则应至少考虑金额、批量数量、同一操作者频率、账户风险、服务类型和是否为紧急处置。
3. 批准后的执行必须引用 approval_id；重复执行必须幂等。
4. 每日对账应比较账单、支付、账户流水、退款、上游开通尝试和服务状态，并把异常分派给责任人。
5. 管理端只能展示其权限范围内的审计事件；导出需要单独权限与下载留痕。

## 验收取证要求

| 验收项 | 所需证据 |
| --- | --- |
| 申请、审批、执行分离 | API 授权测试、角色矩阵、同人审批拒绝测试、审批事件时间线。 |
| 紧急授权可追溯 | 临时授权记录、过期回收、通知记录和复核结论。 |
| 状态事件完整 | 对新购、续费、退款、取消、人工开通和失败重试的端到端事件断言。 |
| 日志可用性 | 从 Invoice、Order、Payment、Service 任一入口查询同一关联链路，并验证无订单账单。 |
| 对账可执行 | 每日对账报告、异常队列、处理时限和抽样复核结果。 |
