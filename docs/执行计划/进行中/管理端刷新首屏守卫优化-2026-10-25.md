# 管理端刷新首屏守卫优化

## 背景

管理端（`frontend-admin-v3`）刷新任意页面时都要先白屏等待一段固定的接口往返，实测与本机 API 无延迟对照如下：

- 用户详情页列表可点：基线 430ms；给所有接口各加 600ms 延迟后变成 1,947ms；再叠加 4G 网络与 4× CPU 降速则 7,129ms。
- 请求时序（每个接口 600ms）：110ms 发出 `/v2/admin/auth/info`，729ms 才收到，916ms 才并发发出 `users/1/services`、`users/1`、`member-levels` 等 5 个业务请求。即该接口独占约 619ms 且完全阻塞后续请求。
- 生产环境该接口 ttfb 实测 542–653ms（本机直连为 255ms）。

根因在两处：

1. `frontend-admin-v3/src/permission.ts:34` 的守卫条件是 `if (!permissionStore.menuBuilt || !userStore.userInfo?.name)`，命中后无条件 `await userStore.getUserInfo()`。
2. `frontend-admin-v3/src/store/modules/permission.ts` 的 `menuBuilt` 没有持久化，刷新即为 `false`；而 `frontend-admin-v3/src/store/modules/user.ts` 的 persist 只 `pick: ['userInfo']`，于是每次刷新必然进入该分支，必然串行请求一次 `/v2/admin/auth/info` 后才放行目标路由。

`permissionStore.setupMenus` 内部调用的 `buildMenus` 是纯同步计算，不产生网络请求，所以只要本地已有可用权限资料，刷新时完全可以跳过这次请求。

## 范围与验收

- [x] 刷新复用本地资料：已有持久化 `userInfo` 且未过期时，刷新不再请求 `/v2/admin/auth/info`。
- [x] 保留回源兜底：本地无资料、无 token、或资料超过有效期（5 分钟）时，仍回源一次该接口。
- [x] 权限一致性：菜单仍按最新权限构建，`meta.permission` 页面级校验逻辑不变（`permission.ts:63-69` 未改动）。
- [x] 会话清理：`logout` / `resetLocalSession` / 双因素挑战分支均复位水合标记与在途请求。
- [x] 个人资料页 `pages/user/index.vue:180` 的强制刷新语义不受影响（仍调用 `getUserInfo`）。
- [x] e2e 覆盖刷新不重复请求、过期回源、有资料但无 token 三条路径。
- [x] `npm run lint` / `npm run build` / `npm run test:e2e` 通过。

## 实施步骤

1. `store/modules/user.ts`：新增 `profileHydrated`、`profileSyncedAt` 状态与模块级在途请求 `pendingUserInfoRequest`，新增 `ensureUserInfo()`（已水合直接返回本地资料，未水合复用同一个在途请求），对齐用户端 `frontend-user-v4-console/src/store/modules/user.ts:108-122` 的既有模式。
2. `store/modules/user.ts`：persist 增加 `profileSyncedAt`，并用插件官方 `afterHydrate` 钩子在 `$patch` 之后标记水合状态；以 Cookie 中的 token 是否存在为准，并加 `PROFILE_HYDRATION_TTL_MS = 5 * 60 * 1000` 有界过期。
3. `permission.ts:34`：命中「菜单未构建」分支后，先判断 `userStore.profileHydrated`，已水合则跳过网络径直用缓存权限 `setupMenus`；未水合才 `await userStore.ensureUserInfo()`。
4. 新增 `e2e/permission-refresh.spec.ts`：断言首次访问请求 1 次、刷新后仍为 1 次、把 `profileSyncedAt` 改到 TTL 之外后刷新恢复到 2 次。
5. 跑 `npm run lint`、`npm run build`、`npm run test:e2e`。

## 风险与回滚

- 权限时效风险：复用本地资料意味着管理员权限被调整后，菜单最长要等到下一次「刷新 + 资料已过期（5 分钟）」才更新。注意有效期只在水合阶段求值一次——**常驻不刷新的标签页不受 5 分钟约束**，其菜单会一直停留在加载时的权限，直到手动刷新或重新登录。后端每个业务路由都挂了 `permission:` 中间件（见 `backend/routes/v2-admin.php:62/68/76/85/90/126/130/149` 等），前端守卫不是唯一防线，越权请求会被服务端拒绝；页面级 `meta.permission` 校验仍然生效。
- 多账号切换风险：同一浏览器另一个标签页用别的账号登录会覆盖 `admin_token` Cookie 与 `localStorage.user`，但本标签页内存中的 `userInfo` 不会自动失效（`src` 内无 `storage` 事件监听）。本标签页在自身刷新前仍以旧账号资料渲染菜单与姓名；首个业务请求会因新 Cookie 的权限不同被后端拒绝，不会造成越权。
- 令牌失效风险：Cookie 中的 token 失效时，首个业务请求会 401，`utils/request/index.ts` 的 `onUnauthorized` 会清 token 并跳登录页，不会停留在半登录态。
- 回滚：本次只改 `src/store/modules/user.ts`、`src/permission.ts` 与新增一个 e2e 文件，回滚即 `git checkout` 这两个文件并删除该 spec，无数据迁移、无接口契约变化。
- 验证不足时的处置：若线上出现权限滞后投诉，把 `PROFILE_HYDRATION_TTL_MS` 调小或直接改为 `0`（等价于退回每次回源）。

## 决策日志

| 日期       | 决策                                                               | 原因                                                                                                                                                                           |
| ---------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 2026-10-25 | 用水合标记 + 本地权限重建菜单，而不是给 permission store 加 persist | `menuBuilt` 只是构建结果的布尔位，持久化它会让菜单在没有权限数据时也「看起来已构建」，语义更脆；把「资料是否可用」收敛到 user store 单一真源更稳。                            |
| 2026-10-25 | 给本地资料加 5 分钟有效期，而不是无条件信任 localStorage            | 管理员权限可能在后台被调整，需要给陈旧缓存一个上界；5 分钟与后端会话活跃度检查的量级匹配，清缓存会立即失效，常驻标签页则依赖后端 `permission:` 中间件兜底。                                                        |
| 2026-10-25 | 不恢复「每次刷新必请求 auth/info」的兜底分支                        | 后端每个业务接口都有 `permission:` 中间件兜底，前端重复请求只增加首屏串行等待，不提升安全性。                                                                                 |
