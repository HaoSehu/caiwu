# 日志分层与容量治理整改方案

## 背景

2026-08-22 的日志审查确认：本地库 8 张日志表约 304MB，占库体积 90% 以上；`operation_logs` 与 `activity_logs` 的历史双写、插件运行元数据、调度日志镜像和归档未形成生产闭环，是数据库膨胀的主要原因。

代码止损已经完成：插件运行元数据限制为叶子字符串 8KB、整体 16KB；`activity_logs` 成为在线唯一真源；`operation_logs` 停止写入并转为只读遗留表；管理端 Laravel 文件重写清理旁路已冻结。生产归档闭环、V2 两阶段协议和空间回收仍未完成。

本计划吸收 Laravel 12 的 `daily`、Monolog 3、结构化 JSON、`Log::shareContext()` 等能力，并借鉴 ZJMF-CBAP-10.4.6 的“显式业务操作才入数据库审计”的低写入模型。

### 目标

- 关键安全和业务审计事件进入 `activity_logs`。
- 普通 API 访问、慢请求、异常和调试上下文进入结构化轮转文件，不默认写数据库。
- 邮件、短信、插件运行、支付网关和调度日志按业务责任与合规边界分别治理。
- 可归档数据经过“暂存、校验、发布、清除”的可靠协议。
- 管理端不再提供绕过归档的物理删除入口。
- 通过容量、增长率、归档成功率和磁盘水位监控形成闭环。

### 非目标

- 不改变支付、余额、账单和自动化幂等状态的业务语义。
- 未完成生产只读基线前，不删除历史数据、不调整已批准的保留政策、不执行 `OPTIMIZE TABLE`。
- 不把 `automation_logs`、财务/支付/审计数据或未分类日志流纳入通用归档。
- 不开放归档文件任意下载、路径读取或历史数据编辑。

## 日志流分类与保留边界

建立后端只读日志流目录，声明每个流的唯一真源、用途、在线期限、归档资格、责任人和冷检索能力。

| 日志流 | 在线真源 | 处理方式 | 默认边界 |
| --- | --- | --- | --- |
| `access` | 结构化文件 | JSON 日志、按日轮转、集中采集 | 普通 API 不落 `activity_logs` |
| `auth` | `activity_logs` + 结构化文件 | 关键认证结果入库，访问明细入文件 | 凭据和令牌不落日志 |
| `business` | `activity_logs` | 关键业务动作入库 | 保留 actor、resource、result、trace_id |
| `schedule` | `schedule_run_logs` / `schedule_task_runs` | 保留一个规范展示真源 | 活跃状态不得归档 |
| `message` | `message_logs` | 独立字段大小和保留策略 | 正文、参数、收件人单独治理 |
| `plugin-runtime` | `integration_plugin_runtime_logs` | 数据库保存摘要和受限元数据 | 原始大报文不无限存库 |
| `gateway` | `gateway_logs` | 财务/合规确认前不进通用归档 | 仅保存必要状态和摘要 |
| `automation` | `automation_logs` | 业务幂等状态专门治理 | 永久排除通用归档与普通清理 |

`activity_logs` 保留 `event_id`、`stream`、`trace_id`、actor、resource、result 等稳定字段。所有写入入口最终必须使用统一事件写入器；普通访问日志写入失败不得阻断业务，关键审计写入失败必须告警并进入可观测失败计数。

## 实施步骤

### P0：生产止损与基线

1. 在授权生产只读环境采集各日志表的行数、最早/最新时间、按日增长、`DATA_LENGTH`、`INDEX_LENGTH`、索引和 `EXPLAIN`。
2. 检查 `archive_audit_logs`、归档报告、队列失败记录、磁盘水位、旧归档目录和外部消费者。
3. 以当前代码校正文档中“8 张表”的过时描述；未经财务/合规确认，不把 `gateway_logs`、`automation_logs`、`schedule_task_runs` 纳入普通删除。
4. 在 V2 归档协议上线前，禁止生产使用旧版直接 `--file --purge` 路径；管理端清理只能做只读预览或受审计申请。
5. 确认普通 API 日志的审计白名单、数据责任人和保留期限。

交付物：生产容量基线、日志流目录、保留策略确认单、归档运行证据。

### P1：Laravel 12 文件日志与数据库降载

1. 在 `backend/config/logging.php` 增加 JSON daily 通道，使用 Monolog 3 `RotatingFileHandler` 和 `JsonFormatter`，设置明确 `maxFiles`；生产检查禁止退化到无轮转的 `single`。
2. 在 `LogOperation` 中间件复用 `X-Request-Id`，通过 `Log::shareContext()` 注入 request/trace/actor 上下文，并在请求结束、异常和常驻进程边界清理上下文。
3. 普通 API 只写方法、路径、状态、耗时、用户类型、服务名等小字段；成功 GET、列表刷新和成功轮询不再默认写 `activity_logs`；错误、认证失败、写请求和慢请求按可配置规则记录。
4. `ActivityLogService` 与 `OperationLogService` 统一事件写入器，始终填充 `event_id`、`stream`、`trace_id`。
5. 管理端文件读取兼容 JSON 日志、daily 多文件聚合和 `laravel_file` 来源，不暴露物理路径。
6. 明确调度日志唯一展示真源，避免同一执行同时作为独立运行记录和 activity 镜像重复增长。

交付物：代码、迁移（如需）、定向测试、日志量对比报告。

### P2：V2 归档与冷热检索

1. 新增批次/归档物元数据，使用 `planned -> staging -> verified -> published -> purging -> purged` 状态机。
2. 外部工具只写 `.part` 暂存文件，不使用导出与 `--purge` 同步执行。
3. 流式校验表头、行数、ID 边界、文件大小和 SHA-256，完成 flush/fsync 后原子发布文件和 manifest。
4. 仅按已发布 manifest 的固定边界分块删除源记录；中断可恢复，重试不重复生成归档物。
5. 归档报告、执行日志、manifest 纳入独立保留清理；旧 JSON/JSONL 和孤立 `.part` 只盘点告警，不直接删除。
6. 管理端显示在线、已归档、不可用来源；归档不完整时不能以空结果冒充无数据。
7. 首先灰度低风险日志流，支付网关、自动化幂等和未经批准流保持排除。

交付物：V2 服务、命令、恢复 dry-run、健康检查、管理端查询和端到端测试。

### P3：生产灰度与空间回收

1. 全表 dry-run，逐表核对候选数、索引选择和执行报告。
2. 先小表灰度，再逐流放开；任何行数、文件、哈希或审计不一致立即停止。
3. 连续至少 7 天健康检查正常后，才允许清退已批准历史数据。
4. 归档稳定一个周期后，在独立维护窗口执行 `OPTIMIZE TABLE`，单独测量 `.ibd` 和操作系统空间变化。
5. 归档成功后再处置停写的 `operation_logs` 存量和旧归档格式。

交付物：灰度报告、空间回收前后对比、回滚记录和最终验收。

## 监控与验收

### 必须监控

- 每张日志表行数、数据/索引字节和每日新增行数。
- 日志表 GB/天增长率、归档候选积压量。
- 最近成功归档时间、失败批次、非终态批次和孤立 `.part`。
- 队列 `failed_jobs` 数量、归档任务积压和任务超时。
- JSON 文件轮转状态、归档报告目录和整盘可用空间。

### 验收条件

- 普通成功 GET 不再新增 `activity_logs` 审计行；关键业务事件各生成一条唯一 `event_id`。
- 同一调度执行在管理端不重复展示，进行中的 `schedule_task_runs` 不被归档。
- JSON 文件按日轮转，超过 `maxFiles` 自动删除；生产 `single` 配置被检查拒绝或告警。
- 归档物未进入 `published` 前，源表候选行数不减少；重试不会生成重复最终文件。
- 归档失败能在任务台账、健康接口和告警中发现；连续 7 天无成功批次必须告警。
- 日志查询支持在线/归档/不可用来源，不以空结果冒充无数据。
- 归档和空间回收前后提供每表行数、数据/索引字节、归档文件字节和整盘可用空间对比。
- 不改变 `payments`、`account_transactions`、`automation_logs` 等受保护数据的删除语义。

## 收益

### 直接收益

1. **数据库写入量下降**：普通成功 GET 不再同步执行审计表 `INSERT`，`activity_logs` 新增量与 API 请求量脱钩。
2. **容量增长变慢**：消除历史双写路径；插件元数据已有 16KB 上限；本地 304MB、占库 90% 以上的基线应在归档和空间回收后显著下降。
3. **单行空间可控**：普通访问只保存小字段，大型插件请求/响应不再无限进入数据库。
4. **请求性能改善**：减少数据库事务日志、二级索引维护和同步写竞争；P95/P99 需通过压测和生产灰度实测，不预先承诺固定百分比。
5. **归档可靠性提升**：校验和 manifest 发布前不删除源数据；中断、重试、磁盘满和篡改均可定位与恢复。
6. **审计完整性提升**：关键事件保留操作人、资源、结果、`trace_id` 和 `event_id`；冷热查询明确来源，不因切源重复或缺页。
7. **故障排查效率提升**：请求、队列和上游调用可通过共享 request/trace 上下文串联，并可被集中日志平台检索。
8. **运维可见性提升**：能够量化“每天增长多少、归档是否成功、候选积压多少、磁盘还能使用多久”。

### 收益口径

仓库现有证据可以确认：双写已消除、插件元数据已限长、文件日志已降噪、管理端文件重写旁路已冻结。数据库总容量下降、API P95/P99 改善、每日增长率和磁盘回收量必须通过生产灰度实测，不把静态审查结果写成已实现收益。

## 风险与回滚

- 采样规则过宽会造成审计缺失：先建立事件白名单和对账样本，再逐步降低普通访问写库范围。
- JSON 日志格式切换可能影响现有管理端解析：先补解析器和兼容测试，再切换通道。
- 常驻进程共享上下文可能串数据：请求、队列开始和结束都必须清理，并补异常路径测试。
- 归档误删风险：V2 上线前只 dry-run；任何 manifest、哈希、行数或审计不一致停止后续表。
- 空间回收可能阻塞数据库：`OPTIMIZE TABLE` 只在独立维护窗口执行，不纳入应用命令自动调用。
- 回滚时可停止新归档任务并保留已发布归档物；不得恢复旧版无校验 `--purge` 路径。

## 事实与边界

- 归档产物**不内联**网关请求/响应明细：`gateway_logs` 库行明细外置到文件后为 null，归档 CSV 只含状态字段；明细在线寿命即 `GATEWAY_LOG_DAYS=90`，第 91 天起随文件轮转物理删除（与库行归档期一致）。若未来需更长证据期，须延长 `GATEWAY_LOG_DAYS` 或归档时内联明细，另行评估。
- 已知权衡：`GatewayDetailFile::read()` 按行扫描当日文件，文件增大后详情打开为 O(n)；`write()` 未做落盘 `file_exists` 确认；`now()` 与 RotatingFileHandler 实际写文件日期存在极低概率的跨午夜 100ms 窗口错位。均属可接受风险，暂不处理。

| 2026-08-23 | `db:logs:capacity` 容量快照注册每日 03:00 心跳任务并写入运行台账 | 为“每日增长多少、磁盘还能撑多久”提供趋势数据；命令只读，不触碰业务数据 |
