# 消息发送体系按 howstack 重构 · 2026-11-03

## 背景

管理端的消息模板页已按 howstack-bos 的「消息配置」形态合并为单页（`frontend-admin-v3/src/pages/notifications`，2026-11-03 完成），但**后端仍是旧模型**，页面只是把两套独立模板拼成了一张矩阵：

1. **没有「消息场景」这一层**。`notification_templates` 以 `(channel, code)` 存模板，邮件 100001–100030、短信 100001–100033 是两套独立编号，语义不对齐（邮件 100003「登录IP提醒」vs 短信 100003「账单未付款提醒」）。页面只能按模板名聚合同名项，跨渠道的同一业务事件无法合并成一行。
2. **没有「接收对象」建模**。模板只有 `audience` 一个 `user/admin` 字符串；同一场景面向客户与面向管理员是两条互不相干的记录，无法表达「一次业务事件同时通知客户与内部人员」。
3. **没有「接收组」与按渠道的发送策略**。每渠道的启停、通道引用、标题正文、厂商模板号只能挂在模板行上，不能像 howstack 那样一个场景挂多组（关联客户 / 内部人员 / 群机器人），并按组声明接收范围（创始管理员、指定部门/角色/管理员）。
4. **验证码与业务通知共用同一条同步链路**。`SendAccountCodeService` 在同一函数里限流、发码、写缓存；验证码走 `NotificationService`/`SmsService`，会落 `message_logs`（含验证码明文），与 howstack「验证码不进普通通知队列和日志」的口径相反。
5. **投递语义松散**。邮件靠 Laravel 队列 `tries=3` + 数组 backoff，短信同步直发、失败即抛；两者都没有统一的「租约领取、unknown 不重试、逐次尝试记录」语义，也没有「结果未知不自动重发」的硬约束。
6. **敏感载荷未加密落库**。`message_logs.content/params_json` 明文存正文与参数；howstack 对投递 payload 一律加密，日志表只留安全错误码。

**用户裁决（2026-11-03）**：「直接按 howstack-bos-main 进行重构」，先出方案。即数据模型、发送链路、验证码独立服务、管理端接口都对齐 howstack 的结构，不做只在旧表上打补丁的中间态。

**关联资料**：[短信模板管理-2026-10-11](短信模板管理-2026-10-11.md)（运营商审核闭环，本计划保留并改挂到新模型）、[安防与履约加固改造-2026-10-21](安防与履约加固改造-2026-10-21.md)（FUL-2 管理员通知吞异常，本计划在传输层统一处理）。

**非目标**：

- 不引入 Webman/phx/Workerman，继续沿用 Laravel 12 + Redis 队列 + `queue:work`。
- 不照搬 howstack 的 `SensitiveDataCipherInterface` 实现细节，改用 Laravel `Crypt`（`APP_KEY`，已支持旧密钥轮换）。
- 不做钉钉/企业微信/飞书机器人的新增接入（现网未接），只在模型中预留 `robot` 组与渠道枚举，实现留空。
- 不改变用户可见的模板文案与变量集合（迁移时原样搬运）。
- 不重做管理端「消息配置」页面结构（2026-11-03 已完成），只把数据源与接口切到新模型并补「接收组」编辑能力。

## 目标模型（对齐 howstack）

### 数据表

| 表 | 说明 | 与 howstack 对应 |
| --- | --- | --- |
| `message_configurations` | `(audience, message_type)` 唯一；整条 JSON 配置（含各组渠道策略）加密存放；`revision` 乐观锁 | 同名表 |
| `messages` | 业务事件流水：`event_key` 唯一（幂等）、`scene`、`purpose`、`business_type`、`business_id` | 同名表 |
| `message_recipients` | 每条消息的接收对象：`audience`、`account_id`、`target_key`、`read_at`（站内已读） | 同名表 |
| `message_deliveries` | 各渠道投递任务（即 Outbox）：`request_key` UUID、`channel`、`payload_encrypted`、状态机、租约 | 同名表 |
| `message_delivery_attempts` | 逐次尝试结果：状态、安全错误码、耗时，不存地址与正文 | 同名表 |

保留并收口的旧表：

| 旧表 | 处置 |
| --- | --- |
| `notification_templates` | **保留为场景模板目录**：新增 `scene_code` 列把模板挂到场景，成为 `MessageTypeCatalog` 的数据库载体；`channel/code` 唯一键保留 |
| `message_logs` | **保留为管理端审计视图的数据源**，由传输层写入；`content/params_json` 继续存明文（项目红线：管理端与日志不脱敏） |
| `user_notifications` | 保留，由 `message_recipients` 的 `message` 渠道投递结果同步写入（或直接改为读 `message_recipients`，见决策日志 D3） |
| `sms_provider_templates` | 保留，映射层改挂到 `message_configurations` 的 `sms` 渠道配置上 |

### 发送链路

```text
业务代码
  ├─ 普通通知：MessagePublisher::publish(eventKey, scene, businessType, businessId, memberId, variables, audiences)
  │    └ 事务内写 messages + message_recipients + message_deliveries（payload 加密）
  │    └ 队列消息只带 delivery_id（不序列化地址/正文）
  ├─ 验证码：VerificationMessageSender::send(scene, method, target, challengeId, code, config)
  │    └ 同步直发，不写 messages/message_logs 正文，不重试
  └─ 测试发送：管理端直接走 Transport（记 message_logs，不写 messages）
dispatch（queue:work）
  └ DispatchDelivery::consume(deliveryId)
       ├ claim()：锁行 + 租约 120s + attempts+1 + attempts 行
       ├ recipient 已停用 → failed/paused，不重试
       ├ message 渠道 → delivered（站内消息只写 user_notifications）
       ├ email/sms → MessageTransportInterface::send()
       │    └ 通道修订号必须匹配，否则 failed/configuration_changed 不重试
       │    └ 结果映射 accepted|delivered|failed|unknown
       └ finish()：写 attempts 终态；仅 failed & retry & attempts<3 才回到 pending，退避 30*2^n
```

### 传输层

新增 `App\Services\Messaging\MessageTransport`（单入口），内部：

- `ChannelResolver`：把 `(channel, channel_id, channel_revision)` 解析成插件实例；修订号不匹配直接拒绝（复用现有 `IntegrationDriverBindingResolver` 并补修订号）。
- 邮件：`MailDriverManager`，`MailMessage` DTO（`messageId` 必须回显一致）。
- 短信：`SmsDriverManager`，`SmsMessage` DTO（E.164 校验、参数名匹配、禁序列化、`__debugInfo` 脱敏）；大陆手机号自动转 `+86`。
- 结果统一为 `TransportResult(status, error, retry)`，**只有 `failed` 且明确可重试才 `retry=true`，`unknown` 一律不重试**。
- 传输层负责写 `message_logs`（管理端审计，不脱敏）与 `message_delivery_attempts`（安全错误码），两者职责分离、互不替代。

### 验证码独立链路

新增 `App\Services\Auth\VerificationMessageSender`，对齐 howstack：

- 读取 `message_configurations` 中该场景 `customer` 组的渠道配置，要求：组启用、渠道启用、`channel_id>0`、模板内容含 `{{code}}`。
- 先 `channel` 预检（修订号 + 启用状态），再生成 challenge。
- challenge 存 `verification_challenges` 表（新表）：`challenge_id`、`purpose`、`method`、`target_hash`、`binding_hash`、`code_hash`、`status`、`attempts`、`expires_at`；**只存 HMAC-SHA256 摘要，明文验证码不落库**。
- 同步发送，失败即抛，不写 `messages`，不重试；`message_logs` 仍记录（项目红线：管理端可见完整验证码），但**不写 `messages` 流水**。
- 现有 `VerificationCodeService`（缓存式）与新表并存期：先双写，切换后删除缓存读路径。

## 风险与回滚

- **双写窗口**：S3–S4 期间新旧链路并存，`notification_templates` 仍是真源，`message_configurations` 由回填命令生成；窗口内新写走旧链路，读也走旧链路，避免分叉。切换点单列，不做灰度混跑。
- **加密密钥**：`message_configurations.configuration_encrypted` 与 `message_deliveries.payload_encrypted` 使用 `APP_KEY`；`APP_KEY` 轮换已有旧密钥兼容（`.env.example` 已声明），但**必须验证 `Crypt` 解密回退链**，否则历史配置不可读。
- **验证码渠道切换**：验证码从缓存式切到 challenge 表后，缓存内未过期的旧验证码仍需可校验；过渡期 `verify*` 同时查两处，过期后删除缓存分支。
- **管理端断档**：`/notification-templates` 下线前必须确认三端无引用（`frontend-admin-v3` 与 e2e 全部切到 `message-scenes`），否则保留只读兼容。
- **回滚条件**：S1–S2 可删表回滚；S3 起若投递出现「重复发送」，立即停用队列消费者并回退到旧发送服务（旧代码在 S6 前不删除）。
- **不可破**：`message_logs` 不删行、不脱敏；验证码明文仅存在于 `message_logs`，不得进入 `message_deliveries`/`messages`；`request_key` 重试保持不变。

## 待确认

四项已于 2026-11-03 由用户裁决「按你的倾向」，结论如下，不再作为开放问题：

1. **站内消息** → **保留双表**：`user_notifications` 仍是站内消息真源；`message` 渠道投递成功时同步写入，`message_recipients.read_at` 不作为站内已读真源。理由：迁移 493 行历史 + 改动站内已读链路的收益小于风险，且 howstack 的 `read_at` 与 caiwu 现有已读模型语义不完全一致。
2. **场景清单裁剪** → **只映射现有 53 条模板**：不新增 howstack 有而 caiwu 无实现的场景（`refund_pending` / `invoice_pending` 等）；未映射模板进 `__unmapped` 场景保留原样。理由：场景目录是代码声明，先有发送实现再建场景，避免建出永不发送的空场景。
3. **权限码** → **沿用 `settings.view` / `settings.manage`**：不拆新权限码。理由：消息配置本就属系统设置域，拆码会让现有管理员角色全部失去访问权，需要额外授权迁移。
4. **机器人组** → **只建模型字段，不做投递**：`MessageGroups::KINDS` 与渠道枚举保留 `admin`、`robot` 与 dingtalk/wecom/feishu 位，`channelsFor()` 返回空集，实现留空。理由：现网未接机器人，未验证链路不进运行时。

## 模板编号维护约定（强制）

caiwu 与 howstack 结构不同：howstack 没有模板表，模板就是场景配置 JSON 的字段，用场景码（`order_paid`）标识；caiwu 有独立的 `notification_templates` 表，运营商模板审核按模板 ID 走，模板必须是独立实体。因此**编号一致性需要人工维护**，以下是强制约定：

1. **同一场景，邮件与短信使用同一编号。** 例如 `order_paid` 场景邮件 100016 与短信 100016 指同一条「订单支付成功」。
2. **新增模板前先查同场景另一渠道的编号**，复用该号；不要新分配。
3. **一个场景多档位提醒时**，首档对齐邮件编号，补充档位进 `100049+` 扩展段，并在常量注释里标明属于哪一档。
4. **邮件与短信不得共用编号却指向不同消息**——这是本次统一要消除的问题（历史上 100021 邮件=管理员新订单、短信=订单退款）。
5. **编号只在 `SmsTemplateCatalog` / `NotificationService` 常量和数据库里维护**，业务代码不硬编码数字。
6. **改编号必须同时更新**：`notification_templates`、`message_scene_templates`、`settings` 里的 `sms_template_provider_template_id_*` 等键、以及对应常量。运营商模板 ID 会随编号失联，生产环境执行前必须确认。

当前场景→编号对照以数据库为准（`message_scene_templates` 关联表 + `notification_templates`），改完用下面这条校验首档一致性：

```php
// 每个场景邮件与短信的首档编号必须相同
foreach ($scenes as $scene => $channels) {
    sort($email = $channels['email']); sort($sms = $channels['sms']);
    assert($email[0] === $sms[0], "场景 {$scene} 编号不一致");
}
```

**与 howstack 的差异记录**：howstack 用场景码做唯一标识，天然不会有编号漂移；但它的公众号渠道虽然声明了、校验了模板 ID，传输层仍返回 `channel_not_integrated`（只实现 email/sms）。caiwu 选择删除公众号渠道而非保留空壳，理由是没有模板载体、保留会误导。

### 阿里云号码认证插件修正（2026-11-04）

**问题**：测试发送短信报「阿里云号码认证短信插件仅支持内置验证码模板，不支持系统短信模板正文发送」。

**诊断过程与结论订正**：

1. 初判为「插件自我设限」——`sendMessage()` 是空壳，但 `querySmsTemplates()` 能调通 API。据此一度把 `sendMessage` 改为调 `dysmsapi` 的 `SendSms`、能力改为 `['verify_code','message']`。
2. **该判断有误**：用户指出本插件接入的就是**阿里云号码认证服务（dypnsapi）**，不负责通用短信。`querySmsTemplates` 能调通只因账号恰好也有 dysmsapi 权限，不代表插件职责。
3. 实测印证两套 API 互斥：把号码认证模板号 `100001` 传给 `SendSms` 会返回「短信模板不合法」——号码认证模板（100001–100005，纯数字）与短信服务模板（`SMS_xxx`）是两套体系。

**最终实现**：

- 插件能力恢复为 `['verify_code']`（只有验证码），并注释说明插件职责边界。
- `sendMessage()` 保留但**明确职责**：号码认证模板号（`^10000[1-5]$`）路由到 `SendSmsVerifyCode`，其余一律返回「本插件为阿里云号码认证服务，仅支持内置验证码模板」。
- `NotificationTemplateTestSendService` 的判据用 `needsBuiltinVerifyChannel()`（插件无 `message` 能力时走内置验证码通道），阿里云号码认证符合该分支。
- 修改插件文件后需重跑 `IntegrationPluginService::install()` 刷新 `source_hash`，否则包摘要校验会阻止执行。

**实测**：`100001` 走号码认证 API **发送成功**（`success=true`）；`SMS_xxx` 被明确拒绝并给出职责说明。

验证：`phpstan` 0 错、`pint` PASS、`plugins:audit-registrations` 通过、全量 phpunit **1351 passed**。

### 二次审查：投递链路缺陷（2026-11-04）

| # | 缺陷 | 后果 | 修复 |
| --- | --- | --- | --- |
| 1 | `TransportResult::failed()` 全部未传 `retry=true` | 重试/退避/上限整套机制是死代码，任何明确失败一次即终态 | 通道未配置与厂商拒绝改为可重试；收件人非法仍不可重试 |
