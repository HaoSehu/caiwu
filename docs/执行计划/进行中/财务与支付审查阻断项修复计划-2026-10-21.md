# 财务与支付审查阻断项修复计划 · 2026-10-21

## 背景

技术方案评审团（架构 / 安全 / 验收三视角）对财务与支付域做只读全链路审查后给出 **不放行** 结论。审查报告：《财务与支付功能审查报告-2026-10-21》。本计划是该报告的执行台账，只处理已复核落地的缺陷，不重开已裁决议题。

**目标**：清零 10 项阻断，让财务/支付域达到可放行状态；并在放行前修掉 7 项 P1。

**非目标**：
- 不重做 2026-10-20 财务核心重构（内核四服务、9 张表、切换链路已成立，本届不推翻）。
- 不做网关原路退款（2026-10-10 / 2026-10-20 两次裁决维持只退余额）。
- 不重构 InvoiceService / CouponService 巨型文件（架构 P2，另立计划）。
- 不改金额为整数分、不复活 `order_item_units`。

## 风险与回滚

- **批次 1 改可退额口径**会改变账面口径，影响所有历史部分退款账单的展示值；上线前需用 `finance:audit-ledger-consistency` 与 `backfill-order-refund-amount --dry-run` 对比存量差异。
- **批次 2 触及 000015 迁移白名单**：任何「为了过迁移而补白名单」的改动都必须同时补 `hasColumn` 短路，否则等于绕开唯一自检。
- **批次 3 的 `block` 默认值**会拒绝存量 482 张无 service_id 账单的退款（它们本就查不到交付事实）。这是有意收紧，不是误伤；如运营需要为个别账单放行，走「订单侧退款入口 + 二次确认」并留操作人，不新增配置开关。
- **`trustProxies` 若配置错误**会让所有请求 IP 变成伪造值，比现状更危险；必须只信任已知反代 IP 并在预发验证。
- **回滚**：各批次相互独立，可按批次回滚代码；批次 2 涉及数据归档，仅可在 T+7 窗口前回滚。
