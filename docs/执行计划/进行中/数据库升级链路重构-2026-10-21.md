# 数据库升级链路重构 · 2026-10-21

## 背景

代码库已有 `php artisan migrate`、schema baseline 与 76 个增量迁移，但缺少版本语义和失败保护：没有代码版本来源、没有数据库版本账本、没有升级流水、没有迁移锁、没有备份前置校验。本次重构补齐这五件事，并顺带治理迁移体系自身的幂等与基线漂移问题。

规范真源见 [数据库升级规范](../../参考资料/数据库/数据库升级规范.md)，本文只记录实施过程与决策。

## 风险与回滚

1. 白名单可能掩盖真实误删：每条必须带 reason 与 recorded_at，status 命令输出孤儿总数。
2. 全库备份体积随日志表增长：当前数十 MB 可接受，膨胀后改为「结构全量 + 日志表仅结构」。
3. 生产首次必须 `--adopt`：刻意设计，已写入 Runbook。
4. 回滚：代码可整体回退；两张新表不影响旧代码，可保留。

## 决策日志

| 日期 | 决策 | 原因 |
| --- | --- | --- |
| 2026-10-21 | 薄封装 Laravel migrator 而非自研执行器 | 框架已有 batch/pretend/schema-path，自研无收益且失去保障 |
| 2026-10-21 | 版本放 `version.json` 而非 `config/` | `config:cache` 会固化旧版本号，导致误判「已最新」 |
| 2026-10-21 | 孤儿迁移走白名单 | 实测 54 条历史孤儿，硬性「缺失即拒绝」会永久锁死链路 |
| 2026-10-21 | 命令用 `db:` 前缀 | 现有测试硬断言业务 `migrate:*` 恰为 37 个，新增会破坏基线 |
| 2026-10-21 | 不做自动回滚，区分 failed / recovery_required | MySQL DDL 不可回滚，以「本次是否有迁移成功」决定能否原地重试 |
| 2026-10-21 | 已入库历史迁移不改，登记 lint 豁免 | 遵守「迁移只新增」原则 |
| 2026-10-21 | `--adopt` 改为先迁移后记账 | 账本表由迁移创建，只记账不迁移会让「账本存在但表不存在」成为永久状态 |
| 2026-10-21 | 迁移盘点必须纳入 `_archive` 目录 | 归档迁移仍在 `migrations` 账本中，只扫 `migrations/` 会把 120 条归档误判为缺失 |
| 2026-10-21 | 已采纳库再传 `--adopt` 必须拒绝 | 静默忽略会让操作者误以为重新采纳生效，实际执行的是普通升级 |
| 2026-10-21 | `--dry-run` 消息只打印一次 | 原实现把 migrator 原始输出既包 `<info>` 又单独打印，出现重复行 |
