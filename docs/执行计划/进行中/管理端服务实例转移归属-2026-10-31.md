# 管理端服务实例「转移归属」

## 背景

管理端需要在用户之间转移实例归属：把某个产品实例从当前归属用户名下迁到另一位用户名下。此前仓库内没有可用入口（历史提交 `521c9c62` 的 M6 服务过户已被 `4d0c87f7` 整批回滚，全仓 grep `transfer` 只剩银行转账文案）。

现状约束：`services.user_id` 是归属的唯一真源；`ServiceDetailService` 的详情缓存键与服务列表分组的概览缓存键都含 `user_id`，改归属后必须让新旧两个 `userId` 的键同时失效，否则原持有者仍能读到实例、接收方看不到实例。

## 范围与验收

- [x] 入口落在既有模块：管理端服务控制台 `/admin/users/:id/services/:serviceId` 实例操作区，「改名称」之后新增「转移」按钮，仅 `user.manage` 权限可见；入口只看权限，不看实例状态与到期时间（暂停、已删除等实例同样可点）。
- [x] 后端新增 `POST /api/v2/admin/users/{user}/services/{service}/transfers`，挂在 `USER_MANAGE` 写组内（不新增权限码），单独限流 `throttle:10,1,admin-user-service-transfer`。
- [x] 归属变更原子生效：锁内复核原归属 → `forceFill(['user_id' => 接收方, 'auto_renew' => 0])` → 强审计写入；任一步失败整体回滚，不留半生效数据。
- [x] 校验与拦截：产品实例不属于该用户（404/40400）、接收方不存在/软删/禁用（422）、接收方与当前归属相同（422）、存在待支付账单（422）、存在已付未履约账单（422）、锁内发现归属已被他人变更（409/40900）、强审计写失败（500 且回滚）。实例状态与是否到期不参与判定。
- [x] 审计：`activity_logs` 记录 `service.console.transfer`（管理员主体），并写原持有者 `service.record.transferred_out`、接收方 `service.record.transferred_in`、管理员 `user.service.record.transferred` 三条旁路流水；服务控制台操作日志页签展示「转移归属」及原归属/接收方/备注明细。
- [x] 通知：补入邮件模板 `100030`「实例归属变更通知」，向原持有者与接收方各发一封。
- [x] 自动生成物由脚本重生成，`composer api:check` 与 `npm run docs:check` 通过。
- [x] 验证：后端 Feature 21 例全绿，管理端 build、eslint、e2e 全绿。

## 实施步骤

1. 只读定位：路由分组与权限码、控制器与请求类范式、`HandlesAdminUserServices` 既有 `deleteService` 的缓存失效与双写审计范式、`ServiceDetailService` 缓存键生成、`ServiceOverviewService` 概览缓存、`OperationLogService` 主体回落规则。
2. 后端自内向外：`TransferUserServiceRequest` → `transferService()` → `assertServiceTransferable()` → 控制器动作 → 路由与限流。
3. 缓存失效：赋值前快照旧 `updated_at` 与 `from_user_id`，用一个改回旧值的内存副本清旧键，再用事务内刷新后的实例清新键；`forgetGroupedOverviewCacheFor()` 对新旧两个 `userId` 各调一次。
4. 审计与通知：显式传 `actor_type=admin`，避免 `OperationLogService` 按 `service->user_id` 回落成接收方主体；`writeStrict` 保证日志写失败时归属变更回滚。
5. 前端：`api/user.ts` 增 `serviceTransfer`，服务控制台加按钮、弹窗（接收方远程搜索 + 备注）、成功后 `router.replace` 到接收方控制台重新拉详情。
6. 补测试：后端 Feature 覆盖正常转移与全部异常分支（含暂停、已删除等全状态可转移）；管理端 e2e 覆盖成功转移跳转、后端拒绝保留弹窗、暂停与已删除实例的入口可用。

## 风险与回滚

- 归属变更不可逆：接口无「撤销」动作，回滚只能再转移一次。转移前拦截未结清/未履约账单，避免转移后同周期可重复建单造成双扣。
- 历史订单与账单仍留在原账号（`orders.user_id` / `invoices.user_id` 不级联），新持有者的「相关账单」页签为空，属既定语义，已在弹窗文案说明（实例控制台的「相关订单」页签已按需求移除）。
- 自动续费被重置为 0：避免原账号余额替新持有者扣费。`renew_coupon_id` 等续费配置随实例走，不清除。
- 迁移只新增：`2026_10_31_000001` 补模板 `100030`（已有自定义模板则跳过）、`2026_10_31_000002` 补 `invoices(service_id,status,id)` 复合索引；两者 `down()` 均不破坏数据（索引可删，模板补入为单向同步）。
- 回滚方式：删路由与前端入口即下线功能；已发生的归属变更需人工再转移。

## 决策日志

| 日期       | 决策                                                       | 原因                                                                                                 |
| ---------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 2026-10-31 | D1 复用 `USER_MANAGE`，不新增权限码                      | 转移是写操作；放只读组等于把写能力下放给只读账号；权限表现无 transfer 码，新增会扩散到角色配置。     |
| 2026-10-31 | D2 状态不参与转移资格判定                                  | 业务要求运行中 / 暂停 / 已删除 / 异常 / 已到期均可转移；状态限制与到期限制已整体移除，账务闸门与锁内复核仍兜底。 |
| 2026-10-31 | D3 转移前置拦截待支付与已付未履约账单                      | 续费单查询带 `user_id`，转移后新持有者查不到旧账号那张单，同周期可再建单再付款。                     |
| 2026-10-31 | D4 强审计失败即回滚                                        | 归属变更无审计就失去追溯能力；用 `writeStrict` 把日志失败升级为事务失败。                            |
| 2026-10-31 | D5 不清 `order.user_id` / `invoice.user_id`               | 历史单据属既成事实，级联改写会破坏财务溯源；新持有者看到空页签属既定语义。                            |
| 2026-10-31 | D6 自动续费重置为 0                                        | 续费会从归属账号扣款，跨账号自动扣费会造成资金纠纷，交由接收方显式开启。                              |
| 2026-10-31 | D7 成功后跳到接收方控制台                                  | 原路由的 `userId` 已不再持有该实例，详情接口会 404，必须换身份否则页面报错。                          |
