# 管理端数据库备份队列化 · 2026-10-22

## 背景

管理端「导出数据库备份」原本在 HTTP 请求内同步执行 `mysqldump`：`DatabaseStatusController::exportBackup()` 直接调用 `DatabaseStatusService::createBackup()`，内部用 `Symfony\Component\Process` 的 `Process::timeout(600)` 跑子进程，再把产物用 `response()->download(...)->deleteFileAfterSend(true)` 一次性回吐。

这条链路有四个问题：

1. **请求超时截断**：宝塔 PHP-FPM 默认 `request_terminate_timeout` 远小于 600 秒，dump 跑到一半请求被切断，产物不完整，且没有任何失败反馈。
2. **占用 FPM 进程**：备份期间该 FPM worker 全程被占用，同期其它请求排队。
3. **与禁用函数策略冲突**：生产按 1.2 节只放开 `proc_open`，而把长事务压在 Web 侧等于让 FPM 长期持有子进程，与「需要 fork 的活尽量放 CLI」的部署口径相反。
4. **无进度可见性**：前端只能死等，用户重复点击会并发起多个 dump。

## 范围与验收

- [x] 导出接口改为投递队列任务并立即返回 `task_id`，请求内不再跑 `mysqldump`
- [x] 新增任务状态查询接口，供前端轮询
- [x] 新增下载接口，只按任务 ID 换回服务端文件名，并做文件名白名单校验
- [x] 任务状态用缓存承载（项目无 `job_batches` 表），TTL 2 小时
- [x] 前端改轮询：投递 → 每 2 秒查一次 → 完成自动下载
- [x] 失败不吞：任务标 `failed` 且异常向上冒泡，进入队列重试与 `failed_jobs`
- [x] 契约测试覆盖投递、轮询、404、防穿越、成功与失败收敛

## 实施步骤

### S1 任务状态与队列任务 — 已完成

- 新增 `backend/app/Services/System/DatabaseBackupTaskService.php`
  - 常量 `TASK_TTL_SECONDS = 7200`，状态 `queued` / `running` / `completed` / `failed`
  - `dispatch(?int $actorId, ?string $ipAddress): array`：`Cache::add()` 抢占在途标记（`system:database:backup:in_flight`，TTL 3600 秒），已有任务在跑时抛 40900/409；抢到后生成 UUID `taskId`，写 `queued`，投递 Job，返回 `[id, status, task_id, message]`
  - 投递失败（队列连接不可用等）时先 `markFailed('备份任务投递失败：…')` 再向上抛出，任务收敛为 `failed`，不挂在 `queued` 等 TTL 到期
  - `find(string $taskId): ?array`、`markRunning()`、`markCompleted()`、`markFailed()`
  - `completedFilename(string $taskId): ?string`：只有 `completed` 且文件名通过白名单才返回
- 新增 `backend/app/Jobs/ExportDatabaseBackupJob.php`
  - `tries = 1`（重试会重复产出备份文件）、`timeout = 900`（大于 `mysqldump` 的 600 秒）、`onQueue(BackupQueue::name())`（独占 `backup` 队列）、`afterCommit()`
- 新增 `backend/app/Support/BackupQueue.php`：`name()` 对 `CAIWU_BACKUP_QUEUE` 的空串/纯空白兜底为 `backup`，含逗号时直接抛 `InvalidArgumentException`。`.env` 显式写空值时 `env()` 返回空串、config 默认值不生效，空队列名会被 DatabaseQueue 回退成 `default`，而 `default` 属于 business 组，900 秒导出会重新堵住业务队列。`ExportDatabaseBackupJob`、`queue:drain`、`app:serve` 与调度命令清单四处共用
  - `handle()`：`markRunning` → `createBackup` → `markCompleted`；异常先 `markFailed` 再 rethrow
  - `failed()`：兜底把任务收敛为 `failed` 并写 `Log::error`
- `backend/app/Support/CacheKey.php` 新增 `databaseBackupTask(string $taskId)` → `system:database:backup:{taskId}`

### S2 下载安全 — 已完成

- `DatabaseStatusService::isBackupFilename()`：`/^backup_\d{14}_[a-z0-9]{6}\.sql$/`
- `DatabaseStatusService::backupPath()`：拼接前强制 `basename()`
- 下载接口三段校验：任务不存在/未完成 → 40400；文件名不合白名单 → 40400；文件已被清理 → 40400「备份文件已被清理，请重新导出」

### S3 接口与路由 — 已完成

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/v2/admin/database/backups` | 投递任务，返回 `task_id` |
| GET | `/api/v2/admin/database/backups/{taskId}` | 查询状态 |
| GET | `/api/v2/admin/database/backups/{taskId}/download` | 下载已完成产物 |

三条路由均在 `DATABASE_MANAGE` 权限组内，`{taskId}` 约束 `[0-9a-fA-F-]{36}`。新增 `ShowDatabaseBackupTaskRequest` 做 UUID 校验并禁止分页参数。

### S4 前端 — 已完成

- `frontend-admin-v3/src/api/admin/database.ts`：`exportBackup()` 改为「投递 → 轮询（2 秒 / 最多 450 次，即 15 分钟，对齐后端 Job 超时）→ 完成则用裸 `fetch` 带 Bearer 拉流并 `createObjectURL` 下载」
- 失败时抛任务里的 `message`；轮询超时提示「备份仍在后台执行，请稍后回到本页重试下载」
- 轮询遇到错误时只有业务码 `40400`（任务不存在/已过期）才清本地 `taskId`；断网、超时、5xx 时备份仍在服务端跑，清掉就丢了下载入口
- `frontend-admin-v3/src/pages/admin/system/database/index.vue`：确认框正文改为「备份在后台执行，完成后会自动下载，期间可以继续留在本页」，确认后立即关闭弹窗并提示已提交
- `taskId` 落 `localStorage`（键 `caiwu.admin.database.backupTaskId`）：`onMounted` 调 `resumePendingBackup()`，本地有未收敛任务时接着轮询并在完成后自动下载；下载失败保留记录供重试，任务收敛后再清掉
- e2e：`frontend-admin-v3/e2e/database-backup.spec.ts` 覆盖「点击导出 → 轮询完成 → 清 taskId」「刷新后续轮询并自动下载」「轮询网络错误保留 taskId」「轮询任务过期清 taskId」四条链路

## 风险与回滚

1. **缓存承载任务状态**：缓存被清空或过期（2 小时）后任务查不到，前端提示「备份任务不存在或已过期」；备份文件仍在磁盘上，可按文件名手工取。这一点是刻意取舍——项目没有 `job_batches` 表，为一次备份新建批次表不划算。
2. **队列未运行即无法备份**：`queue:drain` 没跑时任务会一直停在 `queued`，前端 15 分钟后超时提示。这是真实状态，比在 FPM 里跑到一半被切断更可观测。
3. **并发投递（已收敛）**：`dispatch()` 用 `Cache::add()` 抢占在途标记，第二次提交直接 409/40900；任务收敛（`markCompleted`/`markFailed`）按 taskId 比对后释放。标记 TTL 3600 秒覆盖「排队 + Job timeout 900 秒」并留一倍冗余，进程被强杀时最迟 60 分钟后自动解封。
4. **回滚**：代码可整体回退；回退后旧接口路径 `POST /database/backups` 语义变回同步执行，需要同步回退前端。备份文件与缓存键无 schema 依赖，无需迁移。

## 决策日志

| 日期 | 决策 | 原因 |
| --- | --- | --- |
| 2026-10-22 | 任务状态放缓存而非新建表 | 项目无 `job_batches` 表，备份是低频运维动作，为它加表与迁移不划算；2 小时 TTL 足够覆盖一次导出 |
| 2026-10-22 | `tries = 1`，不允许重试 | 重试会重复生成备份文件，且 `mysqldump` 失败多为配置/权限问题，重试无意义 |
| 2026-10-22 | `timeout = 900` | 必须大于内部 `Process::timeout(600)`，否则队列先杀进程，`failed()` 拿不到 mysqldump 的真实错误 |
| 2026-10-22 | ~~沿用 `default` 队列，不新建队列名~~ → **改为独立 `backup` 队列** | 原判断漏了 `--max-time=50` 只在两次任务之间检查：900 秒的 mysqldump 一旦被 worker 取走，整组 business 队列在导出期间全部排队。现由 `queue:drain` 起第 4 个 worker 独占消费 `backup`，并从 provision/business 里 `array_diff` 掉备份队列，防存量 `.env` 重复消费 |
| 2026-10-23 | 备份先写 `.sql.part` 再原子 `rename` | `Process::timeout(600)` 超时是抛异常而非返回失败结果，半成品若直接叫 `.sql`，会被 `isBackupFilename` 认成可用产物并占掉 10 份保留配额；`.part` 由 `pruneOldBackups()` 顺带清理超龄（1 小时）残片 |
| 2026-10-23 | 下载不再 `deleteFileAfterSend(true)` | 连接中断（浏览器取消、网络抖动）同样走该分支，删了文件再点下载就是 404；保留策略本来就把目录收敛在最近 10 份 |
| 2026-10-23 | 备份 `taskId` 落 localStorage | 备份在服务端后台跑，刷新页面不该丢掉下载入口；回到本页按本地 taskId 续轮询并在完成后自动下载 |
| 2026-10-23 | 续轮询补 e2e 用例 | 这条路径只在刷新页面时才走到，单测覆盖不到「页面挂载即续等」的接线；`database-backup.spec.ts` 临时去掉 `resumePendingBackup()` 会失败，证明它在真正守护该行为 |
| 2026-10-23 | 四个队列组按 backup → provision → automation → business 依次认领 | 原实现只让 provision/business 与 backup 互斥，automation 组没参与，存量 `.env` 把 `CAIWU_SCHEDULE_QUEUE` 写成含 backup 时会出现两个 worker 抢 `backup`，900 秒的 mysqldump 顺着它堵住定时任务组。改成统一「先认领者独占」，四个组两两不重叠 |
| 2026-10-23 | 在途标记 TTL 1800 秒 → 3600 秒 | 排队侧不确定：`queue:drain` 每分钟一轮，前一轮收尾要等 `--max-time=50`，最坏近一分钟才轮到 backup 组；叠加 900 秒导出后 1800 秒只剩十分钟余量，标记提前过期会让去重失效、并发起第二个 mysqldump。3600 秒仍小于任务状态 7200 秒 |
| 2026-10-23 | 前端轮询上限 300 次 → 450 次 | 300 × 2 秒 = 10 分钟，短于后端「排队 + 900 秒」的可能耗时，会出现前端先放弃、后端仍在跑。450 × 2 秒 = 15 分钟，让后端先收敛为 `failed` 再让前端报错 |
| 2026-10-23 | 备份队列名统一走 `BackupQueue::name()` 兜底 | `.env` 显式写 `CAIWU_BACKUP_QUEUE=` 时 `env()` 返回空串，config 默认值 `'backup'` 不生效；空队列名被 DatabaseQueue 回退成 `default`，而 `default` 在 business 组里，900 秒导出会重新造成队头阻塞。四处消费点各写一份判断迟早漏改，收敛成一个静态方法 |
| 2026-10-23 | `BackupQueue::name()` 拒绝逗号分隔的队列名 | worker 把 `--queue` 按逗号拆成多个队列逐个 pop，而 Job 投递只认字面队列名：配成 `backup,archive` 时任务落进一个永远不会被消费的队列，在途标记 3600 秒内不清，用户重提一直被 409 挡。配置错误要在部署时暴露，不能退化成「提交成功但永远不执行」 |
| 2026-10-23 | 前端轮询只在业务码 40400 时清本地 taskId | 原来任何错误都清，断网、超时、5xx 时备份仍在服务端跑，清了就丢下载入口。40400 有两条抛出路径（非 2xx 走响应拦截器、2xx 但 code!==0 走 transformRequestHook），所以同时读 `error.code` 与 `error.response.data.code` |
| 2026-10-24 | 备份队列名配置非法时只跳过 backup 组，不让整轮 drain 停产 | `BackupQueue::name()` 原先在 `workerDefinitions()` 里直接抛，异常冒到 `queue:drain` 后整条命令 FAILURE，provision/business/automation 三个 worker 一个都不起（实测 `CAIWU_BACKUP_QUEUE='backup,archive' php artisan queue:drain` → EXIT=1）；同一抛点还让管理端定时任务页 `overview()` 整体 500。改为 backup 组单独 try/catch：跳过该组 + `Log::critical`，配置错误并入本轮 failures 使 `exit_code=1` 可被运维发现，其余三组照常消费；`overview()` 回退默认队列名并在命令说明里标注「备份队列配置无效」；`exportBackup()` 捕获后返回 42200 可读提示 |
| 2026-10-22 | 下载走独立接口而非把文件名回给前端直链 | `storage` 不在 Nginx 静态目录内；独立接口可以在服务端做白名单与「已完成」双重校验 |
| 2026-10-22 | 前端用裸 `fetch` 拉流，不走 axios 实例 | axios 默认按 JSON 处理，blob 下载需要绕开响应拦截器才能拿到 `content-disposition` |
