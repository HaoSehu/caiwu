# 管理端服务控制台首屏两段式加载

## 背景

上一轮《管理端刷新首屏守卫优化》只解决了 `/v2/admin/auth/info` 串行阻塞。打开「服务控制台」独立页（`/admin/users/:id/services/:serviceId`）仍然长时间只显示工具栏和一块空白，主体迟迟不渲染。

实测证据（服务 318 / 用户 484，本机 Laravel）：

- 前端：`frontend-admin-v3/src/pages/users/service-console/index.vue:13-21` 用 `v-if="!ready"` 挡住整个主体，`ready` 只在 `loadDetail()` 成功返回后才置真；等待期间页面只剩「返回用户详情」「刷新」两个按钮，`shared/user-v3/components/LoadingState.vue` 只有三点跳动动画，没有骨架屏。
- 后端：`backend/app/Services/ClientServiceConsole/ServiceDetailService.php:117-121` 的 `$needsRemoteRefresh` 由 `$refreshRemote || needsRemoteSnapshotRefresh() || needsConnectionHydration() || needsRuntimeStatusRefresh() || needsNatRemoteHydration()` 决定；只要 `provision_data.last_synced_at` 超过 `DETAIL_REMOTE_SNAPSHOT_TTL_SECONDS`（120 秒），就会跳过 30 秒响应缓存，在 `:134-155` 同步调用 `fetchRemoteState()`。
- `fetchRemoteState()`（`:494-593`）四段严格串行：`login` → `getHostDetail` → `fetchModuleStatusPayload` → `fetchNatRemoteConnection`。服务 318（上游 zjmf_finance_api）实测合计 3,003ms（0 / 622 / 1,560 / 821），复测在 3.3–7.9s 之间波动。
- 对比：`getBaseDetailForUser()` 27–70ms，`getDetailForUser()` 冷启动 4,724ms、紧接着第二次 8ms。两者返回字段集合完全一致，差异只在 `upstream.status`（本地快照 `on` vs 上游 `Active`）、`upstream.os` 与 `remote_error`。

结论：首屏被一个「管理端不必要实时」的上游状态同步阻塞。上游状态是增量信息，不该决定页面能否渲染。

## 范围与验收

- [x] 首屏只取本地快照：管理端打开服务控制台时请求携带 `sync_remote=0`，服务端直接返回本地数据，不触发任何上游网络往返。
- [x] 渲染后异步补丁：首屏 ready 之后静默请求 `GET /v2/admin/users/{user}/services/{service}/remote-status`，把运行时与上游状态合并进详情，失败不打断已渲染内容。
- [x] 保留显式刷新：「刷新远程」按钮仍走 `remote-status` 并给出「远程状态已刷新」反馈。
- [x] 契约向后兼容：`sync_remote` 缺省为 true，其它调用方（用户端、既有管理端调用）行为完全不变。
- [x] 参数校验：`sync_remote` 非布尔值返回 422。
- [x] 后端 feature 覆盖六条路径（本地快照、默认同步、远程补丁、非法入参、快照缓存作用域、refresh 冲突）。
- [x] 前端 e2e 覆盖「先渲染本地快照 → 远程状态补丁 → 手动刷新 → 补丁失败降级 → 工具栏刷新失败提示」。
- [x] 代码审查补丁：本地快照写独立缓存作用域、`refresh` 与 `sync_remote=0` 互斥、工具栏刷新失败可见。
- [x] `php artisan test` / `composer analyse` / `composer format:check` / `composer audit:plugins` / `vue-tsc` / `eslint` / `npm run build` / `npm run test:e2e` 全部通过。

## 风险与回滚

- 数据滞后风险：本地快照的 `upstream.status` / `upstream.os` 可能比上游旧，最长滞后到一个同步周期。首屏随后会拉 `remote-status` 补丁，且页面上仍有显式「刷新远程」；`sync_remote` 缺省值保持 true，需要强一致的调用方不受影响。
- 缓存语义风险：`getBaseDetailForUser()` 不写 `last_synced_at`，不会把快照标记成「新鲜」，因此不会让后续缺省请求误判为无需同步。新增用例 `test_sync_remote_disabled_returns_local_snapshot_without_touching_upstream` 对此断言（`last_synced_at` 保持 null）。
- 缓存键风险（审查发现，已修复）：`getBaseDetailForUser()` 原先无条件写 `buildDetailResponseCacheKey()` 的权威 detail 键，而该键与 `getDetailForUser()` 共用。若本地快照与上游同步落在同一秒（`updated_at` 秒级精度未轮转），后续缺省请求会命中未同步的旧快照；该键按用户+实例共享，客户端详情接口也读同一键。现改为 `snapshot` 作用域独立键，用例 `test_local_snapshot_writes_scoped_cache_instead_of_authoritative_detail_cache` 锁定「快照不得写权威键」。
- 范围风险：业务主流程仍不改 `ServiceDetailService.php` 的同步逻辑，只调整缓存键作用域（+3 行）；回滚成本低。
- 回滚：撤销上述 8 处改动并删除新增 feature 测试、还原 e2e 断言；无数据迁移、无接口契约破坏（新增参数可选，`refresh`+`sync_remote=0` 组合原本就是无效调用）。

| 2026-10-25 | 不改 `ServiceDetailService.php` 的核心同步流程 | 该文件 1,484 行、被用户端与管理端共用；在门面加短路分支即可达成目标，改动面最小，回归风险最低。                                     |
| 2026-10-25 | 审查后给本地快照单独缓存作用域，而不是让 base 不写缓存 | 保留 30 秒重复打开同一实例的收益；独立键即可隔离污染，`forgetDetailCaches()` 一次清两个键避免脏数据滞留。                           |
| 2026-10-25 | `refresh` 与 `sync_remote=0` 组合直接 422，而不是让 refresh 生效 | 二者语义冲突：refresh 要求强同步，sync_remote=0 要求不碰上游。静默丢弃调用方意图比报错更难排查。                                     |
