# 财务核心破坏性重构（重建 + 一次性切换）· 2026-10-20

## 背景

财务是系统最高风险面。近半年已修完「资金流拆分」「退款双通道」「收入净额口径」等缺陷，但结构性问题仍在：

1. **余额不可溯源**：`user_accounts.cash_balance` 只有一个标量，`account_transactions` 只记「变了多少」，不记「花的是哪笔钱」。退款直接加余额，无法回答「退的是哪笔充值」。
2. **写口未真正收敛**：`AccountService` 只有绝对赋值 `setCashBalance`，余额与台账靠调用方各自双写；`ReferralService` 仍直写余额与台账。
3. **幂等只在前端**：仅 Redis `idempotency_key`，不比对请求体，同键换内容会复用旧单。
4. **退款不看交付**：退款不检查服务是否已交付、不释放库存、不终止实例；`manual_mark` 与 `balance` 两套口径并存，互斥守卫散落两处。

**用户裁决（2026-10-20）**：允许重建财务表 / 一次性整体切换 / 删除 `manual_mark` 通道 / 不做原路退款（只做退款到余额）/ 交付到三端。

**非目标**：不做网关原路退款；不做实例级金额分摊（`order_item_units` 不复活）；不重建 referral 子账本；不把金额列改为整数分。

## 范围与验收

### 数据模型（9 张新表）

- [ ] `finance_accounts`：现金账户，接管 `user_accounts.cash_balance`。
- [ ] `finance_ledger_entries`：不可变台账，接管 `account_transactions`，**保留 `account_type`**（含 referral 行）。
- [ ] `finance_funding_lots` / `finance_consumptions`：资金批次与消费映射（FIFO）。
- [ ] `finance_refunds` / `finance_refund_allocations`：退款单与批次证据，删 `refund_method`，加 `funds_moved`。
- [ ] `finance_operations`：DB 幂等 + 操作审计。
- [ ] `finance_migration_runs` / `finance_cutover_inbox`：切换记录与窗口期回调暂存。

### 内核

- [ ] `FinanceAccountService`：`credit/debit/balanceCents`，余额+台账+批次同事务。
- [ ] `FinanceLedgerService`：唯一台账写口，算 `balance_after`。
- [ ] `FundingLotAllocator`：FIFO 分配、恢复、负批次跳过。
- [ ] `FinanceIdempotencyService`：同键同体重放、同键异体 409，幂等行事务外提交。

### 不变式（测试锁定）

- [ ] `account_type='cash'` 时 `SUM(lots.remaining) == accounts.available_amount`。
- [ ] 每笔正数现金台账有且仅有 1 个 lot；负数台账 consumption 合计 == `abs(change_amount)`。
- [ ] `payments` / 台账 / 退款行数只增不减。

### 切换

- [ ] `finance:rebuild` 默认 dry-run，`--execute` 写入，G1–G7 闸门全绿才继续。
- [ ] `000013` 重指 `recharge_records` 两条外键到新表。
- [ ] T+7 执行 `000014`（删 `cash_balance`）与 `000015`（旧表改名归档）。

### 三端

- [ ] admin-v3：`RefundDialog` 单通道、批次区块、订单侧退款入口。
- [ ] v4-console：流水来源列、退款记录区块、幂等头。
- [ ] shared：`FUNDING_SOURCE_TYPE_MAP` / `REFUND_BLOCK_REASON_MAP`，删 `REFUND_METHOD_MAP`。

## 风险与回滚

- **窗口内写入**：强制维护模式 + 写事务探测 + 备份 + `finance_cutover_inbox` 兜住支付回调。
- **外键重指**：`recharge_records` 两条外键必须先验证引用值 100% 命中新表，再由 `000013` 切换；失败即 abort。
- **批次与余额不等**：6 个闸门硬阻断；188 个历史不平用户按 2026-10-10 裁决追加 `calibration` 台账与批次，不伪造历史。
- **回滚**：窗口内回滚代码 + 表名恢复；窗口后 7 天内 `cash_balance` 仍在同事务热备，回滚代码即可继续用旧内核。`000014/000015` 推迟到 T+7，是保留回滚能力的必要条件。
- **不可破**：资金历史行不物理删除（旧表改名归档）；不篡改已完成单据金额；`payments` 不删。

## 切换 Runbook（S8 执行手册，生产窗口照此执行）

> 前提：S0–S6 代码已随发布上线；本窗口只做「数据重建 + 回调暂存 + 验证」。
> 全程预计 20–40 分钟（取决于台账行数，当前 684 行量级 < 1 分钟）。

### T-1 天（窗口前）

1. 备份：`mysqldump` 全量导出 `account_transactions`、`refunds`、`user_accounts`、`recharge_records`、`invoices`（回滚锚点）。
2. `.env` 追加 `FINANCE_CUTOVER_INBOX=true`，`php artisan config:cache`。
3. 预告：暂停宝塔 cron（`php artisan schedule:run`）与队列 worker；确认无进行中的支付回调（`payments` 近 5 分钟无 pending）。

### T0 窗口开始

4. `php artisan down --secret=finance-cutover`（业务页 503，**支付回调路由仍在**，回调会进收件箱并 ack 成功）。
5. `php artisan finance:cutover-run`——**一键编排**：前置检查 → rebuild dry-run → rebuild --execute --fresh（七闸门）→ 000013 外键重指 → 闸门复验 → 三方一致性校验（余额==批次==热备列）。任一步失败自动停机并打印回滚指引；幂等可重跑（已完成的环境只做验证）。
   - 细项分解（等价手工命令，仅当需要分步排查时使用）：dry-run → `finance:rebuild`；重建 → `finance:rebuild --execute --fresh`；外键 → `migrate --path=database/migrations/2026_10_20_000013_*`；复验 → `finance:rebuild --verify-only`。**000013 必须在重建之后**（断言校验旧表引用可解析到新表，新表为空时故意失败拦住错误顺序）。
6. 人工抽查：`finance_reconciliation_diffs` 里的 `unallocated_debit` 行数与演练一致（差异数不同 = 连错环境）。

> ⚠️ 部署顺序红线：发版自动跑 `php artisan migrate` 会把 `000013` 提前执行（此时新表为空，断言失败会**卡死部署**）。
> 发版阶段迁移请用 `--path` 排除 `2026_10_20_000013_*`，或等窗口内由 `finance:cutover-run` 按正确顺序执行。

### T0 冒烟（按顺序，任一失败即回滚）

9. `finance:cutover-run` 的第 5/6 步已含闸门复验与三方一致性校验（全绿才会走到收尾清单）。
10. 抽一个真实用户走 tinker 内核冒烟：credit → debit → 批次合计 == 余额 == 热备列。
11. `php artisan up`，人工下一单余额支付 + 一单后台退款到余额，核对台账/红字账单/批次。

### T0 收尾

12. `php artisan finance:replay-cutover-inbox`——重放窗口内回调；失败行保留 pending，人工核对。
13. `.env` 移除 `FINANCE_CUTOVER_INBOX`（改回 false），`config:cache`。
14. 恢复 cron 与 worker；观察 `php artisan queue:failed` 与 `laravel-*.log` 30 分钟。

### 回滚预案（任一步失败且不可修复）

- **数据层**：新表整体 `DROP`（`finance_accounts`/`finance_ledger_entries`/`finance_funding_lots`/`finance_consumptions`/`finance_refunds`/`finance_refund_allocations`/`finance_operations`/`finance_migration_runs`/`finance_reconciliation_diffs`/`finance_cutover_inbox`），`000013` 的 down() 把 `recharge_records` 两条外键指回旧表——旧表全程未被改动，数据零损失。
- **代码层**：回滚到切换前版本（git revert / 上一个 release），`.env` 移除 `FINANCE_CUTOVER_INBOX`。
- 窗口内已入收件箱的回调：回滚后由旧代码的网关重试机制自然补投（渠道侧未拿到失败应答）。
- **T+7 后回滚窗口关闭**：`000015` 删 `cash_balance` 前先置 `FINANCE_HOT_STANDBY=false`；此后旧代码无法运行。

### T+7 归档（切换稳定 7 天后）

`000015/000016` 已就位但**默认空转**（未设 `FINANCE_ALLOW_RETIRE=true` 时跳过并记 warning，迁移记录照常落库）——发版/测试环境常规 migrate 不会误删。真正执行按以下两步重放：

1. 确认切换后稳定 7 天、无未对齐差异（`finance:rebuild --verify-only` 语义此时已退役，改看 `finance_reconciliation_diffs` 为空）。
2. `.env` 置 `FINANCE_HOT_STANDBY=false` + `FINANCE_ALLOW_RETIRE=true`，`config:cache`（000015 内置双保险：热备未关直接抛错拒绝删列）。
3. `php artisan migrate:rollback --force --path=database/migrations/2026_10_21_000015_drop_user_accounts_cash_balance_column.php`（此前记录为空转，down 同样空转，仅移除记录）
4. `php artisan migrate --force --path=database/migrations/2026_10_21_000015_drop_user_accounts_cash_balance_column.php`（真正删列）
5. 同法两步执行 `000016`（`account_transactions`→`archived_account_transactions`、`refunds`→`archived_refunds`，改名保留不 DROP）
6. `php artisan finance:rebuild` 应报"旧表已归档，命令退役"（护栏生效验证）。
7. 移除 `FINANCE_ALLOW_RETIRE`，`config:cache`；回滚窗口自此永久关闭（回滚只能走 `archived_*` 表导回）。

已在 `idc_test` 完成全序列机制验证（跳过→实跑→回滚还原→记录回填），终态与迁移前完全一致。
