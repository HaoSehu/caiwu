## 需求解析

本次需求不是单纯罗列页面功能，而是回答五个可治理的问题：

1. 订单、账单、支付、履约和服务实例分别对什么结果负责，边界是否清楚。
2. 用户所称“项目类型”在现有代码中实际对应什么分类，谁能变更，变更后如何保留历史语义。
3. 一笔交易从商品选择到上游履约，能否以同一关联标识回放人员、状态、金额与外部调用。
4. 取消、退款、人工开通等高风险动作能否做到职责分离、留痕、复核和对账。
5. 发现问题后，如何以可回滚、可验收的工程计划整改，而不是直接改表或大规模重构。

本报告将“已由代码或结构快照证实的事实”与“需要实库、生产日志或业务负责人确认的事项”分开。未执行写测试、未查询生产数据、未修改业务代码或数据。

## 术语裁决与负责的类型

在后端 app、routes 与 database 目录中未发现 Project 实体、project_type 字段或“项目类型”领域模型。因此，本报告暂将需求中的“项目类型”解释为可售商品的分类；若其实际指交付项目、客户项目或研发项目，需要另建领域模型和责任台账，不能与 ProductType 混用。

| 概念 | 真实来源 | 当前取值或形态 | 推荐责任口径 |
| --- | --- | --- | --- |
| 业务产品类型 | ProductType 常量 | cloud_server、game_cloud、cloud_desktop、bare_metal、cdn、physical_machine、web_hosting、other | 产品负责人对分类定义与生命周期负责。 |
| 商品种类或一级分类 | ProductType 设置及 first_product_groups | 动态 value、label、visible、sort_order，映射到一个业务产品类型 | 商品目录负责人对显示、上架和分类变更负责。 |
| 订单类型 | OrderType | new、renew、upgrade | 履约负责人对服务开通、续费或附加配置处理负责。 |
| 账单类型 | InvoiceType | new、renew、recharge、upgrade、deduction、refund、referral_credit、manual | 财务负责人对应收、冲正、余额和凭证语义负责。 |
| 履约种类 | 配置快照中的业务元数据和处理器 | 新购、续费、流量包、主机升降级等 | 交付负责人对上游动作、重试与人工处置负责。 |

商品分类存在两层：固定的业务产品类型与可动态维护的商品种类。ProductTypeService 会将动态种类同步为一级商品分组；删除时会检查当前分组和商品使用量，但本轮未看到分类版本、生效时间、审批人或历史类型变更台账。因此，分类不是“可随意改名的菜单项”，而应纳入目录治理。

## 已验证的交易链路

    商品目录与报价
        -> CheckoutService
        -> Invoice（财务凭证）
        -> Order（开通投影，部分类型可为空）
        -> Payment / AccountTransaction
        -> PaidOrderBusinessFlowDispatcher
        -> 队列或同步履约
        -> Service、上游绑定、开通尝试

### 新购

CheckoutService 要求幂等键和报价令牌，使用用户维度缓存锁、数据库事务和商品行锁；同一事务中创建未付账单、开通投影订单、库存与优惠快照，并写入操作记录。支付回调还具备验签、金额/商户校验、状态短路和回调留档。履约任务使用唯一任务、重叠锁和订单锁，正常新购成功或失败都会写上游开通尝试。

这意味着新购路径已具备良好的并发与重复回调防护，不应被报告为“整体失控”。

### 续费与流量包

客户续费可走 invoice-only 语义，服务续费处理器有独立锁、已完成标记和上游账单恢复逻辑。流量包在创建账单后会创建并绑定内部 Order，再由订单路径履约。这两类路径说明“账单不一定有订单”是设计允许的情形，整改不能强制把所有账单一律改成订单。

### 主机升降级：P0 静态履约断链

已证实的静态路径如下：

    host_upgrade 账单创建
        -> 仅创建 Invoice(type=upgrade)，未创建或绑定 Order
        -> 支付成功后进入无 Order 的 upgrade 分支
        -> 被交给流量包桥接处理器
        -> 处理器仅告警并返回空结果
        -> 调用方无条件视为已处理

真正的主机升降级上游调用只存在于接收 Order 的处理方法。当前已读的 ServiceUpgradeServiceTest 仅覆盖账单创建，以及人工构造 Order 后的履约，未覆盖真实的“host_upgrade 账单 -> 支付 -> 上游履约”闭环。

结论为：已证实存在静态不可达履约分支，风险是已支付的主机升降级未进入预期履约、上游尝试与服务状态记录。尚未进行集成测试或实库核查，不能表述为已经发生资金损失；但在修复并验证前，应按 P0 控制该业务入口。

## 权限与职责分离现状

管理端已对读写路由使用认证和权限中间件，客户查询也按 user_id 限制归属。针对敏感变更，静态代码显示：

- invoice.manage 可直接执行账单取消和按账单退款。
- user.manage 同时覆盖人工创建/开通服务、删除服务、服务退款、电源操作和密码重置等多个高影响动作。
- order.manage 常量与角色映射存在，但在已检索的管理端路由中未发现由其单独保护的订单变更入口。
- 提现存在单独审批路由，但本轮审阅的账单取消、退款和人工开通路径未发现对应的财务审批关口。

这不是对任何现有管理员的风险判断，而是权限粒度和双人复核尚无法由当前静态实现证明。企业化整改应把“申请、审批、执行、复核”拆开，并保留紧急授权的事后证据。
