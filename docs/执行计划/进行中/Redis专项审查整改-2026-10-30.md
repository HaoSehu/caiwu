# Redis 专项审查整改 · 2026-10-30

## 背景

Redis 专项审查报告指出：当前部署把 Redis 同时用于缓存与分布式锁，但键空间前缀、连接分层与「拿不到锁怎么办」三件事在文档里没有统一口径，配置示例也留着一条与当前取值矛盾的行：

1. `REDIS_PREFIX`（队列与 `Redis::*` 直接操作）与 `CACHE_PREFIX`（Cache 门面）两套前缀各自默认空串，文档没写清分工，也没写「多实例共用一个 Redis 时必须区分」。
2. 三层连接（`default` 锁/队列、`cache` 业务缓存 DB1、`volatile` 高频短 TTL DB2）只在配置注释里存在，运维侧没有可查的口径。
3. `Cache::lock` 失败时的处理散落在 20 余处源码里，三种语义（无锁执行 / 跳过本轮 / 抛 409）没有成文规则，新增代码只能靠模仿。
4. `backend/.env.example` 里 `REDIS_QUEUE_RETRY_AFTER=90` 是生效行，但当前 `QUEUE_CONNECTION=database` 下它根本不生效；且 90 低于作业 timeout（历史审查 `V9-config-ops.md:63-73`），一旦真切到 redis 队列驱动就是「作业还在跑就被重新入队」。
5. 生产预检脚本对 `CACHE_STORE` / `REDIS_PASSWORD` 有校验，对「多实例共用一个 Redis 但前缀为空」这个真实故障模式没有只读检查。
6. 两处「故意不按常规写」的代码（`UpgradeLock` 用 `flock`、`MediaLibraryOrganizer` 清理历史键）缺少登记，后来者容易当成疏漏改掉。

本计划第二轮（R7–R12）包含运行时代码整改：把散落的 volatile 存储入口、TTL 字面量、队列驱动判定、日志写入收口为 `backend/app/Support` 下的四个入口类，并给健康探针补 Redis 可用性检查。第一轮（R1–R6）确实只动文档、`.env.example` 注释与预检脚本，本轮追加的代码改动逐条列在 S7–S12。

## 风险与回滚

1. **预检新增 warning 会被误读为通过**：`[WARN]` 不进 `failed`，`process.exitCode` 保持 0。这是刻意的——预检的退出码被发布脚本用来卡发布，无法判定实例数时让所有单实例部署挂掉比漏检更糟。判定依据只认显式环境变量，宁缺勿猜。
2. **`--json` 输出形状**：仅在存在 warning 时追加 `warnings` 字段，未改动 `results` 结构与 `ok` 语义；下游若严格校验字段集合需注意。
3. **文档示例不含密钥**：三层连接、前缀示例全部只用变量名与默认值，未写入任何主机、端口或凭据实值。
4. **回滚**：R1–R6 只动文档、`.env.example` 注释与预检脚本的只读检查，回滚即恢复对应文件；R7–R12 改动 `backend/app` 与 `backend/config`，回滚按 S7–S12 的分条还原对应文件即可，不涉及数据迁移（新迁移只有模板 100030 一条，且为幂等补入）。

## 决策日志

| 日期 | 决策 | 原因 |
| --- | --- | --- |
| 2026-10-30 | 键空间内容写进「部署与调度指南」3.4 节，不新开参考资料 | 该文档已在 3.3 节末尾写明「Redis 当前用于缓存」，键空间是同一口径的展开；另开一份会让「Redis 怎么用」出现第二个真源，运维还要在两份之间比对。 |
| 2026-10-30 | 锁降级语义按「重复执行的后果」分三档，而不是按调用方是 HTTP 还是 CLI 分 | 决定要不要吞掉锁失败的，是重复执行会不会多扣钱、多开通、把状态机推错；同一段资金逻辑既可能被 HTTP 触发也可能被队列触发，按调用方分会给出两套互相矛盾的规则。 |
| 2026-10-30 | 状态机推进与资金路径拿不到锁统一转 `BusinessException(40900, 409)`，存量 422 点不一次性改 | 409 的语义就是「与资源当前状态冲突、可稍后重试」，前端能据此提示「处理中」而不是当失败重试；422 会被前端当参数错误、500 会触发告警系统当故障，两者都会把正常并发挡成异常。存量点已在源码里被调用方显式处理，改状态码等于改响应契约，须单独评估，故本轮只约束新增代码。 |
| 2026-10-30 | `volatile` 存储层固定连接名、库号经 `REDIS_VOLATILE_DB` 解析 | 库号是环境相关的（同机多项目、多环境都要错开 DB），必须能按环境改；而连接名一旦也做成可配，就可能出现「改了 `REDIS_CACHE_CONNECTION` 却把高频临时态写进业务缓存库」的误配，验证码、限流、VNC 临时令牌就会和业务缓存同库不同 TTL 地混在一起。固定连接名让三层隔离由代码保证，环境差异只留一个数字。 |
| 2026-10-30 | 预检在多实例判定不出时只给 warning，不报 error | 这个仓库默认是单实例宝塔部署，拿不到实例数时如果按「可能多实例」报失败，所有单实例环境都会被自己的预检卡住发布；而伪造失败会让团队直接跳过预检，比漏检更危险。因此判定依据只认显式环境变量，缺声明就提示、不阻断。 |
| 2026-10-30 | `REDIS_QUEUE_RETRY_AFTER` 改为注释行而不是删掉 | 当前 `QUEUE_CONNECTION=database` 下它不生效，留生效值会让人误以为在调优；但将来切 redis 队列驱动时这一项是必需的，删掉就丢了「必须大于最长作业 timeout」这个约束。注释行既让当前状态诚实，又保留切换时的正确参考值。 |
