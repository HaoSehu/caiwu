# TDesign 规范逐页对齐（两端全页面）

## 背景

管理端 `frontend-admin-v3`（62 个页面文件）与用户控制台 `frontend-user-v4-console`（56 个页面文件）虽然都已使用
TDesign Vue Next，但组件用法、视觉令牌、文案口径、加载与空态处理长期各自演化，与 `docs/DESIGN.md` 存在系统性偏差：
标签变体混用 outline、表格数据拉取不挂原生 loading、分页缺每页条数、对话框确认按钮出现「保存/提交/创建」等第三种口径、
时间列直出裸字符串、硬编码色值与像素圆角、用户可见文案出现「弹窗/侧边栏/...」。

本计划按页面为推进单位完成全量核对与最小化修正，基准只有两个：TDesign Vue Next 官方文档（经 tdesign-mcp-server 取得）
与 `docs/DESIGN.md`。

## 目标与非目标

目标：

- 两端全部 118 个页面文件（管理端 62 + 控制台 56）逐页给出结论，不抽样、不只改典型页。
- 同一规则在两端用同一标准；官方文档与 DESIGN.md 是唯一裁决依据。
- 改动落在规范对齐必需的最小行范围内。

非目标：

- 不重写页面结构，不引入新的状态管理、请求层或组件抽象。
- 不修改接口调用、数据逻辑、路由与业务流程。
- 不处理 `frontend-user-v3-www`（官网端的组件体系迁移独立推进，见本目录《www端TDesign组件体系迁移-2026-11-01》；该端已于 2026-11-01 完成 Element Plus → TDesign Vue Next 迁移，本计划的逐页对齐规则尚未覆盖它）。

### 官方文档核对锚点（经 tdesign-mcp-server 取得）

- `t-tag`：`theme` 默认值即 `default`，`variant` 默认 `dark`，可取 `dark/light/outline/light-outline`。因此「t-tag 未写 theme」本身不构成违规，
  只有表达**状态语义**的标签必须显式映射 `success/warning/danger/default`。中性标签（ID、编码、HTTP 方法、角色名、类型名、消息片段）保持默认即合规。
- `t-table`：`loading` / `loadingProps` / `empty` / `pagination` / `asyncLoading` 为组件自带能力，数据拉取态的规范做法是绑 `loading`，
  外层 `t-loading` 或 `t-card :loading` 不构成 §4.3 的满足。
- `t-empty`：仅有 `action/description/image/imageStyle/size/title/type`，**没有 `content` 属性**；空态文案只能落 `title` 或 `description`。
- `t-form`：`label-align` 可取 `left/right/top`；`label-width="0"` 的表单没有 TDesign 可视标签，R9 不适用。
- `t-pagination`：`page-size-options` 提供每页条数切换；`t-table` 内嵌 `pagination` 对象时对应键为 `pageSizeOptions`。

## 实施步骤

1. 建立规则基线并把 DESIGN.md 条款落到可机读的判定口径（引号感知的开放标签扫描器，避免 `t-form-item` 误判与属性内 `>` 断行）。
2. 按模块拆分到子代理并行推进（管理端产品/用户/财务营销/内容日志通知/系统外围，控制台服务控制台/订单账单充值/账户内容，各写独立目录）。
3. 每页先核对后改动，只动规范对齐必需行；官方未覆盖或与业务冲突的先登记再裁决。
4. 独立交叉复核（管理端 65 个 .vue 全量、控制台 92 个文件全量），复核只读不改，缺陷回收给 Lead。
5. 两端构建 + 两端 e2e 全量回归。

## 保留、未处理与取舍

以下条目经核对后**有意不改**，逐条给出依据；不存在「因时间不足未处理」的页面。

### 标签与语义（R1）

- `t-tag theme` 默认即 `default`，中性信息标签（ID、编码、HTTP 方法、消息片段、角色名、类型名、账单编号）保持默认是合规写法，
  不为凑数硬加 `theme`。全库 `variant="outline"` 仅剩 194 处且全部挂在 `t-button`（按钮官方次操作变体），`t-tag` 已 0 处。
- `theme="primary"` 承载属性/分类标签保留（发票分类、营销分组类型等 9 处）。§4.2 只规定四类语义态映射，未禁止 primary 用于属性标签。

### 时间格式（R4）

- `invoice.due_date` 列不改前端：后端 `InvoiceService.php` 已按 `Y-m-d` 下发，模型 `due_date` 为 `date` 转型，直渲染即符合 §6 的纯日期写法。
- `coupon-campaigns` 的 `next_run_at`/`last_dispatched_at`、`logs` 的清理时间等直渲染保留：后端已下发 `Y-m-d H:i:s`；
  套 `formatDateTime` 会把业务空态（未配置/暂未发放）吃掉成 `--`，属于可见行为变更。
- 站内信的「刚刚 / N 分钟前 / M-D」相对时间保留（`layouts/components/Header.vue` 的 `formatInboxTime`）：站内信惯例，规范未覆盖。
- 图表轴标签、装饰性问候日期属绘图/装饰文本，不在时间列口径内。
- 订单续费入口的 `renewData.expires_at` 直渲染保留：后端已按 `Y-m-d H:i:s` 下发，转换会改变空态文案。

### 文案（R4 R5）

- 具体名词空态（「暂无用户」「暂无账单」「暂无实名认证记录」等 40 余种）保留：§6 禁用列是「空空如也/没有任何内容/查无此人」，
  通用「暂无数据」全库仅 9 处，单页改造会形成孤例。
- 「新增用户」→ 已改「新建用户」；但「新增」不等于被禁的「添加/增加」，全站 46 处在用的「新增 XX」保留。

## 风险与回滚

- 风险：按钮文案改动牵连 e2e 断言。已同步 3 个 spec，两端 e2e 全绿；如有遗漏，e2e 会直接报「元素未找到」而非静默通过。
- 风险：`formatDateTime` 对空值返回 `--`，与部分页面原有 `-` 或占位文案不同。已逐页核对只替换原本就直出裸时间的列，
  业务空态由后端下发文案的列未替换。
- 回滚：全部改动为单文件级别的属性/文案/样式行，`git checkout -- <file>` 即可按文件回退，无数据与接口变更，不需要迁移或重启。
