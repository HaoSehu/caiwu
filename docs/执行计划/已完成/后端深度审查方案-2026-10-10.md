# 后端深度审查方案（只读）· 2026-10-10

## 背景

`backend/` 现状：`app/` 985 个 PHP 文件、13.96 万行应用代码；`Services/` 已收敛为 21 个业务域；`Http/Controllers` 68 个、`Console/Commands` 86 个、`plugins/` 7 个能力域；路由真源分布在 `routes/{api,v2-admin,v2-client,console,web}.php`。

此前已有多轮审查，本方案**不重复**它们，而是做「闭环复验 + 多维度深扫」：

- **2026-08-23 六领域审查**（原报告已丢失，结论经 09-23 复验）。
- **2026-08-26《API 接口安全与性能修复方案》**：修复 v2 越权/信息暴露/N+1 的 M1–M5、L1–L6，自述剩余 Service/Resource 补查、前置通配符 LIKE、索引慢查询、插件运行时**另行立项**。
- **2026-09-23《后端全面审查报告》**（[报告](../../设计文档/后端/后端全面审查报告-2026-09-23.md)）：21 智能体静态只读，产出 P0×1（组合支付预扣余额可被二次退回）、P1×约 37、P2×约 90、死代码与一次性命令清单、修复批次建议 B0–B7。该报告**未落地修复**，且自述存在未覆盖项。
- **2026-10-03 财务全链路与溯源审查**、**2026-10-05 优惠券智囊团审查**：专项域已覆盖。
- **2026-10-10 运行态巡检**（`docs/_local/后端与数据库巡检报告-2026-10-10.md`）：DB/Redis/公开 API/就绪探针/队列积压的运行态体检，**非代码审查**。

**驱动本次审查的两个新事实**：

1. **9-20 以来已落地 50 次提交**（含「财务支付服务按五条资金流拆分」「修正充值单取消窗口判断并阻断混付旧单复用与充值补录账单退回余额」等直接触及 09-23 P0-1 与多条 P1 的改动），历史结论的**当前有效性未知**，必须逐条复验，防止「已修项当新债」或「回归项被漏掉」。
2. 09-23 审查的**未覆盖项仍然空档**：三端前端调用面未核实、并发与竞态仅静态分析、6 个 `*MigrationService` payload 映射未逐表核对、54 条孤儿迁移未对照、生产侧 `.env`/调度/发布未验证。

**目标**：以多智能体并行编队对 `backend/` 做一次覆盖「静态深扫 + 动态验证 + 前端交叉 + 未覆盖域」的只读审查，产出可逐条跟踪的分级清单与可排期修复批次，并把 09-23/10-03/10-05 的存量发现收敛为「仍存在 / 已修复 / 已回归 / 无法判定」四态台账。

**非目标**：

- 不修改任何生产代码、不跑迁移、不动 git；工作区当前干净（HEAD `83bcd280`，仅 `.workbuddy-ai/` 未跟踪），审查不得污染。
- 不复做已闭环的 2026-08-26 M1–M5/L1–L6，也不重复 10-03 财务、10-05 优惠券的专项结论；承接其**未覆盖项**。
- 不纳入视觉/前端 UI 实现、不纳入部署环境本身。

## 范围与验收

**范围**：`backend/` 全量——`app/`、`routes/`、`config/`、`database/`、`plugins/`（7 域，排除各插件内嵌 `vendor/`）、`scripts/`、`tests/`。基线为当前工作区（HEAD `83bcd280`）。三端前端**仅作调用面交叉核对**，不审查其实现。

**验收**：

- [ ] 覆盖面：`app/` 全部 PHP 文件落在某维度审查范围内；全部路由逐条过 V1/V3；`plugins/` 7 域、`config/`、`migrations/`、`scripts/`、`tests/` 逐项过 V5/V9/V7。
- [ ] 闭环台账：09-23（P0×1 + P1×约 37）、10-03、10-05 存量发现逐条落到「仍存在 / 已修复 / 已回归 / 无法判定」四态之一。
- [ ] 证据质量：每条发现含 `文件:行号`；量化结论（引用 0 次、无分页、命中 N 次、EXPLAIN rows）可复算；主进程抽检关键结论。
- [ ] 动态验证：至少完成 P0-1 并发复现尝试、3 条重点慢查询 EXPLAIN、2 处 N+1 查询计数、就绪探针/队列语义核对。
- [ ] 前端交叉：三端 API 调用点扫描完成，产出「可下线/可合并」候选的**前端确认清单**。
- [ ] 不新增 docs 失败项：`npm run docs:check` 失败数不高于当前既有基线。
- [ ] 零代码改动：审查结束 `git status` 与 Wave 0 基线一致（仅新增审查文档）。
- [ ] 关键结论已同步到会话（`docs/` 除 `参考资料/` 外不进 git）。

## 实施步骤

### Wave 0 · 基线快照与历史台账（主进程）

录 `git status --porcelain` 与 HEAD SHA；跑 `composer analyse`、`composer format:check`、`php artisan test`、`npm run docs:check` 记录基线；导出 `artisan route:list --json` 与 PHP 文件行数清单；建立「历史发现台账」（09-23 报告 P0/P1 + 08-26 未覆盖项 + 10-03 + 10-05）。中间产物入 `docs/_local/后端深度审查-2026-10-10/wave0/`。**不刷新** `docs/自动生成/` 与 schema 基线，漂移作为发现记录。

### Wave 1 · 多维度静态深扫（9 维度，每轮并行 ≤4 个智能体）

按上表 V1–V9 各派一个智能体；V1/V2/V3 因风险最高各配一次「反向质疑」复核。每份报告全文落盘、只回传 ≤35 行摘要。

### Wave 2 · 动态与运行时验证（3–4 个智能体，串并结合）

- **动态-1 并发复现**：以 Feature 测试/时序注入复现 09-23 P0-1（组合支付取消 × 回调/轮询并发）与优惠券双花、补录并发；结论标注「已复现 / 未复现 / 无法复现」。
- **动态-2 查询与索引**：对 `schedule_task_runs` 关键字检索、前置通配符 `LIKE '%kw%'`、`products` 全列查询跑 `EXPLAIN`/`EXPLAIN ANALYZE`，实测 rows 与耗时。
- **动态-3 数据量与 N+1**：用 `DB::listen`/查询计数对 2–3 条重点列表接口实测每请求查询数。
- **动态-4 运行态语义**：承接 10-10 巡检，核对 `/api/ready` 各检查项语义、队列 `retry_after` vs Job `timeout`、`withoutOverlapping` 覆盖、失败任务进入 `failed_jobs` 的路径。

### Wave 3 · 前端调用面交叉核对（1 个智能体）

扫描 `frontend-admin-v3/`、`frontend-user-v3-www/`、`frontend-user-v4-console/`、`shared/` 对后端 API 的调用点，与路由真源比对，产出：死端点候选（后端有、前端零调用）、只读端点的调用方、可合并端点的影响面。**裁决口径**：前端零调用仅作「候选」，最终下线仍需用户确认。

### Wave 4 · 未覆盖域深挖（2 个智能体，并行）

- **G1 迁移与配置**：6 个 `*MigrationService`（约 5,000 行）逐表核对 payload 映射；实库 `migrations` 表与仓库文件对照，裁决 54 条孤儿迁移是否已达成 schema；`.env.example` 键覆盖与实读键差异；配置项运行时消费计数。
- **G2 测试与插件**：测试覆盖矩阵与关键未覆盖点；插件动态装载、fake provider、`plugins/*/vendor` 排除正确性；`phpstan-baseline.neon` 归因复核（模型属性注解杠杆）。

**硬性要求**：G1/G2 每条结论独立复验；承接 09-23 已实证的假阳性清单（防误改），未复验结论不进最终报告。

### Wave 5 · 汇总定级与登记（主进程 + 1 个交叉验证智能体）

去重合并（同问题跨域报出时合并）；按项目口径定级（P0=资金/权限/数据损坏/线上可用性，P1=正确性缺陷与明显性能安全风险，P2=可维护性/冗余/卫生）；标注与在跑方案的归并关系；产出修复批次建议（每批 = 可独立验证与提交的单元）。

**产物**：中间报告 `docs/_local/后端深度审查-2026-10-10/<wave>/`；最终报告 `docs/设计文档/后端/后端深度审查报告-2026-10-10.md`；本计划三处登记（`docs/catalog.json`、`docs/执行计划/README.md`、`docs/执行计划/进行中/README.md`）。

**回滚**：本计划只新增文档、不改代码；回滚 = 删除新增文档并撤销三处登记。

## 风险与回滚

| 风险 | 处置 |
| --- | --- |
| 审查中发现真 P0 | 记录并在报告中置顶；是否中断审查立即修由用户决定，AI 不自行修 |
