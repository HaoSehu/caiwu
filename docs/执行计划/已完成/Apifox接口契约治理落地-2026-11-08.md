## 决策日志

| 日期 | 决策 | 理由 |
| --- | --- | --- |
| 2026-11-08 | 端点存在性以 `getEndpoint` 为准，`listEndpoints` 大页结果可能滞后 | 排查中遇到 `listEndpoints` 返回 390 条仍含已删端点，而 `getEndpoint` 对同一 id 返回 404；以 `getEndpoint` 与分页 `total` 交叉确认真实数量 |
| 2026-11-08 | 合并入口时补 `ListInvoicesRequest` 的 `type=refund` 白名单 | 旧入口 `ListUserInvoicesRequest` 放行 `refund`，合并到 `/admin/invoices` 后漏掉，用户详情页选中「退款」会 422；这是合并造成的功能回归，改 Request 而非改测试 |
| 2026-11-08 | 账单列表的三级分组查询断言由 1 次改为 2 次 | 账单有两个商品外键（`invoices.product_id` 与 `order.product_id`），两条链各批量预载一次是必要且恒定的；真正的 N+1 会随行数增长 |
| 2026-11-08 | DNS 解析用例改为注入必然失败的传输器 | 本机代理的 fake-ip DNS 把任意域名解析成 198.18.x.x，`.invalid` 也不例外，用例依赖真实 DNS 会假失败 |
| 2026-11-08 | 25 条失败用例归因为测试库状态而非产品缺陷 | 逐条定位到 `system_installation` 空、种子迁移归档、配置占位文案、场景关联缺失四类；修复落在迁移与测试基类，未改业务逻辑 |
| 日期 | 决策 | 理由 |
| --- | --- | --- |
| 2026-11-08 | 只合并 4 组列表/详情 Resource，Coupon/Campaign 暂不合并 | 二者列表含 `user_ids`、`locked_fields` 等重字段，合并会固化「列表=详情」结构，且与 `API格式规范.md` §11.5.1「列表 Resource 不返回详情字段」冲突 |
| 2026-11-08 | 保留 `summaryForClient()` 不删 | 4 处仍在调用（含 `UserService` 与测试），删除会破坏多处 |
| 2026-11-08 | 用 Workflow 并行处理批量端点 | 单上下文连续手写 186 条同类 JSON 出错率不可接受，并行 agent 各自独立校验更可靠 |
| 2026-11-08 | `533998187` 改为 binary 而非 JSON | 控制器返回 `BinaryFileResponse`，契约必须如实反映 |
| 2026-11-08 | 动态键 object 用 `object` + 描述降级 | Apifox MCP schema 不支持 `additionalProperties` |
| 2026-11-08 | 无 Resource 的端点保持 data 为空，不编造结构 | 4 条端点的响应结构由 Service 手写，编造会与真实响应偏离；记录为技术债后续补齐 |
| 2026-11-08 | 错误响应覆盖按「是否有请求体」区分 422 | 无请求体的 GET/DELETE 不需要 422，机械要求 422 会产生不存在的契约 |
