# 数据库升级规范

本文是 caiwu 数据库升级的唯一真源。其他文档只链接本文，不复述规则，避免出现第二个版本。

## 一、三个账本，职责分离

| 账本 | 位置 | 写入方 | 作用 |
| --- | --- | --- | --- |
| 代码版本 | `backend/version.json` | 发版人 | 声明当前代码包版本与最低可升级版本 |
| 数据库版本 | `system_installation.app_version` | `db:upgrade` | 数据库实际升级到的版本 |
| 迁移账本 | `migrations` 表 | Laravel migrator | 已执行的迁移文件名 |
| 升级流水 | `system_upgrade_runs` | `db:upgrade` | 每次升级的来源、目标、状态、备份与失败摘要 |

代码版本刻意不放入 `config/`：部署流程含 `php artisan config:cache`，版本一旦进入配置缓存，发版覆盖文件后进程仍读到旧值，会把「新代码 + 旧版本号」误判为已是最新。

## 二、三条命令

### `php artisan db:upgrade-status`

只读。输出代码版本、数据库版本、待执行迁移、孤儿迁移、基线一致性与最近一次升级。

退出码：`0` 一致 / `2` 需要处理（待执行迁移、非白名单孤儿、版本不一致、基线滞后）/ `1` 执行错误。

部署脚本可据此判断：退出码 2 表示有活要干，不代表命令坏了。

### `php artisan db:upgrade`

受控执行。选项：

| 选项 | 说明 |
| --- | --- |
| `--force` | 非交互执行必需 |
| `--dry-run` | 只打印将执行的 SQL，不写库不记账 |
| `--skip-backup` | 跳过备份；production 环境一律拒绝 |
| `--adopt=<版本>` | 首次采纳既有数据库 |

执行顺序：取锁 → 校验版本清单 → 校验版本推进 → 校验迁移清单 → 全库备份 → 写升级记录 → 委托 migrator → 成功推进版本 / 失败保留摘要。

### `php artisan db:migration-lint`

只读。检查迁移文件命名规范与结构变更幂等守卫。已执行的不可改迁移通过 `database/migrations-lint-exempt.json` 显式豁免。

## 三、正常发布 Runbook

1. 备份当前数据库（生产必做，即使 `db:upgrade` 自带备份）。
2. 拉取代码，`composer install --no-dev --optimize-autoloader`。
3. 运行 `php artisan db:upgrade-status`，核对待执行迁移清单是否符合本次发布预期。
4. 进入维护窗口，运行 `php artisan db:upgrade --force`。
5. 运行 `php artisan db:upgrade-status`，确认退出码为 0。
6. 清缓存并重建生产缓存，重载 PHP-FPM / 队列消费。
7. 做完关键读写冒烟后退出维护模式。

## 四、首次采纳既有数据库

已经存在的生产库没有升级账本，第一次必须显式采纳：

```bash
php artisan db:upgrade --adopt=$(php -r 'echo json_decode(file_get_contents("version.json"), true)["version"];') --force
```

采纳会先执行待迁移（建出账本表），再写入版本记录。采纳版本必须等于当前代码包版本，否则命令拒绝——这是防止用采纳把「真实存在的待执行迁移」掩盖掉。

## 五、失败恢复矩阵

| 阶段 | 本机处理 | 记录状态 | 再次执行 |
| --- | --- | --- | --- |
| 锁被占用 | 直接返回，不动库 | 不记录 | 等锁释放后重试 |
| 版本降级或跨版本直跳 | 拒绝，不动库 | 不记录 | 修正版本号后重试 |
| 非白名单孤儿迁移 | 拒绝，不动库 | 不记录 | 人工核对后补白名单或补回文件 |
| 备份失败 | 拒绝，不迁移 | 不记录 | 修 mysqldump 或磁盘后重试 |
| 迁移失败，本次 0 个成功 | 保留备份 | `failed` | 修代码后原地重试 |
| 迁移失败，本次 ≥1 个成功 | 保留备份，禁止自动重跑 | `recovery_required` | 人工核对实库与备份后前向修复或整体恢复 |
| 迁移成功但记账失败 | 抛错，版本不推进 | `running` 残留 | 用 `db:upgrade-status` 诊断后人工补记账 |

MySQL 的 DDL 无法随应用事务回滚，因此不存在「自动回滚数据库」这条路。代码回退必须确保旧代码仍兼容已经升级的库结构。

## 六、迁移开发规则

1. 只新增迁移，不改已执行的历史迁移。
2. 结构变更必须带 `Schema::hasTable` / `Schema::hasColumn` 守卫，使中断后重试不会因「已存在」失败。
3. 新表新字段必须写中文 `COMMENT`。
4. 采用先扩展、再回填、后收缩；删除字段放到后续版本。
5. 已执行的不可改迁移若缺守卫，登记到 `database/migrations-lint-exempt.json`，写明原因与日期，不修改文件本身。

## 七、schema baseline

`database/schema/mysql-schema.sql` 是新环境初始化的唯一结构来源，`baseline-meta.json` 记录导出时的表数、迁移数与提交号。

导出前脚本会校验没有待执行迁移，否则拒绝——避免把半程结构固化成新基线。确需强制导出时加 `--force`。

```bash
php backend/scripts/export_schema_baseline.php
```

## 八、孤儿迁移白名单

`database/migrations-orphans.json` 登记「`migrations` 表有记录但代码包中已无文件」的历史迁移。当前 54 条，均在 2026-04 至 2026-08 期间被删除且未归档。

白名单是安全阀：清单内缺失允许升级，清单外缺失一律拒绝。新增条目必须人工确认并写明原因，禁止脚本自动追加，否则会掩盖真实的迁移误删。
