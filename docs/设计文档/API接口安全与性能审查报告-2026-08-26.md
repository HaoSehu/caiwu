## 中等严重度问题

### M1 NAT 转发删除缺少归属校验

- 文件：`backend/app/Services/ClientServiceConsole/ServiceNatService.php:142-160`
- 路由：`DELETE /api/v2/client/services/{id}/nat-forwardings/{forwardingId}`

`deleteNatForwardingForUser` 已取得 `$natContext['list']`（当前主机的转发规则集合），但未校验 `$forwardingId` 是否属于该集合，直接拼入上游请求：

```php
[$runtime, $supplier, $hostId, $jwt, $natContext] = $this->resolveNatAclContext($service, true);
$payload = ['func' => 'delNatAcl', 'id' => $forwardingId];   // 缺归属校验
```

同层安全组实现每个写操作前均调用 `assertSecurityGroupVisibleToCurrentHost($service, $groupId)`，见 `ServiceSecurityGroupService.php:228`、`:260`、`:306`。NAT 删除缺少对等的纵深防御。

触发场景：用户 A 以自己的 `serviceId` 配合枚举得到的 `forwardingId` 发起删除，是否越权完全取决于上游是否按 JWT 会话 host 校验 `id`，本仓库无兜底。

建议修复：

```php
throw_if(
    ! collect($natContext['list'])->contains(fn ($item) => (int) ($item['id'] ?? 0) === $forwardingId),
    new BusinessException('端口转发规则不存在或不属于当前服务', 42200)
);
```

### M2 工单回复引用查询 N+1

- 文件：`backend/app/Services/Ticket/TicketService.php:1268-1288`
- 路由：`GET /api/v2/admin/tickets/{ticket}/replies`、`GET /api/v2/client/tickets/{ticket}/replies`

`v2Replies` 已预构建 `$staffMap` 避免发送者名 N+1（`TicketService.php:530-536`），但 `formatReply` 对每条带引用的回复重新逐条查库：

```php
if (! empty($reply->quote_reply_id)) {
    $quoted = TicketReply::where('ticket_id', $reply->ticket_id)->find(...);  // 每条 1 次
    $quoted->loadMissing('ticket.user:id,nickname,email');                    // 每条 1-2 次
    if ($isQuotedStaff) {
        $admin = AdminUser::query()->find((int) $quoted->user_id);            // 每条 1 次
```

一页 20 条全带引用约 60-80 次额外查询。`resolveTicketReplies`（`TicketService.php:1321-1340`）被 `detail()` 调用时加载全部回复且不分页，同一 N+1 无上界。

附带 I/O 放大：`formatReply` 对每个附件执行 `File::exists()`、`File::mimeType()`、`File::size()`（`TicketService.php:1116-1124`），单条最多 9 张图，一页 20 条最多约 540 次文件系统调用。

建议修复：在 `v2Replies` / `resolveTicketReplies` 内按 `quote_reply_id` 批量预取被引用回复与对应管理员，构建映射后传入 `formatReply`；附件元数据改为落库时固化，读取端不再逐个 stat 文件。

### M3 管理端内容列表 N+1

> **2026-08-26 复验：本项失效。** 当前 `adminList()`（`ContentArticleService.php:36-43`）已含 `with(['contentCategory', 'creator:id,username,nickname', 'updater:id,username,nickname'])` 预加载，懒加载不存在；该项不再列入修复，详见 [执行计划](../执行计划/已完成/API接口安全与性能修复方案-2026-08-26.md)。

- 文件：`backend/app/Services/Content/ContentArticleService.php:74-79`
- 路由：`GET /api/v2/admin/content/articles`

管理端 `list()` 未 `with('contentCategory')`，而 `AdminContentArticleListResource.php:29-30` 访问 `$article->contentCategory`，每行触发一次懒加载。同文件的 `publishedList()`（`:171`）已有 `->with('contentCategory:id,name,slug')`，公开端正确、管理端遗漏。

建议修复：管理端 `list()` 补 `->with('contentCategory:id,name,slug')`。

### M4 登录场景验证码接口可用于用户枚举

- 文件：`backend/app/Services/Auth/SendAccountCodeService.php:34-42`、`:76-84`
- 路由：`POST /api/v2/client/auth/phone-code`、`POST /api/v2/client/auth/email-code`（`purpose=login`）

`purpose=login` 时先判定账号是否存在，不存在直接抛「手机号未注册」/「邮箱未注册」。同模块 `resetPassword`、`loginByCode` 均为先校验验证码再解析用户并统一返回「账号或验证码错误」，发送接口破坏该一致性。

现有缓解：路由 3 次/分钟；`MessageRateLimitService` 另有 IP 6 次/分钟、目标 5 次/小时与 10 次/24 小时。仍足以在较长窗口内探测用户库。

建议修复：对齐 `resetPassword` 做法，发送阶段统一返回成功并照常消耗限流配额，存在性判定后移到校验阶段。

### M5 `/ready` 泄露基础设施健康明细

- 文件：`backend/app/Http/Controllers/System/HealthController.php:19-35`
- 路由：`GET /ready`（无认证、无限流，`routes/api.php:35`）

响应返回 `checks` 明细，暴露 database、cache、storage、scheduler、scheduler_liveness、task_readiness、queue 各项状态。可用于攻击前架构侦察，以及在队列积压或调度器故障时选择攻击时机。

建议修复：公开响应只保留 `{"status":"ready"}` 与 HTTP 状态码，明细改为认证访问或内网 IP 白名单。

## 低严重度问题

### L1 管理端用户列表三个字段恒为空

- 文件：`backend/app/Services/User/UserService.php:67-77`、`backend/app/Http/Resources/Admin/V2/AdminUserListItemResource.php:33-35`
- 路由：`GET /api/v2/admin/users`

`list()` 的 `select()` 白名单仅含 `id, email, phone, nickname, real_name, verification_status, is_verified, status, created_at`，而 Resource 读取 `company`、`qq`、`member_level_id`。三者 accessor（`app/Models/User.php:86`、`:91`、`:188`）只包装原始列值，列未 select 时入参为 `null`，因此公司与 QQ 恒为空字符串、会员等级恒为 `null`。同时 `User` 模型无 `profile()` 关联，`relationLoaded('profile')` 恒为 `false`，`$profile?->company` 分支永不生效。

对照：`balance`、`credit_limit`、`referral_*_amount` 由 `account` 关联取值，`withReadAggregates()` 已预加载，该部分正常。

建议修复：在 `select()` 补齐 `company`、`qq`、`member_level_id`；若字段已迁移到画像表，则改为预加载对应关联并移除失效的 `getRawOriginal` 分支。

### L2 公开内容接口 Markdown 渲染放大

- 文件：`backend/app/Http/Resources/V2/Content/PublishedContentSummaryResource.php:49-60`
- 路由：`GET /api/v2/site/notices`、`GET /api/v2/site/help-articles`（无认证、未挂 throttle）

`excerpt()` 对每篇文章的完整正文执行 `Str::markdown()` + `strip_tags()` + `preg_replace()`，仅为截取 120 字符；`publishedList` 亦无 select 白名单，完整 `content` 长文本全列进入内存。`page_size` 上限 50，单次请求最多渲染 50 篇完整正文，属可放大的 CPU 消耗。

建议修复：列表查询用 select 白名单排除 `content`；摘要在落库时预生成并持久化，读取端不再实时渲染 Markdown；同时为两个公开列表接口补限流。

### L3 权限码定义但无路由使用

- 文件：`backend/app/Support/AdminPermissions.php`、`backend/routes/v2-admin.php`

`ORDER_MANAGE`、`SITE_VIEW`、`SITE_MANAGE` 在路由文件中零引用（已 grep 确认）。其中 `SITE_MANAGE` 存在权限边界错位：首页 Hero 读写路由（`v2-admin.php:250`、`:263`）实际由 `CONTENT_MANAGE` / `CONTENT_LIST` 把关，导致被授予「内容管理」的员工同时获得首页横幅与视频修改权，而被授予 `SITE_MANAGE` 的角色反而无权修改。

`ORDER_MANAGE` 无对应写操作路由（管理端订单仅有 `index` 与 `show`），属预留权限码，其 `impliedPermissions` 仍正确下发 `ORDER_LIST` 与 `ORDER_DETAIL`，无副作用。

建议修复：确认站点外观与文章内容是否需要分权。需要则把 Hero 路由迁到 `SITE_*` 分组；不需要则删除 `SITE_VIEW`、`SITE_MANAGE` 并同步内置角色定义。

### L4 CSRF 例外路径失效

- 文件：`backend/bootstrap/app.php:61-63`

例外配置为 `api/v2/callback/*`，实际回调路由为 `api/v2/client/payment/alipay/notify` 与 `api/v2/client/payment/notify/{gateway}`，路径永不命中。无实际安全影响（`api/*` 走 api 中间件组，本身不含 CSRF 校验），属误导性死配置。

建议修复：删除该例外，或修正为实际路径并加注释说明 api 路由默认已排除 CSRF。

### L5 推荐返利暴露下级用户完整邮箱

- 文件：`backend/app/Http/Controllers/Client/V2/ReferralController.php:47-51`、`:103-106`
- 路由：`GET /api/v2/client/referral/rewards`、`GET /api/v2/client/referral/direct-referrals`

推荐人可见被推荐人完整邮箱。管理端同场景走 `ReferralService::adminReferralUserProjection` 的 `$privacy->email()` 脱敏，客户端无脱敏，策略不一致。

建议修复：若产品未明确要求展示完整邮箱，客户端改为部分掩码。

### L6 报价接口限流未分维度

- 文件：`backend/routes/api.php:23`
- 路由：`POST /api/v2/site/products/{product}/quote`

`throttle:60,1` 未指定命名维度，60 次/分钟足以支撑竞品批量抓取价格。

建议修复：改为按 IP 的命名限流，或参照 `MessageRateLimitService` 增加 IP 与商品维度的二级限流。

## 已检查未发现问题

- **客户端资源归属**：`ClientActionV2Service` 的 `cancelInvoice`、`cancelOrder`、`markNoticeRead`、`markNotificationRead`、`recallTicketReply` 均以 `where('user_id', $user->id)` 约束；`powerAction`、`resetPassword`、`reinstall` 经 `findUserService`（`ServiceDetailService.php:713-723`）强制 `where('user_id')`。安全组的 group 与 rule 级操作均有二次归属校验。
- **VNC 凭据边界**：`ServiceConnectionResource` 的 `includePassword` 默认 `false`，客户端路由显式传 `false`（`ServiceController.php:44`）；`ServiceDetailResource` 不输出 connection；公开 token 兑换不返回密码，Redis 载荷 `unset(['password'])`；token 为 `bin2hex(random_bytes(24))`，一次性消费，TTL 600 秒（relay 60 秒）。
- **Resource 全量透传**：全目录 grep 无 `return $this->resource->toArray()` 或 `return parent::toArray()`。`SupplierResource` 用 `has_api_key` 布尔并置空密钥字段；`SiteProductDetailResource` 递归过滤 `password`、`secret`、`api_key`、`raw_response`、`third_party_response`。
- **日志 channel 参数**：`AdminLogV2QueryService.php:122-133` 使用严格 `match` 白名单，未知 channel 抛 404，无注入与越权读取。
- **管理端路由权限包裹**：仅 `/auth/info`、`/auth/profile`、`/auth/password`、`/auth/logout` 四条自身账号路由不带权限码，合理；其余全部落在 `permission:` 分组内。未发现写操作被错放进 `_LIST` 组（`POST /coupon-product-groups/batch-products` 虽为 POST 但实为批量读取，归入 `PRODUCT_LIST` 恰当）。
- **N+1 良好实现**：`AdminServiceListService::paginate` 七层关联全预加载；`ClientOrderQueryService`、`ClientPaymentQueryService` 关联指定列预加载；`ReferralService::directReferrals` 用 `whereIn` + `groupBy` 批量聚合收益；`monitorBatch` 用 `parallelGet` 与分类型缓存；`ProductSiteService` 全链路 `Cache::remember` 与批量分组；`UserService::list` 用 `withCount` 与 `withReadAggregates`。
- **CORS**：`config/cors.php` 的 `allowed_origins` 经 `parse_url` 严格校验并 `array_filter`，环境变量缺失时不会退化为通配；`allowed_origins_patterns` 为空；`supports_credentials` 为 `false`。
- **支付与实名回调**：签名中间件在限流之后执行；实名回调具备 nonce replay cache（600 秒）与 5 分钟时间戳窗口；验签失败不泄露内部实现。
- **分页上限**：抽查的客户端、站点端、管理端分页接口均有 `min(..., 50)` 或 `min(..., 100)` 上限，未发现无上界或无分页的全量列表接口。

## 未覆盖项与风险

1. **数据库索引与慢查询未审查**。全仓库大量 `LIKE '%keyword%'` 前置通配符无法命中索引。最需关注 `AdminServiceListService.php:300-333`：对 `service_upstream_bindings`、`service_runtime_snapshots`、`service_connection_snapshots` 三张表的 JSON 长文本列执行 `LIKE '%kw%'`（各 `limit 500`）。数据量增长后管理端服务列表关键词搜索会全表扫描三张大表。建议单独立项做索引与慢查询审查。
2. **管理端多数 Service 实现未细读**。Supplier、Setting、Product、Coupon、Staff、Role、ScheduleTask、DatabaseStatus、Verification、MemberLevel、FinanceMenu、FinanceLedger 等仅核对了路由权限包裹，未逐个读实现查 N+1。原因：本轮三个并行审查子任务全部异常终止（其一因 API 余额不足，其二随进程退出丢失），剩余预算优先覆盖越权与公开接口。
3. **Resource 未逐个细读**。完成敏感字段正则全扫（无命中）与 8 个高风险 Resource 细读，其余约 100 个未逐行确认字段白名单。
4. **无运行时验证**。所有结论来自静态阅读，未执行 `composer analyse`、未跑测试、未发实际请求。N+1 的具体查询次数为代码推断。
5. **插件运行时未审查**。仅覆盖回调验签与密钥输出边界，未审 `PluginRuntimeRegistry`、`PluginInstaller` 等插件装载链路。
