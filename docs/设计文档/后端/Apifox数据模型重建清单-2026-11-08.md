# Apifox 数据模型重建清单 · 2026-11-08

> **执行状态：已完成**（2026-11-08）。75 个模型经 Apifox MCP `updateDataSchema` 重建并逐个回读校验。
> 实测结果：顶层字段 **2250 → 1601（净减 649）**；仍误标为 `string` 的对象/数组字段 **0 处**；
> 117 个模型中 101 个与源码 payload 逐字段一致，其余 16 个为手工修正后更精确的类型（如 `capabilities` 由 string 改为 array）。
> 文档计数已同步：`Apifox数据模型与组件库.md`、`Apifox接口文档项目.md`。


文档摘要：把 117 个 Apifox 数据模型逐个对照 `backend/app/Http/Resources` 的 `toArray()` 源码真实结构，算出需重建的 78 个模型、字段增减与类型修正明细。本清单是《API 架构优化分析报告》P0-1 / P1-2 的可执行版本。

- 读者画像：后端开发、接口文档维护
- 生成方式：`toArray()` 静态解析（严格模式，见第 3 节），逐模型 `getDataSchema` 比对
- 前置更正：报告原结论「99 处 / 41 模型」经复核不成立，实测为 **178 处类型错 / 78 个模型需重建**

## 3. 解析口径（可复核）

提取脚本对每个 Resource 只做以下判定：

1. 只取 `toArray()` 方法体顶层 `key => expr`，不展开嵌套
2. `$this->helper(...)` 递归读取 helper 方法体：
   - `return [...]` 字面量 → `object` + 子字段
   - `collect()->map()` / `::collection()` → `array` + items
   - `number_format()` → `string`（金额）
   - `->format()` → `string`（时间）
3. `(int)` → integer，`(bool)` → boolean，`(string)` → string
4. `cond ? [...] : null` → object；`array_merge(...)` → object
5. `Resource::make(...)->resolve()` → object（嵌套资源）
6. `stripSensitiveKeys()` / `sanitizeArray()` → object +「动态键」描述

已用 `AdminUserServiceListItemResource` 试点验证：26 个顶层键的判定与手工核对 27/27 一致。

## 4. 执行方式

每个模型四步：

1. `getDataSchema` 读当前状态
2. 按本清单「源码字段数」重写 `jsonSchema`：`properties` 只保留源码顶层键，`required` 清空
3. `updateDataSchema` 写入
4. `getDataSchema` 回读确认

全部完成后需同步：

- [Apifox数据模型与组件库.md](../../参考资料/接口/Apifox数据模型与组件库.md) 的「117 个 / 2250 字段」
- [Apifox接口文档项目.md](../../参考资料/接口/Apifox接口文档项目.md) 的模型计数
- 端点侧 `data` 包装（如 `data.invoice`）与模型顶层键对齐
