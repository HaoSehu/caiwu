### 1.5 三个复用率（口径 + 实测）

> 口径说明：`listEndpoints` 的响应数组对 401/403/422 返回 `reference: true` + `referencedResponseId`，不展开 `jsonSchema`；对 200 则展开并内联 `$ref`。两类必须先区分，否则会把「引用组件」误判成「无结构」。本报告以 `getEndpoint` 对 `533998431` 抽样确认。

**a) 响应模型绑定率** = 成功响应 `data` 以 `$ref` 指向数据模型的接口数 ÷ 接口总数

```
169 / 403 = 41.9%
```

- 绑定：169 条（200 响应的 `data` 内联 `{"$ref": "#/definitions/327161xxx"}`，分页接口则是 `data.list.items.$ref`）
- 未绑定：234 条（200 响应的 `data` 为 `{}` 或 `{"type":"object"}`）
- 已知边界（不计缺陷）：`AdminProductOperationPayloadResource`、`SiteConfigResource` 对应 8 条接口保持通用 `object` 是预期行为

**b) 统一错误组件覆盖率** = 引用 401/403/422 组件的接口数 ÷ 应鉴权接口数

```
169 / 366 = 46.2%
```

- 应鉴权接口：366 条（`auth.type = securityscheme`），公开接口 37 条（`auth.type = noauth`，与描述里的「访问控制：公开」完全一致）
- 引用 401：169、引用 403：169、引用 422：169（`referencedResponseId` 分别为 342592984 / 342592985 / 342592997）
- **未覆盖 197 条**：这些接口同时缺失 401、403、422 三种错误响应定义，不是只缺一种

**c) 分页公共参数覆盖率** = 引用分页公共参数的列表类接口数 ÷ 列表类接口总数

```
0 / 79 = 0%
```

- 列表类接口：79 条（口径 = 响应 `data` 含 `list` 的 41 条 ∪ 查询参数含 `page` 的 72 条）
- 全部 403 条接口的 `commonParameters` 字段均为 `{}`，公共参数组 id 1062378 引用数为 **0**
- 手工 `page` / `page_size` 参数覆盖率则很高：72/72 都有 `page`，72/72 都有 `page_size`
- 但 `page_size` 上限描述出现三种口径：最大 100（56 条）、最大 50（15 条）、最大 200（1 条）

## 二、🔍 问题清单

### P0 · 阻断 / 契约错误

#### P0-1 数据模型把嵌套对象与数组错误标成 `string`（**已于 2026-11-08 修复**）

- 证据（modelId + 字段）：
  - `AdminUserServiceListItemResource`（id **327161321**）——`product`、`invoice`、`upstream`、`machine_category`、`specs` 五个字段在 Apifox 里是 `type: string`
  - `AdminInvoiceSummaryResource`（id **327161285**）——`user`、`order`、`product`、`summary` 四个字段 `type: string`
  - `AdminServiceListItemResource`（id **327161365**）——`connection`、`user`、`product`、`order`、`invoice` 五个字段 `type: string`
  - `ServiceDetailResource`（id **327161332**）——`product`、`invoice`、`runtime`、`traffic`、`actions` 五个字段 `type: string`
- 源码事实（`backend/app/Http/Resources/Admin/V2/AdminUserServiceListItemResource.php:105-140`）：`upstream()`、`product()`、`invoice()` 都 `return [ ... ]`，是嵌套对象；`specs()` 是 `->map(...)->values()->all()`，是对象数组
- 影响面：按 117 个模型与 Resource 源码逐字段比对，**70 个对象字段 + 29 个数组字段被标为 `string`，横跨 41 个模型**。这些模型被 14 条接口直接 `$ref` 引用（如 `GET /admin/users/{user}/services` 533998376、`GET /admin/invoices` 533998211、`GET /admin/finance/recharges` 533998195）
- 后果：前端按文档生成类型会得到 `string`，运行期实际拿到对象；管理端 `frontend-admin-v3/src/pages/users/detail/index.vue:901` 正是读 `row.upstream.dedicated_ip`，与文档类型直接矛盾
- 归因：模型由静态解析 `toArray()` 得到，`$this->helper(...)` 形式的调用无法判定返回形态，被默认归为 `string`（`docs/参考资料/接口/Apifox数据模型与组件库.md` 只声明了「嵌套对象…标为 `object`」，未覆盖 helper 调用这一路径）
- **修复结果（2026-11-08）**：按 `toArray()` 源码重建 75 个模型，顶层字段 **2250 → 1601**，`string` 误标 object/array **126 → 0**。解析器经 6 轮修正（三目内联数组、`Resource::make()->resolve()`、跨类继承 helper、`mapWithKeys`、`array_map`、返回类型声明兜底）。详见 [Apifox 数据模型重建清单](Apifox数据模型重建清单-2026-11-08.md)

#### P0-2 Apifox 缺失 2 条真实路由（**已于 2026-11-08 同步修复**）

- 证据：
  - `GET /api/ready` —— `App\Http\Controllers\System\HealthController@ready`，`backend/routes/api.php`，`public`，中间件 `api`
  - `GET /api/secure-assets/view` —— `App\Http\Controllers\SecureAssetController@show`，`backend/routes/api.php`，`public`，中间件 `web, signed:relative`；这是 `API格式规范.md` §9.2 明确列出的「非 JSON 例外」
- 影响面：三端 405 个操作与 Apifox 403 条做逐条 `method+path` 比对，route-only 恰好这 2 条、apifox-only 为 0。这 2 条也是任务书「401 → 403」差额的全部来源
- 后果：Apifox 上没有 `/api/ready`（就绪探针）与 `/api/secure-assets/view`（签名图片流）的任何契约，前端/运维无法从文档获知
- **修复结果**：经 Apifox MCP `createEndpoint` 补入「系统」文件夹（folderId 99233688），endpointId **534165810**（`/api/ready`）与 **534165811**（`/api/secure-assets/view`），均按源码真实语义定义响应（含 503/50300 未就绪分支、binary 文件流与 404 分支）。回读确认：Apifox 403 → **405**；原有接口的 401/403/422 组件引用改动数 **0**

#### P0-3 197 条应鉴权接口完全没有错误响应定义（**已于 2026-11-08 修复**）

- 证据：169 条接口的 401/403/422 是组件引用；剩余 **197 条** 应鉴权接口连响应条目都没有，只有孤立的 200
- 实测计数：`responses` 长度 = 1 的接口 234 条，其中 37 条是公开接口（合理），**197 条是应鉴权接口（缺失）**
- 影响面举例：`GET /admin/finance/ledger`（533998190）、`GET /admin/dashboard/recent-invoices`（533998183）、`GET /client/payments/summary`（533998460）
- 后果：接口文档无法表达「未登录返回 40100」「无权限返回 40300」「校验失败返回 42200」；这与 `API格式规范.md` §4.1 的错误码映射表脱节
- **修复结果（2026-11-08）**：363 条应鉴权接口 **全部覆盖**（按「有请求体需 422、无请求体只需 401/403」口径）。178 条经并行 agent 补齐；`533998187`（备份下载）改为 `binary` 200 + 401/403 + 404——原为 JSON 信封属契约错误

## 四、📎 附：Apifox 与代码漂移对照表

### D-0 基线口径差异（先说明）

任务书写的基准是「401 条源路由」。当前实测：源路由 **403**、HTTP 操作 **405**、Apifox **403**。差额 2 条即下表 D-1/D-2，因此「Apifox 应为 403 条」这一结论**成立**，只是推导路径应为「405 操作 − 2 条 `GET|POST` 拆分重合 = 403」，而非「401 + 2」。

| 计数方式 | 405 操作 | 403 接口 | 差额解释 |
| --- | --- | --- | --- |
| 44 条 `GET\|POST` 路径 | 88 | 44 | Apifox 规范要求拆成两条，故不产生差额 |
| 8 条 GET+PUT+DELETE 路径 | 24 | 24 | 一操作一接口 |
| 293 条单方法路径 | 293 | 293 | — |

> 结论：Apifox 的 403 与「405 操作」不是可加总关系，`listEndpoints` 按 method+path 计，405 中包含 2 条 Apifox 无记录的接口（D-1/D-2）。
