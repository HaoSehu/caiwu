# 过期数据归档方案

- 适用范围：归档服务与命令（`backend/app/Services/System/LogArchiveV2Service.php`、`backend/app/Console/Commands/DatabaseArchiveLogs*`）、归档配置（`backend/config/log_archive.php`）、调度注册（`backend/app/Services/Automation/Heartbeat/Providers/CoreScheduledTaskProvider.php`）、归档台账（`archive_items`、`archive_audit_logs`），以及账单 `invoices`、订单 `orders`、支付单 `payments`、支付回调 `payment_callbacks` 四类财务数据。
- 关联规格：`docs/产品规格/进行中/日志检索与归档协同-2026-08-01.md`
- 关联计划：`docs/执行计划/进行中/日志分层与容量治理整改方案-2026-08-23.md`

## 背景与问题

系统今天已经有一套**只服务于日志**的归档能力，但没有任何面向账单、支付单、订单的能力，两者之间的能力落差是本方案要回答的核心问题。

已存在的事实（均以运行代码为准）：

| 能力 | 当前实现 | 边界 |
| --- | --- | --- |
| 归档协议 | `log_archive.protocol` 默认 `v1`（`backend/config/log_archive.php:7`）；`v2` 为两阶段协议 | 协议开关只影响心跳调用哪条命令，不改数据语义 |
| 归档对象 | `log_archive.tables` 白名单 10 张日志表（`backend/config/log_archive.php:31-50`） | 只有白名单能归档 |
| 显式排除 | `log_archive.excluded_tables` 8 张（`backend/config/log_archive.php:52-62`）：`archive_audit_logs`、`account_transactions`、`payments`、`payment_callbacks`、`invoices`、`invoice_items`、`failed_jobs`、`automation_logs` | **四个财务表已被代码显式冻结**（账单、账单明细、支付单、支付回调），不是遗漏；`account_transactions` 属 2026-10-21 已整表退役的另一类 |
| 在线保留期 | `retention_days=90`（`config/log_archive.php:10`，`:9` 注释「数据库日志统一在线 90 天，gateway 明细文件 GATEWAY_LOG_DAYS 亦为 90」）、`file_retention_days=180`（`:11`）；运行时以 `SettingService::getLogArchiveConfig()` 读库覆盖为准，缺省回落到 config（`SettingService.php:120-121`），边界 1..3650（`:300-301`） | 单一全局值，不按流分层 |
| 归档落盘 | `archive_root=storage_path('app/private/log-archives')`（`:14`），注释明确「始终落在后端 storage 目录内，不支持 NAS 或外部挂载目录」（`:13`） | 出库即失败 |
| 状态机 | `planned → staging → verified → published → purging → purged`，旁支 `failed` / `needs_recovery`（`LogArchiveV2Service.php:20-28`、`ArchiveItem.php:9-31`） | 源数据只在 `published` 之后才允许删除 |
| 恢复 | 只有 `restoreDryRun()`（`LogArchiveV2Service.php:368`），docblock 原文「只读恢复校验……**不导入数据**」 | **仓库内不存在把归档物导回库的实现** |
| 调度 | 心跳任务 `log-archive`，cron `0 2 * * *`，`timeout 3600`、`lockTtlSeconds 3660`、`manualTriggerable: false`（`CoreScheduledTaskProvider.php:117-140`） | `backend/routes/console.php` 只注册 4 条 Schedule，归档不在其中 |
| 可观测面 | `db:logs:archive:health`（心跳 `log-archive-health`，`everyTicks(4)` 即每小时）与 `db:logs:capacity`（在同一任务内作为附加观测维度调用，`runCapacitySnapshot()`，失败只写 `capacity_error`）、`archive_items` 台账 | 管理端零归档接口 |

现存问题按严重度排列：

1. **能力不对称。** 日志可以「导出 → 校验 → 发布 → 按边界删除」，财务数据没有任何等价路径，一旦生产环境需要按保留期收敛，只能手工 SQL，这正是历史事故的成因（`docs/设计文档/后端/后端深度审查报告-2026-10-10.md:47` 记录的 V9-01：`DatabaseEngineeringService.php:228-271` 曾对 `invoices`/`invoice_items`/`payment_callbacks` 执行无 dry-run 的物理删除）。
2. **恢复链路断在半路。** `restoreDryRun` 只证明「归档物没坏」，不能把数据放回去；写进文档和运维口径的「可恢复」因此缺少最后一跳。
3. **保留期只有一种口径。** 90 天对所有日志流一刀切，而 `gateway_logs`（支付审计）与 `schedule_ticks`（调度心跳）的证据价值并不相同；财务侧则一个配置项都没有，`backend/config` 全目录只有 `log_archive.php` 含 `retention_days`/`file_retention_days`（已复核 24 个配置文件）。另有一处口径分叉需要留意：`SettingService::getLogArchiveConfig()` 的兜底默认写的是 `config('log_archive.retention_days', 30)`（`SettingService.php:120`），而 config 里的实际值是 90——库中无该键时以 config 的 90 生效，但代码里的 30 是一个容易误读的常量，配置改造时必须一并统一。
4. **规模判断与直觉相反。** 实库口径下财务五表合计约 7 千行（`invoices` 3,096、`invoice_items` 2,857、`orders` 380、`payments` 346、`payment_callbacks` 391），总量不到 5MB；日志表单表最大也才 6.52MB。**财务数据现在不是容量瓶颈**，把它当容量问题处理会引入与收益不匹配的风险。

## 目标与非目标

- 目标 1：为「什么算过期」给出可判定的条件——每类数据有明确的判定字段、判定顺序和保留期来源，而不是一句「按需要清理」。
- 目标 2：让「已归档」成为系统里的一等状态，能回答「这条记录现在在在线库、归档物，还是已不可用」。
- 目标 3：补齐恢复的最后一跳：从归档物按批次还原并与原始记录逐项比对一致。
- 目标 4：复用既有 V2 协议、全局锁、台账与健康检查，不新建第二套归档基础设施。
- 目标 5：给出分批推进顺序与每批的前置条件，避免把高风险批次塞进同一轮。

- 非目标 1：本方案**不删除**任何财务行。支付记录只改状态、不物理删除是硬约束（`docs/治理/WORKING_RULES.md:24`、`docs/BACKEND.md:205`）。
- 非目标 2：不在本方案内变更 `log_archive.retention_days` 的现值，也不在保留期责任人未确认前放开任何一张新表。
- 非目标 3：不恢复 2026-08-24 已按产品决策移除的管理端归档检索入口与 API（见关联计划 :190-191）；冷检索继续走 CLI。
- 非目标 4：不把 `automation_logs`（幂等状态）当普通日志处理，`StaleRecordPruneService.php:21` 已把资金凭证与幂等状态列为永不删除。
- 非目标 5：不在本方案内实施代码改动，本文只产出设计与推进顺序。

## 归档对象与过期判定

### 判定顺序

任何一条记录只有在同时满足下面三项时才可被判为过期，缺一项都不成立：

1. **终态。** 记录已进入不可再流转的状态；仍在 `queued`/`running`/`retrying` 的执行、仍可被回调改写的支付、仍可能被退款冲正的账单都不算终态。
2. **时间窗口。** 终态时间早于「现在 − 该流保留期」，且保留期有明确来源（配置项或已批准的保留政策），不能由代码里写死的常量代替。
3. **引用闭合。** 记录的同批数据不会被其它在线行以 `RESTRICT` 外键或业务语义引用；引用未闭合时，整组数据一起判定，不允许单条先走。

### 对象清单

| 数据类别 | 在线真源与规模 | 过期判定依据 | 归档通道 | 本方案结论 |
| --- | --- | --- | --- | --- |
| 业务与安全审计 `activity_logs` | 白名单内，`created_at` 有索引 | `created_at < now - retention_days` | V2 文件归档（已实现） | 沿用现状，仅补保留期分层 |
| 登录审计 `admin_login_logs` | 白名单内 | 同上 | V2 文件归档 | 沿用现状 |
| 消息 `message_logs`、`message_delivery_attempts` | 白名单内 | 同上 | V2 文件归档 | 沿用现状 |
| 调度 `schedule_run_logs`、`schedule_ticks`、`schedule_task_runs` | 白名单内 | 同上，且 `status` 必须为终态（`success`/`failed`/`dispatch_failed`），`queued`/`running`/`retrying` 一律不归档 | V2 文件归档 | 需补终态前置条件（当前靠时间窗口间接保证） |
| 集成与网关 `integration_plugin_runtime_logs`、`gateway_logs`、`service_provision_attempts` | 白名单内 | 同上 | V2 文件归档 | `gateway_logs` 属支付审计证据，保留期需单独确认 |
| 账单 `invoices` | 3,096 行 / 40 列；`invoice_no` UNIQUE、`status` 四态（0 待支付 / 1 已支付 / 4 已取消 / 5 已退款）、`created_at` 有索引 | `status ∈ {1,4,5}` 且 `fulfillment_pending_at` 为空、`requires_refund = 0`、`refunded_at` 已确定，再叠加时间窗口 | **当前无通道**（显式排除） | 不进 V2 文件归档；见「备选方案与取舍」 |
| 账单明细 `invoice_items` | 2,857 行 / 11 列；无独立时间列，只能随 `invoice_id` 走；外键 `CASCADE`（`docs/DATABASE.md:1527`） | 不单独判定，**永远随账单整体判定** | 无 | 与账单同批，不接受单表处理 |
| 订单 `orders` | 380 行 / 33 列；`order_no` UNIQUE、`status` 四态、`created_at` 有索引 | `status ∈ {1,4,5}` 且不存在关联的未终态账单/支付单 | 无 | 与账单同批 |
| 支付单 `payments` | 346 行 / 23 列；`status` 四态（0 待支付 / 1 成功 / 4 已取消 / 5 已退款）；`invoice_id` 为 `RESTRICT`（`docs/DATABASE.md:2248`） | `status ∈ {1,4,5}` 且不再有可改写状态的回调，且未被 `finance_refunds`/`refunds` 以 `RESTRICT` 引用 | 无 | **最晚处理**，见推进顺序 |
| 支付回调 `payment_callbacks` | 391 行 / 14 列；`payment_id` **NOT NULL** 且 `CASCADE`（`docs/DATABASE.md:2186`） | 不单独判定，`payment_id` 非空决定它无法脱离支付单存在 | 无 | 不得单独搬移 |

### 关键结论

- **日志类与财务类必须走两条不同通道。** 日志可以「导出成文件再删库行」，因为它们只是事件流水；财务数据被 `RESTRICT` 外键和审计语义钉在一起（`finance_refunds.invoice_id`、`refunds.invoice_id`、`payments.invoice_id`、`referral_rewards.order_id` 全是 `RESTRICT`），删行会被数据库直接拒绝，即便绕过也会留下悬空引用。
- **`payment_callbacks` 的搬移能力为零。** `payment_id` 非空 + `CASCADE` 意味着支付单一动，回调就得跟着动；而支付单不能物理删除，回调也就无法独立归档。
- **最小不可分割单元是「一个账单 + 它的明细 + 关联支付单 + 支付回调」。** 任何按表推进的方案都必须在批次边界上按 `invoice_id` 聚簇，否则恢复时无法重建一致的账务视图。
- **财务侧的过期判定目前只能停在纸面。** 判定条件可以写清楚，但没有可执行的通道，这一点必须如实呈现，不能用「已设计」冒充「已具备」。

## 归档方式与存放位置

### 数据分层

```
写入               在线只读期              归档期                不可用
 │                    │                      │                     │
 ├─ 业务写入 ────────►│ 在线库（真源）        │                     │
 │                    │  status=终态          │                     │
 │                    └─过保留期─► 归档物 ───┤                     │
 │                                  （文件/表）│                     │
 │                                            └─过文件保留期─► 物理消失
 └─ 归档动作只由受控任务触发，业务代码不参与
```

三段的含义：

- **在线库（真源）**：所有业务读写都只看这里，管理端接口、用户端接口、对账脚本一律不感知归档存在。
- **归档期**：数据已从在线库移出，但可由显式来源参数检索、可按批次恢复。归档物必须自带校验信息（行数、ID 边界、SHA-256），否则不承认其可恢复。
- **不可用**：归档物过保留期被清理后，系统只能回答「该时间段数据已按保留政策清理」，不能返回空结果冒充「本来就没有」。

### 通道一：日志走既有 V2 文件归档（复用，不新建）

- **存放位置**：`storage_path('app/private/log-archives')/v2/{Y-m}/{batch_id}/`，三件套 `.part`（暂存）、`.log`（发布）、`.manifest.json`（元数据），目录 0750、文件 0640（`LogArchiveV2Service.php:2032-2074`）。
- **路径约束**：归档根必须位于 `storage_path` 内，否则服务直接抛 `V2 archive root must remain inside backend storage.`（`:493-496`）。这条是硬边界，方案不尝试放宽。
- **发布原子性**：`.part` 写完后 `fflush`/`fsync` 再 `rename` 为最终文件，manifest 最后写；未发布的 `.part` 在任何情况下都不作为恢复依据。
- **与在线数据的区分**：在线数据在 MySQL，归档数据在文件系统，二者不共享存储；台账在 `archive_items`，一行对应「一个批次里的一个表」，状态字段就是该批次当前所处阶段。
- **manifest 必含字段**：`protocol`、`batch_id`、`table`、`cutoff_at`、`id_min`、`id_max`、`expected_rows`、`exported_rows`、`file`、`file_size`、`checksum_sha256`、`id_sequence_sha256`、`published_at`（`:897-911`）。恢复与检索都以 manifest 为唯一入口，不接受直接扫目录。

### 通道二：财务数据（本方案暂不落地，只定结构）

结论先行：**在保留期责任人确认、引用闭包验证通过之前，财务数据只做只读盘点与保留期声明，不搬移任何一行。** 这样做有三条依据：

1. 规模不成立——财务五表（账单 `invoices`、账单明细 `invoice_items`、订单 `orders`、支付单 `payments`、支付回调 `payment_callbacks`）合计约 7 千行、不到 5MB，搬移带来的容量收益接近零，而每一次搬移都在动审计证据。
2. 通道不成立——其中四个财务表被 `config/log_archive.php:52-62` 显式排除（`orders` 不在排除名单内，但它是归档闭包的一部分，单独处理会切断账单与订单的对应关系），要走文件归档就必须先从排除名单里移除，而移除动作本身等于一次保留政策变更。
3. 恢复不成立——`restoreDryRun` 只能校验文件完整性，没有导入实现；在恢复能力补齐前扩大归档范围，等于把「可能取不回来」的数据量做大。

若后续确认必须做，本方案建议的形态是**按账单聚簇的逻辑搬移**，而不是文件归档：

| 设计点 | 建议形态 | 理由 |
| --- | --- | --- |
| 存放位置 | 归档表 `archived_invoices` / `archived_invoice_items` / `archived_orders` / `archived_payments` / `archived_payment_callbacks`，结构与在线表一致并追加 `batch_id`、`archived_at` | 财务要能对账、要能按编号查，文件形态回答不了 |
| 与在线区分 | 表名前缀 `archived_` + `batch_id` | 已有先例：`2026_10_21_000016_archive_legacy_finance_tables.php` 把 `account_transactions` → `archived_account_transactions`、`refunds` → `archived_refunds` |
| 搬移单元 | 以 `invoice_id` 为闭包，账单 + 明细 + 支付单 + 回调同批 | 引用不闭合会造成悬空 |
| 前置改造 | `payments.invoice_id`、`finance_refunds.invoice_id`、`refunds.invoice_id`、`referral_rewards.order_id` 四处 `RESTRICT` 需改为 `SET NULL` 或改为值快照 | 否则删除在线行时数据库直接拒绝 |
| 表退役 | 不适用 | 那是「整表停用」，不是「按行过期」，两者不能混用同一机制 |

「先例可复用」需要打折：`2026_10_21_000016` 的整表改名带 `FINANCE_ALLOW_RETIRE` 护栏，且改名会让既有命令直接撞 `1146`——`BackfillOrderRefundAmountCommand.php:132`、`AuditLedgerConsistencyCommand.php:64,85` 都要先判表存在性再选数据源。按行归档不会让整表消失，但会让**行**消失，任何按时间范围统计的历史报表都会在归档日之后悄悄变少，这是该形态最大的隐形成本，必须在推进前评估。

## 查询与恢复

### 查询

| 场景 | 现有能力 | 本方案要求 |
| --- | --- | --- |
| 在线日志 | 管理端日志列表与详情（`GET /v2/admin/logs` 系列，`backend/routes/v2-admin.php:301-310`） | 保持不变 |
| 归档日志清单 | `db:logs:archive-v2:list`（`--table` / `--status` / `--batch-id` / `--limit 1..500`），只读，含可恢复性校验 | 保持不变 |
| 归档日志检索 | `db:logs:archive-v2:search`（`--table`、`--start-date`、`--end-date` 必填），流式扫描已发布文件，返回批次/ID/时间/文件名，**不暴露物理路径** | 保持不变 |
| 归档健康 | `db:logs:archive:health --json`（候选积压、最近成功/失败批次、报告与文件规模），每小时心跳 | 保持不变 |
| 财务归档查询 | **无任何通道** | 待新增只读命令才有，本方案只登记需求，不实现 |

查询侧的红线：**不允许以空结果冒充「无数据」。** `db:logs:archive-v2:list` 在归档物缺失时的语义是「不可恢复」，对应的财务查询也必须能区分「本就没有」与「已归档且不可用」两种空——`GatewayDetailFile::read()` 用 `detail_unavailable` 区分这两种空，是同类问题的既有做法，可对齐。

### 恢复

现状必须说清楚：`restoreDryRun(string $batchId)`（`LogArchiveV2Service.php:368-404`）只做三件事——读 manifest、核对最终文件与大小、比对 SHA-256，返回 `restorable` 布尔与 `reason`；不匹配时 `reason` 为「manifest 或归档物缺失/不匹配，不能作为恢复依据」。命令侧 `--restore-dry-run` 有严格的前置校验（`DatabaseArchiveLogsV2Command.php`）：不能与其它执行模式组合（`:43-44`）、必须配合 `--batch-id`（`:55-56`）、不接受 `--table`（`:58-59`）。

因此恢复分两级设计：

**第一级（已具备）——可恢复性判定。** 先跑 dry-run，得到「这批归档物是否还能用来恢复」。这一步是只读的，可随时执行、可重复执行。

**第二级（待新增）——按批次导入。** 需要新增的能力边界：

- **输入**：`batch_id`（+ 可选 `--table` 限定），其余边界全部从 manifest 读，不接受调用方另给时间范围，避免与归档时的切点不一致。
- **幂等**：以「表名 + 主键 id」为自然键，目标行已存在则视为已恢复并计入 `skipped`，不覆盖、不删除现有行。恢复不产生新 id，因此可以安全重跑。
- **一致性校验**：导入完成后再算一遍行数、ID 边界与 `id_sequence_sha256`，与 manifest 不符即整体回滚并置该批次为 `needs_recovery`；不允许「部分成功算成功」。
- **不删归档物**：恢复完成后归档物原样保留，恢复与否不改变归档证据；如需回收空间另走 `cleanup`，与恢复解耦。
- **台账**：恢复动作独立记一次，不复用 `archive_items` 的 `purged_at` 语义，避免把「删过」和「恢复过」混成一个字段。

**取回后与原记录一致的判定口径**：行数相等、主键集合相等（`id_sequence_sha256` 相同）、每行字段值相等（比对 CSV 内容与回读行的哈希）、且 `created_at`/`updated_at` 不被改写。四项全中才算一致；缺任何一项都按「不一致」处理。

## 执行方式与异常处理

### 执行方式

| 数据类别 | 触发方式 | 节奏 | 人工干预 |
| --- | --- | --- | --- |
| 日志归档 | 定时为主（心跳任务 `log-archive`，cron `0 2 * * *`），CLI 手工为辅 | 每日一次，避开 `stale-record-prune`（`30 3 * * *`）与 `finance-operations-prune`（`40 4 * * *`） | 命令侧 `manualTriggerable: false`，手工只能跑 CLI，不经管理端 |
| 日志健康检查 | 定时（心跳 `log-archive-health`，`ScheduleRule::everyTicks(4)`，即每小时） | 只读；`status !== healthy` 时任务记失败 | `manualTriggerable: true` |
| 日志容量盘点 | 无独立任务：`db:logs:capacity` 由 `runHealthCheck()` 内部调用（`CoreScheduledTaskProvider.php:487`），采集失败只写 `capacity_error` 不改健康判定 | 随健康检查每小时一次 | — |
| 日志表容量护栏 | 定时（心跳 `log-capacity-guard`，`ScheduleRule::everyTicks(24)`，即每 6 小时） | 只读，超阈值以非零退出码告警 | `manualTriggerable: true` |
| 财务归档 | **本方案不开放自动执行**；任何搬移只允许人工在独立维护窗口内、先 dry-run 后执行 | — | 必须双人复核 |
| 财务盘点 | 定时只读 | 每日 | — |

三条执行纪律：

1. **新建调度一律注册进 `CoreScheduledTaskProvider`，不改 `backend/routes/console.php`。** 该文件当前只有 4 条 Schedule（心跳、队列、存活、代金券），所有业务定时任务都经心跳统一派发，绕过它会让任务失去台账与超时保护。
2. **必须取全局锁。** `acquireGlobalLock()`（`LogArchiveV2Service.php:2090-2104`）用 `storage_path('framework/cache/log-archive.lock')` 的 `flock(LOCK_EX|LOCK_NB)`，冲突直接抛 `Another log archive process is already running.`。`archive`/`archiveAndPurge`/`purge`/`cleanup` 全部在锁内执行并在 `finally` 释放，新入口必须同样处理。
3. **失败关闭（fail-closed）。** `archiveAndPurge` 在任一表失败时跳过源数据清除并回写 `purge_skipped`（`:119-142`）——这条语义要作为所有新入口的默认，不允许出现「导出失败但已经删了」的路径。

### 进度反馈

进度**只**记在 `archive_items`，不是 `archive_audit_logs`。后者只由 V1 写入（`LogArchiveService.php:749,763`），V2 完全不写，混用会造成两套真源。`archive_items` 的字段就是进度本身：

| 阶段 | 已写入的进度字段 | 读者 |
| --- | --- | --- |
| `planned` | `expected_rows`、`id_min`、`id_max`、`cutoff_at` | 概览、积压统计 |
| `staging` | `part_path`、`started_at` | 中断定位 |
| `verified` | `exported_rows`、`file_size`、`checksum_sha256`、`verified_at` | 是否可发布 |
| `published` | `published_path`、`manifest_path`、`published_at` | 可恢复性判定、冷检索 |
| `purging` | `deleted_rows`（分块递增） | 清除进度 |
| `purged` | `purged_at` | 完成判定 |

对外可读的反馈面只有三个：`db:logs:archive-v2:list`（批次清单）、`db:logs:archive:health --json`（健康摘要）、心跳运行台账。管理端没有归档进度展示，也不在本方案内新增。

### 失败与中断处理

| 场景 | 现状行为 | 处理要求 |
| --- | --- | --- |
| 导出阶段中断 | 批次停在 `staging`，`.part` 残留 | 保留 `.part` 供排查，**不自动清理**；重跑生成新批次，不复用旧 `.part` |
| 校验不通过 | 停在 `staging`，不发布 | 不入检索、不可恢复；修复根因后重跑 |
| 发布后清除失败 | 置 `needs_recovery`，记录 `recordPurgeFailure` | 人工介入，按可重试分类决定是否重跑 `purge` |
| 可重试的清除错误 | `isRetryablePurgeFailure` 判定后允许重试 | 重试仍走同一批次与同一边界 |
| 归档根越界 | 直接抛异常，不落盘 | 视为配置错误，不改代码放宽 |
| 锁冲突 | 抛 `Another log archive process is already running.` | 不改小锁粒度、不允许强制解锁 |
| 磁盘不足 | 归档侧**当前没有空间检查**：`backend/app` 内只有 `MediaFileService::guardDiskSpace()`（`:495-508`，上传前 `disk_free_space` 判余量）与 `DatabaseLogCapacityCommand.php:47`（只读快照 `free_bytes`）两处 | 归档入口需在**开始前**自行检查，而不是写一半才失败；可对齐 `guardDiskSpace` 的写法，不新造第三套 |
| 批次台账异常 | `archive_items` 缺少唯一约束（索引为 `batch_idx`/`created_idx`/`status_idx`/`table_status_idx`，无 UNIQUE） | 重试逻辑必须自己保证不重复建批次，或补齐唯一约束——列入待确认 |

## 推进顺序

三批推进，每批独立可用、可回滚，**不允许跨批合并上线**。

### 批次一：补齐日志侧恢复能力（低风险，先做）

- 前置：无。全部复用既有 V2 协议与校验链。
- 内容：①按批次导入能力及其一致性校验；②导入的幂等与重复执行保护；③恢复动作在`archive_items`之外的独立记录；④`schedule_task_runs` 补终态前置条件。
- 完成判定：任一已发布批次可 dry-run 通过 → 导入 → 行数/主键集合/字段值/时间戳四项与 manifest 一致；同一批次重复导入不产生新行。
- 回滚：导入是纯增量，回滚只需停止使用该命令，不涉及数据回退。

### 批次二：保留期分层与财务只读盘点（与批次一可并行）

- 前置：保留期责任人确认（待确认 P-02）。
- 内容：①`log_archive` 从单一 `retention_days` 扩展为按日志流配置，保留现有键作为默认值以保证向后兼容，并顺带消除 `SettingService.php:120` 兜底默认 30 与 config 90 的口径分叉；②财务五表的只读盘点并入既有的容量快照通道（`db:logs:capacity` 的 `summary`/`log_archives`/`disk` 结构，由 `runCapacitySnapshot()` 调用，`CoreScheduledTaskProvider.php:385-428`），按行数、最早/最新时间、按日增长、字节数输出；③明确 `gateway_logs` 的保留期归属。
- 完成判定：每个日志流都能回答「在线期限多少、谁批准、归档资格有无」；盘点报告可复现。
- 依赖：批次二的输出是批次三的输入。

### 批次三：财务归档（默认不启动）

- 前置（全部满足才启动）：①批次二完成且盘点数据经财务/合规确认；②四处 `RESTRICT` 外键的处置方案定稿；③批次一的恢复能力在日志侧验证过至少一轮；④明确「按行归档会让历史统计口径变小」的接受结论。
- 内容：归档表结构、按 `invoice_id` 聚簇的搬移、搬移后的只读查询、以及全部读写这些表的命令的护栏改造（参照 `BackfillOrderRefundAmountCommand.php:132`、`AuditLedgerConsistencyCommand.php:64,85` 的存在性判断写法）。
- 完成判定：搬移前后账务视图一致；任何按时间范围的报表能明确区分「本就没有」与「已归档」；恢复可回放。
- 默认决策：**不满足前置就不启动**，保持 `excluded_tables` 现状。

### 依赖关系

```
批次一（日志恢复）──┐
                    ├─► 批次三（财务归档）
批次二（保留期+盘点）┘
```

批次一是「让恢复真的能恢复」，批次二是「让保留期有依据」，两者互不阻塞；批次三同时依赖两者的产出，因此必须排在最后。

## 备选方案与取舍

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| A. 全部四类数据统一走 V2 文件归档 | 只有一套协议、一套台账、一套运维口径 | 财务被 `RESTRICT` 外键锁死，删行会被数据库拒绝；把审计证据移出库后无法对账 | **否决** |
| B. 财务数据按行逻辑搬移到 `archived_*` 表 | 结构一致、可查询、可对账、可恢复 | 需先处置四处 `RESTRICT`；按时间范围的历史统计口径会变小；规模收益接近零 | **保留，作为批次三唯一候选**，且不满足前置不启动 |
| C. 财务表加 `deleted_at` 软删除 | 改动最小，查询加个条件即可 | 与「删除即真删，禁止为交易核心表恢复软删除」直接冲突（`docs/DATABASE.md:3911`）；历史上 `2026_10_25_110100_remove_soft_deletes_from_trade_tables.php` 刚刚移除休眠软删列 | **否决** |
| D. 直接物理删除过期数据 | 实现最简单 | 违反支付不删除铁律；V9-01 已证明后果 | **否决** |
| E. 不归档，只做容量监控与保留期声明 | 零风险、零改动 | 回答不了「历史数据放哪」与「怎么取回」 | **作为批次二的落地形态采用**，不单独构成完整方案 |
| F. 归档物放 NAS/外部挂载 | 存储可与库分离 | `config/log_archive.php:13` 明确不支持；越界会直接抛异常 | **否决** |

取舍总结：**日志沿用文件归档，财务退回「只读盘点 + 保留期声明」，直到前置条件齐备。** 这不是回避，而是把「不能删」这件事在设计层面固定下来，避免后续被当成待办事项驱动出高风险改动。

## 影响面与风险

| 风险 | 触发条件 | 后果 | 缓解 |
| --- | --- | --- | --- |
| 恢复导错数据 | 调用方自行给时间范围而非读 manifest | 与归档切点不一致，产生重复或缺失 | 只接受 `batch_id`，边界一律从 manifest 读 |
| 重复导入 | 同批次重跑 | 主键冲突或行数翻倍 | 自然键幂等 + 导入后校验行数与主键集合 |
| 归档物被误删 | 有人手工清目录 | 不可恢复 | 清理只走 `cleanup`，且保留期`file_retention_days` 前不动 |
| 台账无唯一约束 | 并发重试 | 同批次多条记录 | 待确认后补唯一约束或应用层保证 |
| 保留期被一刀切延长 | 无人负责 | 归档形同虚设 | 每个流必须有责任人与批准记录 |
| 财务统计口径漂移 | 按行归档上线 | 历史报表静默变小 | 报表必须区分本就没有/已归档；上线前评估 |

| 命令撞表不存在 | 表被改名或行被搬走 | `1146` 直接报错 | 所有读写命令先判存在性再选数据源，参照既有先例 |
