# 后端整体工程深度审查报告

- 审查时间：2026-05-24
- 审查范围：`backend`
- 审查方式：静态代码审查 + 配置核查 + 最小验证尝试
- 审查角色：框架工程师、安全工程师、数据库 DBA、分布式架构师、业务后端工程师、API 接口工程师、缓存中间件工程师、消息队列工程师、云原生运维工程师、性能压测工程师、分布式事务工程师、数据灾备工程师、应用风控工程师、权限体系工程师、日志告警工程师、代码规范工程师

## 1. 总体结论

当前后端项目基于 Laravel 12，已经形成较清晰的领域划分，核心业务按认证、商品、账单、支付、服务开通、推荐返佣、上游接口、系统配置等模块拆分，整体具备中大型业务后台的基础骨架。

优点：

- 控制器整体较薄，主要业务逻辑已下沉到 `app/Services`
- 支付、账单、余额、服务开通等关键链路普遍引入了事务、锁和幂等意识
- 鉴权、权限、操作日志、风控、通知、上游驱动等已有基础设施
- 已开始从 `order-first` 收口到 `invoice-first`

主要风险：

- 支付网关请求关闭 TLS 证书校验，属于高风险安全问题
- 支付成功后的履约、返佣、优惠券同步、管理员通知仍大量依赖请求尾部执行，不是严格可靠异步
- `invoice-first` 已是主链，但权限、通知、旧订单兼容逻辑仍有混用
- 数据库默认连接与模型显式连接存在双轨口径，长期维护风险较高
- 回调验签、日志脱敏、调度互斥、默认队列配置等方面仍有明显改进空间

结论判断：

- 从“可开发、可运行”看，当前工程已具备持续迭代能力
- 从“高并发支付型业务的长期稳定运行”看，当前工程仍未完全达标
- 建议先完成支付安全、可靠异步、权限收口、连接治理四项整改，再进入更大规模功能扩展

## 2. 严重问题清单

### 2.1 High：支付网关请求关闭 TLS 证书校验

- 文件：`backend/app/Services/PaymentGateway/AlipayFaceToFaceService.php`
- 位置：约第 233-237 行
- 现象：
  - 支付宝网关请求使用 `->withoutVerifying()`
- 风险：
  - 生产环境下会关闭 HTTPS 证书校验
  - 存在中间人攻击、代理劫持、网关响应伪造风险
  - 支付链路不应接受此类降级
- 整改建议：
  - 生产环境强制启用证书校验
  - 如确需兼容特殊环境，仅允许通过显式 env 开关在本地调试关闭
  - 为支付网关增加 CA bundle 配置项与启动自检
- 验收标准：
  - 生产环境配置下不再出现 `withoutVerifying()`
  - 支付请求失败时能区分证书异常、网络异常、业务异常

#### 详细修改方法

1. 修改 `backend/app/Services/PaymentGateway/AlipayFaceToFaceService.php`
   - 删除固定的 `->withoutVerifying()`
   - 改为读取配置，例如：
     - `alipay.ssl_verify`
     - `alipay.ca_bundle`
2. 修改 `backend/config/alipay.php`
   - 增加：
     - `ssl_verify`，默认 `true`
     - `ca_bundle`，默认空字符串
3. 修改 `backend/.env.example`
   - 增加：
     - `ALIPAY_SSL_VERIFY=true`
     - `ALIPAY_CA_BUNDLE=`
4. 在请求构建时做分支处理
   - `ssl_verify=true` 时启用系统证书校验
   - `ca_bundle` 非空时，通过 `withOptions(['verify' => $caBundle])` 指向证书
   - 仅在本地开发环境且显式配置时才允许关闭校验
5. 为配置错误增加日志
   - 如果生产环境关闭 TLS 校验，启动时或首次请求时输出 `error` 级日志

#### 推荐实施方案

- 推荐采用“配置驱动 + 生产强约束”方案：
  - 本地：允许用 env 控制
  - 测试/生产：默认必须开启
- 推荐增加一个私有方法统一构造 Http Client：
  - `buildHttpClient(): PendingRequest`
  - 这样后续支付宝 `precreate/query/refund` 都不会再散落安全配置

#### 涉及文件

- `backend/app/Services/PaymentGateway/AlipayFaceToFaceService.php`
- `backend/config/alipay.php`
- `backend/.env.example`

#### 验证步骤

1. 本地开启 `ALIPAY_SSL_VERIFY=true`，确认请求正常
2. 手动配置错误证书路径，确认能明确报证书校验错误
3. 检查生产配置模板，确认默认不允许关闭

### 2.2 High：支付成功后的后置业务仍依赖 terminating/尾部同步执行

- 文件：`backend/app/Services/Finance/PaymentService.php`
- 位置：
  - `handlePaidInvoice` 约第 1272 行
  - `provisionPaidInvoice` 约第 1339 行
  - `dispatchInvoiceOnlyReferralReward` 约第 1374 行
- 现象：
  - 支付成功后履约、返佣、优惠券同步、管理员通知等逻辑并未完全切到可靠队列
  - 仍存在 `app()->terminating(...)` 和请求尾部执行
- 风险：
  - PHP 进程被回收、超时、中断时，支付已成功但后续业务可能未完成
  - 会出现“已付款未开通”“已付款未返佣”“已付款未通知”这类最终一致性缺口
  - 故障后难以自动补偿和回放
- 整改建议：
  - 支付事务内只做状态落库
  - 履约、返佣、通知、优惠券同步全部投递数据库队列
  - 为每个 Job 增加幂等键、执行状态和失败重试/补偿机制
- 验收标准：
  - 支付成功后核心后置动作全部可通过队列重放
  - 任意 Job 重复执行不会造成重复开通、重复返佣、重复通知

#### 详细修改方法

1. 收口支付成功后的动作清单
   - 当前至少包括：
     - 服务开通/续费履约
     - 推荐奖励发放
     - 优惠券使用同步
     - 管理员通知
2. 修改 `backend/app/Services/Finance/PaymentService.php`
   - `handlePaidInvoice()` 中不再直接调用：
     - `provisionPaidInvoice()`
     - `dispatchInvoiceOnlyReferralReward()`
     - `notifyInvoicePaidAfterResponse()`
   - 改为只投递 Job
3. 新增或补齐 Job
   - `ProcessPaidInvoiceFulfillmentJob`
   - `ProcessPaidInvoiceReferralRewardJob`
   - `SyncPaidInvoiceCouponUsageJob`
   - `SendPaidInvoiceAdminNotificationJob`
4. 为每个 Job 增加幂等保护
   - 幂等键建议使用：
     - `invoice_id + action`
   - 可落表 `automation_logs` 或新增业务执行记录表
5. 明确重试策略
   - 履约类：有限重试，失败进入人工处理或补偿命令
   - 通知类：可多次重试，失败不阻断交易主链
   - 推荐奖励：必须幂等，失败可重放
6. 为支付后业务流建立统一调度器
   - 推荐保留一个 Dispatcher，例如：
     - `PaidInvoiceBusinessFlowDispatcher`
   - 所有投递逻辑统一在 Dispatcher 中处理，避免散落在 `PaymentService`

#### 推荐实施方案

- 推荐采用“交易落库 + 统一 Dispatcher + 多 Job 分发”的结构：
  - 第一步：支付事务内只更新 `invoice/payment`
  - 第二步：Dispatcher 按场景投递队列任务
  - 第三步：每个 Job 独立幂等执行
- 推荐按账单类型拆分履约：
  - `new` 新购
  - `renew` 续费
  - `upgrade` 升级/流量包
- 推荐把“支付后业务流执行状态”做成可观测结构，而不是只看日志

#### 涉及文件

- `backend/app/Services/Finance/PaymentService.php`
- `backend/app/Services/Order/PaidOrderBusinessFlowDispatcher.php`
- `backend/app/Jobs/*`
- 可能新增：
  - `backend/app/Services/Finance/PaidInvoiceBusinessFlowDispatcher.php`

#### 验证步骤

1. 支付成功后确认仅落库并投递任务，不再同步执行业务后置动作
2. 人工重复执行同一个 Job，确认不会重复开通/返佣/通知
3. 模拟 Job 失败后重试，确认最终结果正确
4. 检查队列积压时，支付主链仍能快速返回

### 2.3 High：管理员支付通知权限口径仍依赖旧订单权限

- 文件：`backend/app/Services/Finance/AdminOrderNotificationService.php`

  - 权限体系继续分叉，后续越改越乱

  - 通知接收权限改为 `INVOICE_*` 体系

     - `ORDER_DETAIL`
     - `ORDER_MANAGE`

     - `INVOICE_LIST`
     - `INVOICE_DETAIL`
     - `INVOICE_MANAGE`
2. 梳理后台所有账单相关通知、摘要、概览、日志导出逻辑
   - 确认是否还存在基于 `order.*` 的收件人判定

4. 增加过渡兼容说明
   - 如果历史角色仍只配置了 `order.*`，需要提供一次迁移脚本或权限补齐逻辑

#### 推荐实施方案

- 推荐分两步：
  - 第一步：通知口径先切到 `invoice.*`
  - 第二步：梳理全后台是否仍有 `order.*` 依赖
- 如果线上已有历史角色数据，建议增加一次“权限映射补齐”脚本，而不是只改代码等待自然修复

#### 涉及文件

- `backend/app/Services/Finance/AdminOrderNotificationService.php`
- `backend/app/Support/AdminPermissions.php`
- 可能涉及角色/权限初始化脚本或数据修复脚本

## 3. 重要改进项

### 3.1 Medium：实名认证回调验签强度偏弱

- 文件：`backend/app/Http/Middleware/VerifyCallbackSignature.php`
- 位置：约第 20-35 行
- 现象：
  - 验签方式为 `md5(certify_id + key)`
- 风险：
  - 无时间戳、无随机数、无重放保护
  - 仅能算简化校验，不适合长期作为关键回调签名方案
- 建议：
  - 改为 `hash_hmac('sha256', canonical_payload, secret)`
  - 增加时间戳、nonce、有效期和重放防护

### 3.2 Medium：数据库默认连接与显式连接双轨并存

- 文件：`backend/app/Providers/AppServiceProvider.php`
- 位置：约第 17-27 行
- 现象：
  - 运行时强制把 `database.default` 设为 `mysql`
  - 大量核心模型又显式绑定 `idc`
- 风险：
  - 新代码一旦忘记显式连接，容易落到默认库
  - 默认连接与业务真库口径不统一，排障成本高
- 建议：
  - 明确唯一运行时真库口径
  - 要么默认连接统一为 `idc`
  - 要么所有核心聚合根和仓储类统一显式指定连接

### 3.3 Medium：队列默认值与项目规范不一致

- 文件：`backend/config/queue.php`
- 位置：约第 4 行
- 现象：
  - 默认 `QUEUE_CONNECTION` 为 `sync`
  - `.env` 与 `.env.example` 虽设为 `database`，但默认值仍不安全
- 风险：
  - 缺配置或新环境时会退化为同步执行
  - 放大接口耗时与失败影响面
- 建议：
  - 默认值改为 `database`
  - 启动时校验当前环境是否误用 `sync`

### 3.4 Medium：Windows 文件缓存场景下主动关闭调度互斥

- 文件：`backend/routes/console.php`
- 位置：约第 21-29 行、56-61 行
- 现象：
  - Windows + file cache 场景主动跳过 `withoutOverlapping`
- 风险：
  - 定时任务可能重入
  - 自动续费、账单清理、状态同步等任务若业务幂等不完整，会导致重复执行
- 建议：
  - 生产环境强制 Redis 锁
  - 所有任务自身保留幂等防护，不能只依赖调度锁

### 3.5 Medium：接口访问日志脱敏仍偏黑名单式

- 文件：
  - `backend/app/Http/Middleware/LogOperation.php`
  - `backend/app/Support/SensitiveDataSanitizer.php`
- 现象：
  - 日志记录 `request->all()`
  - 已有脱敏，但仍主要靠字段黑名单
- 风险：
  - 业务敏感字段、第三方票据、会话 cookie、部分支付账户信息可能漏打
- 建议：
  - 逐步从黑名单转为白名单日志策略
  - 按账户、身份、支付、凭证、密钥五大类补全脱敏策略

### 3.6 Medium：业务异常 HTTP 状态未显式透传

- 文件：
  - `backend/app/Exceptions/BusinessException.php`
  - `backend/app/Support/ApiResponseBuilder.php`
- 现象：
  - `BusinessException` 构造支持 HTTP 状态
  - `render()` 未显式传递 status，主要依赖错误码推断
- 风险：
  - 不利于后续扩展更细粒度 HTTP 语义
  - 网关、监控、前端重试策略可能受影响
- 建议：
  - 将显式 HTTP 状态透传给 `ApiResponseBuilder::error`

  - 影响本地联调、Sanctum stateful 域与回调地址推导
- 建议：
  - 除非仓库明确提供本地 HTTPS 方案，否则统一本地协议

## 5.17 工程师视角落地方案

本节不是管理视角，也不是抽象治理视角，而是站在一线后端工程师的角度，回答“这件事代码到底怎么改、先改哪里、怎么避免把线上搞炸”。

### A. 支付链路安全整改方案

#### 目标

- 去掉支付网关不安全的 TLS 降级
- 不影响现有支付宝预下单、查单、退款主流程
- 保证本地、测试、生产三套环境都有明确行为

#### 工程实施思路

1. 先不动业务逻辑，只抽 Http Client 构建
   - 在 `AlipayFaceToFaceService` 中新增统一方法，例如：
     - `buildGatewayRequest(): PendingRequest`
   - 把 `precreate/query/refund/request` 里分散的 `Http::asForm()` 收到这里
2. 把 TLS 行为改成配置驱动
   - 配置层新增：
     - `ALIPAY_SSL_VERIFY`
     - `ALIPAY_CA_BUNDLE`
   - 代码中统一转成：
     - `verify => true`
     - 或 `verify => 'ca-bundle-path'`
3. 给不安全配置加保护
   - `production` 环境下如果 `ssl_verify=false`，直接拒绝启动或至少记录 `error`
4. 最后再补日志和测试
   - 先保证代码结构对，再补失败可观测性

#### 推荐代码改法

- 先做一个小重构，不直接在现有 `request()` 方法里继续堆条件
- 推荐结构：

```php
private function buildGatewayRequest()
{
    $request = Http::asForm()
        ->timeout(15)
        ->retry(1, 200);

    $verify = config('alipay.ssl_verify', true);
    $caBundle = trim((string) config('alipay.ca_bundle', ''));

    if ($verify === false) {
        $request = $request->withoutVerifying();
    } elseif ($caBundle !== '') {
        $request = $request->withOptions(['verify' => $caBundle]);
    }

    return $request;
}
```

#### 工程师注意点

- 不要一上来全局搜 `withoutVerifying()` 全删
  - 先确认是不是支付链路、上游链路、测试链路
- 生产环境不能接受“先改了再看”
  - 必须先准备证书/配置说明
- 如果历史环境确实依赖关闭校验，必须给迁移窗口，不要硬切

### B. 支付成功后业务流消息化方案

#### 目标

- 把“支付成功后”的履约、返佣、通知、优惠券同步全部从请求线程拿出去
- 让支付接口只负责交易状态落库
- 让所有后置动作支持重试、补偿、重放

#### 工程实施思路

1. 先建立统一调度器
   - 新增 `PaidInvoiceBusinessFlowDispatcher`
   - 不要把投递逻辑继续散在 `PaymentService`
2. 再把同步逻辑换成投递逻辑
   - 当前直接执行：
     - `provisionPaidInvoice`
     - `dispatchInvoiceOnlyReferralReward`
     - `notifyInvoicePaidAfterResponse`
   - 改成：
     - `dispatchFulfillmentJob`
     - `dispatchReferralRewardJob`
     - `dispatchCouponSyncJob`
     - `dispatchAdminNotifyJob`
3. 每个 Job 自己幂等
   - 不依赖 Dispatcher 幂等
   - 不依赖“队列不会重复投递”这种假设
4. 最后再删旧的 `terminating` 逻辑
   - 先并行保留一版灰度
   - 验证稳定后彻底移除

#### 推荐拆分方式

- `ProcessPaidInvoiceFulfillmentJob`
  - 负责履约
  - 按账单类型再分流到新购/续费/升级
- `ProcessPaidInvoiceReferralRewardJob`
  - 负责返佣
- `SyncPaidInvoiceCouponUsageJob`
  - 负责优惠券占用/核销状态同步
- `SendPaidInvoiceAdminNotificationJob`
  - 负责管理员通知

#### 推荐幂等方案

- 使用 `automation_logs` 或独立执行记录表
- 唯一键建议：
  - `task_key + action + resource_type + resource_id`
- 示例：
  - `paid_invoice_flow + fulfillment + invoice + 123`
  - `paid_invoice_flow + referral_reward + invoice + 123`

#### 工程师注意点

- 不要把“查状态再执行”当成完整幂等
  - 真正幂等要有执行记录或唯一约束
- 不要把所有后置动作塞进一个大 Job
  - 一个大 Job 失败会让故障域过大
- 通知类失败不应回滚交易
  - 履约/返佣/通知的失败语义不同，重试策略不能一刀切

### C. `invoice-first` 收口方案

#### 目标

- 明确账单是唯一交易主实体
- 旧 `order` 只保留兼容，不继续承载新能力

#### 工程实施思路

1. 先梳理所有仍依赖 `order` 的地方
   - 权限判断
   - 通知收件人
   - 日志动作命名
   - 后台概览统计
   - 退款入口
2. 标记三类代码
   - 主链代码：必须改成 `invoice-first`
   - 兼容桥接：可暂时保留
   - 历史废弃：确认无用后删除
3. 先改读取逻辑，再改写入逻辑
   - 避免新写入先切了，旧读取还没跟上
4. 最后补文档和权限映射

#### 推荐执行策略

- 第一阶段：
  - 通知、权限、控制器入口全部优先按 `invoice` 收口
- 第二阶段：
  - `OrderService` 仅做兼容桥接
- 第三阶段：
  - 给 `order` 相关类补 `@deprecated` 注释和迁移说明

#### 工程师注意点

- 不要试图一次性删除全部 `order` 代码
  - 这种项目明显还有历史兼容负担
- 先把“新路径不能再依赖旧模型”守住
  - 比“一次删干净旧代码”更现实

### D. 权限体系收口方案

#### 目标

- 账单、支付、退款、通知统一走 `invoice.*`
- 旧 `order.*` 不再作为主权限来源

#### 工程实施思路

1. 先改服务层判定
   - 尤其是通知和后台账单相关服务
2. 再改路由与菜单口径
   - 保证前后端语义一致
3. 最后做角色迁移
   - 给历史角色批量补 `invoice.*`

#### 推荐迁移做法

- 建一个权限映射表：
  - `order.list -> invoice.list`
  - `order.detail -> invoice.detail`
  - `order.manage -> invoice.manage`
- 写一次性迁移脚本：
  - 扫角色已有权限
  - 自动补齐对应 `invoice.*`

#### 工程师注意点

- 不要只改代码，不补历史角色数据
  - 否则线上会出现“代码对了，角色没权限”的假故障
- 不要让通知逻辑偷偷读旧权限
  - 这类问题最隐蔽

### E. 数据库连接治理方案

#### 目标

- 统一运行时真库口径
- 避免默认连接和显式连接混用造成误写

#### 工程实施思路

1. 先做盘点
   - 哪些模型显式 `idc`
   - 哪些模型依赖默认连接
   - 哪些服务直接 `DB::transaction()` 未指定连接
2. 再定策略
   - 推荐策略：核心交易域全部显式 `idc`
   - 辅助代码若必须走默认连接，也要文档说明
3. 分批治理
   - 第一批：`User`、认证、支付、账单、余额、服务
   - 第二批：内容、日志、配置、通知
4. 最后加约束
   - 新增模型或服务时必须说明连接策略

#### 推荐工程方案

- 短期：
  - 补齐核心模型 `protected $connection = 'idc'`
  - 高风险事务改成 `DB::connection('idc')->transaction(...)`
- 中期：
  - 收口默认连接策略
- 长期：
  - 增加静态检查或 code review 规则，禁止核心域漏配连接

#### 工程师注意点

- 不要一刀切全仓统一替换 `DB::transaction`
  - 先从交易域开始
- 连接治理很容易改出隐藏 bug
  - 必须配合集成测试

### F. 日志与告警补齐方案

#### 目标

- 日志可排障，但不泄漏敏感信息
- 关键异常能形成监控和告警

#### 工程实施思路

1. 先收缩日志内容
   - 对请求参数做白名单记录
   - 高风险接口只记录必要字段
2. 再补脱敏规则
   - 手机号、邮箱、支付账号、cookie、上游票据
3. 最后接告警
   - 支付回调签名失败
   - 支付成功后履约失败
   - 返佣失败
   - 队列积压
   - Job 重试超限

#### 推荐代码改法

- `LogOperation` 不要默认整包落 `request->all()`
- 推荐改为按接口模块做白名单字段抽取：
  - 支付：只记 `payment_no/invoice_id/trade_status`
  - 登录：只记账号标识和结果，不记原始凭据
  - 实名认证：只记状态，不记身份证/姓名原值

#### 工程师注意点

- 日志不是越多越好
  - 对支付和认证来说，“可定位”比“全量打印”重要
- 脱敏不要只做字符串替换
  - 最好从结构化字段层面控制

## 7. 建议验收标准

### 支付安全

- 支付网关请求必须启用证书校验
- 回调必须校验签名、应用归属、金额一致性、幂等性

### 异步可靠性

- 支付后所有关键动作均可通过队列重试
- 任意 Job 重复执行不产生重复业务结果

### 权限体系

- 账单、支付、通知、后台菜单统一使用 `invoice.*`
- 旧 `order.*` 仅保留兼容桥接并标注废弃

### 数据一致性

- 关键财务链路仅保留单一交易主实体
- 默认连接与业务真库口径一致

### 可观测性

- 关键链路有结构化日志
- 支付失败、回调失败、履约失败、返佣失败、队列积压有监控和告警

## 7.1 建议测试用例清单

### 支付安全测试

1. 支付网关证书正常时可成功请求
2. 证书错误时请求失败且日志可识别
3. 禁止生产配置关闭 TLS 校验

### 支付回调测试

1. 正常回调可成功入账
2. 重复回调不会重复入账
3. 金额不一致回调会被拒绝
4. 非法 `app_id` 回调会被拒绝
5. 已取消账单回调不会恢复为已支付

### 队列与后置业务测试

1. 支付成功后仅投递任务，不同步执行后置动作
2. 履约任务失败后可重试
3. 推荐奖励任务重复执行不会重复发放
4. 管理员通知任务重复执行不会重复发送

### 权限测试

1. 仅具备 `invoice.*` 权限角色可收到账单通知
2. 仅具备 `order.*` 历史权限角色不会误收
3. 超级管理员仍可正常收到通知

### 支付 TLS 改造回滚

- 保留旧逻辑作为短期兼容开关，但默认关闭

- 回滚窗口结束后必须彻底移除旧路径

### 权限口径回滚

- 保留一次性迁移脚本
- 若角色映射异常，可快速恢复旧权限数据快照
