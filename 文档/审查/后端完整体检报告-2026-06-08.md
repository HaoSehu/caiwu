# Laravel 12 后端完整体检报告与后续修复路线图

生成日期：2026-06-08  
审查对象：`backend` Laravel 12 后端，联动抽查 `frontend-client`、`frontend-admin-v3` 中会直接展示 API message 或错误提示的路径。  
审查基线：当前代码、真实路由、只读命令输出、子代理审查结论。本轮不把旧开发文档、旧规范、历史迁移文件当作绝对真源。  
执行边界：未读取或输出 `.env`、secret、token、password、私钥等敏感值；未执行数据库初始化、数据库迁移或历史迁移补跑；未调用真实第三方接口；未修改业务代码。

## 0. 总体结论

当前后端已经完成一批前置安全修复：设置接口不再返回敏感 `value` 原值，供应商接口不再返回 `api_key` 原值，生产维护服务不再物理删除 `payments`，支付宝回调路由已挂 `verify.alipay.callback`，支付后关键 Job 已有 `failed()` 钩子和异常重抛，后端默认 locale 已是 `zh_CN`。

但完整体检后仍不建议进入大规模业务迭代。当前剩余风险集中在 6 类：

1. **P0 安全风险**：公开 VNC token 接口返回连接 `password`，且公开读取不消费一次性 token。
2. **P0 财务审计风险**：退款只更新 `Payment`/`Order`，未稳定更新 `Invoice` 退款状态；收入统计仍按 `InvoiceStatus::PAID` 汇总。
3. **P0 财务流水风险**：混合支付预占余额恢复会物理删除 `balance_logs`。
4. **P1 队列可靠性风险**：`RunScheduleTaskJob` 超时、重试、重叠锁和队列消费清单不一致。
5. **P1 API 与中文体验风险**：前端仍有多处直接展示 `error.message`，后端部分上游错误原文仍可能进入 `BusinessException`。
6. **P1/P2 插件化治理风险**：支付、实名、短信、上游已半插件化；邮件、对象存储、统一回调、统一异常、provider-aware 缓存仍未完整落地。

整体评级：**C+，需要先关闭 P0/P1 后再继续业务扩展**。

## 5. P0 必须优先修复

### P0-01 公开 VNC token 接口返回连接密码且不消费 token

证据：

- `backend/routes/client.php:43`：`GET /vnc-tokens/{token}` 只挂 throttle，无认证。
- `backend/app/Http/Controllers/Client/ServiceController.php:562-565`：直接返回公开 token payload。
- `backend/app/Services/ClientServiceConsole/ServiceVncService.php:156-166`：公开 payload 包含 `password`。
- `backend/app/Services/ClientServiceConsole/ServiceVncService.php:158`：公开读取调用 `loadVncTokenParams($token, false)`，不消费 token。

风险：VNC URL token 一旦进入浏览器历史、代理日志、Referer、截图或前端报错上下文，在有效期内可重复换取连接凭据。该风险不依赖后台权限，属于 P0。

修复方案：

1. 公开接口不返回 `password`，改由 VNC relay 服务端内部换取上游凭据。
2. 如果必须保留独立 VNC 页面，公开路径必须消费一次性 token、缩短 TTL、绑定用户会话/IP/UA 指纹，并在成功换取后立即失效。
3. 日志中只允许记录 token 哈希或掩码，不记录原始 token、密码、完整 URL。
4. 补 Feature Test：首次请求不含 `password`，重复请求失败，过期 token 失败，日志脱敏。

### P0-02 退款未同步 `Invoice`，收入统计可能高估

证据：

- `backend/app/Services/Finance/PaymentService.php:1167-1174`：支付宝退款成功后更新 `PaymentStatus::REFUNDED` 和 `OrderStatus::REFUNDED`。
- `backend/app/Services/Finance/PaymentService.php:1288-1298`：余额退款路径同样更新 `Payment` 和可选 `Order`。
- 上述路径未同步 `InvoiceStatus::REFUNDED`。
- `backend/app/Services/Finance/AdminFinanceQueryService.php:151`：收入统计按 `InvoiceStatus::PAID` 汇总。

风险：退款完成后账单仍可能保持已支付，收入报表、产品销量、财务审计和用户账单展示会出现不一致。该风险直接影响财务口径。

修复方案：

1. 退款事务内锁定并更新 `Invoice`：`status=REFUNDED`、`refunded_at`、退款金额、退款方式、操作人和 trace_id。
2. 收入统计显式排除退款账单，或按退款流水抵扣。
3. `InvoiceService` 的显示状态不应只靠 Payment 派生，需要持久化账单状态。
4. 补测试：支付宝原路退款、余额退款、重复退款、部分/全额边界、收入统计不计入退款。

### P0-03 混合支付预占余额恢复会物理删除财务流水

证据：

- `backend/app/Services/Finance/PaymentService.php:541`：支付宝预下单失败时调用 `restoreReservedMixBalance(..., suppress_logs=true)`。
- `backend/app/Services/Finance/PaymentService.php:1781-1802`：`suppress_logs=true` 时删除匹配的 `BalanceLog`。
- `backend/app/Models/BalanceLog.php:45-46`：删除事件只清理用户余额缓存。

风险：财务流水被物理删除后，预占、恢复、投影和后续审计缺少完整链条，难以排查混合支付失败和余额争议。

修复方案：

1. 禁止物理删除 `balance_logs` 财务流水。
2. 改为新增反向流水或撤销流水，保留原流水并标记撤销关系。
3. 同步 `account_transactions` 或其他投影状态，确保审计链可追溯。
4. 补测试：预下单失败恢复余额不删除原流水，新增反向流水，余额最终正确，投影不残留。

## 6. P1 高优先级治理

### P1-01 设置 GET 接口有写库副作用

证据：

- `backend/app/Services/System/SettingService.php:67`：读取设置时调用 `syncFallbackSettingsToDatabase()`。
- `backend/app/Services/System/SettingService.php:359`：支付 fallback 包含 `alipay_private_key`。
- `backend/app/Services/System/SettingService.php:381-401`：缺失项会通过 `Setting::setValues()` 落库。

风险：GET 请求不应产生写库副作用；敏感 fallback 即使已加密，也不应在后台读取时自动持久化。

修复方案：GET 只读；新增显式“初始化默认配置”命令或后台动作；敏感 fallback 不自动落库；补单测断言 GET settings 不调用 `setValues()`。

### P1-02 客户端账单详情复用 admin DTO

证据：

- `backend/app/Http/Controllers/Client/InvoiceController.php:350`：用户端 `transformInvoice()` 调用 `adminDetail()`。
- `backend/app/Services/Finance/InvoiceService.php:295-321`：admin detail 输出 `raw_status`、`raw_status_label`、`payments.trade_no`、退款字段。

风险：用户端响应混入管理端字段，增加内部状态、第三方流水号、退款细节暴露面，也让客户端契约被 admin 需求牵动。

修复方案：新增 `ClientInvoiceResource` 或 `ClientInvoiceDetailDTO`；用户端白名单输出；测试断言不包含 `raw_status`、`payments.*.trade_no` 等内部字段。

### P1-03 `RunScheduleTaskJob` 超时、重试和重叠锁不一致

证据：

- `backend/app/Jobs/RunScheduleTaskJob.php:35-37`：`tries=1`、`timeout=1800`。
- `backend/app/Jobs/RunScheduleTaskJob.php:50-52`：`WithoutOverlapping()->releaseAfter(10)->expireAfter(1800)`。
- `backend/config/queue.php:16`：database queue `retry_after=1500`。
- `backend/routes/console.php:282`：生产短 worker `--timeout=1200`。

风险：长任务可能被 worker 提前杀掉；在其他 worker 场景下 `retry_after` 早于 Job timeout 可能导致重复可见；重叠任务 release 后因为 `tries=1` 可能直接进入失败。

修复方案：统一 `job timeout < worker timeout < retry_after`；对重叠任务提高 tries 或改为 `dontRelease()`；补 `failed()` 钩子和参数关系测试。

### P1-04 队列消费清单不一致

证据：

- `backend/routes/console.php:282`：生产 schedule worker 消费 `provision,referral,notification,coupon,default`。
- `backend/app/Jobs/RunScheduleTaskJob.php:150-155`：手动积压消费只跑 `referral,provision,default`。
- `backend/app/Console/Commands/ServeBackendStackCommand.php:182-185`：本地 `app:serve` 队列只跑 `provision,referral,default`。

风险：`notification`、`coupon` 队列在本地/手动路径可能滞留，测试和生产表现不一致。

修复方案：抽统一配置，例如 `config('queue.caiwu_worker_queues')`；schedule、手动 drain、app:serve 和测试共用。

### P1-05 管理员手动标记支付可创建第三方成功 Payment

证据：

- `backend/app/Services/Order/OrderService.php:511-522`：管理员手动标记支付时可创建 `PaymentStatus::SUCCESS`，`callback_raw.source=admin_manual`。
- `backend/app/Services/Order/OrderService.php:754-756`：`alipay`、`wechat` 会进入创建 Payment 的白名单。
- `backend/app/Services/Order/OrderService.php:597-600`：恢复未支付时把 `gateway in ['alipay','wechat']` 的成功 Payment 视为真实支付记录。

风险：人工动作可能被后续逻辑当作真实第三方资金流入，违反 Payment 边界，影响审计与恢复能力。

修复方案：管理员手动确认走独立审计记录或 `manual_receipts`；如必须保留 Payment，需显式 `gateway=manual` 并与第三方真实资金流隔离。

### P1-06 实名回调签名可重放

证据：

- `backend/app/Http/Middleware/VerifyCallbackSignature.php:16-24`：签名只用 `certify_id + key` 的 MD5。
- 未见 timestamp、nonce、请求体绑定和 replay cache。

风险：同一回调包可被重放；签名没有绑定完整请求体，抗篡改能力不足。

修复方案：改为 HMAC-SHA256；签名覆盖规范化请求体、timestamp、nonce；引入短 TTL replay cache；日志记录脱敏回调 attempt。

### P1-07 支付宝普通日志绕过脱敏器

证据：

- `backend/app/Services/PaymentGateway/AlipayFaceToFaceService.php:122`：直接 `Log::info` 记录 precreate 响应。
- `backend/app/Services/PaymentGateway/AlipayFaceToFaceService.php:203-207`：直接记录 refund 响应。
- `backend/app/Services/System/GatewayLogService.php:30-31` 已使用 `SensitiveDataSanitizer`。

风险：虽然网关审计日志有脱敏，普通 Laravel 日志仍可能落入签名、网关原始字段或上游错误内容。

修复方案：普通日志也统一调用脱敏器；只记录必要字段和 trace_id；补日志脱敏测试。

### P1-08 上游错误原文可能进入 API message

证据：

- `backend/app/Services/Provisioning/ProvisionService.php:711-712`：上游 `msg/message` 被拼进 `BusinessException`。
- `backend/app/Services/Provisioning/ServiceRenewService.php:796-797`：续费同类问题。
- `backend/app/Services/Automation/ServiceStatusSyncService.php:476-478`：状态同步同类问题。
- `backend/app/Services/ClientServiceConsole/ServiceDetailService.php:674-675`：控制台详情同类问题。

风险：第三方英文、技术错误、供应商内部字段可能直接成为 API message 或前端提示，不符合“用户可见文案必须简体中文”和“第三方原文只进脱敏日志”的要求。

修复方案：新增 `ThirdPartyErrorMapper` 或 `IntegrationException`，API 只返回可信中文文案；第三方原文进入脱敏日志和内部上下文。

### P1-09 前端仍存在 `error.message` 直出

证据：

- `frontend-admin-v3/src/pages/users/detail/index.vue:1824`

- `frontend-admin-v3/src/pages/products/index.vue:3655`
- `frontend-client/src/views/client/Profile/composables/useSecurityDialogs.js:157` 等多处

风险：axios、浏览器、第三方原文或英文异常会直接显示给用户。

修复方案：统一 `toUserMessage(error, fallback)`，只接收后端可信中文 message；未知错误回退固定中文；隐藏或移除 `en_US` 自动切换入口。

### P1-10 自动化批处理存在无界读取与索引缺口

证据：子代理审查命中 `BillingAutomationService`、`ServiceLifecycleAutomationService`、`InvoiceCleanupAutomationService` 多处 `get()` 后 PHP 循环过滤；新增 `gateway_logs`、`activity_logs` 查询组合条件与迁移索引不完全匹配。

风险：数据量增长后 schedule 每分钟执行会拖慢数据库和 worker，且日志后台查询容易全表扫描。

修复方案：日期条件下推 SQL，使用 `chunkById/lazyById`，限制单轮处理量；新增迁移补组合索引，禁止改历史迁移。
