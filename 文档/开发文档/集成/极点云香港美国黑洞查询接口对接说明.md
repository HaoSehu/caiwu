# 极点云香港美国黑洞查询接口对接说明

- 文档性质：现行方向 / 上游页面接口抓取说明
- 对齐时间：`2026-04-24`
- 读者画像：后端对接开发、爬取封装开发、联调排障人员
- 适用范围：`https://blackhole.jdidc.cn/`

## 1. 先说结论

`blackhole.jdidc.cn` 这组页面和前一个 `cloud.jdidc.cn` 操作台不一样，它没有暴露出统一的 JSON API。

本次抓取结果显示，这里实际上只有两种可集成形态：

1. 服务端渲染 HTML 查询页
2. 外部流量图片直链

也就是说，如果你要集成到自己的系统：

- `香港1,2,3,5` 和 `美国2/3` 目前只能按“HTML 查询接口”对接
- `美国1` 目前只能按“图片查询接口”对接

没有发现现成的、结构化的、可直接对接的 JSON 返回接口。

## 4. `US23.php` 详细说明

### 4.1 查询方式

`US23.php` 不是前端 AJAX 页面，而是传统服务端渲染查询页。

页面表单特征：

- `method="get"`
- `action=""`，即提交到当前页面
- 输入框参数名：`query`

因此，它的真实调用方式是：

```http
GET /US23.php?query=154.40.43.100
```

### 4.2 已验证行为

我实际验证过：

```http
GET https://blackhole.jdidc.cn/US23.php?query=154.40.43.100
```

返回特征：

- HTTP 状态：`200`
- 返回类型：HTML 页面
- 没有额外 AJAX 请求
- 页面会直接把查询结果渲染进 HTML

对这个 IP 的返回结果是：

- 总记录数：`0`
- 查询结果：`0`
- 全部显示：`0`
- 提示文案：`未找到 IP "154.40.43.100" 的黑洞记录`

### 4.3 清空方式

页面在带查询参数时，会出现一个“清除搜索”链接：

```http
GET /US23.php?
```

等价于回到无查询状态。

### 4.4 页面可观测字段

当前样本没有命中真实黑洞记录，因此只能确定“无数据态”字段：

| 位置 | 含义 |
| --- | --- |
| `总记录数` | 当前结果总记录数 |
| `查询结果` | 当前查询命中的记录数 |
| `全部显示` | 当前显示的记录数 |
| `暂无黑洞记录 / 未找到 IP ... 的黑洞记录` | 无数据提示 |

从模板样式可以推断，这个页面在有数据时应该会渲染表格、状态徽章和剩余时间标签，但本次没有抓到真实样例，无法确认表格列名和字段映射。

### 4.5 对接建议

如果你必须接这个页面，建议按“HTML 查询页”封装，不要假设存在 JSON。

建议封装为：

1. 组装 URL：`/US23.php?query={ip}`
2. 拉取 HTML
3. 解析页面里的：
   - 统计卡片数值
   - 无数据提示
   - 若有表格，再解析表格行

建议你自己的内部结构统一成：

```json
{
  "ok": true,
  "query_ip": "154.40.43.100",
  "total": 0,
  "matched": 0,
  "displayed": 0,
  "records": [],
  "raw_html": "..."
}
```

### 4.6 `curl` 示例

```bash
curl -L 'https://blackhole.jdidc.cn/US23.php?query=154.40.43.100'
```

## 5. `US1.php` 详细说明

### 5.1 页面行为

`US1.php` 页面不是服务端查询黑洞记录，也不是 AJAX 查结构化数据。

它的前端逻辑非常简单：

1. 用户输入 IP
2. 点击“查询流量”
3. JS 直接把图片地址改成：

```text
https://do.yazzi.net/index/history?logo=0&ip={ip}
```

也就是它真正可用的“接口”只有这个图片地址。

### 5.2 前端代码实际逻辑

页面输入框：

- `id="ipInput"`
- `name="query"`

查询按钮：

- `id="searchBtn"`
- `type="button"`

点击按钮时执行：

```js
trafficImg.src = `https://do.yazzi.net/index/history?logo=0&ip=${ip}`;
```

这说明：

- 它不会提交表单到后端
- 不会发 JSON/AJAX 请求
- 不会返回结构化查询结果
- 只是把图片 URL 换掉

### 5.3 已验证行为

我实际抓到的请求如下：

页面初次加载时，前端会默认自动触发一次空 IP 请求：

```http
GET https://do.yazzi.net/index/history?logo=0&ip=
```

结果：

- 返回 `500`

输入 `8.8.8.8` 后点击查询，页面发出的请求是：

```http
GET https://do.yazzi.net/index/history?logo=0&ip=8.8.8.8
```

结果：

- 返回 `200`

### 5.4 重要异常

这个页面当前有一个明显前端 bug：

- 控制台报错：`ReferenceError: ipData is not defined`

原因是页面代码里引用了不存在的 `ipData` 变量。

不过这个错误不会阻止核心图片请求，因为图片地址仍然会被设置。

也就是说：

- 页面有 bug
- 但图片查询能力仍然可用

### 5.5 可对接能力

如果你要集成“美国1黑洞查询系统”，当前能稳定复用的只有图片端点：

```http
GET https://do.yazzi.net/index/history?logo=0&ip=8.8.8.8
```

因此你能做的事情更像：

1. 提供 IP 输入
2. 直接拼图片 URL
3. 把图片嵌入你的系统

而不是：

1. 调结构化 API
2. 拿 JSON
3. 自己绘图

### 5.6 `curl` 示例

```bash
curl -L 'https://do.yazzi.net/index/history?logo=0&ip=8.8.8.8'
```

### 5.7 对接建议

建议把 `US1.php` 视为“图片代理入口”，不要把它当标准 API。

推荐内部封装成：

```json
{
  "ok": true,
  "query_ip": "8.8.8.8",
  "image_url": "https://do.yazzi.net/index/history?logo=0&ip=8.8.8.8"
}
```

如果你未来需要结构化流量数据，只能继续追上游是否还有未公开的数据源接口。

## 6. 你后面集成时的真实选择

### 6.1 香港1,2,3,5 / 美国2/3

当前最稳妥的接法：

- 把 `US23.php` 当 HTML 查询页
- 通过 `query` 参数发 GET
- 解析 HTML 结果

优点：

- 这是当前页面真实在用的能力

缺点：

- HTML 抓取脆弱
- 上游改版容易失效
- 没有稳定字段契约

### 6.2 美国1

当前最稳妥的接法：

- 直接生成 `do.yazzi.net` 的图片 URL

优点：

- 简单
- 当前可用

缺点：

- 只有图，没有结构化数据
- 无法直接做统计分析或告警归档

## 7. 推荐封装方案

建议在自有系统里拆成两个上游能力，而不是强行统一成一个：

### 7.1 `BlackholeHtmlQueryClient`

用于：

- `US23.php`

建议方法：

- `queryUs23Blackhole(ip: string)`

职责：

- 发 `GET /US23.php?query={ip}`
- 返回原始 HTML
- 提取统计值和无数据提示

### 7.2 `TrafficImageClient`

用于：

- `US1.php`

建议方法：

- `buildUs1TrafficImageUrl(ip: string)`

职责：

- 只负责构造图片 URL
- 不负责解释图片内容

## 8. 风险与限制

### 8.1 上游命名不一致

首页名称和落地页功能不完全一致：

- `美国1黑洞查询系统` 实际是 `IP流量查询系统`
- `香港1,2,3,5` 和 `美国2/3` 指向同一页面

因此不要只信首页文案，要以真实 URL 和页面逻辑为准。

### 8.2 没有结构化 API

当前这组站点没有暴露出可直接消费的 JSON API。

这会带来两个后果：

1. HTML 抓取易碎
2. 图片端点无法直接做结构化分析

### 8.3 页面质量一般

已确认的页面问题：

- `US1.php` 初次加载时会自动请求空 IP 图片，触发 `500`
- `US1.php` 前端有 `ipData is not defined` 错误

所以你的系统不要依赖它前端页面本身，应直接复用最底层可用能力。

## 9. 后续建议

如果你后面要继续接这组上游，我建议顺序是：

1. 先把 `US23.php` 做成 HTML 查询封装
2. 把 `US1.php` 只当图片 URL 生成器
3. 再联系上游确认：
   - 香港1,2,3,5 与 美国2/3 是否真的共用同一数据源
   - 是否存在未公开的 JSON 接口
   - 是否能提供 `US1` 的结构化流量接口而不是图片

如果你要，我下一步可以直接在 `backend/app/Services/Upstream/` 里给你把这两类客户端封装出来。
