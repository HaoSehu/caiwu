# 极点云十堰宁波操作台接口对接说明

- 文档性质：现行方向 / 上游操作台实测抓取说明
- 对齐时间：2026-04-24
- 读者画像：后端对接开发、接口封装开发、联调排障人员
- 适用范围：
  - 宁波：`http://160.202.238.2:81/`
  - 十堰：`http://160.202.238.2:90/`
- 替代关系：本文件替代旧版基于 `cloud.jdidc.cn/addons?...` 的十堰/宁波说明，后续对接以 `81/90` 站点为准

## 1. 结论先说清楚

当前十堰和宁波的“操作工作台”真实入口已经不是旧的 `cloud.jdidc.cn/addons?...` 路径，而是：

- 宁波总入口：`http://160.202.238.2:81/`
- 十堰功能页：由 `81` 首页直接跳到 `90` 站点下的具体页面

当前可确认的接口分为三类：

1. **公开 JSON GET 接口**
   - 宁波黑洞：`/api/blackhole.php`
   - 宁波域名过白：`/api/gb.php`
   - 十堰黑洞：`/blackhole/blackholeapi.php`
   - 十堰攻击流量：`/flow/flowapi.php`
   - 十堰七层策略查询：`/use/find.php`
   - 十堰七层策略启停：`/use/request.php`
2. **同页 POST + HTML 结果渲染**
   - 十堰四层策略：`/through/through.php`
3. **页面容器**
   - `blackhole.php`、`flow.php`、`use.php`、`through.php` 本身主要负责 UI，真正可复用的是它们内部调用的接口或页面表单协议

本次实测未发现登录页、Cookie 前置要求或签名参数。至少对读接口来说，当前是可直接访问的公开入口。

## 3. 宁波接口

## 3.1 宁波黑洞查询

### 页面入口

- 页面地址：`http://160.202.238.2:81/blackhole.php`
- 页面表单：`GET` 当前页
- 表单字段：`ip`

页面只是演示壳，真正适合集成的是下面这个接口。

### 实际接口

```http
GET http://160.202.238.2:81/api/blackhole.php?ip={ip}
```

### 已实测返回

无效 IP：

```json
{"code":400,"message":"非法请求","data":null}
```

有效机房 IP、但当前没有黑洞记录：

```json
{"code":200,"message":"查询成功","data":[]}
```

已实测样例：

- `1.1.1.1` → `code=400`
- `114.66.31.123` → `code=200`, `data=[]`

### 当前可确认字段

| 字段 | 说明 |
| --- | --- |
| `code` | 业务状态码 |
| `message` | 返回提示 |
| `data` | 结果数组 |

说明：

- 当前实测没有拿到宁波黑洞命中样例，所以 `data[]` 内部记录结构仍未确认
- 集成时应先把 `data` 当作数组透传，不要提前写死明细字段

### 状态码

来自 `openapi.php` 与 `blackhole.php` 页面：

| 状态码 | 含义 |
| --- | --- |
| `200` | 查询成功 |
| `400` | 非法请求 |
| `401` | 用户名或密码错误 |
| `404` | 参数错误 |
| `429` | 请求过于频繁，请一分钟后重试 |
| `430` | 未查找到相关信息 |

- `gb.php` 页面本身就是一个同页 `GET` 表单

- `openapi.php` 已明确给出正式 API 地址、参数名和状态码
- 本次未执行真实过白提交，只确认了页面协议和官方公开说明

### 状态码

| 状态码 | 含义 |

### 页面侧图表计算规则

页面前端会按下列方式把原始值换算为 Mbps：

```js

```

页面最终展示的指标包括：

- 过滤前平均流量
- 过滤后平均流量
- 过滤前峰值
- 过滤后峰值

这说明该接口更像“规则模板 + 当前启用状态查询”，而不是严格的产品 IP 有效性校验接口。

## 4.4 十堰四层策略实验

### 页面入口

- 页面地址：`http://160.202.238.2:90/through/through.php`

### 查询协议

这不是独立 JSON API，而是同页 `POST`：

```http
POST http://160.202.238.2:90/through/through.php
Content-Type: application/x-www-form-urlencoded

action=search&search_ip={ip}
```

### 已实测页面行为

使用浏览器实际提交查询后，可确认：

- 请求方法是 `POST`
- 提交地址是同页 `through.php`
- 返回内容仍然是 HTML，不是 JSON
- 结果区会渲染“查询结果”表格

对 `160.202.238.52` 的实测结果为：

- 顶部提示：`查询成功`
- 结果文案：`共 0 条记录`
- 表头字段：
  - `规则 ID`
  - `规则名称`
  - `类型`
  - `动作`
  - `方向`
  - `状态`
  - `主机 IP`
  - `操作`

无结果时，表格正文会显示：`未查询到规则`

### 新增规则协议

页面“新增规则”表单同样是同页 `POST`：

```http
POST http://160.202.238.2:90/through/through.php
Content-Type: application/x-www-form-urlencoded

action=add&ip={ip}&mode={1|2}
```

参数说明：

- `mode=1`：屏蔽 UDP
- `mode=2`：屏蔽海外

### 当前边界

- 本次只执行了查询动作
- `add` 写操作没有实际提交
- 结果表格存在“操作”列，说明页面支持删除动作
- 但因为本次没有查到可删除规则，删除协议参数尚未捕获

## 5. 推荐封装方式

不建议再把十堰和宁波强行包装回旧的 `/addons` 体系，建议直接拆成两个上游客户端：

## 5.1 NingboConsoleClient

- 基础地址：`http://160.202.238.2:81`
- 只读接口：
  - `/api/blackhole.php`
- 写接口：
  - `/api/gb.php`

建议封装方法：

- `queryBlackhole(ip)`
- `addDomainWhitelist(ip, domain)`

## 5.2 ShiyanConsoleClient

- 基础地址：`http://160.202.238.2:90`
- JSON 接口：
  - `/blackhole/blackholeapi.php`
  - `/flow/flowapi.php`
  - `/use/find.php`
  - `/use/request.php`
- HTML 页协议：
  - `/through/through.php`

建议封装方法：

- `queryBlackhole(ip)`
- `queryAttackFlow(ip)`
- `queryLayer7Rules(ip)`
- `toggleLayer7Rule(ip, ruleId, enabled)`
- `queryLayer4Rules(ip)`（HTML POST + 解析器）
- `addLayer4Rule(ip, mode)`（写接口，需隔离验证）

## 5.3 四层策略必须单独做 HTML 解析

`through.php` 不是 JSON 接口，因此：

- 不适合直接并入统一 JSON Client
- 应单独做 `application/x-www-form-urlencoded` POST
- 再按 HTML 结果表格解析字段

解析时建议保留原中文列名，不要在第一版就过度抽象。

## 6. 与旧版 `cloud.jdidc.cn/addons` 的关系

当前应视为**已经切换到新入口**：
