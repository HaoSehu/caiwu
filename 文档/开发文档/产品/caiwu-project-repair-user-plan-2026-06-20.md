# Caiwu 项目修复方案（产品经理版）

- 文档性质：项目级修复方案
- 对齐时间：`2026-06-20`
- 读者：产品、项目负责人、研发、测试、客服、运营

## 1. 方案摘要

当前项目的主要问题不是单点功能缺失，而是系统真相、文档口径、交易主链路和权限边界没有同时收口。仓库内现役应用已经明确分为 `backend`、`frontend-admin-v3`、`frontend-user-v3-www`、`frontend-user-v4-console` 和 `shared`，但文档、历史路径和部分业务表述仍存在漂移。修复工作的目标，不是做一轮大而全重构，而是先建立可发布基线，再优先打通账单支付与服务开通两条主链路，最后收权限和体验一致性。  

## 2. 当前判断

### 2.1 当前现状

- 官网与购买入口由 `frontend-user-v3-www` 承担。
- 用户控制台由 `frontend-user-v4-console` 承担，核心路径是 `/client/*`。
- 管理端由 `frontend-admin-v3` 承担。
- 后端以 Laravel 12 为核心，账单、支付、开通、工单、实名、返佣等能力均已存在。
- 生产异步任务由 `schedule:run` 驱动，最坏延迟约 60 秒。

### 2.2 主要问题

- 文档入口和目录口径不稳定，存在旧前端名称和旧路径残留。
- 用户侧“账单”和“订单”的语言边界没有完全收口，容易误导客服、运营和联调。
- 支付、充值、混合支付、退款、重复回调、支付后开通等高风险链路需要重新以当前代码为准验通。
- 服务开通是异步过程，但部分页面和说明容易让用户误解为即时完成。
- 管理端权限虽然已有基础能力，但与岗位、菜单、按钮、敏感操作之间还需要形成更清晰的业务矩阵。

## 3. 修复目标

- 建立当前版本可发布、可回归、可说明的项目基线。
- 统一项目现状说明，清理旧路径、旧前端命名和过时文档入口。
- 确保用户主链路稳定：选品 -> 开账单 -> 支付/充值 -> 开通服务 -> 控制台管理 -> 续费/升级/工单。
- 明确用户、客服、运营、管理员看到的状态和术语。
- 让研发和测试能按统一范围做回归，不再被历史结构误导。

## 4. 方案选项

### 方案 A：全仓同步大修

- 核心思路：前后端、文档、权限、数据口径一起全面收口。
- 影响范围：`backend`、三个前端、`shared`、文档、部分历史脚本。
- 优点：一次性把结构问题和业务问题一起解决。
- 风险：脏工作区和历史改动较多，极易把不在本轮发布范围的内容混进来，回归成本高。
- 粗略工作量：大。

### 方案 B：分阶段主链路修复

- 核心思路：先收住当前真相，再依次修复财务链路、交付链路、权限与体验。
- 影响范围：按阶段分别落在文档、后端、官网、用户控制台、管理端与共享状态层。
- 优点：节奏清晰，便于每一阶段单独回归，能尽快形成可发布基线。
- 风险：需要严格执行边界管理，不能中途重新发散成全仓重构。
- 粗略工作量：中到大。

### 推荐方案

推荐采用方案 B。当前仓库改动面已经较大，先修“真相”和“主链路”比全面铺开更可靠，也更符合发布节奏。

## 5. 分阶段修复方案

### 阶段 0：基线冻结

- 目标：明确本轮发布范围，避免把未确认改动带入修复。
- 主要动作：盘点当前变更，按“本轮发布内”“暂不发布”“异常删除”“生成物/临时产物”分类。
- 影响对象：项目负责人、研发、测试。
- 交付物：一份发布范围清单。
- 阶段验收：没有“来源不明但被带进发布”的文件。

### 阶段 1：文档与路径真相修复

- 目标：让项目结构、当前应用分工和核心路径对齐代码现实。
- 主要动作：恢复文档入口；清理 `frontend-client`、`frontend-user-v3-console`、`frontend-admin` 等过时名称；统一说明 `frontend-user-v3-www` 与 `frontend-user-v4-console` 的职责边界。
- 影响对象：产品、研发、测试、客服、运营。
- 交付物：当前结构说明、产品修复方案、执行文档。
- 阶段验收：旧名称只允许出现在“历史说明”语境，不再作为当前项目路径使用。

### 阶段 2：财务主链路修复

- 目标：确保账单、支付、充值、退款、回调与财务流水可用且口径一致。
- 主要动作：重新验收新购账单、余额支付、支付宝支付、混合支付、充值、取消未支付、重复回调、超时回调、退款、账单与流水同步。
- 影响对象：用户、财务、客服、运营。
- 交付物：一套可回归的财务主链路清单与通过结果。
- 阶段验收：用户可理解账单状态；支付后状态不混乱；第三方支付记录、余额流水和账单状态一致。

### 阶段 3：开通与服务实例链路修复

- 目标：确保支付成功后的开通、续费、升级、流量包和控制台操作符合真实交付状态。
- 主要动作：统一用户可见状态，明确 `待处理 / 开通中 / 已开通 / 失败待处理`；补齐失败补偿与人工接管说明；核对服务详情页、实例控制台、续费和升级续接链路。
- 影响对象：用户、客服、运维、管理员。
- 交付物：服务交付状态口径和关键页面验收结果。
- 阶段验收：支付成功不丢单，失败有补偿路径，异步延迟被正确表达。

### 阶段 4：管理端权限与运营闭环修复

- 目标：让角色、权限码、菜单和敏感操作形成业务上可解释的边界。
- 主要动作：梳理 `super_admin`、财务、运维、客服、产品、供应商管理员、审计只读等角色矩阵；核对退款、人工开通、登录即用户、供应商配置、工单接管等高风险动作。
- 影响对象：后台管理员、财务、客服、运维、审计。
- 交付物：岗位权限矩阵与回归清单。
- 阶段验收：角色只看到该看的、只能做该做的。

### 阶段 5：术语与体验统一

- 目标：统一用户感知，减少客服与联调误判。
- 主要动作：用户侧统一使用“账单”口径；统一状态文案、空态、失败态、处理中提示；固定官网与控制台跳转边界。
- 影响对象：用户、客服、运营。
- 交付物：统一术语与状态说明。
- 阶段验收：用户端不再混用“订单/账单”主语，状态表达与真实系统一致。

## 6. 不在本轮优先范围的事项

- 不做整仓风格统一或无关重构。
- 不把历史迁移、历史脚本或旧解包目录作为当前业务真源。
- 不在未确认发布范围前直接清理所有脏工作区改动。
- 不把“文档修复”扩展成“重写全部历史方案文档”。

## 7. 风险与依赖

- 当前工作区存在大量未归档改动，若不先冻结范围，后续回归成本会持续放大。
- 财务链路和交付链路都涉及异步处理，验收时必须把延迟和幂等作为产品事实处理。
- 权限矩阵若不先明确岗位视角，前后端只能按技术码值修补，无法形成稳定规则。
- 旧文档路径残留较多，若不先清理，新的执行人员仍会被历史名称带偏。

## 8. 项目验收口径

- 文档口径一致：现役应用、职责边界、路径命名、术语解释一致。
- 财务口径一致：账单、支付、充值、退款、回调、流水之间无冲突。
- 交付口径一致：支付后的服务状态、延迟说明、失败补偿路径清晰。
- 权限口径一致：角色、菜单、按钮、敏感动作边界清楚。
- 用户体验一致：状态提示真实，入口稳定，客服可按统一语言解释。

## 9. 建议执行顺序

1. 先做基线冻结和文档真相修复。
2. 再只打财务主链路。
3. 然后修开通与服务实例链路。
4. 最后收权限矩阵和术语体验统一。

这轮修复的原则只有一句话：先把“真实结构”和“交易主链路”修成可发布状态，再处理边角问题和体验细节。
