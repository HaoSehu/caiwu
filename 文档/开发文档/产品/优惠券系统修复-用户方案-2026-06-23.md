# 优惠券系统修复 — 产品方案

> 本文档写给人类阅读，不含技术术语。配套的 Agent 执行文档请见《优惠券系统修复-Agent执行方案-2026-06-23.md》。

## 背景

我们最近做了优惠券（包括活动券）全链路的体检，发现 4 个会影响账目准确的核心问题，以及若干影响稳定性和用户体验的次要问题。如果继续不修，会出现：

- 用户领取的优惠券"看上去还能用"，其实早已用过，下单时报错；
- 用户退款后，同一张优惠券可能被反复使用，运营反复补贴；
- 仅限首次购买用的"新人券"，被退款后变成可再次领用，新人福利被薅；
- 后台偶尔会看到"已使用张数"和"实际已支付张数"对不上，对账困难。

本次修复目标是把优惠券从领、用、退、作废 4 个动作的全过程都改清楚，并给每张用户领取到的优惠券配一个独立编号（uid），方便后续做扫码核销、转赠等扩展。

## 目标

做完后，用户和管理员将看到：

- 每张已领取的优惠券都有一个唯一样编号，可在详情页看到
- "已使用 / 已作废 / 可使用" 三种状态清晰区分，不再互相混淆
- 退款时，普通券恢复可用，但"限首单"的券一旦用过就不可再恢复（避免薅新人福利）
- 用户在下单填写资料时，点一下就锁定该优惠券 10 分钟，杜绝多窗口并发抢单
- 后台对账数据与实际核销状态一致，差异 < 1%

## 方案概述

### 三步走

1. **第一步：修账目**（核心，必做）
   给已领取券表增加 4 列（实例编号、核销时间、作废时间、预占截止时间），把"已使用"状态明确写进数据库，不再靠反查账单表来"猜"。

2. **第二步：让链路稳一点**（健壮性）
   把"支付成功后再补写券状态"这个动作，从"很容易丢"的请求结束后回调，迁移到可重试的队列任务。同时给券模板加外键约束，防止误删券种留下孤儿数据。

3. **第三步：前端展示补全**（体验）
   把"可使用 X/Y 次""限首单""剩余 N 张"等信息补到卡片上；把官网跳到控制台时通过网址兜底传券ID，避免手机浏览器跨域 sessionStorage 失效丢券。

### 业务规则默认假设（请确认）

| 问题 | 我们的建议默认值 | 说明 |
|-----|----------------|------|
| 退款后是否返还次数？ | **返还** | 与主流电商一致，对用户友好 |
| "限首单"券退款后能否再用？ | **不能** | "首单"是身份判定，用过一次就锁死 |
| 预占策略选哪种？ | **加预占截止时间字段** | 比靠锁行更可控，可自动过期 |
| 异步补写状态怎么落地？ | **用队列任务** | 持久化、可重试、不丢账 |

如有任一项与你的预期不符，请在执行前告知调整。

## 功能说明

| 编号 | 功能点 | 说明 | 谁看 |
|------|--------|------|------|
| F1 | 券实例独立编号 | 用户领取到的每张券都有一个唯一串如 `uc_xxxx`，可在券详情页看到 | 用户 |
| F2 | 三状态展示 | 卡片上明确显示"可使用 / 已使用 / 已作废"，不再只有"可用"一种标签 | 用户 |
| F3 | 使用次数标识 | 卡片上显示"可使用 X/Y 次"或"不限次"，限首单的券显示"限首单" | 用户 |
| F4 | 下单预占 10 分钟 | 用户在结算页选了券后，券被锁定 10 分钟，期间其他窗口无法用同一券 | 用户（无感知） |
| F5 | 退款返还普通券 | 普通券退款后自动恢复可用；已使用状态自动清除 | 用户 |
| F6 | 限首单券退款不返还 | 限首单券退款后仍为"已使用"，避免被反复薅 | 用户 |
| F7 | 后台作废券 | 管理员可手动作废用户已领的券，作废后状态置"已作废"、记录作废时间 | 管理员 |

| F9 | 外键约束 | 券模板被引用时禁止删除，避免孤儿数据 | 管理员 |
| F10 | 跨域跳转券恢复 | 官网选券后跳控制台，券ID 同时通过网址兜底传，跨子域不再丢券 | 用户 |

## 用户操作流程

### 用户视角

1. 在控制台点"优惠券中心"
2. 默认看到的就是"可使用"分类
3. 每张卡片右上角有状态标签（可使用 / 已使用 / 已作废），下方有"可使用 X/Y 次"或"限首单"等说明
4. 用户点"详情"可看到券实例编号 `uc_xxxx`
5. 进结算页选券后，券即被锁定 10 分钟，去其他窗口也不会重复扣
6. 支付成功，券自动变"已使用"
7. 之后若发生退款，普通券自动恢复"可使用"；如果当初是限首单券，则仍是"已使用"

### 管理员视角

1. 进入后台优惠券管理
2. 找到任意已发放的券实例，可点"作废"
3. 系统立即把该券状态置为"已作废"、并记录作废时间
4. 对账页面：已使用张数与实际已支付账单数差异稳定在 1% 以内

## 页面/交互变化

- **优惠券中心**（用户端控制台）：
  - 卡片新增"使用次数 / 限首单 / 剩余张数"小标签 chip
  - 状态标签从原来的"可使用 / 不可用 / 已过期"扩展为"可使用 / 已使用 / 已作废 / 已用完 / 已过期"
  - 详情弹层新增"券实例编号"字段
  - 默认筛选标签从"全部"调整为"可使用"

- **结算页**（官网 + 控制台续费）：
  - 选择券后即触发 10 分钟预占（用户无感知）
  - 金额变动时显示"该券已被锁定至 HH:mm"

- **后台优惠券管理**：
  - 用户已领券列表新增"作废"操作
  - 券模板删除操作在存在已领记录时被阻止

## 影响范围

- **对用户**：体验更清晰，状态不再误读；退款后能恢复已使用的普通券；跨子域跳转不再丢券
- **对管理员**：账目更准、对账不再出现"幻觉数据"；可手动作废错发的券
- **对现有功能**：完全向后兼容；老数据通过一次性脚本回填编号和状态，不需用户重领
- **对结算链路**：下单、支付、退款流程会经过预占字段，需做回归测试

## 不做的事（范围外）

- 不引入新的券类型：暂不做满赠、阶梯券、组合券
- 不做转赠与扫码核销功能（本次仅预留 uid 字段做扩展）
- 不做优惠券与会员等级联动（后续单独规划）
- 不重构结算与账单的整体架构（仅打通券状态机器）
- 不改优惠券广场（公开领券）的领取流程
- 不引入分布式锁框架

## 验证方式

请你在上线后用以下场景手测：

1. 领一张券 → 卡片显示"可使用 1/1 次"
2. 用该券支付 → 卡片变为"已使用"
3. 申请退款（普通券）→ 卡片回到"可使用"
4. 用"限首单"券支付后退款 → 卡片仍是"已使用"
5. 在两个浏览器标签同时用同一券下单 → 只有一个下单成功
6. 在官网选好券后跳转到控制台 → 能看到券 ID 并继续结算
7. 管理员手动作废某张券 → 用户端立刻显示"已作废"

如有任何一点未达预期，立即反馈由开发回滚或人工补单。
