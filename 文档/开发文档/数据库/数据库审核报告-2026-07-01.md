## 结论

当前数据库初始化方案 **可以作为上线部署入口使用**，推荐使用：

```bash
python backend/scripts/install_db.py
```

上线前必须满足：

1. `backend/.env` 已正确配置 `APP_ENV`、`DB_*`、`APP_KEY` 或允许脚本生成 `APP_KEY`。
2. 生产环境 `APP_ENV=production` 时必须配置 `INSTALL_ADMIN_PASSWORD`，且不能使用默认弱口令。
3. 目标数据库为空库时，脚本会通过 `backend/database/schema/mysql-schema.sql` 初始化结构；非空库时只跑增量迁移。
4. 当前标准迁移目录中的 70 个迁移文件均已包含在 Baseline 的 `migrations` 记录中，新库导入 Baseline 后不会重复执行这些迁移。

## 四、审核总结

### 结构一致性

**Schema Baseline 与实库结构快照一致**。52 张表、684 个字段、258 个索引、22 个外键均无差异。`AUTO_INCREMENT` 属于运行期计数，日志表会随系统运行变化，不影响初始化脚本可用性。

### 数据健康度

- **核心业务数据完整**：用户、订单、账单、支付、服务等核心表数据量合理，无需干预。
- **大表风险**：`operation_logs`（51 MB）和 `schedule_run_logs`（13 MB）累积量大，应使用现有日志清理/归档能力处理过期数据。
- **表遗留问题**：`balance_logs` 是历史旧余额流水，当前查询侧已转向 `account_transactions`，但清理前必须完成引用确认和归档。
- **新表未接入**：`activity_logs` 表与服务已存在，但当前未发现业务调用入口，因此暂无数据。
- **仓库工件**：根目录遗留的大 SQL dump 文件应确认备份后移出仓库；该文件可能包含敏感业务数据。

### 风险等级

| 风险 | 等级 | 说明 |
|------|:----:|------|
| 数据丢失 | 低 | 核心业务表完整；但任何清理前都必须先归档并确认备份 |
| 性能风险 | 中 | `operation_logs` 和 `schedule_run_logs` 持续增长 |
| 迁移风险 | 低 | 标准迁移文件均已包含在 Baseline 记录中；历史 baseline 记录中有 2 个迁移文件路径/缺失问题需记录 |
| 安全隐患 | 中 | 根目录 SQL dump 可能包含业务/用户数据，应移出仓库并限制访问 |
