## 10. 回滚策略

Phase 1 新增结构的回滚策略：

- 新表迁移必须提供 `down()`，按外键依赖反向删除。
- 给旧表新增的 `plugin_id/gateway_key/driver_key/trace_id` 字段，必须能单独 drop。
- Phase 1 不删除任何旧字段，因此失败时可回滚新增结构并继续旧链路运行。

Phase 2 回填的回滚策略：

- 回填命令必须支持 `--dry-run`。
- 正式执行前输出映射报告。
- 正式写入必须记录 batch id。
- 回填数据应可按 batch id 清除新表记录或重跑覆盖。
- 不允许修改 `payments.amount/status/trade_no` 等财务核心字段。

Phase 3/4 代码切换的回滚策略：

- 在 Phase 4 删除旧字段前，旧字段保留只作为回滚救援数据。
- 代码切换失败时，优先回滚代码；不得通过手工改数据库恢复。

Phase 5 破坏性清理的回滚策略：

- 删除旧字段前必须确认 Phase 2 回填报告、Phase 3 后端测试、Phase 4 前端构建全部通过。
- 删除字段迁移必须保留反向 DDL，但反向迁移只能恢复字段结构，不能恢复已删除前未备份的数据。

## 11. Phase 0 结论

- Phase 0 只读冻结已完成。
- 当前最大风险是 `services.provision_data.provider` 中仍有 `hosting_panel_api` 残留，但供应商和商品已是 `mofang_finance_api`。
- `payments.gateway` 中历史 `balance/manual` 不能物理删除，也不能纳入新第三方插件调用。
- `gateway_logs.gateway=alipay_f2f` 需要在回填时规范到业务 key `alipay` 并关联支付插件。
- Phase 1 可以进入新增结构设计，但执行迁移前必须先处理或确认既有 pending migration。
