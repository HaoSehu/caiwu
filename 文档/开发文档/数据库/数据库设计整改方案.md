- 依据文档：`文档/开发文档/数据库/MySQL数据库设计提示词.md`
- 当前基线：MySQL `idc`，60 张表，80 个数据库级外键（对齐 `migration-output/idc-current-table-structure.md`，同步时间 2026-07-17 01:26:14 +08:00），结构快照见 `文档/开发文档/数据库/当前数据库结构.md`

## 1. 背景

本方案用于把当前数据库逐步调整到 `MySQL数据库设计提示词.md` 定义的设计标准。该提示词的核心要求是：同一事实只存一处，同类概念优先复用一张表，关系字段应声明数据库级外键，表和字段必须可读可维护，索引需要服务真实查询而不是越多越好。

当前库已完成一批基础治理：核心交易链路已有部分外键，余额唯一真源已收敛到 `user_accounts`，旧 `balance_logs` 和 `servers` 已清理，运行日志归档能力已存在。继续整改时不应推翻这些有效成果，应在真实代码路径和实库数据校验后分阶段推进。

## 2. 当前主要问题

### 2.1 商品分组结构（当前基线）

阶段 4 原计划将商品分组结构真源收敛到 `product_groups`。但当前文档基线（`migration-output/idc-current-table-structure.md`）显示：

- 商品分组仍为 `first_product_groups` / `second_product_groups` / `third_product_groups` 三张物理表。
- 本快照**未包含** `product_groups` 自引用表。
- `products.product_group_id` 外键指向 `third_product_groups.id`。
- 三级层级由 `first_product_group_id` 和 `second_product_group_id` 两条外键显式表达，不保留视图或自引用兼容层。

### 2.2 消息日志表已统一

阶段 3 已将 `email_logs`、`sms_logs`、`notification_logs` 合并为 `message_logs`。统一表通过 `channel` 区分短信和邮件，保留插件、驱动、链路追踪、模板、接收者、内容、状态、错误、发送时间和来源快照字段。

阶段结果：
- `message_logs` 当前承接 1,716 条历史发送日志。
- 邮件、短信发送链路只写 `message_logs`。
- 后台日志列表、详情、清理、归档、插件回填和用户日志查询已切到 `message_logs`。
- 旧三表和旧模型已删除；历史迁移文件不改。

### 2.3 外键覆盖已完成可补项

阶段 2 已新增 `php artisan db:audit-foreign-keys --strict`，并将所有 `*_id` 字段分为已有 FK、可补 FK、多态/历史快照不可补 FK 三类。本阶段新增 35 个数据库级外键后，当时实库已有 83 个 FK。按当前 `migration-output` 快照，外键数量为 80；商品分组仍为三级物理表，未切换到 `product_groups` 自引用结构。

仍保留为不可补 FK 的字段包括 `{type, id}` 多态关系、外部平台 ID、批次号、`trace_id`、历史运行快照等。它们已在阶段 2 执行记录中说明原因。

### 2.4 审计链路存在历史缺口

阶段 1 执行前，核心审计命令显示以下历史缺口：

| 指标 | 缺失数量 |
| --- | ---: |
| `invoices.trace_id_missing` | 611 |
| `payments.trace_id_missing` | 191 |
| `services.trace_id_missing` | 90 |
| `account_transactions.trace_id_missing` | 674 |

影响：
- 财务、支付、服务生命周期排障时无法完整串联请求、账单、支付和流水。
- 后续把 `trace_id` 改为更强约束前必须先回填历史数据。

阶段 1 已于 2026-07-08 执行 `php artisan db:backfill-trace-id --execute --json` 完成回填，回填后 `db:audit-core` 中四项 `trace_id_missing` 均为 `0`。后续阶段按已回填后的实库继续推进。

### 2.5 注释和索引治理未完成

当前结构快照中大量表仍显示 `表注释：—`，不少字段注释也为空。索引方面，存在若干需要复核的覆盖关系，例如：
- `invoices_user_id_index` 与 `invoices_user_status_created_idx`、`invoices_user_status_id_idx`
- `services_user_id_index` 与 `services_user_status_id_idx`
- `operation_logs` 和 `schedule_run_logs` 等大表上的日志查询索引

这些索引不应直接删除，必须先用真实查询、`EXPLAIN` 和慢查询数据确认。

## 3. 整改目标

1. 商品分组保持一级、二级、三级三张物理表；商品只保存一个 `product_group_id` 指向三级分组，完整路径通过明确的外键关系解析。
2. 邮件、短信、通知发送日志最终收敛为统一 `message_logs` 表，用 `channel` 区分渠道。
3. 将可声明外键的逻辑外键分批转为数据库级外键；多态关联保留 `{subject_type, subject_id}` 模式并明确注释。
4. 回填核心业务表历史 `trace_id`，新增写入路径继续保证审计字段一致。
5. 补齐表注释、字段注释和枚举值说明，统一索引命名和索引用途说明。
6. 删除确认无调用方的旧表、旧字段、旧模型和旧索引，不保留长期兼容层。

## 4. 非目标

- 不在本方案中直接修改历史 migration。
- 不一次性重写全部业务模型、接口和前端展示。
- 不改变旧接口响应契约；涉及新接口时按 `/api/v2/*` 规范另行设计。
- 不物理删除 `payments` 历史记录。
- 不把运行日志归档、审计日志双写和商品分组重构混在同一个迁移里。

### 阶段 4：商品三级物理分组收口

- `first_product_groups`、`second_product_groups`、`third_product_groups` 分别表达一级、二级、三级分组。
- 二级通过 `first_product_group_id` 关联一级，三级通过 `second_product_group_id` 关联二级；两条关系均由数据库外键约束。
- `products` 只保留 `product_group_id`，且外键指向 `third_product_groups.id`；不保留一、二、三级分组冗余列。
- 完整路径通过三级模型关系链解析，不使用递归查询或兼容视图。

### 阶段 5：快照与日志体系复核

目标：继续按提示词检查“快照/历史版本”和“日志/记录”类表是否还有可合并空间。

重点对象：
- `service_runtime_snapshots`
- `service_connection_snapshots`
- `service_provision_attempts`
- `operation_logs`
- `activity_logs`
- `schedule_run_logs`
- `schedule_task_runs`

处理原则：
- 如果结构一致且查询路径相近，优先合并为一张表加 `snapshot_type` 或 `action`。
- 如果写入热点、保留周期、索引模式明显不同，可以保留拆表，但必须在文档中说明原因。
- 已有归档策略的日志表先验证保留周期和查询性能，不为了形式统一破坏运维可控性。

验收：
- [x] 每张保留拆分的日志/快照表都有明确理由。
- [x] 可合并项已形成单独 migration 任务。
- [x] 归档命令和调度策略仍能覆盖大表增长。

阶段 5 结论：

- `service_runtime_snapshots`、`service_connection_snapshots`、`service_provision_attempts` 保留拆表：运行态快照、连接凭据/入口快照、开通尝试日志的写入时机、敏感字段语义、查询索引和保留周期不同。
- `operation_logs` 与 `activity_logs` 暂不合并：当前由 `OperationLogService` 双写，需完成一个完整账期验收、后台查询切换和归档口径确认后，另起 migration 停写旧表。
- `schedule_run_logs` 与 `schedule_task_runs` 暂不合并：前者服务现有调度日志查询/清理，后者绑定 `schedule_ticks` 表达心跳调度单任务状态。后续如统一，必须先改读路径和保留策略。
- 归档覆盖现状：`operation_logs` 每月归档保留 90 天，`schedule_run_logs` 每周清理保留 30 天，`message_logs` 已接入日志归档能力。

## 6. 风险与控制

| 风险 | 影响 | 控制方式 |
| --- | --- | --- |
| 商品分组重构影响官网、后台、订单快照 | 高 | 单独阶段实施，先做路径一致性测试，再删除旧字段 |
| 消息日志合并影响通知查询和排障 | 中 | 先迁移数据并更新查询入口，确认无调用方后删除旧表 |
| 补外键时发现历史孤儿数据 | 中 | 每个 FK 前先跑孤儿检查，有孤儿先修数据再加约束 |
| 删除索引导致查询退化 | 中 | 删除前保留 EXPLAIN 证据，必要时按查询重建复合索引 |
| 注释补全造成大迁移噪音 | 低 | 按业务域分批提交，每批只改注释和少量索引 |

## 7. 必须遵守的执行规则

- 每个阶段独立提交，不把结构迁移、代码切换、文档刷新混成一个提交。
- 迁移只能新增文件，禁止修改历史 migration。
- 每个子任务完成后执行受影响范围测试；阶段完成后执行完整受影响验证。
- 删除旧表、旧字段、旧模型前必须先用 `rg` 确认无调用方。
- 所有表结构变更后刷新 `当前数据库结构.md` 和 `数据库文档.md`。
- 不保留长期兼容层；商品分组以三级物理表为唯一结构真源，不创建同名兼容视图或外链重定向层。
- 财务、支付、订单、服务相关改动必须额外验证幂等、事务和审计字段。

## 8. 后续开放问题

1. 商品分组固定为三级物理表。若未来业务需要超过三级，必须重新评估表结构和 API，而不是在现有三表上附加隐式层级。
2. 当前有 120 条有效商品尚未绑定三级分组。需先确认 `product_type`、`service_type_code` 和业务菜单编码的映射，再执行一次性回填；商品不允许绑定非叶子分组。
3. `message_logs` 只承接发送通道日志；`user_notifications` 继续表达用户站内收件箱状态。
4. `operation_logs`、`activity_logs`、`schedule_run_logs`、`schedule_task_runs` 的长期保留周期和查询入口仍需按真实使用数据复核。
5. 当前 `db:audit-foreign-keys --strict` 已做到 0 个可补 FK、0 个未分类字段；后续新增 `*_id` 字段必须同步补映射或外键。
