# 数据库设计整改方案

- 文档状态：分阶段执行中；阶段 0-2 已完成，记录见 `文档/开发文档/数据库/数据库整改阶段0-1执行记录.md`、`文档/开发文档/数据库/数据库整改阶段2执行记录.md`
- 编写日期：2026-07-08
- 依据文档：`文档/开发文档/数据库/MySQL数据库设计提示词.md`
- 当前基线：MySQL `idc`，61 张表，83 个数据库级外键，结构快照见 `文档/开发文档/数据库/当前数据库结构.md`

## 1. 背景

本方案用于把当前数据库逐步调整到 `MySQL数据库设计提示词.md` 定义的设计标准。该提示词的核心要求是：同一事实只存一处，同类概念优先复用一张表，关系字段应声明数据库级外键，表和字段必须可读可维护，索引需要服务真实查询而不是越多越好。

当前库已完成一批基础治理：核心交易链路已有部分外键，余额唯一真源已收敛到 `user_accounts`，旧 `balance_logs` 和 `servers` 已清理，运行日志归档能力已存在。继续整改时不应推翻这些有效成果，应在真实代码路径和实库数据校验后分阶段推进。

## 2. 当前主要问题

### 2.1 商品分组三表与新规范冲突

当前商品分组模型仍由 `first_product_groups`、`second_product_groups`、`third_product_groups` 三张表表达，`products` 通过三组外键指向不同层级。提示词明确把该模型列为反例，目标模型应是一张 `product_groups` 表通过 `parent_id` 自引用表达层级。

影响：
- 层级深度被硬编码为三级，后续扩展需要改表、改模型、改接口。
- 二级、三级表字段高度重复，索引和外键也需要重复维护。
- 商品完整路径需要依赖多列拼接，迁移、导入和前端展示都更容易产生分叉逻辑。

### 2.2 消息日志表发散

当前存在 `email_logs`、`sms_logs`、`notification_logs` 三张发送日志表。三者都包含插件、驱动、链路追踪、模板、接收者、内容、状态、错误、发送时间等相近字段。提示词要求该类日志用 `message_logs + channel` 统一表达。

影响：
- 邮件、短信、站内/通知日志的查询、归档、追踪和统计需要分别实现。
- 相同索引和注释规则在多张表重复维护。
- 后续新增推送、微信等渠道时容易继续新建相似表。

### 2.3 外键覆盖已完成可补项

阶段 2 已新增 `php artisan db:audit-foreign-keys --strict`，并将所有 `*_id` 字段分为已有 FK、可补 FK、多态/历史快照不可补 FK 三类。本阶段新增 35 个数据库级外键后，实库已有 83 个 FK，可补 FK 为 0，未分类字段为 0。

仍保留为不可补 FK 的字段包括 `{type, id}` 多态关系、外部平台 ID、批次号、`trace_id`、历史运行快照等。它们已在阶段 2 执行记录中说明原因。

### 2.4 审计链路存在历史缺口

阶段 1 执行前，核心审计命令显示以下历史缺口：

| 指标 | 缺失数量 |
| --- | ---: |
| `invoices.trace_id_missing` | 611 |
| `payments.trace_id_missing` | 191 |
| `services.trace_id_missing` | 90 |
| `account_transactions.trace_id_missing` | 674 |

影响：
- 财务、支付、服务生命周期排障时无法完整串联请求、账单、支付和流水。
- 后续把 `trace_id` 改为更强约束前必须先回填历史数据。

阶段 1 已于 2026-07-08 执行 `php artisan db:backfill-trace-id --execute --json` 完成回填，回填后 `db:audit-core` 中四项 `trace_id_missing` 均为 `0`。后续阶段按已回填后的实库继续推进。

### 2.5 注释和索引治理未完成

当前结构快照中大量表仍显示 `表注释：—`，不少字段注释也为空。索引方面，存在若干需要复核的覆盖关系，例如：
- `invoices_user_id_index` 与 `invoices_user_status_created_idx`、`invoices_user_status_id_idx`
- `services_user_id_index` 与 `services_user_status_id_idx`
- 二级、三级商品分组上的多组前缀相近索引

这些索引不应直接删除，必须先用真实查询、`EXPLAIN` 和慢查询数据确认。

## 3. 整改目标

1. 商品分组最终收敛为一张自引用 `product_groups` 表，商品只保存一个当前分组引用，完整路径通过递归关系解析。
2. 邮件、短信、通知发送日志最终收敛为统一 `message_logs` 表，用 `channel` 区分渠道。
3. 将可声明外键的逻辑外键分批转为数据库级外键；多态关联保留 `{subject_type, subject_id}` 模式并明确注释。
4. 回填核心业务表历史 `trace_id`，新增写入路径继续保证审计字段一致。
5. 补齐表注释、字段注释和枚举值说明，统一索引命名和索引用途说明。
6. 删除确认无调用方的旧表、旧字段、旧模型和旧索引，不保留长期兼容层。

## 4. 非目标

- 不在本方案中直接修改历史 migration。
- 不一次性重写全部业务模型、接口和前端展示。
- 不改变旧接口响应契约；涉及新接口时按 `/api/v2/*` 规范另行设计。
- 不物理删除 `payments` 历史记录。
- 不把运行日志归档、审计日志双写和商品分组重构混在同一个迁移里。

### 阶段 3：统一消息日志表

目标：用 `message_logs` 统一承接邮件、短信和通知发送日志。

目标结构原则：
- `channel` 区分 `email`、`sms`、`notification`，后续渠道继续复用该字段。
- `recipient` 统一表达邮箱、手机号、用户通知目标或第三方 openid。
- `subject` 对短信等无标题渠道可为空。
- `params_json` 只保存模板变量和第三方返回中不稳定的结构，COMMENT 中写明 key 语义。
- `plugin_id`、`driver_key`、`trace_id`、`status`、`sent_at`、`error_msg` 为统一字段。

### 阶段 4：商品分组自引用重构

目标结构原则：

- 商品表只保留一个 `product_group_id` 指向当前叶子或业务确认的所属分组。
- 完整路径通过递归父级链解析，不再在商品表保存一、二、三级分组列。
- 若需要排序、可见性、slug 唯一性，索引围绕 `(parent_id, is_visible, sort_order)` 和 `(parent_id, slug)` 设计。

## 6. 风险与控制

| 风险 | 影响 | 控制方式 |
| --- | --- | --- |
| 商品分组重构影响官网、后台、订单快照 | 高 | 单独阶段实施，先做路径一致性测试，再删除旧字段 |
| 消息日志合并影响通知查询和排障 | 中 | 先迁移数据并更新查询入口，确认无调用方后删除旧表 |
| 补外键时发现历史孤儿数据 | 中 | 每个 FK 前先跑孤儿检查，有孤儿先修数据再加约束 |
| 删除索引导致查询退化 | 中 | 删除前保留 EXPLAIN 证据，必要时按查询重建复合索引 |
| 注释补全造成大迁移噪音 | 低 | 按业务域分批提交，每批只改注释和少量索引 |

## 7. 必须遵守的执行规则

- 每个阶段独立提交，不把结构迁移、代码切换、文档刷新混成一个提交。
- 迁移只能新增文件，禁止修改历史 migration。
- 每个子任务完成后执行受影响范围测试；阶段完成后执行完整受影响验证。
- 删除旧表、旧字段、旧模型前必须先用 `rg` 确认无调用方。
- 所有表结构变更后刷新 `当前数据库结构.md` 和 `数据库文档.md`。
- 不保留长期兼容层；完成切换后删除旧路径。
- 财务、支付、订单、服务相关改动必须额外验证幂等、事务和审计字段。

## 8. 执行前开放问题

1. 商品分组是否允许从“固定三级”升级为“不限层级”。如果业务仍要求最多三级，应在服务层校验，不应继续用三张表表达。
2. 商品是否必须绑定叶子分组。如果允许绑定任意层级，需要明确前端筛选和路径展示规则。
3. `message_logs` 是否承接站内用户通知，还是只承接发送通道日志。若 `user_notifications` 表表达用户收件箱状态，应继续保留。
4. 哪些历史日志需要永久保留，哪些可以进入归档表或外部日志系统。
5. 逻辑外键中哪些属于真实多态关系，哪些只是历史上未补数据库约束。

## 9. 建议下一步

先执行阶段 0 和阶段 1。它们能稳定基线、补齐审计链路，并为后续外键、日志合并和商品分组重构提供可靠证据。阶段 3 和阶段 4 都属于高影响结构迁移，应分别拆成独立实施计划和测试清单后再动手。
