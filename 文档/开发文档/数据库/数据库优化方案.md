## 1. 结论

当前数据库的主要问题不只是日志表变大或索引需要治理，而是第三方能力的归属没有数据库级抽象：

- 插件元数据已经由 `integration_plugins`、`integration_plugin_configs` 承载。
- 运行时已经以 `PluginRuntimeRegistry::execute(domain, slugOrKey, action, payload, context)` 为中心。
- 但供应商、商品、服务、支付、短信/邮件/通知日志仍在各自表里保存 provider/gateway/module 字符串或 JSON 片段。
- 这些字符串缺少外键、状态、优先级、密钥归属、运行审计和绑定历史，导致“代码看起来插件化，数据库仍是旧集成模型”。

本方案的核心是：

1. 保留并强化 `integration_plugins` / `integration_plugin_configs` 作为插件注册与全局配置源。
2. 新增插件绑定层，把供应商、商品、服务、支付渠道、通知驱动等绑定到 `plugin_id`。
3. 新增插件运行日志，把每次插件执行、回调、异常和耗时可审计化。
4. 一次性回填旧字段后，切换代码到新表，最后删除旧 provider/gateway/module 字段和旧 settings 同步路径。
5. 日志归档、索引和缓存只作为第二优先级优化，不能抢在插件化结构前面。

## 2. 当前数据库痛点

### 2.1 插件身份分散

| 位置 | 当前字段 | 问题 |
| --- | --- | --- |
| `suppliers` | `interface_type`、`api_url`、`api_username`、`api_key`、`provider_config` | 上游 provider 和凭证混在供应商主表，不能表达一个供应商多插件、多环境、多账号。 |
| `products` | `provision_module`、`supplier_id`、`supplier_product_id` | 商品直接保存上游模块和上游商品 ID，缺少插件外键和绑定快照。 |
| `services` | `provision_data` JSON | 服务上游实例 ID、provider、运行快照都藏在 JSON，难索引、难审计、难迁移。 |
| `payments` | `gateway` | 支付网关是字符串，不知道来自哪个支付插件版本。 |
| `notification_logs` / `email_logs` / `sms_logs` | provider/driver 信息分散或缺失 | 发送日志无法稳定追溯到具体插件配置。 |
| `settings` | notification/payment/verification 等选项 | 插件配置已经有专表，但仍存在旧全局设置同步，配置归属不清。 |

### 2.2 插件配置和业务绑定混在一起

`integration_plugin_configs` 适合保存插件级默认配置，例如支付宝应用 ID、SMTP 账号池、魔方财务默认 API 端点。

但以下内容不应该继续塞在全局插件配置里：

- 某个供应商使用哪个上游插件。
- 某个商品绑定哪个供应商侧产品。
- 某个服务实例对应哪个上游实例。
- 某个支付入口使用哪个插件、哪个商户号或环境。
- 某个业务场景优先使用哪个短信/邮件插件。

这些都属于“插件绑定”，需要单独建模。

### 2.3 运行审计不足

当前失败日志主要靠普通日志和业务表字段拼接。插件化后必须能回答：

- 哪个插件、哪个版本、哪个 action 被调用。
- 调用来自哪个业务对象，例如订单、账单、服务、供应商或验证码。
- 是否成功、耗时多少、失败原因是什么。
- 请求和响应摘要是什么，敏感字段是否已脱敏。
- 回调是否通过签名，是否幂等命中。

## 3. 设计原则

- 插件注册表是唯一插件身份源：业务表引用 `integration_plugins.id`，不要再把 provider 字符串当关系源。
- provider key 只作为外部协议标识和历史快照保留，例如 `mofang_finance_api`，不得归并成 `hosting_panel_api`。
- 插件全局配置和业务绑定配置分离：全局配置进 `integration_plugin_configs`，绑定级覆盖配置进绑定表。
- 供应商、商品、服务三层上游关系要显式建表，不能继续藏在 JSON。
- 支付、订单、账单、余额、回调仍由平台服务层控制；插件只执行外部能力。
- `payments` 只记录真实第三方资金流入，禁止物理删除任何 Payment 行。
- 迁移必须新增文件，不修改历史迁移，不补跑早期激进迁移。
- 因用户已明确不要求兼容，旧字段只用于一次性回填和校验；切换完成后删除旧字段和旧读取分支。
- 插件安装记录进入业务外键后，卸载语义必须改为禁用/归档，不再物理删除 `integration_plugins` 和仍被引用的配置、绑定、运行记录。

| `archive_audit_logs`、归档文件 manifest | 扩展现有 `db:archive-logs`，纳入普通日志和插件运行日志；永久审计表只冷备不自动删除；归档命令必须 dry-run、锁、防重入、manifest、hash、restore。 | 管理端日志/系统维护页面可展示归档批次、行数、范围、状态和 restore manifest；不新增与现有命令不一致的 `logs:archive` 入口。 | `operation_logs`、`schedule_run_logs`、`notification_logs`、`email_logs`、`sms_logs`、`integration_plugin_runtime_logs` 按策略归档；`payments`、`payment_callbacks`、`gateway_logs`、`invoices`、`invoice_items` 不被普通归档删除。 |
| 破坏性清理涉及旧字段：`suppliers.*`、`products.*`、`services.provision_data`、`payments.gateway`、旧 `settings` key | Phase 4 前必须全仓搜索确认后端不再读取旧字段；删除 `syncLegacySettings()`、`migrateLegacySettings()`、`syncSelectionSetting()` 和 provider fallback；Controller/Service/Resource 只读新表。 | 管理端供应商、商品、插件、日志、支付配置页不再提交旧字段；官网购买/结算和用户控制台服务/支付页面不再消费旧字段；API 清单和前端类型同步刷新。 | 完成 API payload 快照对比、页面冒烟、回填报告归档后再删字段；`rg -n "interface_type|provision_module|supplier_product_id|provision_data|payments.gateway|syncLegacySettings|migrateLegacySettings|syncSelectionSetting"` 只允许迁移历史说明命中。 |

## 4. 目标结构

### 4.1 保留的插件注册表

继续使用现有两张表：

| 表 | 职责 |
| --- | --- |
| `integration_plugins` | 插件安装状态、能力域、slug、plugin_key、入口类、能力声明、配置 schema。 |
| `integration_plugin_configs` | 插件级非敏感配置、加密密钥配置、密钥是否已配置标记。 |

当前能力域以 `PluginDomain` 为准：

| domain | 物理目录 |
| --- | --- |
| `payment` | `backend/plugins/gateways` |
| `verification` | `backend/plugins/certification` |
| `captcha` | `backend/plugins/captcha` |
| `mail` | `backend/plugins/mail` |
| `sms` | `backend/plugins/sms` |
| `upstream` | `backend/plugins/servers` |

建议补充字段：

| 表 | 字段 | 说明 |
| --- | --- | --- |
| `integration_plugins` | `enabled_at`、`disabled_at` | 记录启停时间。 |
| `integration_plugins` | `installed_by`、`enabled_by` | 记录管理员操作人。 |
| `integration_plugins` | `source_hash` | 插件目录关键文件 hash，用于识别代码变更后是否需要复测。 |

插件被供应商、商品、服务、支付、通知或运行日志引用后，后台“卸载”只能执行停用或归档：

- `status=0`、写入 `disabled_at`、保留 `integration_plugins.id`。
- 配置可标记停用或轮换密钥，但不能直接删除仍被绑定引用的 `integration_plugin_configs`。
- 只有确认没有任何绑定、业务记录和运行日志引用时，才允许执行物理清理脚本，并要求单独备份。

### 4.2 通用插件绑定表

新增 `integration_plugin_bindings`，用于非核心或轻量绑定，例如站点默认支付渠道、验证码驱动、某业务场景邮件驱动。

```sql
CREATE TABLE `integration_plugin_bindings` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `domain` VARCHAR(32) NOT NULL,
  `plugin_id` BIGINT UNSIGNED NOT NULL,
  `binding_type` VARCHAR(50) NOT NULL COMMENT 'global/supplier/product/service/payment/notification/custom',
  `bindable_type` VARCHAR(120) NOT NULL DEFAULT 'global',
  `bindable_id` BIGINT UNSIGNED NOT NULL DEFAULT 0,
  `binding_key` VARCHAR(120) NOT NULL COMMENT '同一对象下的绑定名，如 default、renew_notice、recharge',
  `provider_key` VARCHAR(120) NULL COMMENT '外部协议标识快照，如 mofang_finance_api',
  `priority` INT NOT NULL DEFAULT 0,
  `status` TINYINT UNSIGNED NOT NULL DEFAULT 1 COMMENT '0停用 1启用',
  `config_json` JSON NULL,
  `secret_json` LONGTEXT NULL,
  `has_secret_json` JSON NULL,
  `runtime_policy_json` JSON NULL,
  `created_by` BIGINT UNSIGNED NULL,
  `updated_by` BIGINT UNSIGNED NULL,
  `created_at` TIMESTAMP NULL,
  `updated_at` TIMESTAMP NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `plugin_bindings_unique` (`domain`, `binding_type`, `bindable_type`, `bindable_id`, `binding_key`),
  KEY `plugin_bindings_plugin_status_idx` (`plugin_id`, `status`),
  KEY `plugin_bindings_domain_provider_status_idx` (`domain`, `provider_key`, `status`),
  KEY `plugin_bindings_bindable_idx` (`bindable_type`, `bindable_id`, `domain`),
  CONSTRAINT `plugin_bindings_plugin_fk` FOREIGN KEY (`plugin_id`) REFERENCES `integration_plugins` (`id`) ON DELETE RESTRICT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='插件通用绑定表';
```

说明：

- `plugin_id` 是真实关系。
- `provider_key` 是协议快照，方便排查历史和保留外部语义。
- `secret_json` 使用 Laravel `Crypt` 加密，回显只给 `has_secret_json`。
- 通用绑定不替代核心上游表；供应商、商品、服务仍使用下面的专表。

| --- | --- | --- |

`service_upstream_bindings.runtime_snapshot_json` 和 `connection_snapshot_json` 只允许保存轻量冗余摘要，不能继续成为无边界主数据。

### 4.4 支付插件适配

`payments.gateway` 当前是字符串。插件化后建议：

| 字段 | 处理 |
| --- | --- |
| `plugin_id` | 新增，引用 `integration_plugins.id`，domain 必须是 `payment`。 |
| `gateway_key` | 新增，保存支付网关业务入账 key，例如 `alipay`、`yipay`。插件目录 slug 如 `ali_pay`、`yi_pay` 不作为 Payment 业务值。 |
| `gateway` | 回填完成后删除或重命名为 `gateway_key`。 |
| `trade_no` | 保留第三方交易号。 |
| `callback_raw` | 保留最近一次回调摘要，敏感字段脱敏。 |

索引调整：

```sql
ALTER TABLE `payments`
  ADD COLUMN `plugin_id` BIGINT UNSIGNED NULL AFTER `invoice_id`,
  ADD COLUMN `gateway_key` VARCHAR(120) NULL AFTER `plugin_id`,
  ADD KEY `payments_plugin_status_paid_idx` (`plugin_id`, `status`, `paid_at`),
  ADD UNIQUE KEY `payments_plugin_trade_unique` (`plugin_id`, `gateway_key`, `trade_no`),
  ADD CONSTRAINT `payments_plugin_fk` FOREIGN KEY (`plugin_id`) REFERENCES `integration_plugins` (`id`) ON DELETE RESTRICT;
```

注意：

- `plugin_id`、`gateway_key` 在 Phase 1 先允许为空，Phase 2 回填校验通过后再改为 NOT NULL。
- 不物理删除历史 Payment 行。
- 支付插件只负责第三方支付动作和回调验签适配。
- 余额支付、管理员手动开服、免费订单仍不能产生新的 Payment。
- `payment_callbacks`、`gateway_logs` 可补充 `plugin_id`、`gateway_key`、`trace_id`，但不得纳入普通日志自动删除。

### 4.5 通知、短信、邮件插件适配

建议新增或补充：

| 表 | 字段 | 用途 |
| --- | --- | --- |
| `notification_logs` | `plugin_id`、`driver_key`、`trace_id` | 聚合通知追溯到插件。 |
| `email_logs` | `plugin_id`、`driver_key`、`trace_id` | 邮件发送追溯到插件。 |
| `sms_logs` | `plugin_id`、`driver_key`、`trace_id` | 短信发送追溯到插件。 |
| `integration_plugin_bindings` | `binding_type=notification` | 配置不同场景的默认邮件/短信插件。 |

场景示例：

| binding_key | domain | 说明 |
| --- | --- | --- |
| `login_code` | `sms` | 登录验证码短信。 |
| `invoice_notice` | `mail` | 账单提醒邮件。 |
| `renew_notice` | `mail` / `sms` | 续费提醒。 |
| `support_ticket` | `mail` | 工单通知。 |

`settings.notification.sms_driver`、`settings.notification.mail_driver` 等旧选择项在回填完成后删除，运行时只读插件绑定表。

### 4.6 插件运行日志

新增 `integration_plugin_runtime_logs`。

```sql
CREATE TABLE `integration_plugin_runtime_logs` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `trace_id` VARCHAR(64) NULL,
  `domain` VARCHAR(32) NOT NULL,
  `plugin_id` BIGINT UNSIGNED NULL,
  `plugin_key` VARCHAR(120) NOT NULL,
  `slug` VARCHAR(120) NOT NULL,
  `action` VARCHAR(120) NOT NULL,
  `binding_id` BIGINT UNSIGNED NULL,
  `bindable_type` VARCHAR(120) NULL,
  `bindable_id` BIGINT UNSIGNED NULL,
  `actor_type` VARCHAR(50) NULL,
  `actor_id` BIGINT UNSIGNED NULL,
  `status` VARCHAR(30) NOT NULL COMMENT 'success/failed/business_failed',
  `duration_ms` INT UNSIGNED NULL,
  `error_code` VARCHAR(80) NULL,
  `error_message` VARCHAR(500) NULL,
  `request_meta_json` JSON NULL,
  `response_meta_json` JSON NULL,
  `created_at` TIMESTAMP NULL,
  PRIMARY KEY (`id`),
  KEY `plugin_runtime_trace_idx` (`trace_id`),
  KEY `plugin_runtime_plugin_created_idx` (`plugin_id`, `created_at`),
  KEY `plugin_runtime_domain_action_created_idx` (`domain`, `action`, `created_at`),
  KEY `plugin_runtime_status_created_idx` (`status`, `created_at`),
  KEY `plugin_runtime_bindable_idx` (`bindable_type`, `bindable_id`, `created_at`),
  CONSTRAINT `plugin_runtime_plugin_fk` FOREIGN KEY (`plugin_id`) REFERENCES `integration_plugins` (`id`) ON DELETE SET NULL

```

写入规则：

- `PluginRuntimeRegistry::execute()` 包裹统一日志。
- `request_meta_json` 和 `response_meta_json` 只保存摘要，不保存密钥、手机号全文、身份证、银行卡等敏感值。
- 第三方原始错误不直接暴露给用户，但可在日志中保存脱敏摘要。
- 支付回调、实名回调、上游 webhook 必须带 `trace_id` 并落回调/运行日志。

此阶段只建结构，不删除旧字段。

### Phase 2：一次性回填

回填规则：

| 来源 | 目标 | 规则 |
| --- | --- | --- |
| `suppliers.interface_type` | `supplier_plugin_bindings` | 根据 `integration_plugins.domain=upstream` 且 `plugin_key` 匹配 provider key。 |
| `suppliers.api_*` / `provider_config` | `supplier_plugin_bindings` | 非敏感配置进 `config_json`，密钥进 `secret_json`。 |
| `products.provision_module`、`supplier_id`、`supplier_product_id` | `product_upstream_bindings` | 通过供应商绑定找到 `plugin_id`，上游商品 ID 转字符串保存。 |
| `services.provision_data` | `service_upstream_bindings`、`service_runtime_snapshots`、`service_connection_snapshots`、`service_provision_attempts` | 抽取 provider、上游实例 ID、供应商/商品绑定、运行状态、连接信息、开通/续费/同步尝试；未知 key 写入报告，不直接塞回新 JSON。 |
| `payments.gateway` | `payments.plugin_id`、`gateway_key` | 先按 `PaymentGatewayCode` 规范为 `alipay`、`yipay` 等业务入账 key，再匹配 domain=payment 的插件。 |
| `payment_callbacks`、`gateway_logs` | `plugin_id`、`gateway_key`、`trace_id` | 根据 Payment、旧 gateway 和 trade_no 追溯插件，无法追溯的日志保留空 plugin 但输出统计。 |
| notification/email/sms 日志 | `plugin_id`、`driver_key` | 根据旧 driver/provider 设置和日志上下文回填，可为空但要出报告。 |

回填脚本要求：

- 每个来源表输出总行数、成功行数、跳过行数、失败行数。
- 遇到未知 provider/gateway key 直接失败，不自动猜。
- 回填后做反查校验，例如商品绑定数应等于需要自动开通的商品数。
- 所有密钥类字段必须加密写入，不允许明文落库。

### Phase 3：代码切换

后端读取路径切换为：

### 7.2 现有索引治理

继续保留原方案中“先 EXPLAIN，再删除冗余索引”的原则。

可以优先复核：

- `products` 上多个分组状态索引是否被当前首页、商品列表和后台商品页真实使用。
- `notification_logs` 是否需要 `(channel, status, created_at)`。

删除索引的前置条件：

- 用当前生产查询条件跑 `EXPLAIN ANALYZE`。
- 确认没有独立查询依赖被覆盖的单列索引。
- 保留回滚 DDL。
- 每次只删一批，观察慢查询和写入指标。

## 8. 日志归档优化

仓库已存在 `php artisan db:archive-logs`，支持：

- `--dry-run`
- `--execute`
- `--restore=manifest.json`
- `--table=*`
- `--retain-days=`
- `--chunk=`
- `--path=`

因此不要新增 `logs:archive` 命令，应扩展现有 `db:archive-logs`。

### 8.1 归档分级

| 分级 | 表 | 策略 |
| --- | --- | --- |
| 永久审计 | `payments`、`payment_callbacks`、`gateway_logs`、`invoices`、`invoice_items`、`account_transactions`、返佣/提现类审计表 | 不自动删除，可另做只读审计库或冷备。 |
| 普通日志 | `operation_logs`、`schedule_run_logs`、`notification_logs`、`email_logs`、`sms_logs`、`automation_logs` | 由 `db:archive-logs` 导出 manifest 后删除。 |
| 插件运行日志 | `integration_plugin_runtime_logs` | 建议 180 天热数据，之后归档；失败日志可保留更久。 |

### 8.2 对现有归档命令的增强

| 增强项 | 说明 |
| --- | --- |
| 纳入 `schedule_run_logs` | 该表增长快，属于普通调度日志。 |
| manifest 增强 | 写入 batch id、文件 hash、行数、导出范围、删除范围。 |
| 压缩与加密 | JSONL 后增加 gzip 和 AES-256-GCM，加密密钥与 `APP_KEY` 分离。 |
| 审计表 | 新增 `archive_audit_logs`，记录每次归档状态和校验结果。 |
| 并发锁 | 使用 Cache lock 或 Redis lock，避免 schedule 重入。 |
| dry-run 必跑 | 生产执行前必须先生成 dry-run 报告。 |

`archive_audit_logs` 建议字段：

```sql
CREATE TABLE `archive_audit_logs` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `batch_id` VARCHAR(64) NOT NULL,
  `table_name` VARCHAR(64) NOT NULL,
  `mode` VARCHAR(30) NOT NULL,
  `row_count` INT UNSIGNED NOT NULL DEFAULT 0,
  `file_path` VARCHAR(500) NULL,
  `file_size` BIGINT UNSIGNED NULL,
  `checksum_sha256` CHAR(64) NULL,
  `status` VARCHAR(30) NOT NULL,
  `error_message` VARCHAR(500) NULL,
  `started_at` TIMESTAMP NULL,
  `finished_at` TIMESTAMP NULL,
  `created_at` TIMESTAMP NULL,
  PRIMARY KEY (`id`),
  KEY `archive_batch_idx` (`batch_id`),
  KEY `archive_table_status_idx` (`table_name`, `status`, `created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='日志归档审计';
```

## 9. 缓存和队列口径

本方案不把生产队列从 database 切到 Redis。

原因：

- 当前项目规则明确生产队列由宝塔每分钟 `php artisan schedule:run` 驱动。
- `QUEUE_CONNECTION=database` 是当前生产口径。
- 是否切 Redis 队列属于运行架构调整，不是本次数据库插件化适配的必要条件。

可保留的数据库相关缓存优化：

| 对象 | 建议 |
| --- | --- |
| 首页/商品分组 | 继续使用 Laravel Cache，并在商品/分组变更后主动失效。 |
| 后台 Dashboard | 允许 2-5 分钟缓存，不需要每次 COUNT 全表。 |
| 插件配置 | 插件启停或保存配置时清理对应 domain runtime cache。 |
| 供应商/商品/服务绑定 | 可按 `plugin_binding:{domain}:{id}` 做短 TTL 缓存，源数据必须可由 MySQL 重建。 |

如果未来单独推进 Redis 队列，需要另起运行方案，并覆盖 schedule、失败重试、部署和监控，不应混入本方案。

## 11. 回滚和数据保护

| 风险 | 保护措施 |
| --- | --- |
| provider/gateway 回填错误 | 回填前备份；回填脚本生成映射报告；新表带 provider_key 快照。 |

## 12. 成功标准

完成后应满足：

- 新增插件后，数据库不需要给业务表继续添加 provider 字符串字段。
