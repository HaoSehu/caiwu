# 魔方财务员工与权限系统接入方案

- 文档性质：专项方案 / 待落地清单
- 当前状态：仅作后续员工与权限系统改造参考；当前权限执行真源仍是 `permission:{code}` 中间件、`AdminPermissions` 和管理端现有路由权限配置。
- 对齐时间：`2026-07-02`

## 一、文档目标

- 面向当前 `caiwu` 仓库，设计一套可落地的“员工系统 + 角色权限系统”接入方案
- 参考对象为解包目录 `zjmf-manger-decoded-main` 中的员工管理、角色分配、`auth_rule` 权限树
- 目标不是把 ThinkCMF 的实现原样搬进 Laravel，而是在保留当前 `Sanctum + permission:{code}` 架构的前提下完成兼容吸收
- 本文只输出方案、结构、分阶段改造路径，不执行数据库初始化、迁移或代码落地

## 二、现状对照

### 2.1 魔方财务解包结构

员工与 RBAC 的核心结构如下：

- 员工账号：`shd_user`
  - 管理员通过 `user_type = 1` 区分
  - 核心字段包括 `user_login`、`user_pass`、`user_nickname`、`user_email`、`user_status`
  - 扩展字段包括 `language`、`signature`、`is_sale`、`sale_is_use`、`only_mine`、`is_receive`
- 角色：`shd_role`
- 员工-角色关系：`shd_role_user`
- 权限树：`shd_auth_rule`
  - 既承载“权限点”，又承载“后台菜单树”
  - 关键字段：`pid`、`title`、`name`、`url`、`is_display`、`order`
- 角色-权限关系：`shd_auth_access`
- 部门分配：`ticket_department_admin`
- 特殊扩展：
  - `rolepage` / `authpage_access`：另一套页面级授权
  - `secondVerifyResultAdmin(...)`：敏感管理动作二次校验

当前行为特点：

1. 菜单树直接由 `auth_rule` 生成。
2. 权限判断依赖控制器/方法名，如 `app\admin\controller\XxxController::action`。
3. 超级管理员依赖固定用户或角色特判。
4. 员工编辑、角色编辑、禁用启用、部门绑定混在同一套后台逻辑中。

### 2.2 当前 caiwu 结构

当前仓库已经有一套 Laravel 化的后台权限基础：

- 管理员账号：`admin_users`
- 角色：`roles`
- 权限目录：`permissions`
- 角色-权限：`role_permissions`
- 管理员-角色：`admin_user_roles`
- 后端鉴权：
  - `auth:sanctum`
  - `ensure.admin`
  - `permission:{code}`
- 权限码定义：`backend/app/Support/AdminPermissions.php`
- 前端管理端：`frontend-admin-v3`
  - 当前菜单按本地路由和固定分组生成
  - 不是后端动态菜单树
  - `user.ts` 里仍把 `roles` 写死成 `['all']`

当前特点：

1. 权限执行模型是“平面权限码”，不是树形 `controller::action`。
2. 后台菜单与权限树没有统一数据源。
3. 结构上已经支持 `roles / permissions / admin_user_roles`，但员工管理后台还未完整成型。
4. 当前多角色结构是“可兼容但未完全前台化”，实际仍偏单主角色。

## 三、差异与结论

两边不是同一范式，不能直接照抄。

### 3.1 关键差异

1. **权限表达不同**
   - 魔方财务：`auth_rule.name = 控制器::方法`
   - caiwu：`dashboard.view`、`user.list` 这类语义权限码

2. **菜单来源不同**
   - 魔方财务：菜单树和权限树一体
   - caiwu：前端本地静态路由分组，菜单不是后端树

3. **管理员存储模型不同**
   - 魔方财务：管理员和普通用户在一张 `user` 表里，用 `user_type` 区分
   - caiwu：管理员独立在 `admin_users`

4. **运行时鉴权不同**
   - 魔方财务：Session + ThinkCMF Auth
   - caiwu：Sanctum Token + Laravel Middleware

### 3.2 推荐结论

采用“**兼容接入**”，不采用“**整套平移**”。

即：

- 保留当前 `admin_users / roles / permissions / role_permissions / admin_user_roles`
- 吸收魔方财务的三个有效设计：
  1. 员工账号管理
  2. 角色分配
  3. 权限树和菜单树的配置思想
- 放弃直接继承的部分：
  1. `controller::action` 作为最终权限码
  2. Session 缓存鉴权
  3. `auth_rule` 直接驱动全部业务路由
  4. 物理删除管理员的旧做法

## 四、目标结构设计

## 4.1 总体原则

1. **权限执行真源仍是 `permission:{code}`。**
2. **菜单树是配置投影，不是执行引擎。**
3. **管理员账号与业务用户继续分表。**
4. **先按单主角色落地，保留后续多角色扩展位。**
5. **魔方财务兼容层只用于导入和映射，不进入日常运行主链路。**

## 4.2 推荐数据结构

### 4.2.1 保留并复用的现有表

- `admin_users`
- `roles`
- `permissions`
- `role_permissions`
- `admin_user_roles`

### 4.2.2 新增的推荐表

#### 1. `admin_user_profiles`

用于承接魔方财务员工扩展字段，避免把销售/签名/语言等字段全部堆进 `admin_users`。

建议字段：

- `id`
- `admin_user_id`
- `language`
- `signature`
- `is_sale`
- `sale_is_use`
- `only_mine`
- `is_receive`
- `extra_json`
- `created_at`
- `updated_at`

#### 2. `admin_user_departments`

用于承接 `ticket_department_admin` 这一类工单部门绑定。

建议字段：

- `id`
- `admin_user_id`
- `department_code` 或 `department_id`
- `created_at`
- `updated_at`

#### 3. `admin_permission_nodes`

这是本次接入的关键兼容层，用来承接魔方财务 `auth_rule` 的树结构信息，但不替代 `permissions` 作为执行真源。

建议字段：

- `id`
- `parent_id`
- `node_key`
- `node_type`：`group | page | action`
- `title`
- `permission_id`：可空，分组节点允许无权限码
- `route_name`
- `route_path`
- `icon`
- `sort_order`
- `is_menu`
- `is_enabled`
- `source`：`system | mofang_import | custom`
- `legacy_rule_name`
- `meta_json`
- `created_at`
- `updated_at`

说明：

- `permissions` 负责“能不能访问”
- `admin_permission_nodes` 负责“如何组织、如何展示、如何兼容旧树”

### 4.2.3 `admin_user_roles` 的处理边界

当前 `admin_user_roles` 只能作为单主角色桥表使用，第一阶段和第二阶段不扩展多角色语义。

原因：

1. 当前 `AuthService::adminLogin()` 登录时会调用 `AdminRoleBridgeService::syncPrimaryRole()`。
2. `syncPrimaryRole()` 会先删除当前管理员在 `admin_user_roles` 中的全部记录，再插入 `admin_users.role_id` 对应的一条记录。
3. 如果提前给桥表增加 `is_primary`、`assigned_by`、多角色分配等能力，登录会把这些数据抹掉。

因此：

- 第一阶段：继续只维护 `admin_users.role_id` 和一条 `admin_user_roles` 镜像记录。
- 第二阶段：不做多角色，只补角色状态、权限目录和前端权限过滤。
- 第三阶段：如果确认需要多角色，先改造 `AdminRoleBridgeService`，再扩展桥表字段。

## 4.3 魔方财务到 caiwu 的映射关系

| 魔方财务 | caiwu 目标 | 处理方式 |
|---|---|---|
| `shd_user(user_type=1)` | `admin_users` + `admin_user_profiles` | 管理员核心字段进 `admin_users`，扩展字段进 profile |
| `shd_role` | `roles` | 直接映射角色名称、标签、状态 |
| `shd_role_user` | `admin_users.role_id` + `admin_user_roles` | 第一阶段仅保留一个主角色，桥表只做镜像 |
| `shd_auth_rule` | `permissions` + `admin_permission_nodes` | 权限码与树结构拆开 |
| `shd_auth_access` | `role_permissions` | 先映射到标准权限码，再绑定角色 |
| `ticket_department_admin` | `admin_user_departments` | 作为员工范围/工单部门附属能力 |
| `rolepage` / `authpage_access` | 暂不进入第一阶段 | 如确有需求再单独评估 |

## 六、权限模型设计

## 6.1 新增权限码

建议先补齐员工系统自身的权限码：

- `staff.list`
- `staff.manage`
- `role.list`
- `role.manage`
- `permission.list`
- `permission.manage`

如后续要做菜单树维护，可再补：

- `menu.list`
- `menu.manage`

## 6.2 菜单与权限的关系

建议按下面的规则处理：

1. **后端中间件只认 `permission_key`**
2. **第二阶段前端页面才读取 `admin_permission_nodes` 做展示组织**
3. **路由显示判断优先看 `route.meta.permission`**
4. **一个菜单节点可以没有权限码，但叶子页面和动作节点必须能映射到权限码**

这能同时兼容：

- 现有 `permission:{code}` 中间件
- 魔方财务的树结构组织
- `frontend-admin-v3` 的本地路由体系

## 七、接口设计

## 7.1 员工管理

- `GET /api/admin/staff`
- `GET /api/admin/staff/{id}`
- `POST /api/admin/staff`
- `PUT /api/admin/staff/{id}`
- `POST /api/admin/staff/{id}/toggle-status`
- `POST /api/admin/staff/{id}/reset-password`

返回字段建议包含：

- 基础账号信息
- 主角色
- 权限列表
- profile 扩展字段
- 部门绑定

## 7.2 角色管理

- `GET /api/admin/roles`
- `GET /api/admin/roles/{id}`
- `POST /api/admin/roles`
- `PUT /api/admin/roles/{id}`
- `DELETE /api/admin/roles/{id}`
- `POST /api/admin/roles/{id}/copy`

角色详情建议一次返回：

- 角色基础信息
- 已绑定权限码
- 已绑定权限树节点
- 已分配员工

## 7.3 权限目录

- `GET /api/admin/permissions`

说明：

- 第一阶段只提供标准权限码目录，数据来自 `AdminPermissions` 和 `permissions` 表。
- 不在第一阶段暴露 `permission-nodes` API，避免尚未落表就形成前端依赖。
- 第二阶段再增加 `GET /api/admin/permission-nodes/tree`。
- 第三阶段再增加 `POST /api/admin/permission-nodes/import-mofang`，并且必须支持 dry-run。
- 不建议做运行时 `sync-system` 接口去读取前端源码；如需同步前端路由元信息，应做构建期产物或把节点真源移到后端。

## 八、优化与适配重点

## 8.1 不直接继承魔方财务的旧问题

以下问题应在适配时主动修正：

1. **不再用 `controller::action` 作为最终权限码**
2. **不再依赖固定 ID=1 作为唯一超级管理员判定**
3. **不再物理删除管理员作为常规操作**
4. **不把菜单树和权限执行硬绑在一张表里**
5. **不把员工与普通用户混在同一张表里**

## 8.2 前端适配重点

当前 `frontend-admin-v3` 有两个必须处理的点：

1. `user.ts` 里 `roles: ['all']` 是占位写法，需要改成真实角色/权限模型
2. `permission.ts` 当前只做静态菜单分组，没有按真实权限过滤页面

推荐改法：

- 保留静态路由注册
- 先补全所有后台菜单路由的 `route.meta.permission`
- 再在菜单生成阶段按 `route.meta.permission` 过滤
- 后续再决定是否开放后端驱动菜单树

这样风险最低，也最符合现有项目状态。

## 8.3 数据范围适配

魔方财务里这些字段本质上不是“账号信息”，而是“数据范围策略”：

- `only_mine`
- `is_sale`
- `sale_is_use`
- 部门绑定

建议不要只做表单展示，要进一步下沉为查询范围策略：

- 用户列表
- 工单列表
- 财务客户列表
- 销售归属列表

也就是说：

- 第一阶段：先把字段存起来
- 第二阶段：把这些字段真正挂到查询服务上

## 8.4 二次校验适配

魔方财务有 `secondVerifyResultAdmin(...)`。当前仓库没有必要原样复制，但应保留策略位。

建议第二阶段只对以下动作加策略钩子：

- 重置管理员密码
- 修改角色权限
- 修改系统权限目录
- 修改高危配置

实现方式建议是：

- 中间件或服务层策略检查
- 与现有管理端登录态和审计日志配合

## 九、分阶段实施建议

## 9.1 第一阶段：基础接入

目标：

- 后端补齐员工管理、角色管理、权限目录 API
- 前端补齐员工页、角色页、权限页
- 补齐 `frontend-admin-v3` 菜单路由 `meta.permission`
- 权限码与页面权限过滤跑通

这一阶段先不做：

- `admin_permission_nodes`
- `permission-nodes` API
- 魔方旧数据导入
- 多角色组合
- 后端动态菜单
- 数据范围深度控制

## 9.2 第二阶段：优化适配

目标：

- 引入 `admin_permission_nodes`
- 把当前系统权限码组织成后端权限节点树
- 接入部门/销售/只看本人客户等数据范围
- 增加敏感动作二次校验
- 明确旧 `auth_rule` 到新权限码的映射规则

## 9.3 第三阶段：历史导入与兼容

目标：

- 做 `LegacyMofangRbacImportService`
- 支持 dry-run
- 输出“旧角色 -> 新权限码”的映射报告
- 未识别规则不自动放行，只进入待确认清单
- 如确认需要多角色，再改造 `AdminRoleBridgeService` 和 `admin_user_roles`

## 十、最终建议

本次接入建议采用下面这条主线：

1. **以 caiwu 现有 Laravel 权限体系为主干**
2. **以 `admin_permission_nodes` 为魔方财务树结构兼容层**
3. **先做员工/角色/权限目录三件套**
4. **前端先做静态路由下的真实权限过滤**
5. **后续再做数据范围、二次校验、旧数据导入**

这是最稳的做法，因为它既能吸收魔方财务成熟的员工/RBAC 设计，又不会把当前 `Sanctum + permission:{code}` 的基础推翻重来。

## 十一、两轮审核结论

### 11.1 第一轮：方案内部一致性审核

结论：原方向正确，但原文存在阶段边界冲突，已修正。

发现与处理：

1. `admin_permission_nodes` 同时出现在基础结构和第二阶段，容易导致第一阶段接口依赖不存在的数据表。已修正为目标结构保留，但第一阶段不落运行时依赖。
2. 第一阶段原本包含 `permission-nodes` API，但第二阶段才引入节点表。已改为第一阶段只提供 `GET /api/admin/permissions`。
3. `sync-system` 原本被设计成后端运行时接口，但它需要读取前端路由元信息，职责边界不清。已改为不建议运行时读取前端源码。
4. 多角色扩展原本写得过早。已改为第三阶段可选，并且必须先改 `AdminRoleBridgeService`。

### 11.2 第二轮：当前代码适配审核

结论：实施前必须处理四个真实代码前置条件。

1. **登录会重写角色桥表**
   - `AuthService::adminLogin()` 调用 `AdminRoleBridgeService::syncPrimaryRole()`。
   - `syncPrimaryRole()` 会删除当前管理员所有桥表记录，再插入单条主角色记录。
   - 因此第一阶段不能做多角色，只能保持单主角色。

2. **角色状态当前不参与鉴权**
   - `Role` 模型没有 `status` 可填充字段。
   - `resolvedPermissions()` 不判断角色启用/禁用。
   - 角色管理如果要支持禁用，必须同步补 `roles.status` 字段和读取侧过滤。

3. **v3 路由权限元数据不完整**
   - 当前 `frontend-admin-v3` 只有少数页面配置了 `meta.permission`，例如日志和设置。
   - 第一阶段做菜单过滤前，必须先给所有后台菜单路由补齐 `meta.permission`。

4. **前端权限常量落后于后端**
   - `frontend-admin-v3/src/constants/permissions.ts` 没有覆盖后端 `AdminPermissions` 的全部权限码。
   - 第一阶段需要前后端权限码同步，避免页面判断使用不存在的常量。

## 十二、实施方案

### 12.1 总体实施顺序

推荐按四个批次推进：

1. **批次 A：权限基线修正**
2. **批次 B：员工与角色后台 API**
3. **批次 C：v3 管理端页面与菜单过滤**
4. **批次 D：权限节点树、旧系统导入、数据范围**

批次 A-C 是第一阶段必做；批次 D 是第二/第三阶段。

### 12.2 批次 A：权限基线修正

后端：

- 扩展 `AdminPermissions`：
  - `staff.list`
  - `staff.manage`
  - `role.list`
  - `role.manage`
  - `permission.list`
  - `permission.manage`
- 补齐 `permissions` 同步逻辑，确保新权限码能进入目录。
- 如要支持角色禁用，新增 `roles.status` 字段，并让 `Role::resolvedPermissions()` 对禁用角色返回空权限。
- 继续保留 `super_admin => ['*']` 的内置超级权限。

前端：

- 同步更新 `frontend-admin-v3/src/constants/permissions.ts`。
- 给所有后台菜单路由补齐 `meta.permission`。
- 修改 `permission.ts` 菜单生成逻辑：无权限则隐藏对应菜单项，分组无子项则隐藏分组。
- 修改 `user.ts`，去掉 `roles: ['all']` 的占位语义，使用后端返回的真实 `permissions`。

验证：

- 后端执行受影响权限模型测试。
- 前端执行 `cd frontend-admin-v3 && npm run build`。

### 12.3 批次 B：员工与角色后台 API

后端新增：

```text
backend/app/Http/Controllers/Admin/AdminStaffController.php
backend/app/Http/Controllers/Admin/AdminRoleController.php
backend/app/Http/Controllers/Admin/AdminPermissionCatalogController.php
backend/app/Services/Admin/Rbac/AdminStaffService.php
backend/app/Services/Admin/Rbac/AdminRoleService.php
backend/app/Services/Admin/Rbac/PermissionCatalogService.php
```

数据结构：

- 新增 `admin_user_profiles`。
- 新增 `admin_user_departments`。
- 暂不扩展 `admin_user_roles`。
- 暂不新增 `admin_permission_nodes`。

接口：

- `GET /api/admin/staff`
- `GET /api/admin/staff/{id}`
- `POST /api/admin/staff`
- `PUT /api/admin/staff/{id}`
- `POST /api/admin/staff/{id}/toggle-status`
- `POST /api/admin/staff/{id}/reset-password`
- `GET /api/admin/roles`
- `GET /api/admin/roles/{id}`
- `POST /api/admin/roles`
- `PUT /api/admin/roles/{id}`
- `DELETE /api/admin/roles/{id}`
- `POST /api/admin/roles/{id}/copy`
- `GET /api/admin/permissions`

约束：

- 删除员工不做物理删除，默认改为禁用或软删除策略。
- 不能停用当前登录管理员自己。
- 不能删除或禁用最后一个具备 `*` 权限的管理员。
- 修改密码后应撤销该管理员旧 token，避免旧会话继续有效。
- 控制器只负责入参、鉴权、调用服务和响应；业务放到 Service。

验证：

- 针对员工创建、编辑、禁用、重置密码、角色授权、权限目录写 Feature Test。
- 不执行数据库初始化或迁移；迁移文件只提交，运行必须等明确确认。

### 12.4 批次 C：v3 管理端接入

新增页面：

```text
frontend-admin-v3/src/api/admin-staff.ts
frontend-admin-v3/src/api/admin-roles.ts
frontend-admin-v3/src/api/admin-permissions.ts
frontend-admin-v3/src/pages/admin/system/staff/index.vue
frontend-admin-v3/src/pages/admin/system/roles/index.vue
frontend-admin-v3/src/pages/admin/system/permissions/index.vue
```

页面要求：

- 使用 TDesign Vue Next，不引入 Element Plus。
- 列表页从筛选区或表格开始，不新增说明型大页头。
- 员工页包含搜索、状态筛选、角色筛选、创建、编辑、禁用/启用、重置密码。
- 角色页包含角色列表、权限勾选、复制角色、禁用角色。
- 权限页第一阶段只展示权限码目录，不提供后端菜单树编辑。

验证：

- `cd frontend-admin-v3 && npm run build`
- 核查低权限管理员登录后菜单不可见、接口不可访问。

### 12.5 批次 D：权限节点树与旧系统导入

第二阶段：

- 新增 `admin_permission_nodes`。
- 做 `AdminMenuProjectionService`。
- 提供 `GET /api/admin/permission-nodes/tree`。
- 将当前权限码组织成树，用于角色授权页和权限目录页展示。

第三阶段：

- 做 `AdminLegacyPermissionMap`。
- 做 `LegacyMofangRbacImportService`。
- 支持 dry-run，不直接写入。
- 输出导入报告：
  - 旧员工数量
  - 旧角色数量
  - 可映射权限数量
  - 未识别 `auth_rule`
  - 冲突账号
  - 风险角色
- 未识别权限默认不放行，必须人工确认映射。

### 12.6 第一阶段验收标准

第一阶段完成时必须满足：

1. 管理员能在 v3 后台创建、编辑、禁用员工。
2. 管理员能创建角色并分配标准权限码。
3. 登录返回真实权限列表。
4. 菜单按权限过滤。
5. 后端接口按 `permission:{code}` 拦截。
6. 角色禁用后不再产生有效权限。
7. 旧魔方财务数据没有被导入，也没有形成运行时依赖。
8. 未经确认不执行数据库迁移。
