# 后端审查方案

> 适用范围：`backend/`（Laravel 12 + PHP 8.2 + Sanctum 4 + MySQL 8 + Redis + database 队列）。
> 视角：产品经理 + 后端工程师 + 安全/财务审计三方视角叠加。
> 目标：在不破坏当前稳定链路（支付、账单、服务实例、回调、调度）的前提下，按优先级找 bug、堵漏洞、提可维护性，并给出可执行的修复与优化清单。
> 约束：遵循 `AGENTS.md` 与 `后端规范化工程化治理方案.md`，文档与代码冲突时以代码实际行为为准，先记录冲突再修订文档。

## 0. 审查原则与闭环

1. **以代码为准**：文档、`后端API清单.md`、`开发规范.md` 不具备完全真实性，所有结论必须由代码、路由、可观察运行行为、受控验证支撑。
2. **最小必要改动**：只改必要范围，不做无关重构；高风险链路（支付回调、余额扣减、服务开通、上游回滚）改动需先评估再动手。
3. **审查闭环**：每个发现项必须包含 `编号 / 严重度 / 复现路径 / 根因 / 修复方案 / 验证方式 / 负责人 / 状态`，避免漏报和审完不报。
4. **测试先行**：高风险改动先补回归测试（已有 `tests/Feature` 覆盖了大量场景，应复用而非另起炉灶），测试失败先修复再推进。
5. **分批落地**：按 P0 → P1 → P2 分批合并，每批独立可回滚，每批合并后跑 `composer test` + `composer analyse` + `composer format:check`。

## 2. 多视角审查清单

### 2.1 产品经理视角（业务正确性 / 体验 / 边界）

- [ ] **核心业务闭环**：注册 → 实名 → 下单 → 支付 → 开通 → 续费 → 升降级 → 退款 → 注销，每一步状态机是否自洽，是否存在“卡死”中间态。
- [ ] **财务对账**：订单 / 支付 / 账单 / 余额流水 / 佣金 / 提现是否能闭环对账，是否存在“有钱无单、有单无钱、退款不回滚佣金”等典型漏洞。
- [ ] **幂等与重复触发**：支付回调、队列重试、调度补偿、手动重试是否都带幂等键，重复执行是否会导致重复开通、重复扣款、重复发佣金。
- [ ] **用户体验边界**：异步任务最坏延迟 60 秒（宝塔每分钟 `schedule:run` 消费队列）是否在产品文案/前端提示中体现，超时是否有兜底。
- [ ] **权限与多租户**：管理端权限码 `permission:{code}` 是否覆盖所有写操作，用户端是否能越权访问他人订单/账单/工单/服务实例。
- [ ] **可见文案**：API `message`、字段校验错误、用户可见提示是否全部简体中文，是否符合 `后端规范化工程化治理方案.md` §1.7。

### 2.2 后端工程师视角（架构 / 代码质量 / 性能）

- [ ] **分层合规**：Controller 是否薄层，是否存在 Controller 直接 `Http::`、手写 `validate`、散落事务、复杂分支（对照治理方案 §3）。
- [ ] **Service 边界**：财务/支付/服务实例/上游 Service 是否事务+锁+审计+幂等四件套齐全，是否存在跨表流程写在 Model 里。
- [ ] **N+1 与懒加载**：列表接口是否滥用 `with` 缺失导致 N+1，是否有 `loadCount` / `withCount` 误用。
- [ ] **大查询与分页**：是否存在 `->get()` 全表拉取、未分页导出、`limit` 缺失的扫描接口。
- [ ] **队列与调度**：Job 是否声明 `$tries/$timeout/$backoff`，调度是否 `withoutOverlapping`，长任务是否会撞 `schedule:run` 60 秒窗口。
- [ ] **缓存一致性**：Redis 缓存 key 是否带版本/前缀，服务实例/产品库存缓存是否在写操作后失效，是否存在缓存击穿/穿透。
- [ ] **事务范围**：事务内是否调用外部 HTTP（支付、上游），是否存在“先提交再调外部”导致状态不一致。
- [ ] **异常与日志**：是否统一异常响应格式，第三方异常是否被吞，`Log::info` 是否泄漏敏感字段（手机号、身份证、token、密钥）。
- [ ] **静态分析**：`phpstan` 当前 level 5，是否可逐步提升到 7/9，`checkModelProperties: true` 下是否有遗留模型属性错误。
- [ ] **代码风格**：`pint --test` 是否零 diff，是否引入了非 PSR-12/项目约定的写法。

### 2.3 安全与合规视角（OWASP Top 10 对齐）

- [ ] **A01 失效访问控制**：所有写路由是否挂权限中间件，`Client/*` 是否对所有“按 id 查询”做了归属校验（订单/账单/工单/服务实例 owner 过滤）。
- [ ] **A02 加密失败**：`.env` 密钥、支付密钥、上游密钥是否硬编码，是否走 `config/` + `env`，传输是否全 HTTPS，回调签名是否校验（已有 `CallbackSignatureMiddleware`）。
- [ ] **A03 注入**：是否仍有原始 SQL 拼接、`DB::raw` 拼用户输入、`whereRaw` 带未转义变量；排序/字段参数是否走白名单。
- [ ] **A04 不安全设计**：支付回调、退款、提现等高风险流程是否有重试限制、金额上下限、风控规则。
- [ ] **A05 配置错误**：`APP_DEBUG`、CORS、`sanctum.stateful`、`trustedproxy`、`storage/` 权限、`public/` 是否暴露敏感文件。
- [ ] **A06 易受攻击组件**：`composer audit` 是否有 CVE，Laravel/Sanctum/Guzzle 是否在受支持版本。
- [ ] **A07 认证失败**：Sanctum Token 过期、闲置超时（已有 `SanctumIdleTimeoutTest`）、登录风控（`LoginRiskControlService`）是否生效，是否存在 `loginAs` 越权（已有 `AdminLoginAsRedirectUrlTest`）。
- [ ] **A08 数据完整性**：回调签名、 webhook 来源 IP 白名单、文件上传校验（`UploadSecurityTest`）是否覆盖。
- [ ] **A09 日志与监控**：敏感操作（退款、提现、权限变更、登录 impersonate）是否有审计日志，是否能溯源到人。
- [ ] **A10 SSRF**：上游集成、对象存储预签名、回调 URL 是否对用户可控 URL 做了内网 IP/协议白名单。

### 2.4 财务审计视角（资金安全专属）

- [ ] **余额扣减**：是否使用行级锁 + 事务 + 流水表三件套，扣减前是否校验余额 ≥ 金额，是否防并发重复扣减。
- [ ] **支付回调金额校验**：回调金额是否与订单金额一致，币种是否一致，低于订单金额是否拒绝开通。
- [ ] **退款链路**：退款是否触发佣金回滚、是否更新账单状态、是否有“退款成功但订单仍开通”的不一致。
- [ ] **提现风控**：提现金额上限、频次、实名门槛、可提余额校验、人工复审节点是否齐全。
- [ ] **账单幂等**：账单生成、续费账单、佣金结算是否有唯一键约束防止重复生成。
- [ ] **快照与对账**：`AccountBalanceSnapshot` / `AccountLedger` / `AccountTransaction` 是否能重建任意时点余额，是否能与第三方对账文件比对。

### 2.5 运维与可观测性视角

- [ ] **日志结构化**：是否统一 `trace_id`，关键链路（支付、开通、回调）能否串联前后日志。
- [ ] **健康检查**：`/health` 是否覆盖 DB/Redis/队列，是否被宝塔监控消费。
- [ ] **指标**：队列积压、调度延迟、回调失败率、上游失败率是否有暴露渠道（即使只是日志聚合）。
- [ ] **告警阈值**：回调失败、余额对账不平、调度未运行是否有可发现途径。
- [ ] **可恢复性**：`storage/logs` 轮转、`storage/app` 备份、`.env` 多环境隔离是否就绪。

## 3. 审查执行步骤（按周/批次推进）

### 第 0 步：建立基线（半天）
1. 跑通本地：按 `启动指南.md` 启动后端，确认 `php artisan test` 全绿、`phpstan analyse` 当前级别通过、`pint --test` 零 diff。
2. 导出真实路由与控制器映射，与 `后端API清单.md` 比对，输出 **文档/代码冲突清单 A**。
3. 运行 `composer audit`，记录已知 CVE 列表。
4. 跑一遍 `php artisan route:list --json` 存档，作为后续回归基线。

### 第 1 步：自动化静态扫描（1 天）
1. `phpstan analyse --memory-limit=1G`，按文件归档错误。
2. `pint --test`，归档风格问题。
3. 自写脚本扫描：Controller 中 `Http::`、`DB::raw`、`->get()` 无 `limit`、`validate(` 直接调用、`->all()` 入参、`env(` 在 app 目录直接调用。
4. 输出 **静态扫描问题清单 B**。

### 第 2 步：业务闭环走查（2 天，按领域并行）
按以下领域分组走查，每组输出“流程图 + 风险点 + 测试覆盖差距”：
- 支付与回调：`PaymentController` / `PaymentCallbackController` / `PaymentService` / `PaymentGateway/*`
- 财务与账单：`FinanceController` / `FinanceLedgerController` / `AccountLedger` / `Invoice`
- 订单与服务实例：`OrderController` / `ServiceController` / `Provisioning` / `ServiceInstance`
- 优惠券与佣金：`Coupon*` / `Referral*` / `Withdrawal`
- 实名与风控：`VerificationController` / `LoginRiskControlService` / `Security`
- 上游集成：`Upstream` / `Integrations` / `MofangFinance` / `HostingPanelApi`
- 内容与站点：`Site*` / `Content*`（公开读，重点 SSRF/缓存/发布版本）
- 管理后台权限：`Admin*Controller` / `permission:*` 中间件 / 角色

### 第 3 步：测试覆盖差距评估（1 天）
1. 列出现有 `tests/Feature` 已覆盖场景，标注上面走查发现的未覆盖项。
2. 对 P0 风险点（回调重复、余额并发、提现越权、回调金额不符）补回归测试，先红再绿。
3. 评估是否引入假驱动（fake provider）以替代真实第三方调用。

### 第 4 步：分级修复（按 P0/P1/P2 滚动）
- **P0（资金/数据安全/越权）**：立即修，单点合并，必须带回归测试。
- **P1（正确性/稳定性/可观测性）**：本批修，可聚合合并。
- **P2（可维护性/性能/风格/文档）**：滚动修，避免阻塞 P0/P1。

### 第 5 步：回归与收尾
1. 全量 `composer test` + `analyse` + `format:check`。
2. 同步更新 `后端API清单.md`（如确认有路由变更，由脚本重生成，不手改）、`后端规范化工程化治理方案.md` 中已过时条款。
3. 输出 **审查报告**：发现项总表 + 修复记录 + 残留风险 + 下一轮建议。

## 4. 重点关注 bug 高发区（基于代码盘点）

> 以下为根据目录结构与已有测试反推的“最容易出问题”的位置，审查时优先看。

1. **支付回调幂等与金额校验**：`PaymentCallbackController::alipayNotify` 仅记录日志后委托 Service，需确认 `PaymentService::handleAlipayNotify` 内部对 `out_trade_no`、`total_amount`、`trade_status` 做了幂等与金额比对，且失败不抛“success”。
2. **回调签名中间件**：`CallbackSignatureMiddleware` 是否覆盖所有支付/上游回调路由，是否有路由绕过。
3. **余额并发**：`AccountLedger` 写入是否走 `lockForUpdate`，是否在事务内同时更新 `UserAccount` 余额字段，避免“流水与余额不一致”。
4. **服务实例开通失败回滚**：`Provisioning` 在上游开通失败时是否回滚订单/账单状态，是否产生“已付款未开通”的孤儿单，是否有补偿任务。
5. **续费账单与佣金**：`ServiceRenewCouponRegressionTest` / `ReferralRewardLifecycleRegressionTest` 已存在，说明历史上踩过坑，重点回归“续费叠加优惠券后佣金基数”、“提现后佣金状态”。
6. **管理端 loginAs 越权**：`AdminLoginAsRedirectUrlTest` 暗示曾存在 redirect 滥用，需复核 redirect URL 白名单与 token scope。
7. **公开站点 SSRF/缓存**：`Site*Controller` 的 `quote` 已加 `throttle:60,1`，需复核库存/报价接口是否存在用户可控的回源 URL。
8. **文件上传**：`UploadSecurityTest` 已覆盖，需复核 MIME、扩展名、大小、存储路径是否可遍历。
9. **队列任务重试**：`app/Jobs/*` 逐个核对 `$tries/$timeout/$backoff`，特别是会触发财务写操作的 Job。
10. **迁移与历史脏数据**：`migration-output/` 与 `mysql_idc_*.sql` 提示存在历史迁移，需确认线上 schema 与 `database/migrations` 一致，避免“迁移未跑/重复跑”。

## 5. 优化方向（非紧急，但应纳入计划）

1. **phpstan 提级**：level 5 → 7 → 9 分阶段，先修不可忽略错误，逐步收紧 `ignoreErrors`。
2. **Controller 薄层化**：把残留的 `validate`/`Http::`/事务迁移到 FormRequest / Service / Action，按治理方案 §3 执行。
3. **第三方集成插件化**：把支付、实名、魔方、短信、邮件、存储统一到 `Contracts/Integrations/*` + 驱动注册 + DTO + 统一异常，业务层只依赖接口。
4. **API 响应统一**：所有控制器走统一响应包装（`code/message/data/timestamp`），错误码集中在 `Constants/`，避免散落字符串。
5. **审计日志标准化**：高风险写操作统一走 `OperationLog` / `ActivityLog`，带 trace_id、操作人、前后值。
6. **测试金字塔补齐**：Unit 测试覆盖 Service 纯逻辑，Feature 测试覆盖闭环，引入假驱动替代真实第三方，目标 P0 链路 100% 覆盖。
7. **可观测性**：引入结构化日志 + trace_id 贯穿，关键指标（队列长度、回调失败率、对账差异）落地到日志聚合或简易 dashboard。
8. **数据库索引复审**：结合慢查询，复核 `database/migrations` 索引是否覆盖列表查询、外键关联、唯一性约束。
9. **文档同步机制**：把“路由 → API 清单”做成 CI 脚本，PR 改路由必须同步清单，避免文档腐烂。

## 7. 验收标准

- 全部 P0 项状态为“已验证/已回归”，且附回归测试。
- `composer test` / `analyse` / `format:check` 三件套全绿。
- 文档/代码冲突清单 A 中每条要么改代码、要么改文档、要么标注“已知差异不处理”并给出理由。
- 审查结论应输出给当前任务或 PR；只有可长期复用的规则、风险清单或检查项才沉淀回本方案或 `后端规范化工程化治理方案.md`。
- 涉及规则变化的，同步更新 `AGENTS.md` / `后端规范化工程化治理方案.md` / 相关 skills。
