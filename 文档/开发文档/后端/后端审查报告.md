### B-001 已修复 ✅
- 用 root 授权 `idc@127.0.0.1` + `idc@localhost` 全权，运行 `backend/scripts/install_db.py` 初始化独立测试库 `idc_testing`（50 张表 + 默认管理员）。

- 验证：原失败用例 `ClientFinanceBalanceLogRegressionTest` 转绿；全量 `php artisan test` 由"全红（Table 'idc.users' doesn't exist）"恢复为 **3 failed / 3 skipped / 438 passed (2637 assertions)**。

### B-010 已修复 ✅（P1 性能 bug）
- 根因：[`backend/app/Models/Product.php`](backend/app/Models/Product.php) `optionalSelectColumns()` 对每个候选列单独调 `hasColumn()`，触发 N+1 次列信息查询（SQLite 下 `pragma_table_xinfo`）；`ProductDisplayNameResolver::resolveCustomDisplayNameText` 又对每个 `custom_display_name` 为空的产品重复调用，导致 site group catalog 请求产生 15 次表结构查询（应 ≤1）。
- 修复：`optionalSelectColumns` 改用 `getColumnListing('products')` 一次拿全列后小写过滤；新增 `cachedProductColumns()` 按连接名静态缓存列清单，整请求只查一次。
- 验证：`SiteProductReadServiceTest` 12 passed（原 1 failed）。

### B-011 已修复 ✅（P2 测试环境）
- 根因：`ServiceUpgradeServiceTest` 经 `MySqlSchemaState` 加载 schema dump 时调用 `mysql` CLI，但宝塔环境 `mysql.exe` 位于 `D:\BtSoft\mysql\MySQL8.0\bin` 且未加入系统 PATH，Symfony Process 继承的 PATH 找不到 mysql。
- 修复：[`backend/tests/TestCase.php`](backend/tests/TestCase.php) `setUp` 前调用新增 `ensureMysqlClientOnPath()`，按需把 mysql 路径追加到当前进程 PATH（幂等，仅当目标二进制存在时）。
- 验证：该测试不再报 `'mysql' is not recognized`。

### B-012 已修复 ✅（P2 测试代码）
- 根因：`ServiceUpgradeServiceTest` 对 `ServiceDetailService::assertSuccess()`（声明返回 `void`）使用 `->willReturn(null)`，被 Mockery 严格模式以 `IncompatibleReturnValueException` 拒绝。B-011 修复前该测试在 schema 加载阶段就挂，掩盖了此问题。
- 修复：测试中两处 `->method('assertSuccess')->willReturn(null)` 改为 `->method('assertSuccess')`（void 方法不设返回值）。
- 验证：待全量回归确认。

- 验证：`ReferralRewardLifecycleRegressionTest` 2 passed（阻断用例 `expectExceptionMessage('推广返利资金')` 仍命中新文案）。

#### B-015 已修复 ✅（P1 余额在线对账）
- 根因：`ReconcileAccountDomainCommand` 是迁移域一次性对账（对比旧库 balance_logs 与新库 account_ledgers），依赖迁移上下文，不适合在线对账；生产无定时余额对账兜底。
- 修复：新建 [`ReconcileAccountBalanceCommand`](backend/app/Commands/ReconcileAccountBalanceCommand.php)（`reconcile:account-balance`），对账 `account_transactions` 每个 (user_id, account_type) 最新 `balance_after` 快照与 `user_accounts` 对应余额字段（cash/referral_frozen/referral_available/referral_pending_withdrawal/referral_withdrawn），差异 > 0.01 即输出 + `Log::warning` 告警；注册到 [`console.php`](backend/routes/console.php) 每小时调度。
- 验证：测试库 dry-run 0 差异；`schedule:list` 确认 `0 * * * * reconcile:account-balance` 已注册。

#### B-016 已修复 ✅（P1 上游开通孤儿单）
- 根因：`submitUpstreamProvision(throwOnFailure=false)` 吞异常，开通失败仅记 `provision_error` 不回滚，产生"已付款未开通"孤儿单（service.status=PENDING + provision_error 非空 + order.status=PROCESSING）；`SyncProcessingOrderStatus` 已废弃 no-op，`ServiceStatusSyncService` 过滤掉无 host_id 的失败服务，无补偿重试；且 `provisionViaUpstream` 缺上游幂等键回查，盲目重试可能重复开通。
- 修复：新建 [`RetryFailedProvisionCommand`](backend/app/Commands/RetryFailedProvisionCommand.php)（`provision:retry-failed`），扫描孤儿单，**默认 dry-run 只告警**（规避自动重试重复开通风险），`--execute` 才调 `ProvisionService::retryFailedProvision`（已存在的公开方法，含 ensureLocalService/auto_setup 检查/状态判断），用 `provision_data.retry_count` 计数上限 3，超过只告警需人工介入；注册到 [`console.php`](backend/routes/console.php) 每 10 分钟 dry-run 告警调度，管理员据日志核实上游实际开通状态后用 `--execute` 手动重试。
- 残留 P2：上游 `provisionViaUpstream` 幂等键回查改造（先按 invoice_id 查上游已存在 host 再决定是否 checkout）留待后续上游协议改造，本轮通过 dry-run + 人工决策规避重复开通风险。
- 验证：测试库 dry-run 成功；`schedule:list` 确认 `*/10 * * * * provision:retry-failed` 已注册。

## 7. 业务链路走查结论（第 2 步）

### 7.1 支付与回调（无 P0）
- 支付宝异步通知 `handleAlipayNotify`：签名校验 + app_id 商户匹配 + 金额 0.0001 容差比对 + 幂等（`payment_no` 查 + status SUCCESS 早返回）+ `lockForUpdate`+事务 + 重复支付拦截（invoice 已 PAID 时仅记 callback_raw 不二次入账）+ 路由层 `verify.alipay.callback` 双签名中间件。
- 余额支付 `payByBalance` / `payOrderByBalance` / `payByBalanceAndAlipay`：Redis `withLock` + DB::transaction + Invoice/User/UserAccount 三重 `lockForUpdate` + 事务内余额二次校验。
- 充值到账 `completeRechargePayment`：Payment 行锁 + 幂等 + User 行锁。
- **结论**：支付链路工程质量高，作为基准范例。

### 7.2 退款（无 P0，有 B-014 P1）
- `refundOrder` / `refundOrderByAlipay`：锁 + 事务 + 幂等（already_refunded 早返回）+ 全额校验（容差 0.00001）+ 佣金回滚（仅非 already_refunded 时调 `reverseRewardForRefundedOrder`）。
- 退款到余额 `refundInvoiceToBalance` / `refundOrderToBalance`：同样锁+事务+流水。
- **B-014**：已提现佣金退款时 `assertOrderRewardRefundable` 抛错硬阻断，无人工挂账流程，管理员只能看到报错文案，订单卡死无法退款。

### 7.3 账户余额并发（无 P0，有 B-015 P1）
- 10 个余额写入口全部具备 DB::transaction + lockForUpdate + 事务内二次校验（详见走查表）。
- 余额为池化模型（`user_accounts.cash_balance` 直接存储，`AccountTransaction` 仅审计流水）。
- 精度统一 `round(..., 2)` + 容差比较，无浮点 `==`。
- **B-015**：`ReconcileAccountDomainCommand` 可对账但未注册调度，生产无在线余额对账兜底；`UserService::create` 写初始余额未写流水（P2）。

### 7.4 提现与佣金（有 B-013 已修、B-014 待修）
- 提现申请：throttle:3,1 + PENDING 互斥 + 事务 + 行锁 + 余额二次校验；审核通过/拒绝状态机 + 审计日志齐全。
- 佣金结算：`ProcessPaidOrderReferralRewardJob` + `WithoutOverlapping` + Cache lock + `order_id` 唯一索引（双重幂等）+ 冻结→解冻两阶段。
- 佣金回滚：区分 FROZEN/REWARDED，已提现时阻断退款（B-014）。
- **B-013 已修**：补实名校验。
- 残留 P2：提现无单日/单周金额上限、`trace_id` 无唯一索引、解冻仅懒触发无调度。

### 7.5 上游集成（有 B-016 P1）
- 上游 HTTP 有 timeout/connect_timeout；401 时按需重登，鉴权刷新失败不级联。
- **B-016**：`submitUpstreamProvision` 吞异常（`throwOnFailure=false`），开通失败仅记 `provision_error` 不回滚，产生"已付款未开通"孤儿单；`SyncProcessingOrderStatus` 已废弃 no-op，`ServiceStatusSyncService` 过滤掉无 host_id 的失败服务，无补偿重试；且重试不幂等（无上游幂等键回查，重试会重复 checkout 产生第二笔 host）。

### 7.6 路由与中间件（无 P0，有 B-017 文档腐烂）
- 用户端越权：`Client/ServiceController` 全走 `...ForUser($request->user(), $id)`，归属过滤收敛在 Service。
- 中间件覆盖：支付回调 `verify.alipay.callback`、实名回调 `verify.callback`、敏感操作 throttle、认证路由 `auth:sanctum`+`ensure.client`/`ensure.admin`、写操作 `permission:{code}`。

### 7.7 静态扫描（无 P0）
