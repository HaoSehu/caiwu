# 定时任务对齐与 Hook 说明

- 文档性质：开发对齐记录
- 对齐日期：2026-06-22
- 旧系统来源：`zjmf-manger-decoded-main/app/admin/command/Cron.php`
- 当前入口：`backend/routes/console.php`

## 1. 当前结论

Caiwu 当前使用 Laravel Scheduler 统一承载定时任务，生产只需要每分钟执行：

```bash
php artisan schedule:run
```

调度内已经包含一轮 `queue:work --stop-when-empty`，不要额外依赖生产常驻 `queue:work`。

本次对齐后新增了轻量调度 Hook：

- `task.before`
- `task.after`
- `task.failed`
- `tick.every_minute`
- `tick.every_five_minutes`
- `tick.hourly`
- `tick.daily`

Hook 默认没有监听器，不改变现有行为；只有在 `backend/config/schedule_hooks.php` 注册监听器时，对应周期 Hook 才会进入 Laravel Schedule。

## 2. 旧 ZJMF Cron 职责对照

| 旧系统职责 | 旧系统位置 | Caiwu 当前承接 |
| --- | --- | --- |
| Cron 入口、锁、开始/结束记录 | `Cron::execute()` | `schedule:run` + Laravel `withoutOverlapping` + `ScheduleRunLogService` |
| 调度前后 Hook | `before_cron` / `after_cron` | `ScheduleHookService::HOOK_TASK_*` 与周期 Hook |
| 每 5 分钟 Hook | `after_five_minute_cron` | `tick.every_five_minutes` |
| 半小时任务：流量、模块任务、自动暂停/删除 | `halfHourCronJob()` | 状态同步、生命周期维护、供应商能力；流量类需按供应商能力继续拆分 |
| 日任务：账单、工单、订单、日志等 | `dailyCronJob()` | `BillingAutomationService`、`InvoiceCleanupAutomationService`、`TicketAutomationService`、日志归档预检 |
| 到期暂停/删除产品 | `host()` | `ServiceLifecycleAutomationService` |
| 续费提醒、账单催付、逾期 | `invoice()` / 信用额账单方法 | `BillingAutomationService`；信用额账单不属于当前 invoice-only 主线 |
| 工单自动关闭 | `ticket()` | `TicketAutomationService` |
| 未付款订单/充值账单清理 | `order()` / `invoice()` | `InvoiceCleanupAutomationService` |
| 上游状态/实例信息同步 | `hostInfo()` / `syncUpstreamProductInfo()` | `ServiceStatusSyncService`、`ProductCatalogService::syncUpstreamProductConfigOptions()` |
| 模块 Cron 插件 | `moduleCron('FiveMinuteCron'/'DailyCron')` | 不照搬全局函数插件；后续用供应商接口契约或 `schedule_hooks` listener 承接 |
| 队列消费 | 旧系统队列/异步方法 | `queue-backlog-drain` 每分钟短轮询消费 |

## 3. 暂不 1:1 迁移的旧能力

以下旧能力不应直接复制到 Caiwu，需要按当前产品边界重新确认：

- 信用额账单、信用额逾期暂停、月末还款账单。
- 合同未签订强制暂停。
- 旧 `cancel_requests` 取消申请表驱动的删除逻辑。
- 旧模块目录函数式 `DailyCron` / `FiveMinuteCron`。
- DCIM/魔方云流量清零、流量统计、代理商品带宽同步。
- 数据库备份到 FTP/邮件。
- 自动删除不活跃用户。

## 4. 新增 Hook 使用方式

新增监听器时，优先放在对应业务域或 `App\Services\Automation\Hooks` 下，并实现：

```php
use App\Services\Automation\Contracts\ScheduleHook;

final class ExampleScheduleHook implements ScheduleHook
{
    public function handle(string $hook, array $context = []): mixed
    {
        // $hook: 当前扩展点
        // $context: task_key、task_name、source、duration_ms、summary 等上下文
        return ['handled' => true];
    }
}
```

然后在 `backend/config/schedule_hooks.php` 注册：

```php
ScheduleHookService::HOOK_EVERY_FIVE_MINUTES => [
    App\Services\Automation\Hooks\ExampleScheduleHook::class,
],
```

Hook 失败只写日志，不中断定时任务。需要强一致或资金相关逻辑时，不要只依赖 Hook，应进入正式领域服务并补测试。

## 5. 开发约束

- 新增正式定时任务仍优先写入领域服务，再在 `routes/console.php` 调度。
- 可手动触发的任务需要同步更新 `ScheduleTaskService` 与 `ScheduleTaskTriggerService`。
- 资金、账单、支付相关任务必须考虑事务、幂等和审计字段。
- 不要把第三方请求写进 Hook；仍需走 `Services/Upstream`、`Services/Integrations` 或供应商契约。

## 6. 互斥降级与关键任务 Advisory Lock（2026-06-22 增补）

### 6.1 调度互斥降级识别

`routes/console.php` 在启动时根据 OS 与缓存驱动计算 `$shouldUseScheduleMutex`：

- `Windows` + `cache.default=file` 时降级为 `false`，跳过 `withoutOverlapping`，避免锁文件写入失败导致 `schedule:run` 中断。
- 运行时状态写入 `config('idc.schedule_runtime.mutex')`，含 `enabled` / `degraded` / `mode` / `reason` / `cache_store` / `os_family`，供 `ScheduleTaskService::overview()` 暴露给前端。

### 6.2 降级告警

`App\Services\System\ScheduleRunLogService::record()` 在每次进入时调用 `warnIfMutexDegraded()`：

- 仅当 `mutex.degraded = true` 时写一条 `Log::warning`，提示存在重入风险。
- 用静态标志位 `self::$mutexDegradedWarningEmitted` 保证**每个 `schedule:run` 进程只告警一次**，避免每分钟刷屏。

### 6.3 关键任务 Advisory Lock 兜底

`routes/console.php` 提供 `$withAdvisoryLock(string $lockKey, int $ttlSeconds, callable $callback)`：

- `$shouldUseScheduleMutex = true` 时**直通回调**，避免与 `withoutOverlapping` 双重锁。
- 降级时用 `Cache::store('redis')->lock("schedule:advisory:{$lockKey}", $ttlSeconds)` 兜底：
  - 锁获取失败 → 跳过本次执行，返回 `['skipped' => true, 'reason' => 'advisory_lock_busy']`，写 info 日志。
  - Redis 不可用 → 退化为直接执行并写 warning，避免任务完全停摆（此时 `warnIfMutexDegraded` 已告警）。

目前包了 3 个关键任务：

| 任务 | lockKey | TTL | 理由 |
| --- | --- | --- | --- |
| 服务自动续费 | `service-auto-renew` | 240s | 每 5 分钟跑，避免重复扣款 |
| 账单自动化维护 | `billing-maintenance` | 1800s | 每小时跑，避免重复生成账单 |
| 账户余额在线对账 | `reconcile-account-balance` | 1800s | 每小时跑，避免并发对账错乱 |

新增关键任务时，若涉及资金/账单/对账，应同样用 `$withAdvisoryLock` 包裹，TTL 略大于任务最高频率间隔即可。

### 6.4 前端调度健康卡片

`frontend-admin-v3/src/pages/logs/index.vue` 的「定时任务」Tab 在任务清单上方新增「调度环境与健康」卡片：

- computed `scheduleEnvAlerts` 消费 `ScheduleTaskService::overview()` 的 `environment` 字段。
- 仅在存在异常或值得关注指标时显示，避免绿色噪音。
- 阈值：
  - `schedule_mutex.degraded = true` → warning（展示 reason / cache_store / os_family）
  - `pending_jobs > 50` danger / `> 10` warning / 否则 success
  - `failed_jobs > 0` danger（提示排查 failed_jobs 表）
  - `automation_config.status != 'loaded'` → warning（展示 fallback_reason）

样式在 `src/pages/logs/index.less` 的 `.schedule-env-grid` / `.schedule-env-item--{success,warning,danger}`，复用 TDesign token，未引入新色系。

### 6.5 failed_jobs 运维

`failed_jobs` 表的语义是"已放弃的失败任务，等待人工审视或重试"。运维流程：

1. 前端健康卡片显示 `failed_jobs > 0` 时，用 `php scripts/inspect_failed_jobs.php`（一次性脚本，用完即删）或直接查表排查根因。
2. 若根因已在代码修复（多数情况是历史残留），用 `php artisan queue:flush` 清空，或按 `failed_at` 范围精确删除。
3. 不要无差别重试 `queue:retry`，除非确认根因已修且 payload 仍有效。
