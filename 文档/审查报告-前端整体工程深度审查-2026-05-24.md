## 3. 审查结论总览

当前前端项目已经完成了 Vue 3、Vite、Pinia、Element Plus 的基础统一，并且在以下方面有明确正向建设：

- 两端入口已收敛到 `src/app/*` 新架构层，旧 `src/router/index.js`、`src/utils/request.js` 主要作为兼容转发
- 用户端请求层已具备一定弱网、重试、重复请求控制能力
- 内容详情页存在 `v-html`，但实际渲染链路已接入 Markdown 渲染和统一 HTML 清洗
- 两端都已统一使用 `Element Plus` 与全局样式入口

但从可维护性、安全性、权限一致性、工程收敛度角度看，仍存在 4 类核心隐患：

1. 权限控制停留在组件局部判断，未形成路由级统一拦截
2. 管理端鉴权兼容层存在错误实现，混入了失效的 `client` 分支
3. 管理端与用户端基础能力不对齐，请求、异常兜底、动态资源容灾存在明显差异
4. 管理态与用户态 store/API 交叉耦合，长期会持续放大维护成本

总体评级建议：**中高风险，适合尽快推进一次前端基础治理，而不是继续碎片化修补**

## 4. 高优先级问题清单

## 4.1 P1-管理端路由缺少权限级守卫，存在前端越权访问面

### 问题现象

- `frontend-admin/src/app/router/guards.ts` 仅校验是否登录
- `frontend-admin/src/app/router/routes.ts` 大多数路由 `meta` 只有 `title`
- 页面内虽有 `permissions.includes(...)` 判断，但仅作用于按钮/局部区域
- 如果用户拥有有效后台 token，即使菜单被隐藏，仍可能通过 URL 直接访问受限页

### 风险等级

`P1 / 高风险`

### 影响范围

- 管理端所有需要按权限控制访问的菜单页
- 用户详情、工单、商品、日志、系统设置、通知等后台敏感模块

### 根因分析

- 权限治理停留在页面级和组件级，没有升级到路由级统一标准
- 路由元信息缺少 `permission` / `permissions` / `permissionMode`
- 菜单权限、按钮权限、页面权限没有共用一个权限模型

### 工程师视角修改方案

#### 方案目标

建立“登录校验 + 路由权限校验 + 菜单权限裁剪 + 按钮权限控制”四层统一模型。

#### 详细修改方法

1. 先定义统一路由权限元信息规范

```ts
meta: {
  title: '系统设置',
  requireAuth: true,
  permissions: ['system.settings.view'],
  permissionMode: 'all',
}
```

建议规范：

- `requireAuth: true` 表示必须登录
- `permissions: string[]` 表示访问该页面所需权限
- `permissionMode: 'all' | 'any'` 表示多权限匹配方式
- 无权限页面显式写 `permissions: []`，避免后续误判

2. 在 `frontend-admin/src/app/router/guards.ts` 增加统一权限判断逻辑

落地步骤：

- 登录校验通过后，读取 `to.meta.permissions`
- 从 `userStore.permissions` 获取当前管理员权限集
- 支持 `*` 超级权限兜底
- 权限不足时跳转到统一 `403` 页面，或跳转仪表盘并提示

建议实现顺序：

- 第一步先补守卫判断，不改现有业务页面
- 第二步再逐步补齐路由 `meta.permissions`
- 第三步用脚本或人工校对所有后台菜单与后端权限码映射

3. 引入统一权限工具

建议保留以下能力：

- `hasPermission(code)`
- `hasAnyPermission(codes)`
- `hasAllPermissions(codes)`
- `filterRoutesByPermissions(routes, permissions)`
- `filterMenusByPermissions(menuTree, permissions)`

4. 页面内权限判断仅保留按钮级和操作级

比如：

- 页面可见性：交给路由守卫
- 左侧菜单可见性：交给菜单过滤器
- “删除/审核/解绑”等操作按钮：交给局部权限判断

#### 验收标准

- 任意受限后台地址在无权限时不能直接打开
- 菜单显示与页面访问规则一致
- 权限码变更后只需维护一套配置
- 开发新页面时能按固定模板接入权限

#### 推荐排期

- `第 1 天`：补路由守卫与 403 页面
- `第 2-3 天`：补所有后台路由权限元信息
- `第 4 天`：联调后端权限码并回归测试

## 4.2 P1-管理端 auth 兼容层实现错误，存在失效分支和误导性 API

### 问题现象

`frontend-admin/src/utils/auth.js` 中：

- `getToken('client')` 返回 `null`
- `setToken(token, 'client')` 不执行任何写入
- `isLoggedIn('client')` 永远为 `false`
- `getUserType()` 永远返回 `admin`

同时 `frontend-admin/src/stores/user.js` 仍保留：

- `clientLogin`
- `clientRegister`

这会让代码看起来支持双端鉴权，实际并不成立。

### 风险等级

`P1 / 高风险`

### 根因分析

- 历史兼容代码未彻底删除
- 管理端与用户端鉴权职责边界没有完全拆开
- 当前代码存在“表面支持，实际失效”的危险接口

### 工程师视角修改方案

#### 方案目标

把管理端认证模型收敛为纯后台模型，把用户端认证模型收敛为纯前台模型，彻底取消伪兼容。

#### 详细修改方法

1. 清理管理端 `src/utils/auth.js`

改造方向：

- 只保留 `admin` 相关方法
- 删除 `userType` 参数
- 删除 `client` 分支
- 所有方法语义保持单一

建议收敛成如下接口集合：

- `getToken()`
- `setToken(token)`
- `removeToken()`
- `isLoggedIn()`
- `isSessionExpired()`
- `initSessionActivityTracking()`

2. 清理管理端 `src/stores/user.js`

删除以下不属于后台职责的逻辑：

- `clientLogin`
- `clientRegister`
- `clientAuthApi` 引入

保留后台专属方法：

- `adminLogin`
- `fetchUserInfo`
- `logout`

3. 用户端 `src/stores/user.js` 同步拆分

用户端不应保留：

- `adminLogin`
- 管理端权限集的概念

如果确实需要“登录即返回后台/前台不同用户态”的业务，建议单独放到 `shared/auth/` 做协议层抽象，而不是在两个端各自混写。

4. 为 auth 工具增加最小回归测试

至少覆盖：

- 写 token 后能正确读取
- 退出登录后 token 被移除
- `getUserType()` 返回值与当前工程一致
- 错误调用不存在的分支时直接抛错，而不是静默失败

#### 验收标准

- 管理端代码中不再出现 `clientLogin/clientRegister`
- 用户端代码中不再出现 `adminLogin`
- 所有 auth 方法都只服务当前工程自身
- 新同学阅读 auth 模块时不会误以为它是双端通用实现

#### 推荐排期

- `0.5 天`：清理工具层
- `0.5 天`：清理 store 与 API 引用
- `0.5 天`：联调登录、登出、会话过期回归

## 4.3 P1-权限常量、路由权限、组件权限未统一，长期会持续漂移

### 问题现象

`frontend-admin/src/utils/permission.js` 中定义了旧风格权限常量：

- `ORDER_MANAGE`
- `SYSTEM_SETTINGS`
- `LOG_VIEW`

但页面和路由中大量直接使用字符串字面量，未共用同一来源。

### 风险等级

`P1 / 高风险`

### 根因分析

- 权限码未形成“后端定义、前端消费”的单一来源
- 权限常量未与当前后台模块演进同步
- 没有权限码自动生成或定期校准机制

### 工程师视角修改方案

#### 方案目标

建立“后端权限码清单 -> 前端常量文件 -> 路由/菜单/按钮统一引用”的闭环。

#### 详细修改方法

1. 先确定权限码主数据源

推荐以后端为准：

- 后端维护 `AdminPermissions`
- 前端只消费导出的权限码映射

2. 生成前端权限常量文件

建议文件：

- `frontend-admin/src/constants/permissions.ts`

建议结构：

```ts
export const AdminPermissions = {
  SYSTEM_SETTINGS_VIEW: 'system.settings.view',
  SYSTEM_SETTINGS_EDIT: 'system.settings.edit',
  USER_VIEW: 'user.view',
  USER_EDIT: 'user.edit',
} as const
```

3. 禁止业务代码继续手写权限字符串

统一改为：

```ts
hasPermission(AdminPermissions.USER_EDIT)
```

4. 建立巡检规则

可增加：

- ESLint 自定义规则
- 简单脚本扫描 `permissions.includes('xxx')`
- CI 检查是否存在未登记权限字符串

#### 验收标准

- 权限码来源唯一
- 路由、菜单、按钮共用一套常量
- 删除旧权限码时可通过全局检索快速收口

## 4.4 P1-管理端缺少全局异常兜底与监控接入，线上问题难发现难定位

### 问题现象

从当前启动链未看到：

- `app.config.errorHandler`
- `window.onerror`
- `unhandledrejection`
- 统一前端日志上报
- 静态资源加载失败统一恢复

用户端路由已对动态 import 失败做自动刷新恢复，但管理端没有同类容灾。

### 风险等级

`P1 / 高风险`

### 根因分析

- 当前更偏向业务功能开发，缺少运行治理层
- 管理端默认被认为“内部系统”，但实际上同样承载高价值操作

### 工程师视角修改方案

#### 方案目标

建立统一的前端运行时可观测体系，至少做到“报错能收集、白屏能感知、资源失败能恢复、接口异常能串 trace”。

#### 详细修改方法

1. 在 `bootstrap.ts` 注册 Vue 全局错误处理

建议拦截：

- 渲染异常
- 生命周期异常
- setup 异常
- 事件处理异常

2. 挂载浏览器级异常监听

建议采集：

- `window.onerror`
- `window.addEventListener('unhandledrejection', ...)`
- `window.addEventListener('error', ..., true)` 捕捉静态资源加载失败

3. 建立统一上报字段

建议包含：

- `app_name`
- `app_version`
- `route`
- `user_id`
- `request_id`
- `trace_id`
- `browser`
- `network_status`
- `message`
- `stack`

4. 管理端补动态资源加载失败容灾

参考用户端现有模式：

- 动态 import 失败识别
- 同一路由只自动刷新一次
- 避免死循环刷新

5. 异常分级处理

- 用户可忽略的小错误：本地 toast
- 页面不可用错误：局部错误边界或 fallback 区块
- 全局白屏级错误：统一上报并跳转错误页

#### 验收标准

- 资源加载失败能自动恢复或至少提示刷新
- 线上 JS 报错能追踪到路由、用户、版本
- 复杂接口报错能关联前端 `request_id`

## 5. 中优先级问题清单

## 5.1 P2-管理端与用户端请求层能力不对齐，易形成长期工程漂移

### 现状

用户端请求层已经具备：

- 安全请求去重
- 弱网超时调整
- 429 细分提示
- 取消请求识别
- 公共站点 GET 免 token

管理端请求层目前主要具备：

- 自适应超时
- GET 等安全方法重试
- 基础错误提示

### 风险

- 两个项目同类问题需要分别修复
- 同一类接口错误在两端表现不一致
- 请求层标准无法沉淀为共享规范

### 工程师视角修改方案

1. 提炼 `shared/runtime/http` 公共能力层

公共下沉内容建议包括：

- `requestId`
- 网络状态识别
- retry 判定
- safe request dedupe
- 超时策略
- 标准错误对象包装

2. 两端仅保留业务差异配置

比如：

- 管理端默认登录路由
- 用户端公共站点路由白名单
- token key 不同

3. 统一错误协议

两端都按以下维度处理：

- `401`
- `422`
- `429`
- `5xx`
- 离线
- 超时
- 取消请求

4. 沉淀使用规范

明确哪些接口允许重试，哪些禁止重试：

- 查询类接口：允许有限重试
- 创建订单、支付、删除等写操作：默认不自动重试

#### 验收标准

- 两端请求层能力对齐
- 同类错误提示统一
- 公共修复只改一处

## 5.2 P2-管理态与用户态 store 交叉耦合，职责边界不清晰

### 问题现象

- 管理端 store 混入 `clientAuthApi`
- 用户端 store 混入 `adminLogin`
- `permissions` 这种后台概念出现在非后台模型中

### 风险

- 登录流和权限流彼此污染
- 新增功能时更容易误用错误接口
- 单元测试难以拆分

### 工程师视角修改方案

1. 拆分为端内专属 store

建议：

- `frontend-admin/src/stores/adminUser.ts`
- `frontend-client/src/stores/clientUser.ts`

2. 公共会话能力只放 shared/runtime

保留内容：

- token driver
- session 活跃时间更新
- 过期判断

3. 业务态只保留端内语义

后台：

- `adminLogin`
- `fetchAdminProfile`
- `fetchAdminPermissions`

前台：

- `clientLogin`
- `clientRegister`
- `exchangeLoginCode`
- `fetchClientProfile`

#### 验收标准

- 两端 store 名称、方法、字段语义一眼可辨
- 后台代码不再依赖前台 API
- 前台代码不再携带后台权限模型

## 6. 专项岗位视角整改建议

## 6.1 Vue 框架工程师视角

### 重点判断

- Vue 3 架构基本统一
- 新旧入口并存但当前主要为兼容壳
- 真正问题不在 Vue 版本，而在运行时职责边界未彻底收敛

### 建议动作

- 把 `src/app/*` 定义为唯一正式入口层
- 对旧 `src/utils/request.js`、`src/router/index.js` 增加注释，声明“仅兼容转发，不承载新逻辑”
- 在两端补架构说明文档：入口层、运行时层、业务 API 层、页面层、shared 层职责边界

### 落地标准

- 新增逻辑只能进 `app`、`api`、`stores`、`views` 规范目录
- 不再向兼容层继续添加业务逻辑

## 6.2 前端安全工程师视角

### 重点判断

- `v-html` 当前链路可控，不是首要风险
- 首要风险在权限绕过、异常未监控、认证工具误用

### 建议动作

- 权限前置到路由守卫
- 所有后台高敏页必须配置权限码
- 为 HTML 清洗补安全回归用例
- 请求层错误中保留 `request_id` 与后端日志贯通

### 落地标准

- 地址栏直进受限页必须拦截
- 所有富文本渲染点必须可追溯到 sanitizer

---

## 6.3 组件库研发工程师视角

### 重点判断

- 目前以 Element Plus 为主是正确方向
- 权限按钮、错误区块、空态区块、加载区块仍可进一步沉淀为共享组件

### 建议动作

- 抽 `PermissionGuard` 组件或指令
- 抽 `RequestErrorBlock`、`RetryPanel`
- 抽统一 `PagePermissionDenied`、`PageLoadFailed`

### 落地标准

- 权限展示、错误展示风格统一
- 页面不再重复编写同类状态区块

---

## 6.4 页面架构工程师视角

### 重点判断

- 页面层已逐步从视图中剥离到 composables，但权限和运行治理仍散落

### 建议动作

- 页面只做组装，不做鉴权主逻辑
- composables 只做业务状态与交互，不做全局权限规则定义
- 路由层、store 层、runtime 层职责分离

### 落地标准

- 页面文件长度和复杂度稳定下降
- 权限逻辑可被统一检索和替换

---

## 6.5 性能调优工程师视角

### 重点判断

- 用户端已考虑弱网超时和动态资源重载
- 管理端还缺少同级别运行韧性

### 建议动作

- 同步两端的动态资源失败恢复
- 统一请求层弱网策略
- 对超大表格、日志页、目录页评估虚拟列表或服务端分页上限

### 落地标准

- 弱网、切版本、长列表场景下页面可用性提升

---

## 6.6 路由与状态管理工程师视角

### 重点判断

- 当前最大问题是“路由规则”和“store 语义”未完全对齐

### 建议动作

- 路由 `meta` 成为访问控制主配置
- store 按端拆分
- 403 页面、游客页面、登录回跳策略统一配置

### 落地标准

- 所有路由访问行为可由 `meta + guard` 推导

---

## 6.7 跨端适配工程师视角

### 重点判断

- 用户端部分页面已有响应式细节
- 管理端更偏桌面后台，但仍应保证平板和窄屏可用

### 建议动作

- 给后台关键页面建立最小宽度策略与折叠策略
- 对表格页补横向滚动、筛选区换行、抽屉式操作区方案
- 对用户端目录页、内容页、控制台页继续做移动端验收

### 落地标准

- `1280px`、`1024px`、`768px` 三档宽度均可操作

---

## 6.8 样式工程化工程师视角

### 重点判断

- 全局样式入口统一方向是对的
- 后续要防止局部页面继续手写分裂 token

### 建议动作

- 继续强制使用变量文件和全局 token
- 对新页面审查 `:deep(.el-*)` 滥用
- 建立 SCSS token 使用清单

### 落地标准

- 不新增第二套颜色、阴影、边框体系

---

## 6.9 工程化打包工程师视角

### 重点判断

- 当前构建基础可用
- 更大的问题是异常恢复和版本切换兜底不一致

### 建议动作

- 两端统一 chunk 加载失败处理
- 构建产物注入版本号
- 报错日志中带上前端版本

### 落地标准

- 线上问题能快速确认是否为旧资源缓存或版本不一致导致

---

## 6.10 接口对接工程师视角

### 重点判断

- 当前接口请求封装已在收敛，但双端协议处理不统一

### 建议动作

- 制定前端统一接口错误处理规范
- 禁止页面直接写分散的错误解析逻辑
- 请求封装层透出标准化错误对象

### 落地标准

- 页面层几乎不再手工拼装后端错误提示

---

## 6.11 自动化测试工程师视角

### 建议动作

- 先补基础层测试，再补页面冒烟
- 把“登录、权限、401、422、429、资源更新失败”作为首批自动化场景

### 落地标准

- 每次发版前可自动回归关键用户路径

---

## 6.12 前端运维监控工程师视角

### 建议动作

- 增加全局错误、接口异常、白屏监控
- 打通前后端 `trace_id` / `request_id`
- 做告警分级，避免全量噪音

### 落地标准

- 线上报错能快速定位到用户、页面、版本、接口

---

## 6.13 权限菜单工程师视角

### 建议动作

- 路由、菜单、权限三者共用同一配置模型
- 菜单树由权限过滤器统一裁剪
- 页面内操作按钮再做二次细粒度控制

### 落地标准

- 菜单可见性与页面可访问性始终一致

---

## 6.14 动画交互工程师视角

### 重点判断

- 当前用户端在滚动行为上已考虑 `prefers-reduced-motion`
- 这是好习惯，建议扩展到更多交互细节

### 建议动作

- 后续动画统一遵循“可关闭、可降级、不过度打扰”
- 切页、滚动、抽屉、加载骨架都考虑 reduced motion

### 落地标准

- 有动画体验，但不会影响弱设备和敏感用户群体

---

## 7. 建议整改路线图

## 第一阶段：权限与认证收口

目标：先消除直接安全风险。

建议任务：

- 管理端路由补权限守卫
- 管理端清理错误 auth 兼容层
- 两端 store 按端拆分
- 权限码统一常量化

建议周期：`3-5 个工作日`

---

## 第二阶段：运行治理与异常监控

目标：把问题从“出故障靠猜”变成“出故障可追踪”。

建议任务：

- 两端接入全局异常处理
- 统一动态资源加载失败恢复
- 打通 request_id / trace_id
- 补前端版本与运行环境上报

建议周期：`2-4 个工作日`

---

## 第三阶段：请求层与自动化测试统一

目标：减少重复修复，建立可持续演进能力。

建议任务：

- 提炼 shared HTTP 基座
- 统一错误处理协议
- 补权限定向测试、请求层测试、sanitizer 测试
- 上线前增加 E2E 冒烟

建议周期：`4-6 个工作日`

---

## 8. 验收清单

整改完成后，建议至少逐项确认：

- 未登录访问后台受限页会跳登录
- 已登录但无权限访问后台受限页会被拦截
- 菜单隐藏与页面拦截规则一致
- 管理端不再包含 `clientLogin/clientRegister`
- 用户端不再包含 `adminLogin`
- 资源加载失败时两端都有基础恢复策略
- 所有全局异常都能上报页面、版本、用户和请求信息
- HTML 渲染链具备安全回归测试
- 请求层错误提示口径统一

---

## 9. 最终结论

当前项目前端工程不是“重写级问题”，而是典型的“基础能力已初步建立，但权限、安全、治理、职责边界没有完全收口”的状态。

如果继续按页面需求逐个追加代码，后续会出现以下趋势：

- 权限码越来越乱
- 登录态和用户态继续互相污染
- 管理端与用户端基础层越走越分叉
- 线上报错仍然难追、难复现、难闭环

建议以本报告为基线，先做一次前端基础治理专项，优先处理：

1. 权限守卫
2. auth/store 收口
3. 运行监控
4. 请求层统一

这四项做完后，后续页面迭代成本会明显下降，前端整体稳定性和可维护性会提升一个量级。
